2. Bốn khác biệt kiến trúc nền tảng

1. Process, không phải thread

SQL Server: 1 process, nhiều thread. Postgres: mỗi connection = một OS process riêng do postmaster fork ra. Hệ quả: connection đắt đỏ (~vài MB RAM + chi phí fork), nên production luôn cần connection pooler (PgBouncer — Module 16).

2. MVCC thay vì khoá

SQL Server mặc định: reader chặn writer và ngược lại (trừ khi bật RCSI). Postgres: MVCC luôn bật — UPDATE tạo phiên bản dòng mới, reader đọc phiên bản cũ — đọc và ghi thường không chặn nhau (ngoại lệ quan trọng: DDL cầm khoá ACCESS EXCLUSIVE vẫn chặn cả SELECT — Module 13). Quên NOLOCK đi. Cơ chế xmin/xmax và cái giá dead tuple: Module 12.

3. Bảng là heap — không có clustered index

SQL Server: bảng thường là clustered index, dữ liệu xếp theo key. Postgres: bảng luôn là heap không thứ tự; mọi index đều là secondary trỏ vào heap. Lệnh CLUSTER chỉ sắp lại một lần, không tự duy trì.

4. WAL thay transaction log

Tương đương transaction log nhưng là nền tảng của mọi thứ: crash recovery, replication, PITR, CDC. Hiểu WAL (Module 11) là hiểu một nửa Postgres production.

MVCC — Multi-Version Concurrency Control

Mỗi UPDATE/DELETE không sửa đè dòng cũ mà tạo phiên bản mới, phiên bản cũ giữ lại cho các transaction đang đọc. Mỗi transaction nhìn thấy một "ảnh chụp" (snapshot) nhất quán của database tại thời điểm nó bắt đầu. Đây là khác biệt triết lý lớn nhất so với SQL Server lock-based — và là gốc rễ của cả ưu điểm (đọc thường không bị chặn) lẫn nhược điểm (bloat, VACUUM) của Postgres.

3. Bẫy chữ hoa/thường — lỗi ngày đầu của mọi dân SQL Server

Postgres tự động hạ identifier không có ngoặc kép về chữ thường. SELECT UserID FROM Orders thực chất là select userid from orders. Vấn đề nổ ra khi ai đó tạo bảng bằng tool có ngoặc kép:

case-folding-trap
Ai đó (thường là ORM hoặc tool migrate từ SQL Server) tạo bảng thế này: CREATE TABLE "Orders" ("OrderID" INT, "CustomerName" TEXT); Giờ query kiểu SQL Server quen tay → THẤT BẠI SELECT OrderID FROM Orders; ERROR: relation "orders" does not exist Vì có ngoặc kép lúc tạo, tên giữ nguyên hoa thường → phải ngoặc kép MÃI MÃI SELECT "OrderID" FROM "Orders";
Quy ước nên theo ngay từ đầu

Trong thế giới Postgres, chuẩn de-facto là snake_case toàn chữ thường, không bao giờ dùng ngoặc kép: order_id, customer_name, daily_revenue. Khi migrate schema từ SQL Server, đổi tên ngay tại bước migrate — đừng mang PascalCase sang rồi gánh ngoặc kép suốt đời.

4. Database ≠ Database — không có cross-database query

Ở SQL Server bạn quen SELECT * FROM OtherDB.dbo.Orders. Postgres không cho phép: mỗi database là một ốc đảo cô lập, một connection chỉ sống trong một database. Thứ tương đương "dbo" và cách tổ chức đa môi trường là schema:

SQL Server:  Instance → Database (cross-query OK) → Schema (dbo) → Table
Postgres:    Cluster  → Database (CÔ LẬP)         → Schema       → Table
                                                     ↑ ranh giới tổ chức chính nằm ở đây
Trong PG, "public" là schema mặc định (vai trò ~ dbo, nhưng phân giải tên đi qua search_path — khác biệt có hệ luỵ bảo mật, xem Module 8). Muốn tách staging/analytics/raw → tạo nhiều schema trong CÙNG database
Khi thật sự cần cross-database

Dùng extension postgres_fdw (Foreign Data Wrapper) — mount bảng của database khác như bảng ngoại. Nhưng nếu hai nhóm bảng cần JOIN với nhau thường xuyên, đó là dấu hiệu chúng nên ở cùng database, khác schema ngay từ đầu.

5. ⭐ Transactional DDL — điều SQL Server không có trọn vẹn

Ở Postgres, CREATE TABLE, ALTER TABLE, DROP, CREATE INDEX... đều nằm trong transaction và rollback được. Một file migration 20 bước: bước 19 lỗi → toàn bộ tự huỷ, schema nguyên vẹn như chưa có gì. Đây là lý do các tool migration (Alembic, Flyway, dbt) chạy trên PG an toàn hơn hẳn.

transactional-ddl
Migration nhiều bước trong MỘT transaction — hoặc tất cả hoặc không gì BEGIN; ALTER TABLE orders ADD COLUMN currency CHAR(3) DEFAULT 'VND'; CREATE INDEX idx_orders_currency ON orders(currency); UPDATE orders SET currency = 'USD' WHERE region = 'us'; Phát hiện sai? Một lệnh — schema về nguyên trạng, kể cả DDL ROLLBACK;
Ngoại lệ cần nhớ

Vài lệnh KHÔNG chạy được trong transaction: CREATE INDEX CONCURRENTLY (Module 6), VACUUM, CREATE DATABASE. Và DDL trong transaction vẫn giữ khoá tới khi COMMIT — transaction migration càng dài, production càng nghẹt (mổ xẻ ở Module 13 và Case Study).

Mặc định psql chạy tiếp dù một câu lỗi — thảm hoạ cho migration. ON_ERROR_STOP là cờ bắt buộc trong mọi pipeline:

Kiểu dữ liệu PG đặc trưng — vũ khí SQL Server không có

1. TEXT & quy tắc chọn kiểu — bỏ thói quen NVARCHAR(n)

Ở SQL Server, chọn độ dài NVARCHAR(50/255/MAX) ảnh hưởng lưu trữ và hiệu năng. Ở Postgres: TEXT, VARCHAR(n), VARCHAR lưu trữ và chạy y hệt nhau — VARCHAR(n) chỉ thêm một bước check độ dài. Cộng đồng PG mặc định dùng TEXT cho mọi chuỗi, trừ khi nghiệp vụ thật sự cần chặn độ dài (mã quốc gia CHAR(2)...).

Cho chính xác: TEXT miễn phí so với VARCHAR, không miễn phí so với dữ liệu to

"Y hệt nhau" là so giữa các kiểu chuỗi — còn độ dài giá trị vẫn có giá riêng: dòng càng rộng càng ít tuple nằm vừa một trang 8KB (cache kém đi), giá trị vượt ngưỡng ~2KB bị đẩy sang TOAST với chi phí đọc/giải nén riêng (Module 20), và cột text lớn bị update thường xuyên làm giảm cơ hội HOT update (Module 12). Chọn TEXT thay vì VARCHAR(255) là đúng; nhét cả trang HTML vào một cột rồi SELECT * thì kiểu nào cũng chậm.

2. ⭐ TIMESTAMPTZ — chấm dứt ác mộng timezone

Đây là quyết định kiểu dữ liệu quan trọng nhất với pipeline đa vùng. TIMESTAMPTZ không lưu timezone — nó chuẩn hoá mọi input về UTC khi ghi, và đổi sang timezone của session khi đọc. Một giá trị tuyệt đối duy nhất, hiển thị tuỳ người xem.

timestamp vs timestamptz — khác nhau ở đâu

timestamp (không TZ) lưu "con số thời gian mù" — 09:00 không biết là 9h ở đâu, ai đọc nấy hiểu. timestamptz lưu thời điểm tuyệt đối (UTC bên trong) — 9h sáng Hà Nội và 9h sáng Tokyo là hai giá trị khác nhau, đúng như thực tế. Quy tắc cộng đồng PG: luôn timestamptz trừ khi có lý do rất đặc biệt.

timezone-thực-chiến
Xem timezone session hiện tại (server DE chuẩn nên là UTC) SHOW timezone; Cùng 1 giá trị, hiển thị theo giờ Việt Nam — chỉ trong session này SET timezone = 'Asia/Ho_Chi_Minh'; SELECT created_at FROM orders LIMIT 1; 2026-06-09 21:14:03+07 ⭐ Báo cáo "theo ngày VN" trên server UTC — AT TIME ZONE là chìa khoá SELECT (created_at AT TIME ZONE 'Asia/Ho_Chi_Minh')::date AS local_day, SUM(amount) FROM orders GROUP BY 1 ORDER BY 1 DESC LIMIT 3; DATE_TRUNC theo timezone (PG14+): gọn hơn nữa SELECT date_trunc('day', created_at, 'Asia/Ho_Chi_Minh') AS d, count(*) FROM events GROUP BY 1;
Bẫy báo cáo lệch ngày

Quên AT TIME ZONE, mọi phép ::date trên server UTC sẽ cắt ngày theo UTC — đơn hàng 6h sáng VN (23h UTC hôm trước) rơi vào ngày hôm trước trong báo cáo. Doanh thu lệch vài %, kế toán truy ba ngày không ra. Bẫy tương tự cron timezone bạn từng gặp ở hệ Linux.

3. JSONB — document store ngay trong RDBMS

JSONB lưu JSON đã parse dưới dạng nhị phân: truy cập trường nhanh, đánh index được, và có bộ toán tử giàu. Đây là lý do nhiều team bỏ MongoDB: schema linh hoạt cho phần "đuôi dài" của dữ liệu, vẫn JOIN và transaction được như thường. (SQL Server 2016+ có hàm JSON nhưng lưu NVARCHAR — không cùng đẳng cấp.)

jsonb-operators
-> trả JSONB (đi tiếp được), ->> trả TEXT (để so sánh/hiển thị) SELECT payload -> 'device' ->> 'os' AS os FROM events LIMIT 3; Đường dẫn sâu một phát: #>> '{device,os}' SELECT payload #>> '{device,os}' FROM events LIMIT 3; ⭐ @> "chứa" — toán tử ăn index GIN, trái tim của query JSONB nhanh SELECT count(*) FROM events WHERE payload @> '{"event_type": "purchase", "device": {"os": "ios"}}'; ? — key có tồn tại không SELECT count(*) FROM events WHERE payload ? 'coupon_code'; Bung mảng JSON thành dòng — jsonb_array_elements là bạn thân ETL SELECT e.id, item ->> 'sku' AS sku, (item ->> 'qty')::int AS qty FROM events e, jsonb_array_elements(e.payload -> 'items') AS item; Cập nhật một trường trong JSONB không đụng phần còn lại UPDATE events SET payload = jsonb_set(payload, '{processed}', 'true') WHERE id = 42;
Khi nào cột thật, khi nào JSONB

Trường nào query/JOIN/aggregate thường xuyên → cột thật (kiểu chặt, index B-tree, thống kê planner tốt). Trường nào thưa thớt, đổi schema liên tục, chỉ lọc thỉnh thoảng → JSONB + index GIN (Module 6). Mẫu phổ biến: bảng events có user_id, event_type, created_at là cột thật + payload JSONB cho phần còn lại.

Module 04 — SQL nâng cao

SQL nâng cao PG-only — viết ít, làm nhiều

Bạn đã có window function, CTE, APPLY từ SQL Server. Module này tập trung vào những cú pháp Postgres làm gọn hơn hoặc SQL Server không có: DISTINCT ON, LATERAL, FILTER, GROUPING SETS, và các chiêu CTE mà dân analytics engineering dùng hàng ngày.

› DISTINCT ON — top-1 mỗi nhóm trong 1 dòng › LATERAL — CROSS APPLY phiên bản PG › FILTER — pivot có điều kiện sạch sẽ › GROUPING SETS / ROLLUP / CUBE › CTE: MATERIALIZED & recursive › Đặc sản nhỏ mà võ: ::, string_agg, TABLESAMPLE › Tình huống: phân tích funnel một query

1. DISTINCT ON — "top-1 mỗi nhóm" trong một dòng

Bài toán kinh điển: lấy đơn hàng gần nhất của mỗi user. SQL Server cần ROW_NUMBER() OVER (...) + subquery + WHERE rn = 1. Postgres: một mệnh đề.

distinct-on
⭐ Dòng ĐẦU TIÊN của mỗi user_id theo ORDER BY — gọn hơn ROW_NUMBER 3 dòng SELECT DISTINCT ON (user_id) user_id, id AS last_order_id, amount, created_at FROM orders ORDER BY user_id, created_at DESC; Quy tắc: cột trong DISTINCT ON phải đứng ĐẦU ORDER BY; phần sau quyết định dòng nào "thắng" Nhiều khoá nhóm cũng được: bản ghi giá mới nhất của mỗi (product, region) SELECT DISTINCT ON (product_id, region) * FROM price_history ORDER BY product_id, region, valid_from DESC;
Khi nào vẫn dùng ROW_NUMBER

Cần top-N (N>1) mỗi nhóm, hoặc cần chính con số thứ hạng → vẫn ROW_NUMBER. Chỉ cần "dòng tốt nhất mỗi nhóm" → DISTINCT ON ngắn hơn và thường nhanh hơn (planner có chiến lược riêng cho nó).

2. LATERAL — CROSS APPLY phiên bản Postgres

Bạn biết CROSS APPLY/OUTER APPLY — Postgres gọi nó là LATERAL: vế phải JOIN được phép tham chiếu cột của vế trái, tức một "subquery chạy cho từng dòng".

lateral-join
⭐ Top 3 đơn lớn nhất của MỖI user — bài toán APPLY kinh điển SELECT u.name, o.amount, o.created_at FROM users u CROSS JOIN LATERAL ( SELECT amount, created_at FROM orders WHERE orders.user_id = u.id -- tham chiếu u.id: chỉ LATERAL cho phép ORDER BY amount DESC LIMIT 3 ) o; LEFT JOIN LATERAL ... ON true = OUTER APPLY (giữ user chưa có đơn) SELECT u.name, o.amount FROM users u LEFT JOIN LATERAL ( SELECT amount FROM orders WHERE user_id = u.id ORDER BY created_at DESC LIMIT 1 ) o ON true; LATERAL + hàm bung dòng: tách items của từng event (kết hợp Module 3) SELECT e.id, i.item ->> 'sku' AS sku FROM events e CROSS JOIN LATERAL jsonb_array_elements(e.payload -> 'items') AS i(item);

3. FILTER — pivot có điều kiện, sạch hơn CASE WHEN

Đếm/tổng theo nhiều điều kiện trong một lần quét — SQL Server viết SUM(CASE WHEN ... THEN 1 ELSE 0 END) lặp đi lặp lại. PG có mệnh đề FILTER chuẩn SQL, đọc như văn nói:

Dashboard cần: doanh thu theo (region, channel), theo region, và tổng toàn cục. Ba GROUP BY + UNION ALL = quét bảng ba lần. GROUPING SETS quét một lần:

5. CTE — hai chi tiết PG mà dân SQL Server hay vấp

MATERIALIZED vs NOT MATERIALIZED (PG12+)

PG cũ (≤11) luôn materialize CTE — tính ra bảng tạm, chặn việc đẩy WHERE vào trong → CTE từng nổi tiếng "chậm" trên PG. Từ PG12, planner mặc định inline CTE như subquery (giống SQL Server). Bạn ép hành vi bằng từ khoá: WITH x AS MATERIALIZED (...) để tính đúng một lần (CTE được tham chiếu nhiều lần / muốn cô lập), hoặc NOT MATERIALIZED để ép inline.

x

Bối cảnh: PM hỏi: "Tháng này bao nhiêu user xem sản phẩm → thêm giỏ → mua, tỷ lệ rớt ở mỗi bước?" Bảng events (Module 3) có 150 triệu dòng.

Module 05 — Ghi dữ liệu

Ghi dữ liệu Production — COPY, UPSERT, MERGE

90% công việc ghi của Data Engineer là ba mẫu: bulk load (đổ hàng triệu dòng), upsert (insert-hoặc-update theo key), và batch update an toàn. Postgres có công cụ riêng cho từng mẫu — dùng đúng nhanh hơn dùng sai hàng chục lần, theo đúng nghĩa đen.

› COPY — bulk load chuẩn mực › ⭐ ON CONFLICT — upsert một câu › MERGE (PG15+) — khi nào hơn ON CONFLICT › RETURNING — DML trả dữ liệu › UPDATE/DELETE lớn không nghẹt production › Tình huống: nightly upsert 5 triệu dòng

1. COPY — bulk load chuẩn mực

So tốc độ nạp 5 triệu dòng: INSERT từng dòng ~45 phút, INSERT multi-row batch ~4 phút, COPY ~40 giây. COPY đi đường riêng tối ưu (bỏ qua parse từng câu; riêng tối ưu WAL chỉ có khi wal_level=minimal VÀ bảng được tạo/TRUNCATE trong cùng transaction — bình thường COPY vẫn ghi WAL đầy đủ). Đây là lệnh nạp dữ liệu mặc định của mọi pipeline PG.

copy-patterns
Nạp CSV — khai báo rõ format, header, null marker COPY staging.raw_orders FROM '/data/orders.csv' WITH (FORMAT csv, HEADER true, NULL ''); Nạp từ stdin — trái tim của pipeline streaming (psycopg copy_expert cũng đi đường này) zcat orders.csv.gz | psql -d warehouse -c "\copy staging.raw_orders FROM STDIN CSV HEADER" ⭐ Mẹo tăng tốc: nạp vào bảng UNLOGGED (bỏ WAL) rồi chuyển đổi sau CREATE UNLOGGED TABLE staging.raw_orders_tmp (LIKE staging.raw_orders); UNLOGGED nhanh hơn ~2x nhưng MẤT SẠCH nếu crash — chỉ dùng cho staging tái tạo được
Quy trình staging chuẩn

Đừng COPY thẳng vào bảng đích production. Chuẩn: COPY vào bảng staging (UNLOGGED, không index, không constraint) → validate bằng SQL → INSERT...SELECT hoặc upsert sang bảng đích. Lỗi dữ liệu chết ở staging, không lây sang production — đúng triết lý "raw bất biến" của pipeline.

2. ⭐ ON CONFLICT — upsert một câu, nguyên tử tuyệt đối

"Insert nếu chưa có, update nếu có rồi" — SQL Server dùng MERGE (kèm cả trang gotcha nổi tiếng). Postgres có INSERT ... ON CONFLICT: ngắn, nguyên tử, không race condition.

on-conflict
Upsert kinh điển — EXCLUDED là "dòng định chèn nhưng bị đụng" INSERT INTO dim_users (user_id, email, plan, updated_at) VALUES (1001, 'an@corp.vn', 'pro', now()) ON CONFLICT (user_id) DO UPDATE SET email = EXCLUDED.email, plan = EXCLUDED.plan, updated_at = EXCLUDED.updated_at; Chỉ update khi dữ liệu THẬT SỰ đổi — tránh ghi thừa (WAL + bloat, Module 12) ON CONFLICT (user_id) DO UPDATE SET email = EXCLUDED.email, plan = EXCLUDED.plan, updated_at = now() WHERE (dim_users.email, dim_users.plan) IS DISTINCT FROM (EXCLUDED.email, EXCLUDED.plan); Idempotent insert — chèn trùng thì lờ đi (event dedup, retry-safe pipeline) INSERT INTO processed_files (file_name) VALUES ('orders_2026-06-09.csv') ON CONFLICT (file_name) DO NOTHING;
Điều kiện tiên quyết

ON CONFLICT (cột) đòi hỏi có UNIQUE constraint/index trên đúng cột đó — PG dùng nó để phát hiện đụng độ. Không có unique → lỗi "no unique or exclusion constraint matching". Đây cũng là lý do thiết kế bảng dimension luôn cần natural key unique.

3. MERGE (PG15+) — khi nào dùng thay ON CONFLICT

PG15 thêm MERGE chuẩn SQL — cú pháp quen thuộc với bạn từ SQL Server. Khác biệt then chốt với ON CONFLICT:

ON CONFLICT thắng khi

Upsert đơn giản theo unique key, cần chống race condition tuyệt đối (nhiều writer đồng thời). Nhanh hơn, an toàn hơn dưới concurrency.

MERGE thắng khi

Logic nhiều nhánh: matched thì UPDATE có điều kiện, not matched thì INSERT, matched-mà-nguồn-đánh-dấu-xoá thì DELETE — ON CONFLICT không xoá được. Đồng bộ dimension kiểu SCD là đất của MERGE.

merge-pg15
MERGE INTO dim_products d USING staging.products s ON d.sku = s.sku WHEN MATCHED AND s.is_deleted THEN DELETE WHEN MATCHED THEN UPDATE SET name = s.name, price = s.price, updated_at = now() WHEN NOT MATCHED THEN INSERT (sku, name, price) VALUES (s.sku, s.name, s.price);
Di sản từ SQL Server

MERGE của PG không chống race tốt như ON CONFLICT: hai MERGE đồng thời có thể cùng thấy "not matched" và cùng INSERT → lỗi duplicate. Pipeline batch tuần tự thì vô tư; ghi đồng thời từ nhiều worker → quay về ON CONFLICT.

1. Planner định giá thế nào — cost model trong 5 phút

Trước khi đọc plan, cần biết plan từ đâu ra. Planner không "biết" cách nào nhanh — nó định giá mọi phương án bằng một mô hình chi phí đơn giản đến bất ngờ, rồi chọn phương án rẻ nhất. Toàn bộ chuỗi suy luận:

Thống kê cột (histogram, MCV, n_distinct — do ANALYZE thu thập)
   → selectivity: WHERE này giữ lại bao nhiêu % dòng?
   → cardinality: ước số dòng mỗi bước (cột "rows" trong plan)
   → cost: số dòng × đơn giá (đọc trang tuần tự = 1, trang ngẫu nhiên = 4, xử lý 1 tuple = 0.01...)
   → so giá mọi tổ hợp scan/join → plan RẺ NHẤT thắng
Mọi quyết định (Seq vs Index, Nested Loop vs Hash) chỉ là phép nhân từ thống kê — không có "trí tuệ" nào khác
Hệ quả số 1: thống kê sai → cardinality sai → cả plan sai

Vì cost chỉ là số dòng ước × đơn giá, sai số nằm gần như trọn ở khâu ước số dòng. Ước 12 dòng → Nested Loop trông rẻ; thực tế 500k dòng → thảm hoạ. Đó là lý do "rows ước sai" là hung thủ #1 (mục 5) và ANALYZE sau bulk load là quy tắc sắt. Đơn giá cũng chỉnh được: random_page_cost mặc định 4 là di sản thời HDD — trên SSD để 1.1, nếu không planner "sợ" index scan một cách vô căn cứ (Module 16).

Vì sao Seq Scan thắng khi lấy nhiều dòng

Index scan trả giá trang ngẫu nhiên (đơn giá 4) cho từng dòng tìm thấy; Seq Scan trả giá trang tuần tự (đơn giá 1) cho cả bảng. Lấy 0.1% bảng: index rẻ hơn đứt. Lấy 30%: tổng giá ngẫu nhiên vượt giá đọc thẳng cả bảng — Seq Scan thắng một cách chính đáng. Hiểu phép tính này, bạn hết hoảng khi thấy Seq Scan, và biết Bitmap Scan (mục 3) chính là phương án lai ở khoảng giữa.

2. Đọc cây plan — từ trong ra ngoài, lá chạy trước

giải-phẫu-plan
EXPLAIN SELECT u.country, sum(o.amount) FROM orders o JOIN users u ON u.id = o.user_id WHERE o.created_at > now() - interval '7 days' GROUP BY u.country; HashAggregate (cost=89421.10..89423.60 rows=250 width=40) ← chạy SAU CÙNG Group Key: u.country -> Hash Join (cost=3892.00..86730.10 rows=538200 width=16) Hash Cond: (o.user_id = u.id) -> Index Scan using idx_orders_created on orders o ← lá: chạy ĐẦU TIÊN (cost=0.44..58320.50 rows=538200 width=16) Index Cond: (created_at > (now() - '7 days'::interval)) -> Hash (cost=2400.00..2400.00 rows=119360 width=12) -> Seq Scan on users u (cost=0.00..2400.00 rows=119360 width=12)
cost=X..Y rows=N width=W — bốn con số của mỗi node

X = startup cost (chi phí trước khi trả dòng đầu tiên), Y = total cost (đơn vị trừu tượng, ~số lần đọc page tuần tự), rows = số dòng planner ước node này trả ra, width = số byte trung bình mỗi dòng. Trong bốn con số, rows là quan trọng nhất — mọi quyết định chọn join/scan đều dựa trên nó, và khi nó sai, cả plan sai theo (mục 4).

1. FUNCTION vs PROCEDURE — phân biệt đầu tiên phải nắm

SQL Server gần như mọi thứ là stored procedure. Postgres tách làm hai, và ranh giới nằm ở transaction:

FUNCTION (CREATE FUNCTION)

Chạy bên trong transaction của câu lệnh gọi nó — không thể COMMIT/ROLLBACK bên trong. Trả về giá trị/bảng, gọi được trong SELECT. Là "ngựa thồ" chính: 95% logic DB của PG nằm trong function.

PROCEDURE (CREATE PROCEDURE, PG11+)

Gọi bằng CALL, được phép COMMIT/ROLLBACK bên trong — sinh ra cho batch job dài cần chia transaction (mục 7). Không trả giá trị qua SELECT (chỉ tham số INOUT).

Quy đổi tư duy

SP bên SQL Server làm báo cáo/đọc dữ liệu → bên PG viết FUNCTION RETURNS TABLE. SP chạy batch đêm có nhiều bước commit → bên PG viết PROCEDURE. Đừng cố viết PROCEDURE cho mọi thứ theo quán tính — sẽ vướng ngay vì không SELECT ra được.

3. ⭐ Plan caching — sự thật PG khác SQL Server

Đây là điểm session SQL của bạn cần "phiên dịch" cẩn thận nhất. SQL Server có plan cache toàn cục: compile một lần, mọi session tái dùng. Postgres không có cache toàn cục — nhưng SP vẫn hưởng plan caching, theo cách riêng:

Cơ chế 5-lần-đầu: custom plan → generic plan

Câu SQL trong PL/pgSQL được prepare ngầm và cache theo từng session. Năm lần thực thi đầu, planner lập custom plan theo giá trị tham số thật và ghi nhận chi phí trung bình. Từ lần thứ sáu, nó so với chi phí generic plan (không nhìn tham số): nếu generic không tệ hơn đáng kể → dùng generic mãi, khỏi tốn công plan lại. Điều khiển bằng plan_cache_mode = auto / force_custom_plan / force_generic_plan.

plan-cache-quan-sát
Quan sát cú chuyển generic plan bằng prepared statement (cùng cơ chế với PL/pgSQL) PREPARE q(text) AS SELECT count(*) FROM orders WHERE status = $1; EXPLAIN EXECUTE q('paid'); -- lần 1-5: Filter: (status = 'paid'::text) EXPLAIN EXECUTE q('paid'); -- chạy thêm 4 lần nữa... -- lần 6: Filter: (status = $1) ← placeholder = đã chuyển GENERIC plan Generic plan gây hại (skew/partition)? Ép custom theo phiên hoặc theo function: ALTER FUNCTION fn_upsert_daily_revenue(date) SET plan_cache_mode = 'force_custom_plan';
Generic plan + partition = bom hẹn giờ

Generic plan không biết giá trị tham số → không prune được lúc planning: bảng 365 partition, custom plan chỉ đụng 1 partition, generic plan phải lập kế hoạch và lấy lock trên cả 365. Nói cho chính xác: từ PG11 có runtime pruning — lúc thực thi các ngăn thừa vẫn bị loại (EXPLAIN ANALYZE hiện Subplans Removed: N) — nên pruning không mất hoàn toàn. Chi phí còn lại nằm ở khâu planning: plan/lock trên mọi partition mỗi lần thực thi, plan phình to — vẫn đủ gây triệu chứng kinh điển: "function chạy nhanh 5 lần đầu, từ lần 6 chậm gấp 50". Gặp bảng partition (Module 14) → cân nhắc force_custom_plan cho function đó.

Điểm cộng bất ngờ của PG

Vì plan cache theo session chứ không toàn cục, một plan tồi ở PG không đầu độc cả server như parameter sniffing kinh điển của SQL Server — hỏng đâu chỉ hỏng ở session đó. Nhưng đừng hiểu là miễn nhiễm: biến thể per-session vẫn tồn tại — chính ca "nhanh 5 lần đầu, từ lần 6 chậm" ở box trên (và Ca 2, Module 17) là một dạng sniffing, khi generic plan không hợp với phân bố dữ liệu thật. Đổi lại: connection mới = cache nguội — thêm một lý do dùng connection pooler để tái dùng session (Module 16).

Vì sao mẫu này ăn tiền

Mỗi vòng là một transaction 50k dòng ~1–2 giây: khoá dòng ngắn, VACUUM dọn được dead tuple song song (Module 12), replica không tụt xa, và Ctrl+C giữa chừng chỉ mất batch dở — 79.95M dòng đã commit còn nguyên. So với "một UPDATE 80M dòng chạy 3 tiếng rồi lăn ra chết ở phút 175": khác biệt giữa đêm yên giấc và đêm trắng.

2. ⭐ HNSW — index chủ lực và ba núm vặn

Exact vs ANN — đánh đổi nền tảng

Không index, pgvector quét tuần tự và trả kết quả chính xác 100% (exact KNN) — O(N), chết dần từ vài trăm nghìn vector. Index HNSW chuyển sang ANN (approximate nearest neighbor): nhanh hơn hàng trăm lần, đổi lấy recall ~95–99% (thỉnh thoảng sót một láng giềng thật). Mọi tuning vector search xoay quanh trục recall ↔ tốc độ này.

hnsw-tuning
Build index — m và ef_construction là tham số LÚC XÂY CREATE INDEX CONCURRENTLY idx_chunks_embedding ON doc_chunks USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64); m=16: số cạnh mỗi node (cao hơn → recall tốt hơn, index to hơn) ef_construction=64: ứng viên xét khi chèn (cao hơn → graph tốt hơn, build chậm hơn) ⭐ ef_search là núm LÚC TRUY VẤN — mặc định 40, tăng để đổi tốc độ lấy recall BEGIN; SET LOCAL hnsw.ef_search = 100; SELECT id FROM doc_chunks ORDER BY embedding <=> $1 LIMIT 10; COMMIT; Build nhanh hơn nhiều nếu cho maintenance_work_mem đủ chứa graph SET maintenance_work_mem = '8GB'; -- session build index, không phải global
SET LOCAL, không SET trần — vì pooler

SET hnsw.ef_search trần dính cả session — qua PgBouncer (Module 16), session được tái dùng cho request khác → tham số "rò" sang query của người khác. Chuẩn production: SET LOCAL trong transaction (tự hết hiệu lực khi COMMIT/ROLLBACK) hoặc gắn vào function bằng ALTER FUNCTION ... SET (mẹo từ Module 8).

Giới hạn cần biết trước khi thiết kế

HNSW của pgvector giới hạn 2.000 chiều cho kiểu vector thường (model 3072 chiều như text-embedding-3-large phải hạ chiều, dùng halfvec, hoặc index trên biểu thức cắt chiều). Index HNSW sống trong RAM để chạy tốt: ~6GB cho 1 triệu vector 1536 chiều — tính RAM trước khi hứa với sếp.

3. IVFFlat — còn đất dụng võ không?

HNSW (mặc định nên chọn)

Query nhanh hơn, recall cao hơn, tạo được trên bảng rỗng và chèn dần. Giá: build chậm, RAM nhiều.

IVFFlat (ngách)

Build nhanh, nhẹ RAM — nhưng phải có dữ liệu trước (k-means training) và recall kém hơn. Rule of thumb: lists = rows/1000 (<1M dòng) hoặc sqrt(rows) (≥1M); query chỉnh ivfflat.probes. Hợp: batch re-index định kỳ, ngân sách RAM hẹp.

Index trên SSD

Streaming filtering

Không có "trần ef_search": executor hỏi "ứng viên gần tiếp theo" liên tục tới khi đủ LIMIT thoả filter — giải triệt để bẫy ở mục 4, không mất recall.

SBQ compression

Đọc benchmark có não

1. Process model — vì sao connection đắt

SQL Server: một process, hàng nghìn worker thread nhẹ. Postgres: tiến trình gốc postmaster lắng nghe cổng 5432, và fork một OS process riêng cho mỗi connection (backend). Thread nhẹ vài trăm KB; process PG ngốn vài MB private memory + chi phí fork + context switch nặng hơn.

postmaster fork backend cho từng connection + đàn tiến trình nền; tất cả gặp nhau ở shared memory
Hệ quả thực dụng

(1) max_connections không phải số "miễn phí" — mỗi slot là một process tiềm năng; đặt 1000 không pooler là tự sát. (2) Mỗi backend hiện rõ trong ps aux | grep postgres — kỹ năng soi process Linux của bạn áp dụng trực tiếp: thấy ngay backend nào ăn CPU, đang chạy query gì (PG ghi query vào process title). (3) Một backend crash hiếm khi kéo sập cả cluster — cô lập theo process là một lớp an toàn.

2. Hai tầng cache — shared_buffers và OS page cache

Khác SQL Server (buffer pool ôm gần hết RAM, đọc đĩa kiểu bypass cache hệ điều hành), Postgres cố tình dựa vào OS page cache: dữ liệu nóng có thể nằm ở shared_buffers (cache của PG), ở page cache của Linux, hoặc cả hai (double buffering).

Vì sao shared_buffers chỉ nên ~25% RAM

Đặt shared_buffers = 90% RAM kiểu buffer pool SQL Server là sai trên PG: OS page cache bị bóp chết trong khi PG vẫn đọc/ghi file qua filesystem (cần page cache để nhanh), còn vùng trùng lặp giữa hai tầng cache thành lãng phí. Khuyến nghị cộng đồng: shared_buffers ≈ 25% RAM, và khai cho planner biết tổng cache hai tầng qua effective_cache_size ≈ 50–75% RAM (con số này KHÔNG cấp phát gì, chỉ là "lời khai" giúp planner ưa index scan hơn — Module 16).

soi-cache
Tỷ lệ cache hit của từng bảng — dưới 99% với bảng nóng là đáng nghĩ SELECT relname, heap_blks_hit, heap_blks_read, round(100.0 * heap_blks_hit / nullif(heap_blks_hit + heap_blks_read,0), 1) AS hit_pct FROM pg_statio_user_tables ORDER BY heap_blks_read DESC LIMIT 5; Đây chính là nguồn của "Buffers: shared hit / read" trong EXPLAIN (Module 7)

3. ⭐ WAL — trái tim của durability (và của cả Module 15)

Write-Ahead Log — luật chơi duy nhất

Mọi thay đổi dữ liệu phải được ghi vào nhật ký tuần tự (WAL, thư mục pg_wal/) và fsync xuống đĩa trước khi COMMIT trả về thành công. Trang dữ liệu thật trong RAM (dirty page) được phép ghi xuống đĩa... từ từ, lúc nào tiện. Crash giữa chừng? Khởi động lại, PG phát lại (replay) WAL từ checkpoint gần nhất — dữ liệu đã commit không bao giờ mất. Đây là chữ D trong ACID, cùng triết lý transaction log của SQL Server nhưng vai trò còn rộng hơn: WAL là nguồn cấp cho replication, PITR và CDC (Module 15).

Vì sao COMMIT nhanh đến vậy

COMMIT chỉ cần một cú ghi tuần tự bé tí vào WAL — không phải ghi ngẫu nhiên các trang dữ liệu rải rác. Ghi tuần tự là thao tác đĩa nhanh nhất. Đây cũng là lý do tách WAL ra ổ riêng từng là chiêu tăng tốc kinh điển thời HDD (thời NVMe ít quan trọng hơn).

4. Checkpoint & background writer — trả nợ dirty page

WAL cho phép "khất" việc ghi trang dữ liệu — nhưng nợ phải trả: checkpoint là thời điểm PG xả mọi dirty page xuống đĩa và đánh dấu "từ đây về trước đã an toàn, WAL cũ được tái chế". Tiến trình checkpointer đảm nhiệm, bgwriter tỉa dần dirty page giữa các kỳ.

checkpoint-tuning
Hai núm chính: chu kỳ và trần WAL giữa hai checkpoint SELECT name, setting, unit FROM pg_settings WHERE name IN ('checkpoint_timeout','max_wal_size','checkpoint_completion_target'); Cờ đỏ trong log: checkpoint bị ép chạy dồn dập vì WAL vượt trần khi bulk load LOG: checkpoints are occurring too frequently (24 seconds apart) HINT: Consider increasing the configuration parameter "max_wal_size". Pipeline ETL ghi nặng → tăng max_wal_size (vd 8GB) để checkpoint thưa và êm
Checkpoint và đỉnh I/O

Triệu chứng kinh điển: cứ ~5 phút hệ thống khựng vài giây, iostat cho thấy %util dựng đứng — đúng nhịp checkpoint xả hàng GB dirty page. Thuốc: checkpoint_completion_target = 0.9 (trải việc ghi ra 90% chu kỳ thay vì dồn cục) + max_wal_size đủ rộng. Kỹ năng đọc iostat của bạn từ Linux dùng nguyên si ở đây.

5. Ráp lại: một UPDATE đi qua hệ thống như thế nào

UPDATE orders SET status='paid' WHERE id=42;

1. backend đọc trang chứa dòng 42 vào shared_buffers (nếu chưa có)
2. tạo PHIÊN BẢN DÒNG MỚI ngay trong trang (MVCC — Module 12), trang thành dirty
3. ghi bản ghi thay đổi vào WAL buffer
4. COMMIT → chính backend fsync WAL xuống đĩa (walwriter chỉ gánh phần nền/async) → trả "COMMIT"  ✓ xong với user
5. ...sau đó, lúc nào tiện: bgwriter/checkpointer mới ghi trang dirty xuống data file
Điểm mấu chốt: bước 4 (tuần tự, nhỏ) quyết định độ trễ COMMIT; bước 5 (ngẫu nhiên, to) được trì hoãn — đó là toàn bộ "phép màu" hiệu năng ghi của PG

Bước 2 sinh ra dead tuple → VACUUM (Module 12). Bản ghi WAL ở bước 3 chính là thứ replica nhận được (Module 15). Trang dirty và shared_buffers là thứ bạn tune ở Module 16. Một sơ đồ 5 bước, bốn module chuyên sâu treo trên đó.

1. xmin/xmax — mỗi dòng là một chuỗi phiên bản

Mỗi dòng (tuple) mang hai cột hệ thống ẩn: xmin = ID transaction tạo ra phiên bản này, xmax = ID transaction xoá/thay thế nó (0 nếu còn sống). UPDATE không sửa đè — nó chèn phiên bản mới + đóng dấu xmax lên phiên bản cũ. Mỗi transaction nhìn qua "snapshot" của mình: chỉ thấy phiên bản có xmin đã commit trước khi nó bắt đầu và xmax chưa commit.

soi-xmin-xmax
Cột hệ thống query được trực tiếp — thử trên bảng bất kỳ SELECT xmin, xmax, id, status FROM orders WHERE id = 42; xmin | xmax | id | status -------+------+----+-------- 84211 | 0 | 42 | paid xmax=0: phiên bản đang sống Mở transaction A, UPDATE dòng 42 nhưng CHƯA commit; từ session B nhìn: SELECT xmin, xmax, id, status FROM orders WHERE id = 42; xmin | xmax | id | status -------+-------+----+-------- 84211 | 84392 | 42 | paid B vẫn thấy bản cũ — xmax đã ghi tên "kẻ định thay thế"
Snapshot isolation — vì sao không cần NOLOCK

Reader đọc phiên bản cũ còn hợp lệ với snapshot của mình; writer tạo phiên bản mới. Hai bên không đụng nhau nên không ai chờ ai. SQL Server đạt điều tương tự khi bật RCSI (chép bản cũ vào tempdb); PG thì bản cũ nằm ngay trong bảng — không cần tempdb, nhưng nghĩa là rác tích trong chính bảng của bạn. Một chi tiết nhỏ hay gây bối rối: tuple còn mang hint bit — cờ "transaction tạo/xoá tôi đã commit xong" được ghi lười bởi kẻ ĐỌC đầu tiên chạm vào tuple; vì vậy một SELECT lớn ngay sau bulk load có thể bất ngờ sinh I/O ghi. Không phải bug — là PG đang hoàn tất giấy tờ MVCC.

2. Dead tuple & bloat — hoá đơn được gửi đến

Khi không transaction nào còn cần phiên bản cũ, nó thành dead tuple — xác chết chiếm chỗ trong trang dữ liệu. UPDATE 10 triệu dòng = 10 triệu dead tuple. Bảng phình to hơn dữ liệu thật (bloat) → Seq Scan đọc nhiều block hơn, cache loãng đi, index trỏ vào xác cũng phình theo.

HOT update — lối thoát ít người biết

Nếu UPDATE không đụng cột nào có index và trang còn chỗ trống, PG làm "HOT update": phiên bản mới nằm cùng trang, index không cần entry mới — rẻ hơn hẳn. Hai đòn bẩy thực dụng: (1) đừng index cột bị update liên tục nếu không cần, (2) bảng update nặng đặt fillfactor=80 (chừa 20% chỗ trống mỗi trang cho HOT). 5. Transaction ID wraparound — sự cố hạng nặng nhất của PG

XID wraparound — vì sao VACUUM là bắt buộc, không phải tuỳ chọn

Transaction ID là bộ đếm 32-bit (~4 tỷ, so sánh vòng tròn ±2 tỷ). Nếu một bảng có tuple già hơn ~2 tỷ XID chưa được VACUUM "đóng băng" (freeze), phép so sánh cũ/mới sẽ lộn vòng — dữ liệu đã commit bỗng "tàng hình". PG thà chết chứ không để điều đó xảy ra: nó cảnh báo, rồi từ chối mọi ghi (shutdown bảo vệ) khi sát ngưỡng. Autovacuum có chế độ "to prevent wraparound" sẽ tự chạy bất chấp — thấy nó trong pg_stat_activity nghĩa là hệ thống đã phải tự vệ.

2. Bản đồ khoá — chỉ cần nhớ 4 nhân vật

Row lock (DML / FOR UPDATE)

UPDATE/DELETE khoá từng dòng đụng tới; hai UPDATE cùng dòng thì kẻ sau chờ. Không có lock escalation kiểu SQL Server — triệu row lock không bao giờ "thăng cấp" thành table lock (chúng ghi ngay trên tuple, không phình RAM lock manager).

ACCESS SHARE

SELECT cầm khoá này — yếu nhất, chỉ kỵ duy nhất ACCESS EXCLUSIVE. "Tôi đang đọc, đừng đập bàn của tôi."

SHARE UPDATE EXCLUSIVE

VACUUM, ANALYZE, CREATE INDEX CONCURRENTLY cầm — không chặn đọc/ghi, chỉ kỵ chính nó và DDL. Nhờ vậy autovacuum (Module 12) sống chung hoà bình với production.

ACCESS EXCLUSIVE — trùm cuối

Hầu hết ALTER TABLE, DROP, TRUNCATE, VACUUM FULL cầm — kỵ tất cả, kể cả SELECT. Mọi tai nạn migration đều xoay quanh nhân vật này.

3. ⭐ Lock queue — cú domino giết production

Điều ít người biết: hàng đợi khoá của PG là FIFO nghiêm ngặt. ALTER TABLE đứng chờ một transaction dài nhả khoá — và mọi SELECT đến sau nó phải xếp hàng sau ALTER, dù SELECT vốn chẳng xung đột gì với transaction kia:

T0: SELECT dài đang chạy (ACCESS SHARE, còn 4 phút)
T1: ALTER TABLE orders ...        → chờ T0   (cần ACCESS EXCLUSIVE)
T2: SELECT id FROM orders ...     → chờ T1!  (FIFO — dù chỉ cần ACCESS SHARE)
T3: SELECT ...                    → chờ T1
...toàn bộ app treo 4 phút vì một câu ALTER "5 giây"
ALTER không nguy hiểm vì nó chậm — nó nguy hiểm vì nó biến mọi người đến sau thành con tin của transaction trước nó
Quy tắc số một: lock_timeout cho mọi DDL

Trước mọi migration production: SET lock_timeout = '3s'; — ALTER không lấy được khoá trong 3 giây thì tự huỷ thay vì đứng chắn đường. Migration fail thì chạy lại lúc khác; production treo thì 2h sáng có người gọi bạn. Một dòng lệnh, một đêm yên giấc.

4. Replication slot — con dao hai lưỡi nổi tiếng

Slot — lời hứa "giữ WAL chờ anh"

Slot là bookmark phía primary ghi nhớ consumer (replica, Debezium...) đã đọc tới đâu, và cam kết không xoá WAL chưa được đọc. Replica rớt mạng 2 ngày? Quay lại vẫn đủ WAL, không phải rebuild. Khác replication vật lý (chép byte, replica giống hệt 100%), logical replication giải mã WAL thành dòng sự kiện INSERT/UPDATE/DELETE — chọn được từng bảng, qua được khác version, và là nền của CDC (Change Data Capture):

5. ⭐ Hybrid search với RRF — trộn hai thế giới

RRF — Reciprocal Rank Fusion

Cách trộn hai bảng xếp hạng không cùng thang điểm (ts_rank ~0–1, cosine distance ~0–2 — cộng trực tiếp là vô nghĩa): bỏ điểm, chỉ giữ thứ hạng. Điểm RRF của một document = Σ 1/(k + rank) qua từng bảng xếp hạng (k≈60 theo paper gốc). Document đứng cao ở cả hai bảng nổi lên đầu; đứng cao ở một bảng vẫn có cửa. Đơn giản, không cần tuning trọng số, hiệu quả khó tin — chuẩn de-facto của hybrid search.

hybrid-rrf-query
⭐ Mẫu hybrid hoàn chỉnh: 2 CTE xếp hạng độc lập + FULL JOIN + điểm RRF WITH fts AS ( SELECT id, row_number() OVER (ORDER BY ts_rank(fts, q) DESC) AS r FROM doc_chunks, websearch_to_tsquery('vi', :query_text) AS q WHERE fts @@ q ORDER BY r -- bắt buộc: LIMIT không ORDER BY lấy 40 dòng TUỲ Ý, không phải top-40 LIMIT 40 ), vec AS ( SELECT id, row_number() OVER (ORDER BY embedding <=> :query_emb) AS r FROM doc_chunks ORDER BY embedding <=> :query_emb LIMIT 40 ) SELECT coalesce(fts.id, vec.id) AS id, coalesce(1.0/(60 + fts.r), 0) + coalesce(1.0/(60 + vec.r), 0) AS rrf_score FROM fts FULL OUTER JOIN vec USING (id) ORDER BY rrf_score DESC LIMIT 10; Mỗi nhánh lấy top-40 (rộng hơn kết quả cuối 10 — cho RRF có gì để trộn) Nhánh vec nhớ bài SET LOCAL ef_search và iterative_scan từ Module 9

3. Aurora — "tương thích Postgres" không có nghĩa là Postgres

Khác biệt cốt lõi

Aurora thay tầng storage: 6 bản sao dữ liệu trên 3 AZ, chỉ ship WAL xuống storage (không checkpoint full-page kiểu PG thường). Hệ quả tốt: replica lag thường ~10-20ms, failover <30s, storage tự co giãn tới 128TB.

Cái giá & cái bẫy

Đắt hơn RDS thường; I/O tính tiền riêng (mô hình Standard) — workload quét nhiều có hoá đơn bất ngờ; một số hiểu biết tuning (max_wal_size, checkpoint — Module 11) không áp dụng vì Amazon đã thay phần đó. Đọc kỹ trước khi mang "kinh nghiệm PG thuần" đi tune Aurora.

PG chỉ biết promote bằng tay (Module 15). 5. ⭐ Major upgrade gần-zero-downtime

Minor (16.3 → 16.4): restart vài giây, làm thường xuyên, xong. Major (13 → 16) đổi format dữ liệu nội bộ — ba con đường, ba mức đau:

1. pg_dump/restore

Sạch tuyệt đối, nhưng downtime = thời gian restore — DB 800GB là nhiều giờ. Chỉ cho DB bé.

2. pg_upgrade --link

Hard-link file dữ liệu sang binary mới, không copy — downtime vài phút bất kể size. Chuẩn cho self-host chịu được cửa sổ ngắn. Nhớ: thống kê planner KHÔNG mang theo — phải ANALYZE lại ngay (không là nguyên cluster chạy mù — Module 7).

3. Logical replication blue-green

Dựng cluster version mới, publication/subscription đồng bộ (Module 15), đợi đuổi kịp, cutover vài giây. Gần-zero-downtime thật sự; RDS Blue/Green Deployments chính là mẫu này đóng gói sẵn.

1. Trigger — mẫu audit chuẩn và cái giá phải biết

Use case chính đáng số 1 của trigger với DE: bảng audit "ai đổi gì khi nào" — không tin app tự ghi log, để DB tự ghi:

audit-trigger
CREATE TABLE audit_log ( id BIGINT GENERATED ALWAYS AS IDENTITY, table_name TEXT, op TEXT, row_id BIGINT, old_row JSONB, new_row JSONB, changed_by TEXT DEFAULT current_user, changed_at TIMESTAMPTZ DEFAULT now() ); CREATE FUNCTION fn_audit() RETURNS trigger LANGUAGE plpgsql AS $$ BEGIN INSERT INTO audit_log (table_name, op, row_id, old_row, new_row) VALUES (TG_TABLE_NAME, TG_OP, coalesce(NEW.id, OLD.id), to_jsonb(OLD), to_jsonb(NEW)); RETURN coalesce(NEW, OLD); -- AFTER trigger: giá trị trả về không đổi dữ liệu END $$; FOR EACH ROW: chạy mỗi dòng; NEW/OLD = dòng sau/trước thay đổi (= inserted/deleted của SQL Server) CREATE TRIGGER trg_orders_audit AFTER INSERT OR UPDATE OR DELETE ON orders FOR EACH ROW EXECUTE FUNCTION fn_audit();
Cái giá của trigger

Trigger ROW chạy mỗi dòng, trong transaction của câu lệnh: UPDATE 5 triệu dòng = 5 triệu lần gọi function + 5 triệu INSERT audit — bulk load chậm gấp nhiều lần và bảng audit phình theo. Phản xạ đúng: pipeline bulk (Module 5) thì ALTER TABLE ... DISABLE TRIGGER trg_orders_audit trong cửa sổ nạp (ghi nhận vào log pipeline), hoặc audit bằng CDC (Module 15) thay vì trigger. Và trigger là logic tàng hình — luôn ghi vào tài liệu schema, người sau sẽ cảm ơn bạn.

4. TOAST — bí mật đằng sau JSONB to

TOAST — The Oversized-Attribute Storage Technique

Trang PG cố định 8KB, một dòng không được vượt ~2KB theo mặc định nhắm tới — vậy JSONB 50KB nằm đâu? PG nén rồi cắt giá trị to thành lát, cất sang bảng phụ ẩn (bảng TOAST). Dòng chính chỉ giữ con trỏ. Hệ quả hiệu năng: đọc cột thường = 1 trang; đọc cột đã TOAST = thêm các cú đọc bảng phụ + giải nén (de-toast) — mỗi lần query đụng cột đó.

toast-thực-chiến
Bảng TOAST của bạn to cỡ nào? 4. Notion — 480 shard, và thủ phạm quen mặt

Bài "Herding elephants" của Notion là case study sharding được trích dẫn nhiều nhất giới PG. Chi tiết đắt nhất với bạn: lý do khiến họ buộc phải shard gấp không chỉ là CPU — Postgres monolith của họ tiến gần nguy cơ TXID wraparound vì VACUUM không theo kịp khối lượng ghi. Đúng "sự cố hạng nặng" bạn học ở Module 12, xảy ra với một sản phẩm triệu người dùng.

Shard theo workspace_id

Mọi block/page đều thuộc một workspace → chọn nó làm khoá shard, mỗi truy vấn người dùng chạm đúng một shard. Bài học chọn khoá: theo đường truy cập tự nhiên — y nguyên logic chọn khoá partition Module 14, chỉ khác cấp độ.

App-level, không Citus

480 shard logic trải trên các cụm PG thường, định tuyến ở tầng ứng dụng — họ chọn đồ "nhàm chán" tự kiểm soát thay vì tầng middleware sharding. Số 480 chia hết cho rất nhiều số → sau này gộp/tách cụm vật lý dễ dàng.

Cutover có đối soát

Double-write + bơm nền + script đối soát so từng bản ghi trước khi tráo — phiên bản phóng to của runbook "bảng mới + bơm lát + tráo tên" Module 14. Lần re-shard sau (2023) còn mượt hơn: logical replication, gần zero downtime (Module 15/19).

Lời họ tự dặn — nghe được gì

Notion tự rút ba điều: shard sớm hơn mức tưởng cần (đợi đến lúc bắt buộc thì làm trong thế bị động), nhắm zero-downtime ngay từ đầu thay vì "chịu vài giờ bảo trì", và dùng khoá gộp tự nhiên thay vì chế cột partition riêng. 5. ⭐ Queue-trên-PG — một pattern, cả hệ sinh thái GitHub

Mẫu FOR UPDATE SKIP LOCKED bạn học ở Module 5 không phải mẹo vặt — nó là nền của cả một thế hệ thư viện queue thay Redis/RabbitMQ cho khối lượng vừa: riverqueue/river (Go), oban (Elixir), graphile-worker & pg-boss (Node), good_job & solid_queue (Rails — solid_queue giờ là mặc định của Rails 8), và extension pgmq (Supabase dùng). Đọc schema của chúng, bạn thấy cùng một bộ xương:

Bộ xương chung chưng cất từ các repo trên — từng mảnh bạn đều đã học: CREATE TABLE jobs ( id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, queue TEXT NOT NULL DEFAULT 'default', payload JSONB NOT NULL, run_at TIMESTAMPTZ NOT NULL DEFAULT now(), -- lịch hẹn & retry backoff attempts INT NOT NULL DEFAULT 0, max_attempts INT NOT NULL DEFAULT 5, finished_at TIMESTAMPTZ ); ⭐ Partial index chỉ phủ việc CHƯA xong — bảng 50M job cũ, index vẫn tí hon (M6) CREATE INDEX idx_jobs_pending ON jobs (queue, run_at) WHERE finished_at IS NULL; Worker nhận việc — nguyên tử, đa worker không giẫm nhau (M5) UPDATE jobs SET attempts = attempts + 1 WHERE id = ( SELECT id FROM jobs WHERE queue = 'default' AND finished_at IS NULL AND run_at <= now() AND attempts < max_attempts ORDER BY run_at FOR UPDATE SKIP LOCKED LIMIT 1 ) RETURNING id, payload; Đánh thức worker tức thì: NOTIFY (M20) — chỉ làm chuông, KHÔNG làm nơi chứa việc

(1) Bloat: queue là bảng churn cực đại (mỗi job ≥ 2 lần UPDATE + xoá/dọn) — đúng hồ sơ bệnh nhân Module 12; các thư viện đều có cơ chế dọn job cũ định kỳ và tài liệu của họ nhắc tune autovacuum. 5. Góc nhìn DSA: độ phức tạp của mỗi access path

Mọi quyết định của planner cuối cùng quy về cấu trúc dữ liệu. Hiểu Big-O của từng access path giúp bạn dự đoán plan trước cả khi chạy EXPLAIN:

Vì fan-out của B-tree rất lớn (mỗi block 8KB chứa hàng trăm khoá), "log n" trong Postgres rất nông — 1 tỉ hàng chỉ ~4–5 tầng, tối đa ~5 lần đọc block để tới 1 hàng. Đó là lý do Index Scan gần như luôn thắng Seq Scan khi truy vấn chọn lọc, kể cả trên bảng tỉ hàng. Về JOIN: Nested Loop ~O(A·log B) khi B có index (tốt khi A nhỏ), Hash Join ~O(A+B) nếu hash vừa work_mem (set lớn, không cần sort), Merge Join ~O(A+B) khi hai vế đã sorted (vd theo index/PK).

MVCC âm thầm chi phối plan

Mỗi UPDATE/DELETE để lại dead tuple; bảng bloat khiến cùng số hàng sống nằm trên nhiều block hơn → mọi scan đọc thừa. Quan trọng nhất: Index Only Scan cần visibility map "all-visible" mà chỉ VACUUM cập nhật — bảng vừa ghi nhiều chưa vacuum sẽ tụt xuống Index Scan, mất hết lợi thế. Chi tiết: Module 12 (MVCC & VACUUM).

3. Nhánh A — một query chậm: trình tự EXPLAIN có kỷ luật

Chạy EXPLAIN (ANALYZE, BUFFERS) (trên bản sao/limit nếu query ghi dữ liệu!) rồi đọc theo ĐÚNG thứ tự này — không phải nhìn lung tung:

Bước 1 — tìm node ăn thời gian: node có actual time tổng lớn nhất. 90% án nằm ở 1-2 node. Bước 2 — so rows ước lượng vs thật: rows=100 ước lượng nhưng actual rows=2000000 → planner mù thống kê → mọi quyết định sau đó (chọn nested loop, chọn index) đều dựa trên ảo giác. Thuốc: ANALYZE bang; — rẻ nhất, thử trước tiên; vẫn lệch thì tăng statistics target cho cột lệch. Bước 3 — soi Buffers: shared read khổng lồ = đọc từ đĩa (cache lạnh hoặc bảng quá to so với shared_buffers); temp read/written xuất hiện = tràn work_mem khi sort/hash — tăng work_mem cho phiên đó hoặc giảm dữ liệu vào sort. Bước 4 — mới xét index: Seq Scan trên bảng lớn với filter lọc mạnh → thiếu index (quay lại module 6 chọn loại); index có mà không dùng → thường do hàm bọc cột (WHERE date(created_at)=...), kiểu không khớp, hoặc planner ĐÚNG khi bỏ index vì filter lấy 40% bảng. Thứ tự này quan trọng vì: thêm index cho một plan dựng trên thống kê sai là sửa mái nhà khi móng lệch.

pg_stat_statements — tìm đúng query đáng sửa

Quiz tự kiểm tra — 10 câu trọng tâm

Mỗi câu là một tình huống production. Chọn đáp án và tự giải thích vì sao trước khi mở đáp án; sai câu nào thì quay lại đúng module đó ôn lại.

Câu 1 — MVCC: UPDATE thực chất làm gì? (Module 12)

Trong PostgreSQL, UPDATE một dòng thực chất là gì?

  1. Ghi đè dòng cũ tại chỗ như SQL Server
  2. Tạo phiên bản dòng MỚI (gắn xmin = XID hiện tại) và đánh dấu dòng cũ hết hạn qua xmax; dòng chết nằm lại chờ VACUUM dọn
  3. Chuyển bản cũ sang undo log riêng như Oracle
  4. Khoá toàn bảng rồi ghi đè để đảm bảo nhất quán
Đáp án

B. MVCC của PG là "append phiên bản mới, đánh dấu phiên bản cũ". Hệ quả trực tiếp: workload UPDATE nặng sinh bloat và phụ thuộc sức khoẻ autovacuum — gốc rễ của câu 9.

Câu 2 — Hint bits: SELECT mà sinh write I/O? (Module 12)

Ngay sau khi bulk-load 100 triệu dòng, câu SELECT quét bảng đầu tiên làm đĩa ghi ầm ầm. Vì sao?

  1. PG ghi audit log cho mỗi lần đọc
  2. SELECT phải set hint bits trên từng tuple (đánh dấu transaction tạo nó đã commit) → page thành dirty → phải ghi xuống đĩa
  3. Index được build "lười" vào lần đọc đầu tiên
  4. Checkpoint tình cờ chạy cùng lúc
Đáp án

B. Lần đọc đầu tiên phải tra commit log (clog) rồi ghi kết quả vào hint bit của tuple để lần sau khỏi tra — "người đọc đầu tiên trả tiền". Cách né: chạy VACUUM ngay sau bulk load (hoặc COPY ... FREEZE) để gánh chi phí này một cách chủ động.

Câu 3 — XID wraparound (Module 12)

Một transaction bỏ quên treo suốt nhiều ngày khiến autovacuum không freeze được tuple cũ, tuổi XID của database tiến dần về giới hạn. Điều gì sẽ xảy ra?

  1. Không sao — XID là số 64-bit, không bao giờ cạn
  2. PG cảnh báo, rồi đến ngưỡng sẽ từ chối transaction mới (buộc vacuum ở chế độ khẩn cấp) — vì XID 32-bit quay vòng, dòng "quá khứ" có thể bị coi là "tương lai" và biến mất khỏi mọi snapshot
  3. Chỉ chậm đi một chút do index phình
  4. WAL đầy đĩa và server tự restart
Đáp án

B. Đây là sự cố "database tự đóng cửa" nổi tiếng. Phòng ngừa: theo dõi age(datfrozenxid), không bao giờ tắt autovacuum, và săn transaction/prepared transaction/replication slot treo giữ xmin.

Câu 4 — Lock queue & lock_timeout (Module 13)

Bạn chạy ALTER TABLE orders ADD COLUMN note text; lúc bảng đang bận. ALTER phải chờ một transaction đọc dài. Chuyện gì xảy ra với các SELECT đến SAU, và giảm rủi ro thế nào?

  1. SELECT sau vẫn chạy bình thường vì ALTER chưa cầm được lock
  2. ALTER cần ACCESS EXCLUSIVE và đứng xếp hàng trước → mọi SELECT đến sau phải xếp SAU nó → cả bảng "đứng hình"; giảm rủi ro bằng SET lock_timeout = '2s' + retry
  3. PG tự huỷ ALTER sau 60 giây
  4. SELECT được nhảy hàng vì lock đọc có ưu tiên cao hơn
Đáp án

B. Hàng đợi lock của PG là FIFO: yêu cầu mạnh đứng chờ sẽ chặn mọi yêu cầu yếu đến sau. Một ALTER "chỉ mất 5ms" có thể treo cả hệ thống chỉ vì nó chờ ai đó. lock_timeout ngắn biến "treo cả bảng" thành "ALTER fail, thử lại sau" — rẻ hơn nhiều.

Câu 5 — TIMESTAMPTZ (Module 03)

Cột TIMESTAMPTZ thực sự lưu trữ gì khi bạn insert '2026-07-09 09:00:00+07'?

  1. Chuỗi thời gian kèm timezone gốc (+07) như đã nhập
  2. Thời điểm chuẩn hoá về UTC (một con số tuyệt đối); khi SELECT sẽ hiển thị theo TimeZone của session — timezone gốc KHÔNG được lưu
  3. Giờ địa phương của server tại thời điểm insert
  4. Giống hệt TIMESTAMP, chỉ khác tên
Đáp án

B. TIMESTAMPTZ = "một điểm trên trục thời gian tuyệt đối", không phải "giờ kèm múi". Muốn nhớ người dùng nhập ở múi nào, phải lưu thêm cột tz text riêng. Quy tắc DE: pipeline luôn làm việc bằng TIMESTAMPTZ/UTC, chỉ đổi múi ở tầng hiển thị.

Câu 6 — ON CONFLICT upsert (Module 05)

Để pipeline nạp lại batch không tạo bản ghi trùng, bạn viết INSERT ... ON CONFLICT (event_id) DO UPDATE SET .... Điều kiện bắt buộc để câu lệnh này hoạt động?

  1. Bảng phải có trigger BEFORE INSERT
  2. Phải tồn tại UNIQUE index/constraint (hoặc PK) đúng trên event_id — ON CONFLICT dựa vào đó để phát hiện đụng độ
  3. Chỉ dùng được bên trong PL/pgSQL
  4. Bảng không được phép partition
Đáp án

B. Không có unique constraint khớp với cột trong ON CONFLICT thì PG báo lỗi ngay ("no unique or exclusion constraint matching"). Đây là nền của idempotent load: chạy lại batch bao nhiêu lần kết quả vẫn như một.

Câu 7 — Chọn index: GIN / BRIN / partial (Module 06)

Bảng log 2TB, append-only theo thời gian, query chủ yếu lọc khoảng created_at gần đây. Index nào cho tỉ lệ lợi ích/chi phí tốt nhất?

  1. B-tree trên created_at — an toàn nhất, kích thước không thành vấn đề
  2. GIN trên created_at
  3. BRIN trên created_at — chỉ lưu min/max theo block range, cỡ vài MB cho 2TB, cực hợp dữ liệu có tương quan vật lý theo thời gian
  4. Hash index trên created_at
Đáp án

C. BRIN thắng khi thứ tự vật lý ≈ thứ tự giá trị (append-only theo thời gian). B-tree cũng chạy nhưng tốn hàng chục GB. GIN dành cho jsonb/mảng/full-text; hash chỉ cho so sánh bằng. Bonus: nếu chỉ hay query tập con (vd status='pending') → partial index nhỏ và nóng hơn nữa.

Câu 8 — \copy vs COPY (Module 02/05)

Bạn cần nạp file CSV nằm trên laptop vào PostgreSQL chạy trên RDS (không truy cập được filesystem của server). Cách đúng?

  1. COPY events FROM '/home/me/data.csv' — server sẽ tự đọc file
  2. \copy của psql — đọc file phía CLIENT rồi stream qua kết nối; còn COPY FROM đọc file trên SERVER và đòi quyền phía server
  3. Chỉ còn cách INSERT từng dòng bằng vòng lặp Python
  4. Phải cài extension file_fdw trước
Đáp án

A sai vì đường dẫn đó không tồn tại trên máy RDS. Đáp án B. \copy là lệnh của psql, chạy ở client — đúng công cụ cho managed database. Tốc độ vẫn là COPY protocol, nhanh hơn INSERT hàng chục lần.

Câu 9 — Autovacuum & bloat (Module 12)

Bảng UPDATE nặng: sau vài tuần query chậm dần đều, kích thước bảng phình gấp ba dù số dòng không đổi. Chẩn đoán và hướng xử lý?

  1. Index bị corrupt — REINDEX là xong
  2. Dead tuple tích tụ (bloat) vì autovacuum không theo kịp — soi pg_stat_user_tables (n_dead_tup, last_autovacuum), hạ autovacuum_vacuum_scale_factor riêng cho bảng nóng
  3. WAL quá lớn làm chậm mọi thao tác đọc
  4. Thiếu ANALYZE nên planner chọn sai plan
Đáp án

B. "Chậm dần đều + size phình dù dòng không đổi" là chữ ký của bloat — hệ quả trực tiếp của MVCC (câu 1). Mặc định scale_factor 20% là quá thưa cho bảng lớn UPDATE nhiều; chỉnh per-table bằng ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.01).

Câu 10 — Plan cache 5 lần (Module 08/17)

Function chạy nhanh 5 lần đầu trên mỗi connection, từ lần 6 chậm gấp 50; restart app lại nhanh rồi lại chậm. Nghi phạm và cách xử lý?

  1. Connection pooler lỗi — thay pooler khác
  2. Cache hệ điều hành nguội — cần warm-up
  3. Từ lần 6 planner chuyển sang generic plan; trên bảng partition nó mất pruning lúc planning (phải plan/lock mọi ngăn) → ALTER FUNCTION ... SET plan_cache_mode = 'force_custom_plan'
  4. Autovacuum tình cờ chạy đúng lúc đó
Đáp án

C. Con số "5 lần" là chuông báo plan cache (Module 8). Nhớ chi tiết cho chính xác: từ PG11 runtime pruning vẫn loại ngăn thừa lúc chạy, nhưng chi phí plan/lock mọi partition mỗi lần gọi cộng plan generic ước lượng sai vẫn đủ gây chậm — xem Ca 2, Module 17.
