1. Type hints & module typing

Type hints không ảnh hưởng runtime — Python không ép kiểu lúc chạy. Giá trị thật nằm ở chỗ: mypy/pyright đọc chúng và bắt lỗi trước khi code chạy, IDE gợi ý chính xác, và đồng nghiệp đọc signature là hiểu hàm nhận/trả gì. Với DE, đây là lớp phòng thủ rẻ nhất chống lỗi "NoneType has no attribute".

python — các kiểu typing hay dùng
from typing import Optional, Union, Callable, TypedDict, Protocol Python 3.9+ : dùng list/dict thường thay List/Dict def total(prices: list[float]) -> float: return sum(prices) Optional[X] == X | None (3.10+ ưu tiên cú pháp |) def find_user(uid: int) -> dict[str, str] | None: ... Callable: hàm nhận (int,str) trả bool Handler = Callable[[int, str], bool] TypedDict: dict có "schema" — IDE bắt sai key class Event(TypedDict): user_id: int ts: float action: str

Dùng Protocol cho "structural typing" (duck typing có kiểm tra): bất cứ object nào có đúng method là khớp, không cần kế thừa. Rất hợp để mô tả "thứ gì đó ghi được" mà không trói buộc class cụ thể.

python — Protocol thay vì ABC
from typing import Protocol class Sink(Protocol): def write(self, rows: list[dict]) -> None: ... S3Sink, KafkaSink... chỉ cần có .write() là khớp Sink def load(rows: list[dict], sink: Sink) -> None: sink.write(rows)
mypy mindset

Coi cảnh báo type như lỗi build. Bật --strict cho code mới, dùng disallow_untyped_defs để ép mọi hàm có hint. Khi thư viện ngoài chưa có type, dùng cast() hoặc type: ignore[code] có chú thích — đừng tắt cả file.

2. ⭐ Dataclasses & Pydantic v2

dataclass là cách chuẩn của stdlib để tạo class "chứa dữ liệu" — tự sinh __init__, __repr__, __eq__. Dùng frozen=True cho object bất biến (hashable, an toàn đa luồng), field(default_factory=...) cho mutable default (đừng bao giờ để [] làm default trực tiếp).

python — dataclass
from dataclasses import dataclass, field @dataclass(frozen=True, slots=True) class Partition: table: str date: str tags: list[str] = field(default_factory=list) p = Partition("events", "2026-06-28") frozen → p.date = "x" sẽ raise; hashable → dùng làm key set/dict

Pydantic v2 đi xa hơn: nó validate & coerce dữ liệu lúc runtime — hoàn hảo cho ranh giới hệ thống (đọc JSON từ API/Kafka, config từ env). Khác dataclass, Pydantic kiểm tra kiểu thật và đổi "123" thành 123 nếu field là int. Core viết bằng Rust nên v2 nhanh hơn v1 nhiều lần.

python — Pydantic v2 model & validation
from pydantic import BaseModel, field_validator, ValidationError class Order(BaseModel): order_id: int amount: float currency: str = "USD" @field_validator("amount") @classmethod def positive(cls, v: float) -> float: if v <= 0: raise ValueError("amount phải > 0") return v model_validate: parse dict (vd từ json.loads) → object đã validate o = Order.model_validate({"order_id": "42", "amount": 9.9}) order_id=42 amount=9.9 currency='USD' # "42" → 42 tự coerce

Cho config, dùng pydantic-settings: đọc biến môi trường & .env với kiểu rõ ràng, fail-fast nếu thiếu biến bắt buộc — không còn os.getenv rải rác trả về None.

python — Settings từ env
from pydantic_settings import BaseSettings, SettingsConfigDict class Config(BaseSettings): model_config = SettingsConfigDict(env_file=".env") db_url: str batch_size: int = 1000 debug: bool = False cfg = Config() # đọc DB_URL, BATCH_SIZE... thiếu DB_URL → lỗi ngay

3. Comprehensions vs loop

Comprehension không chỉ ngắn — nó nhanh hơn vòng for + .append() vì tránh tra cứu thuộc tính lặp lại. Nhưng đừng nhồi nhét: nếu logic có nhiều điều kiện hoặc side-effect, vòng for tường minh dễ đọc hơn. Quy tắc: comprehension cho phép biến đổi/lọc thuần (pure), loop cho logic phức tạp hay I/O.

python — comprehension đúng chỗ
Tốt: biến đổi + lọc thuần valid = [r["amount"] for r in rows if r["amount"] > 0] by_id = {u["id"]: u for u in users} # dict comprehension domains = {e.split("@")[1] for e in emails} # set → khử trùng lặp Xấu: nhồi 2 điều kiện + biến đổi lồng → khó đọc, nên viết loop out = [f(x) if cond(x) else g(x) for x in xs if pre(x) and ok(x)]

4. ⭐ Generators & lazy evaluation

Đây là kỹ thuật quan trọng nhất tab này cho DE. Generator (hàm có yield) sinh từng phần tử theo yêu cầu thay vì dựng cả list trong RAM. Đọc file 50GB? List sẽ giết process; generator chỉ giữ 1 dòng tại một thời điểm. Ghép nhiều generator thành pipeline để stream dữ liệu qua nhiều bước mà bộ nhớ gần như phẳng.

python — generator pipeline tiết kiệm RAM
from typing import Iterator def read_lines(path: str) -> Iterator[str]: with open(path) as f: for line in f: # file object đã lazy theo dòng yield line.rstrip("\n") def parse(lines: Iterator[str]) -> Iterator[dict]: import json for ln in lines: if ln: yield json.loads(ln) def only_paid(events: Iterator[dict]) -> Iterator[dict]: for e in events: if e.get("amount", 0) > 0: yield e Ghép pipeline — KHÔNG có list trung gian nào được dựng pipe = only_paid(parse(read_lines("events.jsonl"))) for ev in pipe: # xử lý từng event, RAM gần như phẳng handle(ev)
  read_lines        parse           only_paid        consumer
  ┌────────┐      ┌────────┐      ┌─────────┐      ┌────────┐
  │ 1 dòng │─yield→│ 1 dict │─yield→│ lọc>0   │─yield→│ handle │
  └────────┘      └────────┘      └─────────┘      └────────┘
       ▲ kéo           ▲ kéo            ▲ kéo            │
       └───────────────┴────────────────┴───────────────┘
            "pull": consumer kéo, mỗi lần đúng 1 phần tử đi suốt ống
Lazy pull pipeline — bộ nhớ O(1) bất kể file lớn cỡ nào
Mẹo

Generator expression (x*2 for x in big) dùng () thay vì [] — lazy ngay. itertools.islice, chain, groupby ghép generator cực mạnh. Nhược điểm: generator chỉ duyệt một lần và không có len().

5. Context managers cho tài nguyên

Mọi tài nguyên cần đóng (file, kết nối DB, socket, lock, span tracing) nên dùng with. Nó đảm bảo dọn dẹp kể cả khi có exception — không rò rỉ connection. Tự viết context manager nhanh nhất bằng @contextmanager.

python — contextlib.contextmanager
from contextlib import contextmanager import time, psycopg # ví dụ @contextmanager def db_conn(dsn: str): conn = psycopg.connect(dsn) try: yield conn # phần "with" chạy ở đây conn.commit() except Exception: conn.rollback() raise finally: conn.close() # luôn đóng, kể cả khi lỗi with db_conn(dsn) as c: c.execute("INSERT INTO t VALUES (1)")

6. Decorators thực dụng

Decorator bọc một hàm để thêm hành vi mà không sửa thân hàm — lý tưởng cho mối quan tâm xuyên suốt (cross-cutting): retry, timing, logging, cache. Luôn dùng functools.wraps để giữ tên/docstring gốc (quan trọng khi debug).

python — decorator retry & timing
import time, functools from typing import Callable, TypeVar T = TypeVar("T") def retry(times: int = 3, delay: float = 1.0): def deco(fn: Callable[..., T]) -> Callable[..., T]: @functools.wraps(fn) def wrap(*args, **kwargs) -> T: for i in range(times): try: return fn(*args, **kwargs) except Exception: if i == times - 1: raise time.sleep(delay * (2 ** i)) # backoff return wrap return deco @retry(times=4, delay=0.5) def fetch(url: str) -> dict: ... # call API có thể chập chờn
Tình huống thực tế

Bối cảnh: Một pipeline ETL gọi API tỉ giá hối đoái mỗi giờ. API thỉnh thoảng trả 503 vài giây. Ban đầu không có retry, mỗi lần lỗi là cả DAG fail, on-call bị gọi dậy lúc 3h sáng dù chỉ là lỗi thoáng qua. Bài học: Bọc lời gọi network bằng decorator @retry có exponential backoff giải quyết 95% sự cố giả. Nhưng nhớ retry chỉ cho thao tác idempotent — retry một INSERT không idempotent có thể tạo bản ghi trùng.

1. ⭐ GIL là gì & ảnh hưởng

GIL (Global Interpreter Lock) là một mutex toàn cục trong CPython: chỉ một thread được thực thi bytecode Python tại một thời điểm. Nghĩa là dù bạn có 8 thread trên 8 core, code Python thuần (CPU-bound) vẫn chạy như một core — đa luồng không tăng tốc tính toán thuần.

GIL

Khóa cho phép tại mỗi thời điểm duy nhất một thread chạy bytecode Python. Nó được nhả ra khi thread chờ I/O (đọc file, gọi network, sleep) hoặc khi gọi vào thư viện C đã nhả GIL (numpy, một số nén). Vì vậy threading có ích cho I/O-bound, vô ích cho CPU-bound Python thuần.

 CPU-bound + threading (KHÔNG nhanh hơn):
   core1: [T1][--][T2][--][T1]...   GIL chuyền tay, 1 lúc 1 thread
   ┌──────────── GIL ────────────┐
   │  T1 ─▶ giữ ▶ nhả ▶ T2 giữ ▶ │   tổng thời gian ≈ tuần tự
   └─────────────────────────────┘

 I/O-bound + threading (NHANH hơn):
   T1: req ───(chờ network: NHẢ GIL)─── resp
   T2:     req ───(chờ: chạy được)──── resp   ← chồng lấn thời gian chờ
   T3:         req ──────────────────── resp
GIL nhả khi chờ I/O → thread chồng lấn thời gian chờ; nhưng tuần tự khi tính toán
Lưu ý phiên bản

Python 3.13 có chế độ free-threaded (PEP 703, "no-GIL") thử nghiệm và 3.12+ có per-interpreter GIL (PEP 684). Tương lai GIL sẽ bớt là rào cản, nhưng hôm nay hãy lập trình như GIL vẫn tồn tại — đó là mặc định ở hầu hết deployment.

2. I/O-bound vs CPU-bound

Phân loại workload là bước quyết định. I/O-bound: phần lớn thời gian chờ thứ bên ngoài (HTTP, query DB, đọc/ghi disk/S3). CPU-bound: phần lớn thời gian tính (parse JSON khổng lồ, nén, hash, biến đổi số). Test nhanh: nếu tăng CPU speed mà task không nhanh hơn → I/O-bound.

Đây là bảng tham chiếu dán lên màn hình. Sai lầm phổ biến nhất: dùng multiprocessing cho I/O (tốn RAM vô ích) hoặc threading/asyncio cho CPU thuần (không nhanh hơn vì GIL).

4. asyncio cơ bản

asyncio chạy một event loop trên một thread. Hàm async def là coroutine; await nhường quyền điều khiển khi gặp I/O để loop chạy task khác. asyncio.gather chạy nhiều coroutine "đồng thời" và chờ tất cả xong.

        ┌──────────────── EVENT LOOP (1 thread) ────────────────┐
        │   task A: await io ─┐   (nhường)                       │
        │   task B: await io ─┼─▶ loop chạy task sẵn sàng kế     │
        │   task C: await io ─┘                                  │
        │   ◀── khi io xong, callback đánh thức task tương ứng ──│
        └────────────────────────────────────────────────────────┘
   await = "tôi đang chờ, cứ chạy việc khác đi" → chồng lấn thời gian chờ
Event loop: cooperative multitasking — chỉ nhường tại điểm await
python — async/await & gather
import asyncio async def fetch(name: str, delay: float) -> str: await asyncio.sleep(delay) # giả lập I/O — nhường loop return f"{name} xong" async def main() -> None: gather: chạy đồng thời, tổng ~= max(delay) chứ không phải tổng results = await asyncio.gather( fetch("A", 1.0), fetch("B", 1.0), fetch("C", 1.0), ) print(results) # ~1s chứ không phải 3s asyncio.run(main())
Bẫy chí mạng

Gọi hàm blocking (vd requests.get, time.sleep, query DB đồng bộ) bên trong coroutine sẽ kẹt cả event loop — mọi task khác đứng hình. Dùng lib async (aiohttp, asyncpg) hoặc đẩy việc blocking ra thread bằng await asyncio.to_thread(fn, ...).

5. Giới hạn concurrency với Semaphore

Bắn 10.000 request cùng lúc sẽ làm sập server đích (hoặc bị rate-limit/ban). asyncio.Semaphore(N) giới hạn tối đa N coroutine vào vùng đồng thời cùng lúc — vẫn nhanh, nhưng lịch sự.

python — Semaphore giới hạn đồng thời
import asyncio sem = asyncio.Semaphore(10) # tối đa 10 request song song async def fetch_one(client, url: str): async with sem: # chờ slot trống mới chạy async with client.get(url) as r: return await r.json() async def fetch_all(client, urls: list[str]): tasks = [fetch_one(client, u) for u in urls] return await asyncio.gather(*tasks) # 5000 url, max 10 cùng lúc

6. concurrent.futures

API thống nhất cho thread & process pool, đơn giản hơn asyncio khi bạn chỉ cần "chạy N việc song song với code đồng bộ sẵn có". Đổi giữa I/O và CPU chỉ bằng đổi tên class.

python — ThreadPool (I/O) vs ProcessPool (CPU)
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor I/O-bound: ThreadPool (GIL nhả khi chờ network) def download(url: str) -> bytes: ... with ThreadPoolExecutor(max_workers=20) as ex: data = list(ex.map(download, urls)) CPU-bound: ProcessPool (mỗi process có GIL riêng → song song thật) def heavy_parse(path: str) -> dict: ... with ProcessPoolExecutor(max_workers=8) as ex: results = list(ex.map(heavy_parse, files))

7. Ví dụ thực tế: tải N API + xử lý N file

Hai khuôn mẫu DE gặp hằng ngày. (1) Tải nhiều API song song bằng asyncio + aiohttp với Semaphore. (2) Parse/biến đổi nhiều file nặng CPU bằng ProcessPoolExecutor.

python — tải N API song song (asyncio + aiohttp)
import asyncio, aiohttp async def get_json(session, sem, url): async with sem: async with session.get(url, timeout=aiohttp.ClientTimeout(total=10)) as r: r.raise_for_status() return await r.json() async def fetch_all(urls: list[str]) -> list[dict]: sem = asyncio.Semaphore(20) async with aiohttp.ClientSession() as session: tasks = [get_json(session, sem, u) for u in urls] return await asyncio.gather(*tasks, return_exceptions=True) data = asyncio.run(fetch_all(urls)) # 1000 url ~ vài giây
python — xử lý N file CPU-bound (ProcessPool)
from concurrent.futures import ProcessPoolExecutor, as_completed from pathlib import Path def transform(path: str) -> tuple[str, int]: nặng CPU: đọc, parse, nén... mỗi process 1 core thật rows = sum(1 for _ in open(path)) return path, rows files = [str(p) for p in Path("/data").glob("*.csv")] with ProcessPoolExecutor(max_workers=8) as ex: futures = {ex.submit(transform, f): f for f in files} for fut in as_completed(futures): path, n = fut.result() print(path, n)
Tình huống thực tế

Bối cảnh: Một team cần làm giàu dữ liệu bằng cách gọi 500.000 lần API geocoding. Code ban đầu dùng vòng for tuần tự với requests — ước tính chạy 14 giờ. Họ thử đổi sang ProcessPoolExecutor nhưng RAM nổ vì mỗi process nặng. Bài học: Đây là I/O-bound, không phải CPU-bound — giải pháp đúng là asyncio + aiohttp + Semaphore(50), kéo xuống ~30 phút trên một process. Chọn sai mô hình concurrency tốn cả ngày; phân loại workload trước rồi mới chọn công cụ.

⭐ Điểm chốt

GIL khiến threading vô ích cho CPU-bound Python thuần nhưng hữu ích cho I/O-bound (GIL nhả khi chờ). Phân loại workload trước: I/O-bound + cực nhiều việc → asyncio (nhớ Semaphore và tránh lời gọi blocking); I/O + lib đồng bộ → ThreadPool; CPU-bound → ProcessPool (mỗi process GIL riêng). Tính số học nặng → đẩy xuống numpy/Polars vốn nhả GIL.

2. ⭐ logging chuẩn: hierarchy, handler, formatter, level

Module logging của stdlib có bốn khái niệm, nắm được là hết bối rối: Logger (điểm phát log), Handler (đích đến — stdout, file, service), Formatter (định dạng dòng log), Level (ngưỡng lọc: DEBUG < INFO < WARNING < ERROR < CRITICAL).

Quy tắc vàng: gọi getLogger(__name__) ở mỗi module. Vì __name__ là "etl.extract", "etl.load"… các logger tạo thành một cây phân cấp — log của etl.extract "nổi" (propagate) lên etl rồi lên root. Nhờ đó bạn cấu hình handler/level một chỗ trên cây mà áp cho cả nhánh. Và: cấu hình MỘT LẦN ở entrypoint (hàm main), module con chỉ getLogger rồi log — đừng cấu hình trong module thư viện.

python — logging cơ bản (đã chạy thật)

Log đi từ logger phát → lên các logger cha → tới root, mỗi cấp có thể có handler xử lý. Đây là lý do bạn chỉ cần gắn handler ở một chỗ (root hoặc etl) mà bắt được log của cả cây. Mặt trái: nếu vô tình gắn handler ở nhiều cấp, một log bị in nhiều lần (xem bẫy #1).

3. dictConfig — cấu hình tập trung

basicConfig đủ cho script nhỏ, nhưng dự án thật nên dùng logging.config.dictConfig: một dict (thường nạp từ YAML/JSON) mô tả toàn bộ formatter, handler, và level từng logger. 4. ⭐ Ba cái bẫy kinh điển

› Bẫy 1 — Duplicate handlers (re-run notebook)

Nếu hàm setup của bạn gọi addHandler mỗi lần chạy, và bạn chạy lại một cell notebook (hoặc gọi setup nhiều lần), handler bị cộng dồn — mỗi log in ra nhiều lần.

python — cùng 1 log in 3 lần (đã chạy thật)

Sửa: cấu hình idempotent — chỉ gắn handler nếu chưa có (if log.handlers: return), hoặc tốt hơn là cấu hình một lần duy nhất ở entrypoint bằng dictConfig thay vì trong hàm bị gọi lặp.

› Bẫy 2 — Root logger bị thư viện chiếm

Nhiều thư viện gọi logging.warning(...) thẳng lên root logger, hoặc tệ hơn gọi basicConfig làm hỏng cấu hình của bạn. Nếu bạn nhét mọi thứ vào root, log của app trộn lẫn log lib. Sửa: cấu hình logger riêng của app (vd "etl") với propagate: False, và đặt level cho từng logger thư viện (botocore=WARNING, urllib3=WARNING) như ở mục 3. Đừng để root là nơi mọi thứ đổ về mà không kiểm soát.

› Bẫy 3 — Logging trong multiprocessing

Mỗi process con có không gian riêng; nếu nhiều process cùng ghi một file log, các dòng xen vào nhau hoặc tranh chấp. Mẫu chuẩn: worker chỉ đẩy log vào một Queue bằng QueueHandler, còn một QueueListener ở process chính ghi ra đích duy nhất.

5. ⭐ structlog: log là dữ liệu, không phải chuỗi

Log dạng chuỗi tự do khó truy vấn: khi sự cố, bạn cần lọc "mọi log của run_id=X có level=error" hay "tổng rows_dropped hôm nay" — grep chịu thua. Structured logging biến mỗi log thành một dict/JSON: các field máy đọc được, đẩy thẳng vào Loki/Elasticsearch/BigQuery rồi lọc như dữ liệu. structlog làm điều đó gọn gàng với hai ý tưởng: processor chain (mỗi log đi qua chuỗi bước xử lý — thêm timestamp, level — rồi render JSON) và bind context (gắn run_id, task một lần, mọi log con thừa hưởng).

6. Logging cho pipeline: log gì, ở đâu, correlation id

Log gì? Ở ranh giới mỗi bước: start/done, row counts vào/ra, duration, watermark, số dòng bị drop/reject, và mỗi lời gọi ngoài (retry lần mấy, status code). Đừng log từng dòng trong vòng lặp nóng (đếm rồi log tổng một lần) và tuyệt đối không log secret/PII.

Log ở đâu? Theo tinh thần 12-factor: app ghi ra stdout/stderr và coi log như một luồng sự kiện; để orchestrator (Airflow, Kubernetes, ECS) gom và định tuyến tới nơi lưu trữ. Đừng để app tự mở/xoay file log — đó là việc của hạ tầng.

Correlation id xuyên DAG: sinh một run_id ở đầu DAG, truyền qua mọi task (qua XCom/biến môi trường/tham số), và bind nó vào mọi log. Khi một lần chạy đi qua 8 task trên 3 máy khác nhau, bạn vẫn gom được toàn bộ log của đúng lần chạy đó bằng một bộ lọc run_id=....

7. Nối sang OpenTelemetry & tracing

Log trả lời "chuyện gì đã xảy ra"; tracing trả lời "thời gian đi đâu, chậm ở khâu nào" khi một request/lần chạy đi xuyên nhiều service — bằng khái niệm span (một đoạn công việc có thời lượng) gắn chung một trace_id. 6. Bloom filter (membership xấp xỉ)

Khi cần kiểm tra "đã thấy phần tử này chưa" trên hàng tỉ phần tử mà set thường tốn quá nhiều RAM, dùng Bloom filter: cấu trúc xác suất dùng bit array + nhiều hàm hash. Đặc tính then chốt: không bao giờ báo sót (no false negative) nhưng có thể báo nhầm có (false positive) ở tỉ lệ nhỏ kiểm soát được — đổi độ chính xác lấy bộ nhớ cực thấp.

  thêm "x":  hash1(x)=2  hash2(x)=5  hash3(x)=9  → bật bit 2,5,9
  bit array: [0 0 1 0 0 1 0 0 0 1 0 ...]
  hỏi "x"? : 2,5,9 đều =1 → "CÓ THỂ có"  (đúng hoặc false-positive)
  hỏi "y"? : có ít nhất 1 bit =0          → "CHẮC CHẮN chưa có"
Bloom filter: no false-negative, false-positive nhỏ — RAM cực thấp
Dùng ở đâu

Chống xử lý trùng ở scale lớn (dedup sơ bộ trước khi tra DB), kiểm tra cache miss nhanh, lọc URL đã crawl. Quy trình điển hình: Bloom filter trả lời nhanh "chắc chắn chưa thấy" để bỏ qua tra cứu đắt; chỉ khi nó nói "có thể có" mới tra nguồn chính xác.

7. Hashing, consistent hashing & HyperLogLog

Hashing phân phối dữ liệu vào các bucket/partition. Cách ngây thơ hash(key) % N có nhược điểm: đổi số node N thì hầu hết key phải di chuyển. Consistent hashing đặt node & key lên một "vòng tròn hash" để khi thêm/bớt node chỉ một phần nhỏ key bị xáo trộn — nền tảng partitioning/sharding trong hệ phân tán.

python — partition bằng hash
import hashlib def partition(key: str, num_parts: int) -> int: md5 ổn định & đồng đều hơn hash() built-in (vốn đổi mỗi process) h = int(hashlib.md5(key.encode()).hexdigest(), 16) return h % num_parts partition("user_42", 16) # → luôn cùng partition cho cùng key

Đếm số phần tử distinct chính xác trên tỉ bản ghi cần RAM khổng lồ (phải giữ set). HyperLogLog ước lượng số distinct với sai số ~1-2% chỉ bằng vài KB bộ nhớ — ý tưởng: quan sát số lượng bit 0 dẫn đầu trong hash của các phần tử để suy ra bậc độ lớn của lượng phần tử khác nhau. Đây là cơ chế đằng sau COUNT(DISTINCT ...) xấp xỉ trong nhiều data warehouse (vd APPROX_COUNT_DISTINCT).

HyperLogLog (ý tưởng)

Hash mỗi phần tử thành chuỗi bit. Theo dõi số bit 0 liên tiếp ở đầu (leading zeros) lớn nhất từng thấy: nếu thấy chuỗi có k số 0 dẫn đầu thì khả năng cao đã có ~2^k phần tử khác nhau. Dùng nhiều "registers" + trung bình hài hoà để giảm sai số. Đổi 1-2% sai số lấy RAM từ gigabyte xuống kilobyte.

Tình huống thực tế

Bối cảnh: Cần đếm số người dùng duy nhất truy cập mỗi phút trên luồng 500k event/giây cho dashboard real-time. Dùng set chính xác làm RAM phình tới hàng chục GB và gây GC liên tục. Bài học: Dashboard chỉ cần con số xấp xỉ — thay set bằng HyperLogLog (vài KB mỗi cửa sổ, sai số ~1%). Kết hợp Bloom filter để dedup sơ bộ. Biết khi nào "đủ chính xác" tiết kiệm tài nguyên khổng lồ — đó là tư duy DSA cho DE ở scale lớn.

⭐ Điểm chốt

Chọn cấu trúc dữ liệu theo Big-O: dict/set = hash table O(1) cho membership/dedup, đừng dùng list (O(n) → O(n²)). heapq cho top-k (RAM O(k)) và merge k stream đã sort (external sort). Counter/defaultdict/deque cho đếm/gom nhóm/window. Ở scale lớn, đổi độ chính xác lấy bộ nhớ: Bloom filter (membership xấp xỉ, no false-negative) và HyperLogLog (đếm distinct xấp xỉ). Consistent hashing cho partitioning ổn định khi thay đổi số node.

🎯 Bài tập chương

BT1 CƠ BẢN

Đổi membership check từ list sang set với n tăng dần. Tự kiểm: đo thời gian — bản list tăng theo O(n²) (vọt lên), bản set phẳng ~O(n).

BT2 KHÁ

Dùng heapq.nlargest (hoặc heap thủ công) lấy top-k trên một stream. Tự kiểm: kết quả khớp sorted(...)[:k]; RAM giữ O(k), không tăng theo n (dùng generator, không nạp cả stream).

BT3 THÁCH THỨC

Đếm distinct xấp xỉ bằng HyperLogLog + dedup sơ bộ bằng Bloom filter, so với set chính xác. Tự kiểm: sai số HLL < 2%; RAM giảm nhiều bậc so với set; Bloom không có false-negative.

Resilience: retry, timeout, circuit breaker

Pipeline production fail vì mạng chớp, API 503, DB failover — những lỗi tự khỏi sau vài giây. Code senior khác code junior ở chỗ: phân loại được lỗi nào đáng thử lại, thử lại có kỷ luật, và biết dừng để không tự DDoS hệ thống đang ốm. Module này bù đúng mảng mà chương Logging chưa chạm tới.

Code đã chạy thật

1. Bước 0 — thiết kế cây exception: transient vs permanent

Mọi thứ về retry đứng trên một phân loại: lỗi transient (tạm thời — 503, timeout, deadlock) thử lại có cơ may; lỗi permanent (400 sai payload, 401 sai key, cột không tồn tại) thử lại một triệu lần vẫn thế. Code hoá phân loại này bằng cây exception:

python
class PipelineError(Exception): ... # goc chung — except PipelineError bat het class TransientError(PipelineError): ... # 503, timeout, deadlock → RETRY class PermanentError(PipelineError): ... # 400, 401, schema sai → FAIL NGAY, alert def phan_loai_http(status: int, resp_text: str): if status in (429, 500, 502, 503, 504): raise TransientError(f"HTTP {status}") if 400 <= status < 500: raise PermanentError(f"HTTP {status}: {resp_text[:200]}") # Adapter cua tung nguon (API, DB) DICH loi tho sang 2 loai nay ngay tai bien gioi. # Phan con lai cua pipeline chi can biet transient/permanent — khong can biet HTTP.

2. Retry có kỷ luật với tenacity

Tự viết vòng while + sleep là con đường dẫn tới retry vô hạn và sleep cố định làm nghẽn thêm hệ thống. tenacity gói đủ bốn nguyên tắc: chỉ retry đúng loại lỗi, có trần số lần, backoff nhân đôi + jitter (ngẫu nhiên hoá để trăm worker không cùng thức dậy một nhịp), và log mỗi lần thử:

python — đã chạy

Hai lỗi kinh điển khi dùng tenacity

(1) Quên retry_if_exception_type → mặc định retry MỌI exception, kể cả bug code của chính bạn — bug được thử lại 4 lần rồi mới lộ mặt, log rối tung. (2) Bịa API không tồn tại kiểu retry_if_status — tenacity làm việc với exception, không biết HTTP status; muốn retry theo status thì dịch status thành exception như mục 1 (đây chính là lỗi từng có trong file 04 của bộ này, đã vá 10/07).

3. Retry chỉ an toàn khi thao tác idempotent

Retry một thao tác ghi không idempotent = nguy cơ ghi đôi. Trước khi gắn @retry lên hàm nào, tự hỏi: chạy hàm này 2 lần thì trạng thái cuối có y như chạy 1 lần không? GET/PUT/DELETE: có. POST tạo bản ghi, INSERT chồng, gửi email: không — phải thêm idempotency key hoặc chuyển sang MERGE/upsert trước (ôn lại module Idempotency của khoá Pipeline). Quy tắc gọn: @retry chỉ đặt lên hàm đã idempotent.

5. Circuit breaker — biết dừng khi hệ thống bên kia đang ốm

Retry cứu lỗi chớp nhoáng; khi dịch vụ bên kia sập hẳn 10 phút, một đàn worker retry đều đặn chỉ khiến nó khó sống lại hơn. Circuit breaker (cầu dao) đếm thất bại liên tiếp: chạm ngưỡng → mở mạch, mọi cuộc gọi sau fail-fast ngay lập tức không chạm mạng; sau thời gian hồi phục → hé mở (half-open) cho một cuộc gọi thử; thành công thì đóng mạch lại. Bản tối giản 15 dòng, đã chạy thật:

python — đã chạy
import time class CircuitOpen(Exception): ... class CircuitBreaker: def __init__(self, nguong=3, hoi_phuc_sau=60): self.fail = 0; self.nguong = nguong self.hoi_phuc_sau = hoi_phuc_sau; self.mo_luc = None def goi(self, fn, *a, **kw): if self.mo_luc is not None: # mach dang MO? if time.monotonic() - self.mo_luc < self.hoi_phuc_sau: raise CircuitOpen("mạch MỞ — fail fast") self.mo_luc = None; self.fail = 0 # half-open: cho thu 1 lan try: r = fn(*a, **kw); self.fail = 0; return r # thanh cong → reset except Exception: self.fail += 1 if self.fail >= self.nguong: self.mo_luc = time.monotonic() raise 6 lan goi lien tiep vao API hong (nguong=3): ['that', 'that', 'that', 'FAST-FAIL', 'FAST-FAIL', 'FAST-FAIL'] ← 3 lan dau cham API that; tu lan 4 mach mo, fail ngay khong ton mot round-trip nao

Thứ tự lồng nhau trong pipeline thật: circuit_breaker.goi(ham_da_boc_retry) — retry xử lý chớp giật bên trong, breaker chặn thảm hoạ kéo dài bên ngoài. Kết hợp với structured logging của chương 06 (log attempt, circuit_state thành field) là bạn có đủ đồ nghề vận hành.

Quiz tự kiểm tra — 10 câu tình huống

Mười tình huống production thu nhỏ, phủ xương sống của module: mock đúng chỗ, GIL & multiprocessing, giới hạn của asyncio, tottime vs cumtime, generator, Pydantic vs dataclass, logging, retry idempotent, DSA ở scale. Câu 1 — Mock đúng chỗ (Chương 03). Bạn test hàm enrich() nằm trong app/etl.py; hàm này có import requests rồi gọi requests.get(...). Muốn test không chạm mạng, bạn patch đường dẫn nào cho chắc ăn nhất?

A. patch("requests.get")
B. patch("app.etl.requests.get") — patch tại nơi tên được tra cứu
C. patch("app.etl.enrich")
D. Không mock được, buộc phải sửa hàm để nhận sẵn dữ liệu

Đáp án

B. Quy tắc vàng: "patch where it's looked up, not where it's defined" — patch tên trong namespace của module đang dùng nó. Ở đây là app.etl.requests.get. A đôi khi chạy được (vì app.etl.requests trỏ tới cùng module requests), nhưng nếu etl.py viết from requests import get thì A trượt — B luôn đúng vì nhắm đúng binding module đang dùng. C mock luôn chính hàm đang test → không kiểm tra gì. D không cần thiết: mock chính là để khỏi phải đổi thiết kế chỉ vì test (dù dependency injection cũng là cách tốt bổ sung).

Câu 2 — GIL & CPU-bound (Chương 02). Một job chạy hàm Python thuần (vòng lặp tính điểm phức tạp) trên 1 triệu bản ghi, một luồng mất 40 phút. Bạn đổi sang ThreadPoolExecutor(max_workers=8) nhưng thời gian gần như không đổi. Vì sao và sửa thế nào?

A. Cấu hình pool sai; tăng max_workers lên 32
B. Đây là CPU-bound; GIL chỉ cho một thread chạy bytecode Python tại một thời điểm → threading không tăng thông lượng CPU. Dùng ProcessPoolExecutor
C. Cần đổi mỗi lần tính thành async def + await
D. Máy chỉ 1 CPU, không cách nào nhanh hơn

Đáp án

B. Tính toán Python thuần là CPU-bound ở tầng bytecode. GIL serialize bytecode nên 8 thread vẫn như 1 cho CPU-bound; threading chỉ giúp I/O-bound (GIL nhả khi chờ I/O). ProcessPoolExecutor né GIL vì mỗi process có interpreter + GIL riêng, chạy song song thật trên nhiều core. A vô ích (thêm thread không phá được GIL). C sai: asyncio không cho CPU chạy song song, còn làm nghẽn event loop. D sai khi máy nhiều core (gần như luôn); mà kể cả 1 core thì gốc vấn đề vẫn là GIL. (Mẹo phụ: đẩy phần số học nặng xuống numpy/Polars — vốn nhả GIL — cũng là một lối thoát.)

Câu 3 — Khi nào asyncio vô dụng (Chương 02). Trường hợp nào asyncio không giúp (thậm chí có hại)?

A. Gọi 10.000 API HTTP bằng client async
B. Đọc 500 object nhỏ từ S3 đồng thời
C. Một vòng lặp Python thuần tính toán nặng, không có I/O
D. Chờ 200 truy vấn DB qua driver async

Đáp án

C. asyncio chỉ tăng thông lượng khi có thời gian chờ I/O để xen kẽ nhiều tác vụ. CPU-bound thuần không có điểm await nào để nhường — một coroutine tính toán sẽ chặn cả event loop, mọi thứ khác đứng hình. A/B/D đều I/O-bound, đúng đất diễn của asyncio (miễn dùng client async). Với CPU-bound: ProcessPool hoặc vectorization. Bẫy phụ cùng họ: gọi một hàm đồng bộ blocking (vd requests, time.sleep) bên trong coroutine cũng làm nghẽn loop — dấu hiệu asyncio bị dùng sai.

Câu 4 — tottime vs cumtime (Chương 06 · Performance). cProfile báo: parse_row có tottime=45s, cumtime=48s (gọi 2 triệu lần); run_pipeline có tottime=0.2s, cumtime=120s. Nên tối ưu hàm nào trước?

A. run_pipeline vì cumtime tới 120s
B. parse_row vì tottime 45s — thời gian thực sự cháy trong thân nó
C. Cả hai như nhau
D. Không hàm nào; cProfile không đáng tin

Đáp án

B. cumtime (cumulative) gồm cả thời gian các hàm con gọi bên trong — run_pipeline có cumtime 120s chỉ vì nó là top-level chứa mọi thứ, không phải vì bản thân nó chậm (tottime chỉ 0.2s). tottime (loại trừ hàm con) mới chỉ đúng nơi CPU cháy: parse_row 45s trên 2 triệu lần gọi là hotspot thật — vectorize hoặc giảm số lần gọi. A là bẫy kinh điển: tối ưu hàm cha có cumtime cao là tối ưu nhầm chỗ. D sai — cProfile đáng tin, chỉ cần đọc đúng cột.

Câu 5 — Generator dùng một lần (Chương 01). Đoạn code: g = (x for x in range(3)); print(sum(g)) in ra 3; ngay sau đó print(list(g)) in ra gì?

A. [0, 1, 2]
B. []
C. 3
D. Raise StopIteration

Đáp án

B. Generator duyệt đúng một lần; sum(g) đã tiêu thụ hết phần tử, g cạn → list(g) trả []. Đây là bẫy khi tưởng generator như list: không có len(), không tua lại, muốn duyệt nhiều lần phải tạo mới (hoặc itertools.tee, hoặc vật chất hoá thành list — đánh đổi RAM). D sai: list() nuốt StopIteration và trả list rỗng, không raise.

Câu 6 — Pydantic hay dataclass (Chương 01). Dữ liệu JSON từ Kafka (chưa tin cậy, có thể thiếu field hoặc sai kiểu) sắp đi vào pipeline. Chọn gì cho ranh giới này?

A. @dataclass cho nhẹ và nhanh
B. dict thô, kiểm tra tay bằng if
C. Pydantic BaseModel — validate & coerce, báo lỗi rõ field nào
D. TypedDict để mypy bắt lỗi

Đáp án

C. Ranh giới hệ thống với dữ liệu không tin cậy cần validate lúc runtime: Pydantic ép kiểu ("42"→42), báo lỗi đúng field hỏng, fail-fast. A sai: dataclass không validate lúc chạy — age: int vẫn nhận chuỗi mà không kêu. D sai: TypedDict chỉ là gợi ý tĩnh cho mypy; runtime không kiểm tra gì nên dữ liệu Kafka lệch kiểu vẫn lọt. B là "kiểm tra tay" dễ sót và khó bảo trì. Dataclass hợp cho struct nội bộ đã tin cậy — không phải ranh giới ngoài.

Câu 7 — Duplicate handler (Chương 06 · Logging). Trong Jupyter, một cell gọi logger.addHandler(StreamHandler()) và bạn chạy lại cell đó 4 lần. Giờ mỗi logger.info(...) in ra 4 dòng giống hệt. Vì sao?

A. Jupyter cache log lại
B. getLogger(tên) trả cùng một object; mỗi lần chạy addHandler cộng thêm một handler → 4 handler cùng in
C. Level bị hạ xuống DEBUG
D. Do log propagate lên root

Đáp án

B. getLogger("x") trả cùng một object mỗi lần (singleton theo tên), nên addHandler lặp lại cộng dồn handler; 4 lần chạy = 4 handler, mỗi handler in một bản → 4 dòng. Sửa: cấu hình idempotent (if not logger.handlers:) hoặc dùng dictConfig một lần ở entrypoint. D cũng có thể gây nhân đôi (handler ở cả logger lẫn root), nhưng ở đây nguyên nhân trực tiếp là cộng dồn handler trên cùng logger. A/C không liên quan.

Câu 8 — print vs structured logging (Chương 06 · Logging). On-call cần lấy "mọi lỗi của run_id=abc trong 8 task của một DAG". Cách nào biến việc này thành một truy vấn thay vì grep mò?

A. print() kèm run_id ra stdout rồi grep chuỗi
B. structlog render JSON, bind run_id; mỗi log là field máy đọc → lọc run_id="abc" AND level="error" trong log store
C. Ghi mỗi task một file .txt riêng
D. Tăng level lên DEBUG cho nhiều chi tiết hơn

Đáp án

B. Structured logging biến mỗi dòng thành bản ghi có field (run_id, level, task, rows…), đẩy vào Loki/Elastic/BigQuery rồi truy vấn như dữ liệu — chính xác, gộp xuyên task/máy. A (print + grep) mong manh: định dạng tự do, traceback xuống dòng phá grep, không lọc được nhiều chiều. C phân mảnh, khó gộp một lần chạy xuyên task. D chỉ tăng độ ồn, không giúp lọc. Correlation id (run_id) bind sẵn chính là chìa khoá.

Câu 9 — Retry idempotent (Chương 01 · 05). Step load() chạy INSERT INTO orders (...) VALUES (...) (không khoá duy nhất). Bạn bọc @retry(3). Lần đầu INSERT đã chạy ở DB nhưng client nhận timeout; retry chạy lại. Hậu quả?

A. Không sao, retry luôn an toàn
B. Bản ghi trùng — INSERT không idempotent, chạy lại tạo thêm dòng; cần MERGE/UPSERT theo khoá hoặc INSERT ... ON CONFLICT
C. retry tự rollback lần trước
D. DB tự khử trùng

Đáp án

B. Retry chỉ an toàn cho thao tác idempotent (chạy lại cho cùng kết quả). INSERT thuần không idempotent: nếu lần đầu đã ghi nhưng client tưởng fail, retry ghi thêm → trùng. Sửa: thiết kế đích idempotent — UPSERT/MERGE theo khoá tự nhiên, INSERT ... ON CONFLICT DO NOTHING, hoặc dedup theo id lần chạy. C/D là ảo tưởng: DB không tự rollback/khử trùng nếu bạn không định nghĩa ràng buộc. Đây là lý do mẫu "at-least-once + đích idempotent" được ưa dùng thay cho exactly-once.

Câu 10 — DSA ở scale (Chương 07). Cần đếm số người dùng duy nhất mỗi phút trên luồng 800k event/giây cho dashboard (chấp nhận sai số nhỏ). Dùng set() chính xác thì RAM phình hàng chục GB. Lựa chọn đúng?

A. Giữ set, mua thêm RAM
B. Dùng list + kiểm tra trùng
C. HyperLogLog — đếm distinct xấp xỉ với vài KB mỗi cửa sổ, sai số ~1–2%
D. Sort rồi đếm các đoạn liên tiếp

Đáp án

C. Dashboard chỉ cần con số xấp xỉ: HyperLogLog đếm cardinality với bộ nhớ gần hằng số (KB) bất kể số phần tử, sai số ~1–2% — đổi độ chính xác lấy RAM giảm nhiều bậc, hợp streaming scale lớn. A không mở rộng (RAM tăng tuyến tính theo số distinct). B thảm hoạ: membership trên list là O(n) → tổng O(n²), lại tốn RAM như set. D cần giữ toàn bộ để sort (O(n) RAM + O(n log n) thời gian), vô lý cho stream vô hạn. Có thể ghép Bloom filter để dedup sơ bộ. Biết khi nào "đủ chính xác" là tư duy DSA cho DE ở scale lớn.
