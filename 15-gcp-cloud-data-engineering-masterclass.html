1. Tại sao GCP thống trị modern data stack

Google xây dựng BigQuery từ bài học của Dremel (2006) — một internal tool để query petabyte dataset trong seconds. BigQuery không phải data warehouse truyền thống; nó là serverless analytical engine dùng Dremel tree execution và Colossus file system bên dưới. Điểm khác biệt cốt lõi:

⚡ Serverless architecture

Không cần manage cluster. BigQuery auto-scales từ zero đến petabyte mà không có query timeout trên một single query. Bạn chỉ trả tiền cho data scanned (on-demand) hoặc slot reservation.

🔬 Columnar storage

Capacitor — proprietary columnar format của BigQuery — nén 10× so với row-based. Một query trên 10TB có thể chỉ scan vài GB thực sự cần thiết. Đây là lý do BigQuery mạnh ở analytical workloads.

🤖 BigQuery ML tích hợp

Train XGBoost, time series, k-means, deep learning models bằng SQL trực tiếp trong BigQuery — không cần export data sang Python environment. Giảm 80% friction giữa data và ML.

Tình huống: Fintech startup 30 người, 20TB data/tháng, cần real-time fraud detection. Họ chọn GCP vì (1) BigQuery ML cho model training không cần extra infra, (2) Pub/Sub cho real-time ingestion, (3) Dataflow cho stream processing, (4) Cloud Run cho serving model API — tất cả tích hợp native với nhau.

4. Khi nào KHÔNG nên dùng GCP

Cảnh báo — GCP quirks cần biết

GCP có một số điểm khác biệt quan trọng với AWS mà nếu không chuẩn bị sẽ gây surprise:
(1) IAM deny policies là additive vs AWS deny-explicit — mất thời gian debug nếu quen AWS.
(2) Persistent Disk pricing tính cho full provisioned size, không phải used size.
(3) Egress cost GCP cao hơn AWS cho cross-region transfer.
(4) BigQuery slots có thể surprise billing nếu không set quota.
(5) GKE egress không free-tier như AWS EKS.

  • Workload nhỏ (< 1TB/tháng): BigQuery tính on-demand $6.25/TB scanned (us, giá thay đổi theo region/thời điểm). Với dữ liệu nhỏ, Cloud SQL + Metabase rẻ hơn và đủ dùng.
  • Toàn bộ stack đã trên AWS: Multi-cloud tăng complexity gấp 3×. Chỉ consider GCP khi có lý do business rõ ràng.
  • Heavy Windows/.NET workloads: Azure tốt hơn rõ ràng cho enterprise Microsoft stack.
  • Kafka là requirement cứng: GCP có Google Cloud Managed Service for Apache Kafka (GA cuối 2024); trước đó phải tự vận hành trên Dataproc/GCE hoặc dùng Confluent Cloud. Nếu team cần Kafka expertise sâu hoặc hệ sinh thái Confluent, vẫn có thể cân nhắc Confluent trên GCP.

1. GCP IAM — Core Concepts

GCP IAM hoạt động theo nguyên tắc who can do what on which resource, tương tự AWS nhưng với terminology và hierarchy khác:

👤 Member

Ai đang truy cập. Có nhiều loại: user:, serviceAccount:, group:, domain:, allUsers, allAuthenticatedUsers. Ưu tiên service account cho workload tự động.

📜 Role

Tập hợp permissions. 3 loại: Primitive (Owner/Editor/Viewer — tránh dùng), Predefined (như roles/bigquery.dataEditor), Custom (tự define). Dùng Predefined roles cho production.

🎯 Resource

Cái được bảo vệ: Project, Folder, GCS bucket, BigQuery dataset, Pub/Sub topic...

2. Service Account Keys — rủi ro lớn nhất

Service Account Keys là file JSON chứa private key của GCP service account. Chúng là attack surface lớn nhất trong GCP security. Nếu key bị expose lên GitHub, attacker có thể truy cập toàn bộ permissions của SA đó.

Cảnh báo — Never commit SA keys

Policy khuyến nghị: Không bao giờ tạo service account key cho workload trên GCP. Dùng Workload Identity Federation thay thế. Nếu bắt buộc phải dùng key (legacy system), rotate thủ công mỗi 90 ngày và audit bằng Cloud Asset Inventory.

Workload Identity Federation (recommended)
# Thay vì SA key, bind SA với GKE workload gcloud iam workload-identity-pools create my-pool \ --location="global" \ --description="GitHub Actions workload identity" Created workload identity pool [my-pool]. # Grant SA access to workload identity pool gcloud iam service-accounts add-iam-policy-binding \ df-processor-sa@my-project.iam.gserviceaccount.com \ --role="roles/iam.workloadIdentityUser" \ --member="principalSet://iam.googleapis.com/projects/123/locations/global/workloadIdentityPools/my-pool/attribute.repository/my-repo"

Data platform GCP nên được isolate trong dedicated VPC. Các service managed (BigQuery, GCS, Pub/Sub) có firewall internal, nhưng compute (Dataproc, Dataflow worker, GKE) cần VPC config rõ ràng.

Admin Activity

Luôn enabled, ghi tất cả API calls thay đổi resource (CREATE, UPDATE, DELETE). Không tốn phí.

Data Access

1. GCS Architecture — Colossus file system

GCS được xây dựng trên Colossus — thế hệ tiếp theo của Google File System (GFS). Colossus là distributed file system được thiết kế cho Petabyte-to-Exabyte scale với key improvements so với GFS:

Colossus — metadata layer

Metadata (bucket, object location) được store trong distributed DB (Chubby lock service) — không phải single master như HDFS NameNode. Single namespace với 10B+ objects.

Data layer

Data được stripe across nhiều disks và datacenters. Durability 99.999999999% (11 9's) qua Reed-Solomon erasure coding — chịu được 2 disk failures mà không mất data.

Consistency model

GCS cung cấp strong consistency — sau khi write hoàn tất, read thấy ngay data mới. Khác với S3 eventual consistency. Không có read-your-writes anomaly.

2. Data Lake Folder Structure — Medallion Architecture

Data lake trên GCS nên theo Medallion Architecture: Bronze (raw) → Silver (cleansed) → Gold (business-ready). Mỗi layer là một GCS bucket hoặc folder prefix riêng.

Naming convention: prefix over folder

GCS không có "real folders" — year=2026/month=01/ là key prefix convention. BigQuery và Dataflow đọc partition từ prefix này. Dùng year=, month=, day= (lowercase, có dấu =) để BigQuery tự detect partitioning.

4. Lifecycle Rules & Cost Optimization

Lifecycle rules tự động transition objects giữa storage classes theo age. Đây là cách đơn giản nhất để giảm GCS cost mà không cần code.

4.1 GCS Cost breakdown

Storage cost

Standard: $0.020/GB, Nearline: $0.010, Coldline: $0.004, Archive: $0.0012. Tính trên data stored, không tính trên API calls.

Operation cost

Class A (write/delete/list): $0.05/10,000 ops. Class B (read): $0.004/10,000 ops. Get bucket/object metadata: $0.0004/10,000 ops.

Key Points M3
  • GCS built on Colossus — strong consistency (khác S3 eventual consistency), Reed-Solomon erasure coding cho durability 11 9's
  • Data lake structure: Medallion (Bronze→Silver→Gold) với GCS bucket hoặc prefix cho mỗi layer
  • Partition naming: year=YYYY/month=MM/day=DD — BigQuery tự detect partitioning từ prefix
  • File format: Parquet + Snappy là standard cho analytical workloads trên GCP
  • Lifecycle rules tự động tier data: Standard → Nearline (30d) → Coldline (90d) → Archive (365d) → Delete (compliance)
  • BigQuery external tables query GCS trực tiếp — dùng cho staging, convert sang native table cho production query performance

Tình huống: Bucket data lake để toàn Standard → chi phí lưu phình. Sửa: lifecycle chuyển Nearline (30 ngày) → Coldline → Archive; bật Autoclass nếu pattern truy cập khó đoán; đặt GCS cùng region với BigQuery để query khỏi tốn phí egress.

BigQuery & Serverless Data Warehouse

1. BigQuery Architecture — Dremel + Colossus

Dremel — query engine

Compiler parse SQL thành execution tree. Leaf nodes đọc data từ storage, intermediate nodes aggregate. Có thể xử lý thousands queries song song.

3. Partitioning & Clustering — Tối ưu query cost

Partitioning và clustering là hai kỹ thuật quan trọng nhất để giảm query cost trên BigQuery. Chúng giúp BigQuery skip scanning data không liên quan — giảm cả thời gian lẫn tiền.

partition-cluster.sql
-- Partition by date column — BigQuery skip partitions không cần thiết CREATE TABLE `prod.orders` PARTITION BY DATE(order_date) CLUSTER BY customer_id -- Sort rows within partition by customer_id OPTIONS ( partition_expiration_days = 365, require_partition_filter = TRUE -- Enforce partition filter để tránh accidental full scan ) AS SELECT order_id, customer_id, order_date, amount, status, created_at FROM `source.orders_raw`; -- Partition by ingestion time (tự động từ _PARTITIONTIME pseudo-column) CREATE TABLE `prod.events` PARTITION BY DATE(_PARTITIONTIME) OPTIONS (require_partition_filter = TRUE) AS SELECT * FROM `source.events_raw`; -- Clustering on multiple columns (max 4) — best for high-cardinality filters CREATE TABLE `prod.user_events` PARTITION BY DATE(event_date) CLUSTER BY country, platform, event_type OPTIONS (require_partition_filter = TRUE) AS SELECT * FROM `source.user_events_raw`;
require_partition_filter = TRUE

Setting này bắt buộc query phải có filter trên partition column. Nếu không, query fail. Đây là guardrail tốt nhất để prevent accidental full table scan trên large partitioned tables. Luôn enable cho tables > 10GB.

3.1 Partition vs Clustering — khi nào dùng gì

  • Partition: Khi filter chính là date/time column (most queries filter by date). Partition cardinality thấp (ngày = 365 partitions/năm).
  • Clustering: Khi filter bằng non-date columns (country, category, customer_id). Clustering cardinality cao — sort rows trong partition.
  • Dùng cả hai: Partition by date + cluster by high-cardinality columns là best practice cho fact tables.

4. Streaming Pipeline — Pub/Sub to BigQuery

streaming_pipeline.py — Pub/Sub → Dataflow → BigQuery Streaming
import apache_beam as beam from apache_beam.transforms.window import FixedWindows from apache_beam.transforms.trigger import AfterWatermark, Repeatedly, AfterCount, AccumulationMode from apache_beam.options.pipeline_options import StandardOptions class ParseEventFn(beam.DoFn): def process(self, element, window=beam.DoFn.WindowParam): import json try: event = json.loads(element.decode('utf-8')) window_start = window.start.to_utc_datetime().isoformat() yield { 'event_id': event['event_id'], 'event_type': event['type'], 'user_id': event['user_id'], 'session_id': event.get('session_id'), 'properties': json.dumps(event.get('properties', {})), 'timestamp': event['timestamp'], 'window_start': window_start, 'bq_insert_time': beam.utils.timestamp.Timestamp.now().to_utc_datetime().isoformat(), } except Exception: pass # Dead letter in production def run(): options = beam.pipeline.PipelineOptions( project='my-project', region='us-central1', temp_location='gs://my-data-lake/_temp/', runner='DataflowRunner', ) options.view_as(StandardOptions).streaming = True with beam.Pipeline(options=options) as p: events = ( p | 'ReadFromPubSub' >> beam.io.ReadFromPubSub( subscription='projects/my-project/subscriptions/user-events-df-sub', # chỉ truyền 1 trong 2: topic HOẶC subscription ) | 'FixedWindow60s' >> beam.WindowInto( FixedWindows(60), trigger=AfterWatermark( early=Repeatedly(AfterCount(100)), ), accumulation_mode=AccumulationMode.DISCARDING, ) | 'ParseEvent' >> beam.ParDo(ParseEventFn()) | 'WriteToBigQuery' >> beam.io.WriteToBigQuery( table='my-project:prod.user_events_stream', insert_retry_strategy='RETRY_ON_TRANSIENT_ERROR', write_disposition=beam.io.BigQueryDisposition.WRITE_APPEND, ) ) if __name__ == '__main__': run()

5. Autoscaling & Performance Tuning

Autoscaling modes

THROUGHPUT_BASED: Dataflow tự scale dựa trên backlog. NONE: Fixed workers. Throughput-based là default cho streaming và recommended cho batch với variable input size.

Worker configuration

machine_type: n1-standard-4 (4 vCPU, 15GB RAM) là sweet spot. disk_size_gb: 100GB default, tăng cho I/O-heavy jobs. num_workers: initial workers.

Dataflow Shuffle

Dataflow dùng Google Cloud Storage shuffle (network-based) thay vì local disk shuffle (như Dataproc). Điều này loại bỏ disk I/O bottleneck nhưng tăng network egress cost. Để estimate shuffle cost: ~$0.01 per GB shuffled. Batch pipeline với nhiều GroupByKey shuffle có thể tốn significant shuffle cost.

Key Points M5
  • Apache Beam = unified abstraction cho cả batch và streaming. Viết code một lần, deploy lên Dataflow, Flink, Spark runners
  • Batch: ReadFromText/GCS → ParDo transforms → WriteToBigQuery. Streaming: ReadFromPubSub → Window → WriteToBigQuery Streaming API
  • Dead letter pattern: dùng TaggedOutput để tách good/bad records — bad records ghi vào GCS dead letter bucket
  • Autoscaling: THROUGHPUT_BASED cho streaming. Initial workers + max workers cần tuned cho workload
  • Dataflow Shuffle là network-based — không disk bottleneck như Spark, nhưng tốn shuffle egress cost
  • DirectRunner cho local testing/debugging, DataflowRunner cho production

Tình huống: Pipeline streaming Dataflow trễ và đắt khi traffic tăng đột biến. Sửa: bật Streaming Engine + autoscaling; windowing/triggers hợp lý; xử lý late data bằng watermark + allowed lateness. Beam cho phép cùng code chạy batch lẫn stream; Dataflow managed nên khỏi quản cluster như Dataproc.

Pub/Sub & Real-time Messaging

Pub/Sub là managed messaging service cho real-time ingestion trên GCP. Nó hoạt động theo publish-subscribe pattern: publishers gửi messages vào topics, subscribers nhận messages từ subscriptions. 1. Pub/Sub Architecture

Hình 6: Pub/Sub — one topic, many subscriptions, independent consumers

Topic

Named resource nơi publishers gửi messages. Messages được retain 7 days (configurable). Topic không storage riêng — nó distribute messages đến subscriptions.

Subscription

Named sink attached to topic. Có thể have multiple subscriptions for one topic — mỗi subscriber nhận independent copy. Subscription lưu messages cho đến khi acknowledged.

Message

Gồm: data (binary payload, max 10MB), attributes (key-value metadata), message_id (unique), publish_time. Messages được deduplicated trong 10 minutes window.

3. Ordering & Exactly-Once Delivery

Pub/Sub guarantee: At-least-once, not exactly-once

Pub/Sub đảm bảo mỗi message được deliver ít nhất một lần. Trong một số trường hợp (network retry, subscriber crash before ack), message có thể delivered nhiều lần. Nếu application cần exactly-once semantics, implement deduplication ở consumer side: dùng message_id + Redis/GCS deduplication check, hoặc BigQuery INSERT với primary key conflict.

exactly-once-consumer.py
from google.cloud import pubsub_v1 import redis subscriber = pubsub_v1.SubscriberClient() subscription_path = 'projects/my-project/subscriptions/user-events-sub' redis_client = redis.Redis(host='10.128.0.5', db=0) processed_key_prefix = 'pubsub:processed:' def callback(message): msg_id = message.message_id dedup_key = f'{processed_key_prefix}{msg_id}' if redis_client.exists(dedup_key): message.ack() # Already processed — skip but ack return try: data = json.loads(message.data.decode('utf-8')) # Process: insert to BigQuery insert_to_bigquery(data) redis_client.setex(dedup_key, 7200, '1') # Dedup for 2h message.ack() except Exception as e: message.nack() # Re-deliver on failure future = subscriber.subscribe(subscription_path, callback=callback) print('Listening...') future.result()

Dataproc & Big Data Processing

Dataproc là managed Apache Hadoop và Apache Spark service trên GCP. Nó tự động hóa việc provisioning, configuring, và scaling cluster cho batch processing workloads. Trong nhiều trường hợp, Dataflow (Beam) đã đủ cho ETL workloads — nhưng Dataproc vẫn cần thiết khi: (1) bạn có existing Spark codebase, (2) cần Hive Metastore integration, (3) cần deep Spark tuning cho large-scale jobs, hoặc (4) cần ML training với PySpark.

1. Dataproc Architecture

Hình 7: Dataproc cluster — Master + Workers + GCS storage (no HDFS required)
GCS thay HDFS

Trên Dataproc, data thường được store trên GCS thay vì HDFS. GCS có durability cao hơn HDFS, không cần replication config, và auto-scales vô hạn. Spark đọc/writes GCS nativaly. HDFS chỉ nên dùng cho shuffle intermediate data (temporary) — đặt trên local SSD cho performance.

5. Dataproc vs Dataflow — Decision Guide

CriteriaUse DataprocUse Dataflow

Rule of thumb

Nếu workload là ETL/data pipeline thuần túy và team dùng Python — dùng Dataflow (Beam). Nếu workload là heavy Spark jobs với existing codebase, ML training, hoặc cần Hive Metastore — dùng Dataproc.

Key Points M7
  • Dataproc = managed Hadoop/Spark. Dùng GCS thay HDFS cho data storage — durability cao, auto-scale
  • Dataproc Serverless: chạy Spark jobs không cần manage cluster, tự động provision và terminate
  • Spark AQE (Adaptive Query Execution): auto-tune shuffle partitions, coalesce tasks — luôn enable
  • Dataproc vs Dataflow: Dataproc cho existing Spark codebase + ML; Dataflow cho pure ETL/streaming
  • Secondary (preemptible) workers: giảm 60-80% cost cho fault-tolerant batch jobs
  • Dataproc Metastore: managed Hive Metastore — share table metadata giữa Dataproc, BigQuery, Dataplex

Tình huống: Cluster Dataproc chạy 24/7 lãng phí. Sửa: ephemeral cluster (tạo–chạy–xoá) qua Workflow Templates; preemptible/Spot VM cho worker; Dataproc Serverless cho job Spark bất thường. Dùng Dataproc khi 'lift-and-shift' code Spark/Hadoop sẵn có; việc mới thuần SQL thì BigQuery khoẻ và rẻ hơn.

1. Materialized Views — Pre-computed Aggregates

Materialized views tự động refresh khi base tables thay đổi — BigQuery maintain incremental update, không recompute toàn bộ. Đây là cách tốt nhất để accelerate dashboard queries mà không tốn thêm compute per query.

materialized-view.sql
-- Tạo materialized view cho dashboard (thay vì query fact table mỗi lần) CREATE MATERIALIZED VIEW `prod.mv_daily_revenue` OPTIONS ( enable_refresh = TRUE, refresh_interval_minutes = 60, set_options_timeout_minutes = 10 ) AS SELECT DATE_TRUNC(order_date, DAY) AS revenue_date, customer_id, COUNT(order_id) AS order_count, SUM(amount) AS total_revenue, AVG(amount) AS avg_order_value FROM `prod.orders` WHERE status = 'completed' GROUP BY 1, 2; -- Materialized view được tự động sử dụng bởi BigQuery optimizer -- Dashboard query chỉ scan materialized view, không scan fact table SELECT revenue_date, SUM(total_revenue) AS daily_total FROM `prod.mv_daily_revenue` WHERE revenue_date BETWEEN '2026-01-01' AND '2026-01-31' GROUP BY 1 ORDER BY 1; -- BigQuery optimizer sử dụng mv_daily_revenue thay vì quét orders table -- Manual refresh ALTER MATERIALIZED VIEW `prod.mv_daily_revenue` SET OPTIONS (refresh_interval_minutes = 30); CALL BQ.REFRESH_MATERIALIZED_VIEW('prod.mv_daily_revenue');

2. Window Functions — Advanced Analytics

window-functions.sql
-- Lũy kế revenue theo customer (cumulative sum) SELECT order_date, customer_id, amount, SUM(amount) OVER ( PARTITION BY customer_id ORDER BY order_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW ) AS cumulative_revenue, AVG(amount) OVER ( PARTITION BY customer_id ORDER BY order_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW ) AS rolling_7day_avg FROM `prod.orders` WHERE status = 'completed'; -- Rank customers by revenue trong mỗi tháng SELECT EXTRACT(YEAR FROM order_date) AS year, EXTRACT(MONTH FROM order_date) AS month, customer_id, SUM(amount) AS total_spent, RANK() OVER (PARTITION BY EXTRACT(YEAR FROM order_date), EXTRACT(MONTH FROM order_date) ORDER BY SUM(amount) DESC) AS revenue_rank, PERCENT_RANK() OVER (PARTITION BY EXTRACT(YEAR FROM order_date), EXTRACT(MONTH FROM order_date) ORDER BY SUM(amount) DESC) AS pct_rank FROM `prod.orders` GROUP BY 1, 2, 3 QUALIFY revenue_rank <= 10 -- Filter top 10 -- Sessionization: group events into sessions (> 30 min gap = new session) SELECT user_id, event_timestamp, SUM(new_session_flag) OVER (PARTITION BY user_id ORDER BY event_timestamp) AS session_id FROM ( SELECT *, CASE WHEN TIMESTAMP_DIFF(event_timestamp, LAG(event_timestamp) OVER ( PARTITION BY user_id ORDER BY event_timestamp ), MINUTE) > 30 THEN 1 ELSE 0 END AS new_session_flag FROM `prod.user_events` )

4. BigQuery Scripting

BigQuery scripting cho phép viết procedural logic: loops, conditionals, dynamic SQL, và temp tables trong một session.

bq-scripting.sql
-- Dynamic table partitioning: create partitioned table từ source BEGIN DECLARE target_date DATE DEFAULT DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY); EXECUTE IMMEDIATE FORMAT(""" CREATE OR REPLACE TABLE `prod.orders_part_%T` PARTITION BY DATE(order_date) AS SELECT * FROM `source.orders_raw` WHERE DATE(order_date) = '%T' """, target_date, target_date); SELECT FORMAT("Created table prod.orders_part_%T", target_date) AS result; END; -- Loop qua nhiều partitions BEGIN DECLARE i INT64 DEFAULT 0; DECLARE partition_list ARRAY; SET partition_list = ARRAY( SELECT DISTINCT DATE(order_date) FROM `prod.orders` WHERE order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 90 DAY) ); FOR record IN (SELECT offset, p FROM UNNEST(partition_list) AS p WITH OFFSET AS offset) DO EXECUTE IMMEDIATE FORMAT(""" MERGE `prod.orders_agg` T USING ( SELECT DATE_TRUNC(order_date, MONTH) AS month, customer_id, COUNT(*) AS order_count, SUM(amount) AS revenue FROM `prod.orders` WHERE DATE(order_date) = '%T' GROUP BY 1, 2 ) S ON T.month = S.month AND T.customer_id = S.customer_id WHEN MATCHED THEN UPDATE SET order_count = S.order_count, revenue = S.revenue WHEN NOT MATCHED THEN INSERT (month, customer_id, order_count, revenue) VALUES (S.month, S.customer_id, S.order_count, S.revenue) """, record.p); END FOR; END;

Key Points M8
  • Materialized views: pre-compute aggregates, auto-refresh incrementally, BigQuery optimizer tự chọn dùng khi beneficial
  • QUALIFY clause: filter on window function results (rank <= 10) — clean hơn subquery
  • Remote functions: call Cloud Run endpoints từ SQL — ML inference, geocoding, external APIs
  • BigQuery scripting: procedural logic, dynamic SQL, MERGE for upserts — dùng cho data engineering workflows
  • Query plan: estimate cost bằng dry run; debug slow query bằng tab Execution details + INFORMATION_SCHEMA.JOBS. BigQuery tự quản lý statistics — không có ANALYZE TABLE
  • Monitor: INFORMATION_SCHEMA.JOBS để track query costs, slot usage, và identify expensive queries

Tình huống: Dashboard join nhiều bảng lớn, lặp lại mỗi lần mở → tốn slot. Sửa: materialized view cho phần tổng hợp; scheduled query làm sẵn mart; tránh JOIN trên cột lực lượng cao chưa cluster; cân nhắc reservation riêng cho workload quan trọng để không giành slot.

Module 10 — Orchestration

Cloud Composer & Airflow-based Pipelines

Cloud Composer là managed Apache Airflow trên GCP. Airflow là workflow orchestration engine — nó định nghĩa pipelines as code (DAGs: Directed Acyclic Graphs), schedule execution, monitor progress, và handle retries. Composer wrapper thêm GCP-native integrations: GKE-based workers, Cloud Storage for DAGs, Native GCP operator.

› 1. Airflow concepts › 2. DAG structure › 3. GCP operators › 4. Variables & XComs

1. Airflow Concepts

DAG

Directed Acyclic Graph — định nghĩa task execution order. Mỗi DAG là Python file trong dags/ folder. Airflow scheduler parse DAGs và execute tasks theo dependencies.

Task

Unit of work — có thể là Operator (action), Sensor (wait-for-event), hoặc TaskFlow function. Task có state: queued, running, success, failed, skipped.

Operator

Pre-defined action templates: BashOperator, PythonOperator, BigQueryOperator, DataflowJavaOperator, GcsToBigQueryOperator...

2. DAG Structure

Module 11 — Governance

Dataplex & Data Governance

Dataplex là data governance và lakehouse platform của GCP. Nó giải quyết bài toán: khi data lake có hàng nghìn GCS buckets và BigQuery datasets, làm sao enforce consistent security, catalog, quality, và lineage trên toàn bộ? Dataplex cung cấp: Zones (logical grouping) → Assets (actual GCS buckets/BQ datasets) → Tasks (discovery, profiling, quality).

› 1. Dataplex concepts › 2. Lake, Zone, Asset setup › 3. Discovery & Catalog › 4. Data Quality

1. Dataplex Concepts

Hình 8: Dataplex hierarchy — Lake → Zone → Asset

Lake

Top-level container, thường 1 lake per environment (prod, staging) hoặc 1 lake toàn organization. Lake-level policies áp dụng cho tất cả zones bên trong.

Zone

Logical partition trong lake. Zone định nghĩa: security level (raw, curated), storage format, access pattern. Zone có zone-level IAM và discovery config.

Asset

Actual data resource: GCS bucket, BigQuery dataset/table. Asset được attached vào zone. Dataplex scan asset để extract schema, metadata, lineage.

# Tạo Dataplex Lake gcloud dataplex lakes create my-data-lake \ --location=us-central1 \ --description="Production data lake" \ --labels=environment=prod,team=data-engineering # Tạo Zone: Raw (cho landing/staging data) gcloud dataplex zones create raw-zone \ --lake=my-data-lake \ --location=us-central1 \ --type=RAW \ --resource-location-type=SINGLE_REGION \ --display-name="Raw Data Zone" \ --description="Landing and raw staging data" # Tạo Zone: Curated (silver/gold data) gcloud dataplex zones create curated-zone \ --lake=my-data-lake \ --location=us-central1 \ --type=CURATED \ --resource-location-type=SINGLE_REGION \ --display-name="Curated Data Zone" # Attach GCS bucket as Asset gcloud dataplex assets create orders-raw-asset \ --lake=my-data-lake \ --zone=raw-zone \ --location=us-central1 \ --resource-type=STORAGE_BUCKET \ --resource-name=//storage.googleapis.com/my-data-lake-raw \ --display-name="Orders Raw Data"

Dataplex Data Quality tasks run rules against tables và ghi violations vào BigQuery hoặc Pub/Sub. Quality rules được defined as YAML.

Key Points M11
  • Dataplex: Lake → Zone → Asset hierarchy. Apply governance (IAM, discovery, quality) ở zone level
  • Zone types: RAW (landing/staging) vs CURATED (silver/gold). Khác nhau ở security posture và access pattern
  • Dataplex Discovery: auto-scan GCS buckets và BQ datasets, extract schema và metadata, register vào Catalog
  • Data Catalog (Dataplex Catalog): unified metadata search — tìm tables, columns, lineage
  • Data Quality: YAML rules → Dataplex Tasks run checks → violations → Pub/Sub alerts hoặc BQ log
  • Lineage: Dataform và Dataflow tự động push lineage events sang Dataplex → track data flow end-to-end

Tình huống: Dữ liệu rải khắp GCS + BigQuery, không ai biết bảng nào tin được. Sửa: Dataplex tạo lake/zone, tự khám phá metadata, gắn data quality + governance tập trung, tag dữ liệu nhạy cảm. Một 'mặt phẳng quản trị' cho data nằm nhiều nơi.

2. BigQuery Cost Control

Quota policies

Set project-level và user-level query quotas: max bytes per day, max query duration. Prevent runaway queries từ accidental SELECT *.

BigQuery Editions (slot commitment)

Flat-rate cũ đã khai tử 7/2023, thay bằng Editions (Standard/Enterprise/Enterprise Plus): slot commitment + autoscaling. Predictable cost, recommend khi query volume lớn và ổn định — xem module FinOps.

On-demand guardrails

Set project-level query.disable_legacy_sql, query.projectUsageLimit. Require partition filter trên all partitioned tables.

bq-quota-setup.sh
# Set project-level query quota (bytes per day) bq mk --reservation \ --project_id=my-project \ --location=us-central1 \ --edition=ENTERPRISE \ --slots=100 \ default-pool # Set admin quota: max query bytes per day per user gcloud alpha bq admin-quotas update \ --project=my-project \ --quota-type=query_per_day_bytes \ --quota-limit=1000000000000 # 1 TB/day --member=user:analyst@example.com

Key Points M13
  • Cloud Monitoring: dashboards + alerting policies + notification channels. Integrate với PagerDuty, Slack, email.

Appendix D — Cost Optimization

Cost Optimization Playbook

Tổng hợp strategies giảm GCP data platform cost 30-60% mà không ảnh hưởng performance.

GCS: Lifecycle automation

Standard → Nearline (30d) → Coldline (90d) → Archive (365d). Cấu hình lifecycle rule trên mỗi bucket. Tiết kiệm 60-80% storage cost.

BigQuery: Partition + cluster

require_partition_filter = TRUE. Cluster by high-cardinality columns. Materialized views cho dashboard queries.

Dataflow: Batch over streaming

Nếu latency 1h acceptable, batch jobs rẻ hơn streaming 40-60%. Batch: chỉ trả cho job duration; Streaming: trả cho persistent workers.

Dataproc: Preemptible workers

Add 20-50% preemptible workers. Spark retry handle preemptions. Tiết kiệm 60-80% cho fault-tolerant batch jobs.

Cost / FinOps trên GCP

Trên GCP, "kẻ phá hoá đơn" số một là BigQuery: một câu SELECT * trên bảng vài TB có thể tốn hàng chục đô la mỗi lần chạy, và một dashboard refresh tự động sẽ nhân nó lên hàng nghìn lần mỗi tháng. FinOps trên GCP xoay quanh việc quét ít byte hơn (BigQuery), lưu rẻ hơn (GCS classes), chạy compute đúng cách (Dataflow/Dataproc), và nhìn thấy mọi thứ qua billing export. 1. Tư duy FinOps

FinOps là kỷ luật làm chi phí cloud hiển thị, quy trách nhiệm được, và tối ưu liên tục — không phải đợt cắt giảm một lần. Vòng lặp: Inform (gắn label, export billing để ai cũng thấy chi phí của mình), Optimize (giảm bytes scanned, chọn storage class, dùng spot/CUD), Operate (budget, alert, quota, review hằng tháng). Trên GCP data, đòn bẩy lớn nhất theo ROI: (1) quét ít dữ liệu hơn trong BigQuery, (2) lưu rẻ hơn ở GCS, (3) dùng compute tạm thời + spot.

Nguyên tắc

BigQuery on-demand tính ~$6.25/TB quét. Một query full-scan 2TB tốn ~$12.5 mỗi lần; partition + cluster để chỉ quét 20GB tốn ~$0.1. Trên GCP, tối ưu bytes scanned cho ROI cao hơn mọi thứ khác.

Editions (Standard/Enterprise)trả theo slot (đơn vị compute), tính theo giây, có autoscalingtải lớn, đều; muốn chặn trần chi phí
Slot reservations + commitmentcam kết số baseline slot (1-3 năm) → giảm giákhối lượng query ổn định, lớn

Quy tắc chuyển đổi: khi chi phí on-demand vượt mức tương đương một reservation chạy đều (nói nôm na, khi bạn đã quét nhiều TB mỗi ngày một cách ổn định), chuyển sang Editions + reservations để có giá rẻ hơn và trần chi phí dự đoán được. Editions cho phép autoscaling slot: đặt baseline + max, BigQuery tự thêm slot khi tải cao và thu về khi rảnh. Tải nhỏ/thử nghiệm thì cứ on-demand cho đơn giản.

3. BigQuery: giảm bytes scanned

Với on-demand, mọi tối ưu là "quét ít byte hơn". Bốn kỹ thuật bắt buộc:

Kỹ thuậtVì sao giảm tiền
Partitioning (theo ngày/ingestion time)partition pruning: chỉ quét partition trong WHERE
Clustering (sắp xếp theo cột lọc)block pruning: bỏ qua block không khớp filter
Tránh SELECT *BQ là cột hoá → chọn ít cột = quét ít byte
maximum_bytes_billedchặn cứng: query vượt ngưỡng sẽ fail thay vì đốt tiền

Thói quen vàng: luôn dry_run trước để biết query quét bao nhiêu byte (dry run miễn phí), và đặt maximum_bytes_billed làm phanh an toàn. Tạo bảng partition + cluster:

sql — BigQuery: partition + cluster để cắt scan
CREATE TABLE analytics.events PARTITION BY DATE(event_ts) -- partition pruning theo ngày CLUSTER BY country, event_type -- block pruning theo cột lọc AS SELECT * FROM analytics.events_raw; -- Query có filter partition + cluster ⇒ chỉ quét phần nhỏ SELECT user_id, SUM(amount) FROM analytics.events WHERE DATE(event_ts) = '2026-06-01' -- cắt theo partition AND country = 'VN' -- cắt theo cluster GROUP BY user_id;
bash — bq: dry_run & chặn trần bytes billed
# 1) dry_run: ước lượng byte quét, KHÔNG tính tiền bq query --use_legacy_sql=false --dry_run \ 'SELECT user_id, amount FROM analytics.events WHERE DATE(event_ts)="2026-06-01"' # → "Query will process 21.4 GB" (xem trước khi chạy thật) # 2) Chặn cứng: query nào quét > 50GB sẽ FAIL, không đốt tiền ngoài ý muốn bq query --use_legacy_sql=false --maximum_bytes_billed=53687091200 \ 'SELECT user_id, amount FROM analytics.events WHERE DATE(event_ts)="2026-06-01"'

Tình huống: Một dashboard Looker Studio refresh mỗi 30 phút, chạy SELECT * trên bảng events 2TB không partition. Mỗi refresh quét full 2TB (~$10); mỗi tháng ~1.440 lần → hoá đơn BigQuery bùng nổ ~$14.000/tháng chỉ cho một dashboard. Cách cứu: (1) dry_run phát hiện mỗi query quét 2TB, (2) partition theo DATE(event_ts) + cluster theo country, (3) sửa query chỉ chọn cột cần và thêm filter partition, (4) đặt maximum_bytes_billed làm phanh, (5) thêm materialized view cho phần tổng hợp. Mỗi refresh giờ quét ~15GB thay vì 2TB. Hoá đơn còn vài trăm đô. Bài học: partition + cluster + bỏ SELECT * là phản xạ bắt buộc trên BigQuery.

4. BigQuery: MV, BI Engine & storage

Materialized views (MV): BigQuery tự duy trì và cập nhật incremental; query trúng MV sẽ quét ít byte hơn nhiều và BQ có thể tự rewrite query để dùng MV. Lý tưởng cho aggregation lặp lại (daily revenue, count theo nhóm). BI Engine: lớp cache in-memory tăng tốc dashboard (Looker Studio) và giảm byte tính phí cho truy vấn lặp — trả theo dung lượng GB reservation. Storage: BigQuery tính storage riêng với hai mức — active (~$0.02/GB-tháng) cho bảng/partition có thay đổi trong 90 ngày, và long-term (~$0.01/GB-tháng, tự động giảm 50%) cho partition không bị sửa quá 90 ngày. Nghĩa là: đừng "đụng" lại bảng cũ vô cớ — mỗi lần ghi reset đồng hồ long-term về active.

sql — BigQuery: materialized view cho aggregation lặp lại
CREATE MATERIALIZED VIEW analytics.daily_revenue_mv AS SELECT DATE(event_ts) AS dt, country, SUM(amount) AS revenue, COUNT(*) AS n_orders FROM analytics.events GROUP BY dt, country; -- Dashboard query trúng MV ⇒ quét ít byte, BQ auto-rewrite khi có thể

6. Dataflow & Dataproc

Dataflow (Apache Beam, serverless): tính theo vCPU + memory + lượng dữ liệu xử lý. Đòn bẩy: bật Streaming Engine (chuyển state/shuffle ra dịch vụ quản lý → worker nhỏ hơn, rẻ hơn cho streaming), Dataflow Shuffle service cho batch (shuffle ngoài worker → bớt VM to), và FlexRS (Flexible Resource Scheduling) cho batch không gấp — dùng máy rẻ + lên lịch trong 6 giờ, tiết kiệm đáng kể.

Dataproc (Spark/Hadoop quản lý): tối ưu bằng ephemeral cluster (tạo cụm cho từng job rồi xoá ngay — không nuôi cụm idle) và preemptible/Spot VM cho worker (rẻ hơn 60-91% nhưng có thể bị thu hồi; giữ một ít worker thường + phần lớn là spot). Pattern chuẩn: dữ liệu nằm trên GCS, cụm Dataproc chỉ sống trong lúc chạy job. Ví dụ cụm ephemeral với secondary worker là spot:

bash — Dataproc: ephemeral cluster + Spot worker
# Tạo cụm sống ngắn, secondary worker dùng Spot (rẻ) gcloud dataproc clusters create etl-ephemeral \ --region=asia-southeast1 \ --num-workers=2 \ --num-secondary-workers=8 \ --secondary-worker-type=spot \ --max-idle=10m # tự xoá khi rảnh 10 phút → không tốn cụm idle # Submit job đọc/ghi GCS, xong thì cụm tự tắt gcloud dataproc jobs submit pyspark gs://scripts/etl.py \ --cluster=etl-ephemeral --region=asia-southeast1

7. Pub/Sub & committed use discounts

Pub/Sub tính chủ yếu theo lượng dữ liệu (throughput) publish + deliver (theo GB), cộng phí lưu message tồn (snapshot/retention) và seek. Vì giá theo volume, đòn bẩy là: gộp message hợp lý (batching ở publisher), đặt message retention đúng nhu cầu (giữ lâu = tốn thêm), và dọn subscription "mồ côi" còn giữ backlog. Tránh để retention 7 ngày khi thực ra chỉ cần vài giờ.

Committed Use Discounts (CUD): cam kết dùng một lượng tài nguyên (vCPU, RAM, hay chi tiêu) trong 1-3 năm để giảm giá 20-57% cho phần compute ổn định (áp dụng cho Compute Engine, và dạng spend-based cho một số service như BigQuery Editions). Nguyên tắc: mua CUD cho phần baseline ổn định, để spot/on-demand lo phần đỉnh. Đừng cam kết quá tay cho tải chưa ổn định — CUD trả tiền dù có dùng hết hay không.
