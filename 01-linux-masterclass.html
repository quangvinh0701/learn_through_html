1. Kiến trúc: từ phần cứng đến lệnh của bạn

Khi bạn gõ ls, lệnh đó đi qua nhiều lớp. Hiểu sơ đồ này giúp bạn biết "lỗi nằm ở tầng nào".

Lệnh của bạn đi từ trên xuống. Kernel là "người gác cổng" duy nhất được chạm vào phần cứng.
Phân biệt nhanh

Linux = cái kernel. Ubuntu/Debian = một distribution = kernel Linux + công cụ GNU + trình quản lý gói (apt) + cấu hình mặc định. Vì vậy ta hay nói "Ubuntu là một distro của Linux".

2. Triết lý cốt lõi: "Everything is a file"

Trên Linux, gần như mọi thứ đều được biểu diễn dưới dạng file: tài liệu, thư mục, ổ đĩa, tiến trình, thiết bị, thậm chí kết nối mạng. Điều này cực kỳ mạnh cho dân data — bạn có thể dùng cùng một bộ công cụ (đọc, ghi, redirect) cho mọi thứ.

/dev/null

"Hố đen". Ghi gì vào đây cũng biến mất — dùng để vứt output không cần.

/proc/cpuinfo

Một "file" ảo do kernel sinh ra, đọc nó để xem thông tin CPU.

/dev/sda

Cả ổ đĩa cũng là một file. Đọc/ghi đĩa = đọc/ghi file này.

3. Vì sao Data Engineer/MLOps "sống" trên Linux

Hạ tầng chạy ở đâu?

  • Cloud servers (EC2, GCE, VM) gần như đều là Linux.
  • Containers (Docker) là công nghệ thuần Linux (namespaces + cgroups).
  • Kubernetes, Spark, Kafka, Airflow chạy trên Linux.
  • Khi pipeline lỗi lúc 2h sáng, bạn SSH vào server Linux để debug.

Linux cho bạn sức mạnh gì?

  • Tự động hoá mọi thứ bằng shell script + cron.
  • Xử lý file dữ liệu khổng lồ bằng stream (không cần load hết vào RAM) — xem Tab 04.
  • Tái lập môi trường chính xác (reproducibility) — nền tảng của MLOps.
  • Kiểm soát tài nguyên: biết job nào ăn hết RAM/CPU.

5. find — tìm file theo mọi tiêu chí

Đây là một trong những lệnh quyền lực nhất cho DE. Cú pháp: find <nơi tìm> <điều kiện> <hành động>.

find — thực chiến
Tìm mọi file .csv trong thư mục data (và con của nó) find /data -name "*.csv" Không phân biệt hoa thường find . -iname "*.parquet" File lớn hơn 1GB — dọn ổ đĩa đầy find /data -type f -size +1G File sửa trong 24h qua (-mtime -1) — kiểm tra batch hôm nay find /var/log -type f -mtime -1 File log cũ hơn 30 ngày → XOÁ (cẩn thận! chạy không -delete trước để xem) find /var/log/app -name "*.log" -mtime +30 -delete Tìm file rồi chạy lệnh trên từng cái: nén mọi .csv cũ find . -name "*.csv" -mtime +7 -exec gzip {} \;
find vs locate

find quét real-time (chính xác, hơi chậm trên cây lớn). locate name tra trong một database đánh chỉ mục (cực nhanh nhưng có thể cũ — cập nhật bằng sudo updatedb). Cần biết file nằm đâu nhanh → locate. Cần lọc theo size/thời gian/loại → find.

1. Giải mã chuỗi quyền 10 ký tự

Khi chạy ls -l, cột đầu tiên như -rwxr-xr-- mã hoá toàn bộ quyền. Đây là cách đọc:

-rwxr-xr-- ⇒ owner=7, group=5, others=4 ⇒ quyền "754". Đây là logic của chmod octal.

Lưu ý: với thư mục, ý nghĩa hơi khác — x nghĩa là "được đi vào (cd) thư mục", r là "được liệt kê nội dung", w là "được tạo/xoá file bên trong".

stdin(0) → chương trình → stdout(1) + stderr(2). Pipe nối stdout sang stdin; redirect đẩy ra/vào file.

CRLF vs LF — vết sẹo lịch sử

Windows kết thúc mỗi dòng bằng hai ký tự \r\n (CRLF), Linux/Mac chỉ dùng một ký tự \n (LF). Khi đọc file Windows trên Linux, ký tự \r dư bị dính vào cuối mỗi trường — cột status bạn tưởng là paid thật ra là paid\r, nên mọi phép so sánh đều trượt.

1. Tiến trình là gì & trạng thái của nó

Mỗi chương trình đang chạy là một process có một số định danh duy nhất là PID. Process có thể sinh ra process con (parent → child), tạo thành cây.

Trong htop, cột S cho biết trạng thái. Thấy nhiều process "D" = nghẽn disk I/O; thấy "Z" nhiều = code quên dọn process con.

4. Tín hiệu (signals) & kill

kill thực ra là "gửi tín hiệu" cho process. Hai tín hiệu quan trọng nhất:

SIGTERM (15) — lịch sự

Yêu cầu process tự dừng gọn gàng (đóng file, lưu state). Luôn thử cái này trước. Đây là tín hiệu mặc định của kill.

SIGKILL (9) — cưỡng chế

Giết ngay lập tức, không cho dọn dẹp. Chỉ dùng khi SIGTERM không ăn thua. Có thể để lại file dở dang/khoá.

⭐ 3.5. Port forwarding — xem UI chạy trên server ở máy bạn

Đây là kỹ năng SSH mà Data Engineer dùng hằng ngày nhưng hiếm khoá nào dạy. Bạn chạy Jupyter, Airflow, hay TensorBoard trên server từ xa — nhưng trình duyệt lại ở máy bạn. Port của server thường bị firewall chặn, không mở ra Internet được. SSH tunnel giải bài toán này: nó "khoan một đường ống" mã hoá, ánh xạ một port trên máy bạn sang port trên server.

Local forwarding: -L cổng_máy_bạn:đích:cổng_đích

"Mọi thứ gõ vào localhost:cổng_máy_bạn hãy chuyển qua đường ống SSH tới đích:cổng_đích nhìn từ phía server." Phổ biến nhất: mở UID của một service nội bộ trên server về trình duyệt local.

4. Chuyển file: scp & rsync

scp đơn giản cho file nhỏ. rsync là chân ái của DE: chỉ truyền phần khác biệt, nén khi truyền, hiện tiến độ, và tiếp tục được khi đứt giữa chừng.

scp vs rsync
scp: copy 1 file lên server scp model.pkl gpu:/mnt/data/models/ scp: tải thư mục từ server về (-r) scp -r gpu:/mnt/data/results ./results ⭐ rsync: đồng bộ thư mục lớn. -a giữ nguyên thuộc tính, -v chi tiết, -z nén khi truyền, --progress hiện % rsync -avz --progress ./dataset/ gpu:/mnt/data/dataset/ ⭐ Resume khi mạng đứt giữa chừng: chạy LẠI đúng lệnh, nó tự tiếp tục rsync -avz --partial --progress bigfile.parquet gpu:/mnt/data/ Đồng bộ & XOÁ file thừa ở đích cho giống hệt nguồn (cẩn thận!) rsync -avz --delete ./src/ gpu:/backup/src/ Loại trừ thư mục không cần (venv, cache) rsync -avz --exclude '.venv' --exclude '__pycache__' ./project/ gpu:~/project/
Dấu "/" cuối nguồn trong rsync rất quan trọng

rsync src/ dst/ copy nội dung của src vào dst. rsync src dst/ (không có "/") copy cả thư mục src vào trong dst (tạo dst/src). Nhầm chỗ này là lỗi kinh điển.

3.5. Timezone & đồng bộ giờ — bẫy "chạy sai giờ" kinh điển

Một job hẹn 0 9 * * * (9 giờ sáng) nhưng lại chạy lúc 16h theo giờ Việt Nam? Thủ phạm gần như luôn là: server đặt ở múi giờ UTC. Hầu hết cloud VM mặc định dùng UTC, còn bạn đọc giờ theo địa phương — chênh 7 tiếng. Đây là lỗi khiến báo cáo sáng bị trễ một cách bí ẩn.

Thực hành chuẩn production: giữ server ở UTC. Nghe ngược đời nhưng đúng — khi có nhiều server ở nhiều quốc gia, để tất cả chạy UTC giúp log khớp nhau, không phải quy đổi múi giờ khi truy vết sự cố. Thay vì đổi giờ cả server, hãy khai báo múi giờ ngay trong job. Lưu ý: CRON_TZ=Asia/Ho_Chi_Minh chỉ hoạt động với cronie (RHEL/Fedora) — Vixie/ISC cron của Ubuntu/Debian không hỗ trợ. Trên Ubuntu/Debian, dùng systemd timer (có tùy chọn Timezone=) hoặc wrapper TZ=Asia/Ho_Chi_Minh command trong dòng cron; với Airflow đặt timezone trong cấu hình DAG. Lập lịch theo giờ địa phương nhưng log theo UTC — tốt nhất cả đôi đường.

!

Clock drift âm thầm phá pipeline. Đồng hồ phần cứng trôi vài giây mỗi ngày. Nếu NTP tắt, sau vài tuần giờ server lệch đủ để: token xác thực bị từ chối ("token issued in the future"), log sai thứ tự, và so sánh timestamp giữa các service ra kết quả vô lý. Luôn đảm bảo System clock synchronized: yes.

2. Mount — gắn ổ vào cây thư mục

Linux không tự gán ký tự ổ. Bạn "mount" một filesystem vào một thư mục (mount point) thì mới truy cập được. Quy trình với ổ mới hoàn toàn:

format & mount ổ mới
⚠ CHỈ làm với ổ MỚI/trống — format sẽ XOÁ SẠCH dữ liệu! 1) Tạo filesystem ext4 trên ổ mới mkfs.ext4 /dev/sdb 2) Tạo thư mục làm điểm mount mkdir -p /mnt/data 3) Mount mount /dev/sdb /mnt/data 4) Kiểm tra (giờ /mnt/data đã có 2TB) df -h /mnt/data /dev/sdb 2.0T 28K 1.9T 1% /mnt/data Gỡ mount khi cần (vd trước khi tháo ổ) umount /mnt/data

Một swapfile cho hệ thống "đường lui": đẩy tạm các trang ít dùng xuống đĩa. Chậm hơn RAM nhiều lần, nhưng còn hơn bị giết.

1) Cấp phát file 4GB (fallocate nhanh hơn dd) sudo fallocate -l 4G /swapfile 2) Khoá quyền — chỉ root đọc/ghi (bắt buộc, nếu không swapon từ chối) sudo chmod 600 /swapfile 3) Định dạng thành vùng swap rồi bật sudo mkswap /swapfile && sudo swapon /swapfile 4) Kiểm tra: dòng swap giờ có dung lượng free -h 5) Tự bật lại sau reboot — thêm vào fstab (xem mục 3) echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
i

Swap là an toàn, không phải tốc độ. Một job dựa nhiều vào swap sẽ chậm thảm hại (gọi là "thrashing"). Đúng vai trò của swap: đệm cho những đỉnh RAM ngắn và tránh OOM Kill đột ngột, không phải để thay cho việc nâng RAM khi job thường xuyên cần nhiều bộ nhớ. Quan hệ giữa swap và swappiness được mổ xẻ kỹ ở Module 14.

7. ACL — chia sẻ thư mục data mà không cần chmod 777

Tình huống kinh điển: thư mục /data/shared cần cho hai user (bạn và đồng nghiệp) cùng đọc-ghi, nhưng họ không cùng group. Phản xạ sai là chmod 777 — mở toang cho mọi user trên máy, một lỗ hổng bảo mật. Quyền Unix cổ điển (Module 3) chỉ có 3 nhóm: owner / group / others — không đủ tinh vi. ACL (Access Control List) cho phép cấp quyền cho từng user cụ thể.

setfacl / getfacl
Cấp quyền đọc-ghi-thực thi cho riêng user "alice" trên thư mục sudo setfacl -m u:alice:rwx /data/shared -d = quyền MẶC ĐỊNH: file mới tạo trong đây tự thừa kế quyền của alice sudo setfacl -d -m u:alice:rwx /data/shared Xem toàn bộ ACL hiện có (dấu + ở cuối ls -l báo hiệu có ACL) getfacl /data/shared user::rwx user:alice:rwx quyền riêng cho alice group::r-x other::r-x
✓

Dấu hiệu nhận biết một file/thư mục có ACL: trong ls -l, sau chuỗi quyền 10 ký tự sẽ có thêm dấu + (vd drwxr-xr-x+). Thấy dấu + nghĩa là "quyền thực tế phức tạp hơn những gì bạn thấy ở đây — chạy getfacl để xem đầy đủ".

1. Vì sao MLOps "phải" dùng container?

Vấn đề không có container

  • Máy dev có Python 3.11, server có 3.8 → vỡ.
  • Thư viện C ngầm (libgomp, CUDA) khác phiên bản → model chạy sai.
  • "Cài lại từ đầu" trên server mới mất cả ngày, dễ sót bước.

Container giải quyết

  • Tái lập tuyệt đối: cùng một image → cùng hành vi mọi nơi.
  • Cô lập: mỗi service có môi trường riêng, không đụng nhau.
  • Triển khai nhanh: nền tảng của Kubernetes, CI/CD, model serving.

2. Container vs Máy ảo — và gốc rễ Linux

Container chia sẻ kernel của host → nhẹ & nhanh. Hai công nghệ kernel làm nên điều đó: namespaces (cô lập) + cgroups (giới hạn tài nguyên).
Mọi thứ bạn đã học đều xuất hiện ở đây

namespaces cô lập tiến trình/mạng/filesystem (nhớ Tab 05 & Tab 02). cgroups giới hạn CPU/RAM mỗi container (Tab 05). Image chính là một filesystem đóng gói (Tab 02), chạy bằng user/permission (Tab 03). Docker không "ảo hoá" — nó chỉ dùng các tính năng cô lập có sẵn của kernel Linux một cách khéo léo.

Cài Docker trên Ubuntu (tóm tắt — theo cách thêm kho an toàn ở Tab 06): cài docker-ce từ kho chính thức của Docker, rồi sudo usermod -aG docker $USER (đăng xuất/vào lại) để chạy docker không cần sudo.

3. Image vs Container — phân biệt cốt lõi

Image (ảnh)

Bản đóng gói bất biến, chỉ-đọc: chứa OS con + thư viện + code. Như "class" hoặc một bản snapshot. Xây từ Dockerfile.

Container

Một thực thể đang chạy của image. Như "object" tạo từ class. Từ một image chạy được nhiều container.

5. Viết Dockerfile cho ứng dụng data

Dockerfile là "công thức" xây image — từng dòng là một bước. Đây là mẫu cho một ứng dụng ETL/serving bằng Python:

Dockerfile
Bắt đầu từ image nền nhẹ có sẵn Python FROM python:3.11-slim Thư mục làm việc trong container WORKDIR /app Copy requirements TRƯỚC để tận dụng cache layer (tối ưu quan trọng) COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt Giờ mới copy code (code đổi thường xuyên → đặt sau) COPY . . Biến môi trường mặc định ENV PYTHONUNBUFFERED=1 Khai báo port app lắng nghe (cho serving) EXPOSE 8000 Lệnh chạy khi container khởi động CMD ["python", "-m", "etl.run"]
build & run
Xây image, đặt tên (tag) là etl-pipeline:v1 docker build -t etl-pipeline:v1 . Chạy, truyền biến môi trường & mount thư mục data của host vào docker run --rm \ -e DATABASE_URL="$DATABASE_URL" \ -v /mnt/data:/app/data \ etl-pipeline:v1
Thứ tự dòng = tốc độ build

Docker cache theo từng layer. Đặt COPY requirements.txt + pip install trước COPY . . để khi bạn chỉ sửa code (không đổi thư viện), Docker tái dùng layer cài đặt → build lại trong vài giây thay vì vài phút. Thêm file .dockerignore (loại .venv, .git, data) để image gọn & build nhanh.

5.5. ⭐ Multi-stage build — image 2GB xuống 200MB

Image Docker đầu tiên của hầu hết mọi người đều "béo phì": vài GB vì lỡ đóng gói cả compiler, file build trung gian, cache. Image to nghĩa là chậm push/pull, tốn tiền lưu trữ, và bề mặt tấn công lớn hơn. Multi-stage build là kỹ thuật chuẩn để giảm kích thước: build trong một stage "đầy đủ đồ nghề", rồi chỉ copy kết quả sang một stage runtime gọn nhẹ.

Dockerfile multi-stage
===== STAGE 1: builder — có đủ compiler để cài gói ===== FROM python:3.11 AS builder WORKDIR /app COPY requirements.txt . Cài vào một thư mục riêng để dễ copy sang stage sau RUN pip install --user -r requirements.txt ===== STAGE 2: runtime — slim, chỉ lấy thứ cần để CHẠY ===== FROM python:3.11-slim WORKDIR /app Chỉ copy gói đã cài từ builder — bỏ lại toàn bộ compiler COPY --from=builder /root/.local /root/.local COPY src/ ./src/ ENV PATH=/root/.local/bin:$PATH CMD ["python", "src/main.py"]
✓

Thứ tự lệnh = tốc độ build. Docker cache theo từng tầng (layer). Đặt COPY requirements.txt + pip install trước COPY src/. Lý do: code thay đổi liên tục còn dependencies thì hiếm khi — nếu chỉ sửa code, Docker tái dùng cache tầng cài gói và build trong vài giây thay vì cài lại từ đầu. Cơ chế OverlayFS đằng sau được mổ ở Module 18.

Module 13 — Lý thuyết chuyên sâu

Kernel & Lời gọi hệ thống (System Calls)

Đây là nơi "phép màu" thực sự diễn ra. Mọi lệnh bạn đã học cuối cùng đều quy về việc nhờ kernel làm hộ qua system call. Hiểu cơ chế này giúp bạn lý giải tại sao một số tác vụ chậm, tại sao có ranh giới bảo mật, và đọc được công cụ như strace khi debug ở tầng sâu nhất.

Phần chuyên sâu tập trung vào "tại sao & như thế nào". Bạn không cần thuộc lòng — đọc để xây mô hình tư duy đúng, rồi quay lại tra khi gặp vấn đề thực tế.

1. Hai thế giới: User space & Kernel space

CPU hiện đại chạy ở nhiều mức đặc quyền (gọi là "ring"). Linux chỉ dùng hai mức: ring 3 (user mode — đặc quyền thấp) cho chương trình của bạn, và ring 0 (kernel mode — toàn quyền) cho nhân. Ranh giới này là nền tảng của sự ổn định và bảo mật.

Privilege boundary (ranh giới đặc quyền)

Ở user mode, chương trình KHÔNG được phép trực tiếp: truy cập phần cứng, đọc/ghi bộ nhớ của tiến trình khác, hay thao tác đĩa/mạng. Muốn làm những việc đó, nó phải "xin phép" kernel. Nhờ vậy một chương trình lỗi chỉ tự sập chứ không kéo sập cả hệ thống.

Vậy làm sao một chương trình ở ring 3 nhờ kernel ở ring 0 làm việc? Câu trả lời là system call — cổng giao tiếp được kiểm soát chặt chẽ và là cách duy nhất để vượt qua ranh giới.

2. Cơ chế của một system call

Khi code Python của bạn gọi open("data.csv"), chuỗi sự kiện sau diễn ra (đơn giản hoá):

Chương trình không tự mở file — nó nhờ kernel. Lệnh `syscall` của CPU là cây cầu được canh gác.

Một số system call bạn "gọi" gián tiếp suốt ngày: read, write, open, close, fork, execve, mmap, socket, clone. Linux có khoảng 350+ syscall. Thư viện C (glibc) bọc chúng thành hàm tiện dụng để bạn không phải viết assembly.

Vì sao điều này quan trọng với DE

Mỗi syscall tốn chi phí chuyển chế độ (mode switch). Một chương trình đọc file 1 byte mỗi lần sẽ gọi read hàng triệu lần → cực chậm. Đọc theo buffer lớn (vài KB–MB mỗi lần) giảm số syscall → nhanh hơn nhiều bậc. Đây chính là lý do mọi thư viện I/O đều "đệm" (buffering), và vì sao xử lý dữ liệu theo lô (batch/chunk) luôn thắng xử lý từng dòng.

4. Bộ lập lịch CPU — CFS (Completely Fair Scheduler)

Bạn có 8 nhân nhưng hàng trăm tiến trình. Kernel phải quyết định ai chạy, trên nhân nào, trong bao lâu. Đó là việc của scheduler. Linux dùng CFS với ý tưởng cốt lõi: chia thời gian CPU công bằng.

  • Time slice (lát thời gian): mỗi tiến trình được chạy một khoảng rất ngắn (vài mili-giây) rồi bị tạm ngưng để nhường nhân cho tiến trình khác. Việc luân phiên cực nhanh tạo ảo giác "mọi thứ chạy song song".
  • vruntime (virtual runtime): CFS theo dõi mỗi tiến trình đã dùng bao nhiêu CPU. Nó luôn ưu tiên cho tiến trình có vruntime thấp nhất (bị "thiệt" nhất) → công bằng.
  • nice / priority: giá trị nice từ −20 (ưu tiên cao) đến +19 (nhường nhịn). Tiến trình "nice" hơn nhận ít CPU hơn khi tranh chấp.
Cập nhật: EEVDF thay CFS từ kernel 6.6

Từ kernel 6.6 (Ubuntu 24.04+, Debian 13), scheduler mặc định là EEVDF (Earliest Eligible Virtual Deadline First) thay cho CFS. Các khái niệm vruntime / nice / weight bạn học ở đây vẫn chuyển giao nguyên vẹn — EEVDF chỉ bổ sung "deadline ảo" để giảm độ trễ cho tác vụ tương tác.

CPU-bound vs I/O-bound — phân biệt sống còn cho DE

CPU-bound: nghẽn ở tính toán (vd biến đổi dữ liệu nặng, train model) → cần nhiều nhân, tăng nhân giúp ích. I/O-bound: nghẽn ở chờ đĩa/mạng/DB (vd đọc file lớn, gọi API) → CPU nhàn rỗi chờ đợi, thêm nhân vô ích, cần tối ưu I/O (đọc song song, batch, cache). Nhìn htop: %CPU cao = CPU-bound; %CPU thấp mà chậm + nhiều process trạng thái D = I/O-bound. Chẩn đoán đúng loại quyết định bạn tối ưu đúng hướng.

5. Chuyển ngữ cảnh (Context Switch) — cái giá của đa nhiệm

Mỗi khi CPU chuyển từ tiến trình A sang B, kernel phải lưu toàn bộ trạng thái của A (thanh ghi, con trỏ lệnh, bản đồ bộ nhớ) rồi nạp trạng thái của B. Đó là context switch. Nó nhanh (cỡ micro-giây) nhưng KHÔNG miễn phí.

Chi phí ẩn của context switch

Ngoài việc lưu/nạp thanh ghi, switch còn làm "nguội" các bộ nhớ đệm CPU (cache, TLB) — dữ liệu của tiến trình mới chưa có trong cache nên truy cập đầu chậm hơn. Tạo quá nhiều luồng/tiến trình (nhiều hơn số nhân) khiến CPU bận switch hơn là làm việc thật — gọi là "thrashing scheduler".

Hệ quả thực tế

Đây là lý do đặt số worker/thread ≈ số nhân CPU thường tối ưu cho job CPU-bound (vd --workers $(nproc)). Đặt 500 luồng trên máy 8 nhân không tăng tốc — chỉ tăng overhead. Xem số context switch: vmstat 1 (cột cs) hoặc pidstat -w.

6. Ngắt (Interrupts) — cách phần cứng "gọi" kernel

Làm sao kernel biết "gói tin mạng đã tới" hay "đĩa đọc xong" mà không phải hỏi liên tục? Câu trả lời: interrupt. Thiết bị phần cứng gửi tín hiệu ngắt (IRQ) tới CPU; CPU lập tức tạm dừng việc đang làm và chạy một interrupt handler của kernel.

  • Top half (nửa trên): phần xử lý ngắt cực ngắn, khẩn cấp — chỉ ghi nhận sự kiện rồi trả CPU ngay (vì trong lúc xử lý ngắt, hệ thống bị "đóng băng").
  • Bottom half (nửa dưới): phần xử lý nặng được hoãn lại, chạy sau khi ngắt kết thúc (softirq, tasklet, workqueue).

Cơ chế interrupt giải thích vì sao Linux có thể chờ I/O mà không "bận rộn quay vòng": tiến trình chờ đĩa được đưa vào trạng thái ngủ (S/D), CPU đi làm việc khác, và chỉ được đánh thức khi interrupt báo I/O hoàn tất. Đây là nền của mô hình I/O hiệu quả.

1. Tại sao cần bộ nhớ ảo?

Mỗi tiến trình tin rằng nó sở hữu toàn bộ không gian địa chỉ liền mạch, riêng tư, bắt đầu từ địa chỉ 0. Đây là một ảo giác đẹp đẽ do kernel + phần cứng dựng lên. Thực tế RAM vật lý bị chia nhỏ, dùng chung, và mỗi tiến trình chỉ chiếm vài mảnh rải rác.

Địa chỉ ảo vs địa chỉ vật lý

Chương trình chỉ thấy địa chỉ ảo (virtual address). Mỗi lần truy cập bộ nhớ, phần cứng dịch nó sang địa chỉ vật lý (chỗ thật trong RAM). Tiến trình A và B có thể cùng dùng địa chỉ ảo 0x400000 nhưng trỏ tới hai vùng RAM vật lý hoàn toàn khác nhau.

Lợi ích then chốt: cô lập (A không thể đọc bộ nhớ của B → bảo mật & ổn định), đơn giản hoá (lập trình viên không cần lo RAM thật nằm đâu), và linh hoạt (có thể dùng nhiều bộ nhớ hơn RAM thật nhờ swap, chia sẻ trang giữa tiến trình, ánh xạ file...).

Không gian ảo của mỗi tiến trình được chia thành các vùng (segment) có vai trò riêng:

Stack mọc xuống, heap mọc lên. Khi xử lý dữ liệu lớn, vùng Heap (và mmap) chính là nơi DataFrame/array của bạn ngốn RAM.

Khi bạn tạo một Pandas DataFrame khổng lồ, bộ nhớ được cấp ở heap (hoặc mmap cho khối lớn). Khi nó vượt RAM vật lý, mọi vấn đề bắt đầu — và đó là lúc các khái niệm bên dưới phát huy.

3. Phân trang (Paging) & MMU

Kernel không quản lý bộ nhớ theo từng byte mà theo từng khối cố định gọi là page (trang), thường 4 KB. RAM vật lý cũng chia thành các "page frame" cùng kích thước. Việc dịch địa chỉ ảo → vật lý là ánh xạ page ảo → page frame vật lý, lưu trong page table.

MMU = Memory Management Unit. TLB = bộ đệm các ánh xạ gần nhất; "TLB miss" khiến truy cập chậm hơn.

Bộ phần cứng MMU thực hiện dịch địa chỉ trong từng nano-giây. Để khỏi tra page table mỗi lần (chậm), CPU có bộ đệm TLB lưu các ánh xạ vừa dùng. Đây là lý do context switch (Tab 13) tốn kém: đổi tiến trình → đổi page table → TLB bị xoá → vài truy cập đầu chậm vì phải dựng lại TLB.

4. Page fault & cấp phát lười (lazy allocation)

Khi tiến trình truy cập một page chưa được nạp vào RAM vật lý, MMU không tìm thấy ánh xạ → phát sinh page fault, kernel nhảy vào xử lý. Có hai loại:

Minor fault (nhẹ)

Page đã ở đâu đó trong RAM (vd page cache, hoặc cần cấp page mới trống) — chỉ cần tạo ánh xạ. Rất nhanh.

Major fault (nặng)

Page phải được đọc từ đĩa (file ánh xạ, hoặc đã bị swap ra đĩa). Chậm hơn hàng nghìn lần vì dính I/O.

Cấp phát lười & overcommit — vì sao VIRT khổng lồ mà không sao

Khi chương trình "xin" bộ nhớ (vd malloc 10GB), Linux KHÔNG cấp RAM thật ngay — nó chỉ hứa hẹn (cập nhật bản đồ địa chỉ ảo). RAM vật lý chỉ thực sự được cấp khi bạn chạm vào từng page (qua page fault). Đây gọi là demand paging + overcommit. Hệ quả: cột VIRT trong htop (bộ nhớ ảo đã hứa) thường lớn hơn nhiều RES (RAM thật đang dùng). Chỉ RES mới là con số đáng lo. Đây chính là lời giải cho thắc mắc ở Module 05.

5. Copy-on-Write (COW) — vì sao fork rẻ

Khi một tiến trình fork (Tab 15), về lý thuyết phải sao chép toàn bộ bộ nhớ của nó cho con — rất tốn kém với tiến trình lớn. Linux khôn ngoan hơn: con và cha dùng chung các page vật lý, đánh dấu chỉ-đọc. Chỉ khi một bên ghi vào một page, kernel mới sao chép riêng page đó ra (copy-on-write).

Cạm bẫy COW trong xử lý dữ liệu Python

Khi dùng multiprocessing với fork (mặc định trên Linux), các tiến trình con ban đầu "miễn phí" chia sẻ dữ liệu lớn của cha nhờ COW. Nhưng nếu con ghi hoặc chỉ chạm vào nhiều đối tượng (kể cả đếm tham chiếu của Python cũng là ghi metadata!), COW kích hoạt và RAM phình lên bất ngờ. Đây là nguyên nhân kinh điển khiến job multiprocessing bị OOM dù "chỉ đọc". Giải pháp: dùng dữ liệu chia sẻ thật (shared memory, Arrow), hoặc nạp dữ liệu sau khi fork.

6. ⭐ Page cache — lời giải cho "RAM của tôi đầy rồi!"

Đây là hiểu lầm phổ biến nhất. Bạn chạy free -h thấy RAM "used" cao chót vót và hoảng. Nhưng phần lớn thường là page cache — và đó là điều TỐT.

Page cache

Linux dùng RAM đang rảnh để lưu đệm nội dung file vừa đọc/ghi từ đĩa. Lần sau đọc lại file đó → lấy thẳng từ RAM, không cần chạm đĩa → nhanh gấp hàng trăm lần. RAM rảnh mà không dùng là lãng phí; Linux triết lý "free RAM is wasted RAM".

7. Swap & swappiness

Khi RAM thật cạn, kernel có thể đẩy bớt các page "ít dùng" xuống một vùng đĩa gọi là swap để giải phóng RAM cho việc khẩn cấp. Swap mở rộng bộ nhớ khả dụng nhưng cực chậm (đĩa chậm hơn RAM hàng nghìn lần).

  • vm.swappiness (0–100): mức độ "hăng hái" dùng swap. Mặc định 60. Server data thường hạ xuống 10 để ưu tiên giữ dữ liệu trong RAM, chỉ swap khi thật sự bí.
  • Thrashing: khi RAM quá thiếu, kernel liên tục swap ra/vào — máy "đứng hình", CPU bận chuyển trang thay vì làm việc. Đây là trạng thái cần tránh tuyệt đối với job dữ liệu.

8. OOM Killer — khi không còn đường lui

Nếu RAM và swap đều cạn mà vẫn có yêu cầu cấp bộ nhớ không thể từ chối, kernel buộc phải hành động kẻo cả hệ thống treo. Nó kích hoạt OOM Killer (Out-Of-Memory Killer): chọn một tiến trình để "hi sinh" và giết nó nhằm giải phóng RAM.

1. Một tiến trình dưới mắt kernel

Với kernel, mỗi tiến trình là một cấu trúc dữ liệu khổng lồ tên task_struct (còn gọi Process Control Block — PCB). Nó lưu mọi thứ kernel cần để quản lý: PID, trạng thái, con trỏ tới page table (bản đồ bộ nhớ — Tab 14), bảng file descriptor đang mở (Tab 16), user/group sở hữu (Tab 03), tiến trình cha, tín hiệu đang chờ, thống kê CPU đã dùng...

PID & PPID

PID = số định danh duy nhất của tiến trình. PPID = PID của tiến trình cha. Mọi tiến trình (trừ PID 1) đều có cha → tạo thành một cây tiến trình có gốc là PID 1 (init/systemd). Xem cây bằng pstree -p.

2. fork + exec + wait — bộ ba khai sinh mọi tiến trình

Linux tạo tiến trình mới theo một mô hình thanh lịch và có phần kỳ lạ: không có lệnh "chạy chương trình X" trong một bước. Thay vào đó là hai bước tách biệt — sao chép chính mình (fork), rồi thay nội dung bằng chương trình mới (exec).

Đây là điều xảy ra MỖI LẦN bạn gõ một lệnh. Shell fork ra bản sao, bản sao exec thành chương trình bạn muốn, shell chờ rồi nhận mã thoát ($?).

Chi tiết từng bước:

  • fork(): tạo một bản sao gần như y hệt tiến trình hiện tại (nhờ copy-on-write ở Tab 14 nên rất rẻ). Điều kỳ lạ: fork "trả về hai lần" — ở tiến trình cha trả về PID của con, ở tiến trình con trả về 0. Cùng một dòng code, hai số phận khác nhau.
  • execve(): nạp một chương trình mới đè lên tiến trình hiện tại — text/data/heap/stack bị thay sạch bằng nội dung của chương trình mới, nhưng PID và các file descriptor đang mở được giữ nguyên (điểm cực quan trọng — xem mục redirection ở Tab 16).
  • wait()/waitpid(): tiến trình cha gọi để chờ con kết thúc và thu nhận mã thoát của nó. Bước này dọn dẹp xác con (xem zombie bên dưới).
Vì sao "fork rồi exec" mà không gộp một bước?

Tách đôi cho phép tiến trình con làm vài việc giữa fork và exec — ví dụ shell mở/đóng/chuyển hướng file descriptor (để làm > out.txt hay pipe |) trước khi chương trình mới chạy. Đây chính là cơ chế nền của mọi redirection & pipe ở Module 04 — shell thiết lập các fd ở tiến trình con rồi mới exec, nên chương trình "không hề biết" output của nó đã bị chuyển hướng.

4. Zombie & orphan — hai số phận của tiến trình con

🧟 Zombie (con chết, cha lơ là)

Con đã kết thúc nhưng cha chưa gọi wait() để thu mã thoát. Kernel phải giữ lại một "xác" (entry trong bảng tiến trình) chứa mã thoát chờ cha đọc. Zombie không tốn RAM/CPU nhưng chiếm một ô PID. Hàng nghìn zombie → cạn PID → không tạo được tiến trình mới.

👻 Orphan (cha chết trước con)

Cha kết thúc khi con còn sống → con "mồ côi". Kernel lập tức nhận nuôi (reparent) con về cho PID 1 (init/systemd). PID 1 có nhiệm vụ wait() dọn xác chúng → orphan không thành zombie vĩnh viễn.

5. Process group, session & controlling terminal

Vì sao Ctrl+C dừng đúng job đang chạy mà không giết cả shell? Vì sao đóng cửa sổ terminal lại giết các tiến trình bên trong? Câu trả lời nằm ở cách kernel nhóm các tiến trình.

Phân cấp: phiên (session) › nhóm (process group) › tiến trình

Khi bạn mở terminal, một session được tạo, gắn với một controlling terminal. Mỗi lệnh/pipeline bạn chạy tạo thành một process group. Một nhóm là "foreground" (đang nắm terminal), các nhóm khác là "background".

Từ đó suy ra mọi hành vi quen thuộc ở Module 05:

  • Ctrl+C gửi SIGINT tới cả foreground process group (không phải toàn session) → dừng job hiện tại, shell vẫn sống vì nó ở nhóm khác.
  • Ctrl+Z gửi SIGTSTP → tạm dừng nhóm foreground (trạng thái T); bg/fg đổi nhóm foreground.
  • Khi terminal đóng (mất kết nối SSH), kernel gửi SIGHUP ("hang up") tới session → mặc định mọi tiến trình trong đó bị giết. Đây chính xác là lý do job của bạn chết khi đóng SSH.
Giờ thì nohup, disown và tmux hiện rõ nguyên lý

• nohup = "no hang up": chạy lệnh sao cho nó phớt lờ SIGHUP → terminal đóng cũng không sao.
• disown: gỡ job khỏi danh sách của shell để shell không gửi SIGHUP cho nó khi thoát.
• tmux/screen cao tay hơn: chúng tạo một session riêng với một terminal ảo (pseudo-terminal) không chết khi bạn ngắt kết nối — bạn chỉ "tách" (detach) khỏi nó. Job vẫn nằm trong session sống của tmux. Lần sau "gắn lại" (attach) là thấy y nguyên. Đây là vì sao tmux là chuẩn vàng cho job dài hơi (Module 07).

Đây là lý do quy trình "SIGTERM trước, SIGKILL sau" (Module 05) quan trọng: SIGTERM cho phép chương trình chạy signal handler để dọn dẹp — flush buffer ghi nốt dữ liệu, đóng kết nối DB, lưu checkpoint, commit offset Kafka — rồi mới thoát. Một data worker viết tốt sẽ "bắt" SIGTERM và tắt sạch sẽ. Trong Kubernetes/Docker, khi pod/container bị dừng, hệ thống gửi SIGTERM, chờ một khoảng "grace period" (vd 30s), rồi mới SIGKILL. Nếu app của bạn không xử lý SIGTERM, nó sẽ bị giết cứng giữa chừng → mất dữ liệu, hỏng transaction. Hãy luôn cài signal handler trong worker xử lý dữ liệu.

1. VFS — lớp trừu tượng "mọi thứ là file"

Linux hỗ trợ hàng chục loại filesystem khác nhau (ext4, xfs, btrfs, tmpfs trong RAM, procfs ảo, NFS qua mạng...). Làm sao cùng một lệnh cat đọc được tất cả? Nhờ VFS — Virtual File System: một lớp trừu tượng trong kernel định nghĩa các thao tác chung (open, read, write, close), còn mỗi filesystem cụ thể "cắm vào" và hiện thực hoá chúng theo cách riêng.

VFS = giao diện chung cho mọi "file"

Đây chính là hiện thực kỹ thuật của triết lý "everything is a file" (Module 01). Một ổ đĩa, một socket mạng, một thiết bị, một file ảo trong /proc — tất cả đều phơi bày qua cùng một giao diện VFS, nên cùng một bộ công cụ (đọc/ghi/redirect/pipe) dùng được cho mọi thứ. Đó là nguồn sức mạnh tổ hợp khủng khiếp của Unix.

2. inode — file "thật sự" là gì?

Đây là phát hiện làm thay đổi cách bạn nhìn file: tên file không phải là file. File thật là một inode — một cấu trúc dữ liệu chứa MỌI thứ về file trừ tên: kích thước, chủ sở hữu & quyền (Module 03), thời gian, và quan trọng nhất là con trỏ tới các khối dữ liệu trên đĩa. Mỗi inode có một số định danh duy nhất trong filesystem.

Thư mục chỉ là một bảng tra "tên → số inode"

Một thư mục thực chất là một file đặc biệt chứa danh sách ánh xạ tên_file → inode_number. Khi bạn mở /data/sales.csv, kernel tra trong thư mục /data để tìm số inode ứng với tên "sales.csv", rồi mới dùng inode đó để tìm dữ liệu. Tên và dữ liệu hoàn toàn tách rời.

4. ⭐ File descriptor & ba bảng — trái tim của I/O

Khi một tiến trình mở file, nó nhận về một file descriptor (fd) — một số nguyên nhỏ (3, 4, 5...). Mọi thao tác đọc/ghi sau đó dùng con số này. Ba số đặc biệt luôn mở sẵn cho mỗi tiến trình: 0 = stdin, 1 = stdout, 2 = stderr (nhớ Module 04!). Bên dưới, fd được hiện thực qua một kiến trúc ba bảng tinh tế:

fd (số) → entry trong bảng open file (chứa offset & chế độ) → inode (file thật). Kiến trúc này giải thích redirection, pipe, và việc dùng chung file.

Vì sao cần tận ba tầng? Vì nó tách bạch ba khái niệm: "cái tên số mà tiến trình dùng" (fd), "trạng thái của một lần mở — đang đọc tới đâu, chế độ gì" (open file entry, chứa offset), và "file vật lý" (inode). Nhờ tách offset ra tầng giữa, hai tiến trình có thể mở cùng file độc lập (mỗi bên offset riêng), HOẶC chia sẻ chung một entry (cùng offset) khi một bên fork từ bên kia.

5. Redirect & pipe hoạt động ở tầng nào

Giờ ta khép lại vòng tròn với Module 04 & 15. Khi bạn gõ python etl.py > out.txt:

  1. Shell fork ra tiến trình con (Module 15).
  2. Trong con, trước khi exec, shell mở out.txt rồi dùng syscall dup2 để làm cho fd 1 (stdout) trỏ vào out.txt thay vì terminal.
  3. Shell exec thành python. Python cứ ghi ra fd 1 như thường — không hề biết fd 1 đã bị "đánh tráo" sang file. Mọi thứ nó print chảy vào out.txt.

Còn pipe A | B: kernel tạo một "đường ống" trong bộ nhớ (cũng có 2 fd: đầu đọc & đầu ghi). Shell nối stdout của A (fd 1) vào đầu ghi, và stdin của B (fd 0) vào đầu đọc. Dữ liệu A ghi ra chảy thẳng sang B mà không qua đĩa. Đó là vì sao pipe nhanh và không tốn file tạm.

Vì sao 2>&1 phải đặt SAU > file

2>&1 nghĩa là "làm cho fd 2 trỏ tới chỗ fd 1 đang trỏ". Nên thứ tự quan trọng: > out 2>&1 = trỏ fd1 vào out, RỒI trỏ fd2 vào (chỗ fd1 = out) → cả hai vào out (đúng). Nhưng 2>&1 > out = trỏ fd2 vào (chỗ fd1 = terminal) trước, RỒI mới đổi fd1 sang out → lỗi vẫn ra terminal (sai). Hiểu kiến trúc fd làm cú pháp khó nhằn này trở nên logic hoàn toàn.

"Too many open files" — lỗi ám ảnh của data service

Mỗi tiến trình có giới hạn số fd mở đồng thời (kernel phải cấp tài nguyên cho mỗi entry). Service xử lý nhiều file/kết nối (web server, ingest nhiều file, nhiều socket DB) dễ chạm trần và báo lỗi Too many open files (errno EMFILE). Đây cực kỳ phổ biến trong hệ thống dữ liệu. Kiểm tra & nâng giới hạn:

ulimit -n xem trần hiện tại · ulimit -n 65536 nâng (phiên hiện tại) · với systemd service đặt LimitNOFILE=65536 trong unit (Module 09) · đếm fd đang mở của tiến trình: ls /proc/<PID>/fd | wc -l. Gốc rễ thường là rò rỉ fd — code quên đóng file/connection (luôn dùng with open(...) trong Python, đóng connection pool đúng cách).

6. Buffer, fsync & độ bền dữ liệu

Khi bạn write(), dữ liệu thường KHÔNG xuống đĩa ngay. Nó được kernel gom vào page cache (Module 14) trong RAM và ghi xuống đĩa sau (write-back) để gộp nhiều ghi nhỏ thành ghi lớn hiệu quả. Tốc độ tuyệt vời — nhưng có rủi ro: nếu mất điện/crash trước khi page cache được ghi xuống đĩa, dữ liệu "đã ghi" đó biến mất.

fsync() — ép dữ liệu thật sự chạm đĩa

fsync(fd) buộc kernel đẩy mọi dữ liệu đang đệm của file xuống thiết bị lưu trữ và chờ tới khi đĩa xác nhận. Đây là ranh giới giữa "tôi đã gọi write" và "dữ liệu đã thật sự an toàn". fdatasync tương tự nhưng bỏ qua một số metadata để nhanh hơn.

Vì sao điều này quan trọng với DE — độ bền & ghi nguyên tử

Mọi database (Postgres, SQLite...) đều gọi fsync tại điểm commit để đảm bảo giao dịch không mất khi crash — đó là chữ "D" (Durability) trong ACID. Hệ quả cho bạn:

• Ghi nguyên tử (atomic write): để một file output không bao giờ bị đọc ở trạng thái "ghi dở", hãy ghi ra file tạm rồi mv (rename) sang tên cuối. rename trong cùng filesystem là thao tác nguyên tử (chỉ đổi ánh xạ tên→inode trong thư mục) — người đọc hoặc thấy file cũ trọn vẹn, hoặc file mới trọn vẹn, không bao giờ thấy nửa vời. Đây là kỹ thuật chuẩn cho output của ETL.
• Đánh đổi hiệu năng vs an toàn: fsync mỗi bản ghi thì an toàn nhưng chậm; gom rồi fsync theo lô thì nhanh nhưng rủi ro mất phần cuối khi crash. Hiểu đánh đổi này giúp bạn cấu hình đúng (vd synchronous_commit trong Postgres, hay chiến lược checkpoint của pipeline).

7. Journaling — vì sao filesystem không hỏng sau khi mất điện

Một thao tác đơn giản như "tạo file" thực ra gồm nhiều bước ghi đĩa (cập nhật inode, cập nhật thư mục, cập nhật bản đồ khối trống). Nếu mất điện giữa chừng, filesystem rơi vào trạng thái mâu thuẫn (vd inode đã cấp nhưng thư mục chưa trỏ tới → "lạc" mất khối đĩa). Journaling giải quyết điều này.

Journal = nhật ký dự định trước khi làm

Trước khi thực hiện một nhóm thay đổi, ext4 ghi ý định đó vào một vùng "journal" riêng. Làm xong thì đánh dấu hoàn tất. Nếu crash giữa chừng, lúc khởi động lại kernel "phát lại" (replay) journal: hoàn tất các thao tác đã ghi đủ, bỏ các thao tác dở dang → filesystem luôn ở trạng thái nhất quán, không cần quét toàn đĩa (fsck) hàng giờ như thời xưa.

ext4 có ba chế độ journaling, đánh đổi giữa an toàn và tốc độ: journal (ghi cả dữ liệu vào journal — an toàn nhất, chậm nhất), ordered (mặc định — chỉ journal metadata nhưng đảm bảo dữ liệu ghi trước metadata), và writeback (chỉ journal metadata, nhanh nhất, ít an toàn hơn). Với server dữ liệu, mặc định ordered là cân bằng hợp lý.

2. Socket, port & cổng vào kernel

Chương trình không tự đụng card mạng — nó nhờ kernel qua một socket. Và socket, đúng tinh thần "everything is a file" (Module 16), cũng là một file descriptor. Bạn read/write lên socket y như lên file — kernel lo phần biến nó thành gói tin.

Port — bộ phân loại của kernel

Một máy có một địa chỉ IP nhưng chạy nhiều dịch vụ (web :80, Postgres :5432, SSH :22). Port (cổng) là con số giúp kernel biết gói tin đến thuộc về dịch vụ nào. Một kết nối được định danh duy nhất bởi bộ bốn: IP nguồn : port nguồn ↔ IP đích : port đích. Đó là cách kernel "ghép" đúng gói tin vào đúng socket của đúng tiến trình.

TIME_WAIT & connection pooling — bài học cho hệ thống dữ liệu

Mỗi kết nối đóng để lại trạng thái TIME_WAIT trong ~60 giây. Một pipeline mở-rồi-đóng hàng nghìn kết nối ngắn tới database (vd mỗi truy vấn một connection mới) sẽ tích tụ TIME_WAIT, cạn port nguồn (chỉ có ~64K port) → lỗi "cannot assign requested address". Giải pháp chuẩn: connection pooling — tái dùng một nhóm kết nối mở sẵn thay vì tạo mới liên tục (SQLAlchemy pool, PgBouncer...). Thấy ss -tan | grep -c TIME-WAIT tăng vọt là dấu hiệu cần pooling. Nhiều CLOSE_WAIT tồn đọng = bug ứng dụng quên đóng kết nối (rò rỉ — liên hệ "too many open files" ở Module 16).

4. Hành trình một gói tin: từ dây tới tiến trình

Khi dữ liệu đến card mạng (NIC), chuỗi sự kiện (liên hệ Module 13 — interrupt):

  1. NIC nhận frame, đặt vào bộ nhớ, rồi phát interrupt báo CPU "có hàng".
  2. Kernel (driver mạng) xử lý: bóc header Ethernet → IP → TCP, kiểm tra checksum, ghép vào đúng kết nối.
  3. Dữ liệu (payload) được đặt vào socket receive buffer — một vùng đệm trong kernel cho socket đó.
  4. Tiến trình của bạn đang read() trên socket (có thể đang ngủ trạng thái S — Module 15) được đánh thức và nhận dữ liệu.

Chiều gửi đi ngược lại: write() đẩy dữ liệu vào socket send buffer → kernel chia thành segment, thêm header → đẩy ra NIC. Việc có buffer ở giữa giải thích vì sao write trả về nhanh dù mạng chậm (dữ liệu mới vào buffer, chưa thật sự gửi xong).

6. ⭐ SSH hoạt động thế nào — và vì sao key an toàn

Module 07 dạy bạn dùng SSH key; giờ ta hiểu vì sao nó an toàn. SSH kết hợp hai loại mã hoá, mỗi loại cho một việc:

Mã hoá đối xứng (symmetric)

Một khoá chung để cả mã hoá lẫn giải mã. Rất nhanh → dùng để mã hoá toàn bộ dữ liệu phiên. Nhược điểm: hai bên phải có cùng khoá mà không được để lộ khi trao đổi.

Mã hoá bất đối xứng (asymmetric)

Cặp khoá public + private. Cái này mã hoá thì chỉ cái kia giải được. Chậm hơn → dùng cho thiết lập & xác thực. Đây là nền của SSH key.

Ba pha: dựng khoá phiên bí mật → xác minh server thật → chứng minh danh tính client. Sau đó toàn bộ phiên được mã hoá đối xứng.

Diễn giải ba pha:

  • Pha 1 — Key exchange: client và server dùng thuật toán Diffie–Hellman để cùng tính ra một khoá đối xứng bí mật chung. Điều kỳ diệu: dù kẻ nghe lén thấy toàn bộ trao đổi, nó vẫn không suy ra được khoá đó. Từ đây, mọi dữ liệu được mã hoá đối xứng (nhanh).
  • Pha 2 — Xác thực server: server chứng minh nó là chính nó bằng host key. Lần đầu kết nối, SSH hỏi bạn xác nhận và lưu vào ~/.ssh/known_hosts. Lần sau nếu host key khác đi → SSH cảnh báo gắt ("REMOTE HOST IDENTIFICATION HAS CHANGED") vì có thể là tấn công man-in-the-middle (kẻ giả làm server).
  • Pha 3 — Xác thực client bằng public-key: server gửi một "thử thách" ngẫu nhiên; client ký nó bằng private key; server kiểm chữ ký bằng public key đã có trong authorized_keys (Module 07). Chữ ký đúng = chứng minh client giữ private key tương ứng.
Vì sao gửi public key khắp nơi vẫn an toàn

Mấu chốt: private key không bao giờ rời máy bạn và không bao giờ được truyền đi — kể cả lúc xác thực. Client chỉ gửi một chữ ký; từ chữ ký không thể tái tạo private key. Vì vậy public key có thể công khai thoải mái (đặt lên mọi server). Đây là toàn bộ lý do SSH key vừa tiện vừa an toàn hơn mật khẩu (mật khẩu phải gửi đi và có thể bị bắt/đoán). Cùng nguyên lý bất đối xứng này vận hành HTTPS/TLS — khi bạn curl https:// hay git push, một cái bắt tay tương tự đang bảo vệ dữ liệu.

Độ trễ vs thông lượng — tối ưu truyền dữ liệu lớn

Hai khái niệm hay nhầm: latency (độ trễ — thời gian một gói đi-về, vd 80ms tới region khác) và throughput (thông lượng — bao nhiêu MB/s). Truyền 1 file 100GB: throughput quyết định. Truyền 1 triệu file tí hon: latency giết bạn (mỗi file tốn vài vòng khứ hồi). Đây là lý do rsync (gộp, nén, một kết nối) thắng copy từng file, vì sao nên gom file nhỏ trước khi truyền (Module 10 — small files), và vì sao đặt compute gần data (cùng region) quan trọng. rsync chạy trên nền SSH nên thừa hưởng toàn bộ mã hoá ở trên — bạn vừa nhanh vừa an toàn.

Container bên trong: namespaces & cgroups

Module 11 dạy bạn dùng Docker; module này vén màn bí mật: container không phải máy ảo, không có phép thuật — nó chỉ là một tiến trình Linux bình thường bị "lừa" rằng nó cô đơn trên máy, nhờ ba công nghệ kernel bạn đã gặp rải rác: namespaces (cô lập tầm nhìn), cgroups (giới hạn tài nguyên), và overlayfs (gói filesystem theo lớp). 1. Sự thật trần trụi về container

Nếu bạn chạy docker run python rồi mở một terminal khác trên host và gõ ps aux, bạn sẽ thấy tiến trình python đó — như một tiến trình bình thường của host. Không có "máy con", không có hypervisor. Container chỉ là góc nhìn bị bóp méo của một tiến trình thường.

Container = process thường + namespaces + cgroups + rootfs riêng

• Namespaces giới hạn tiến trình thấy gì (nó tưởng chỉ có mình nó, mạng riêng, hệ thống file riêng).
• cgroups giới hạn tiến trình dùng bao nhiêu (CPU, RAM, I/O).
• Root filesystem riêng (từ image, qua overlayfs) cho nó một "/" riêng với bộ thư viện riêng.
Đó là toàn bộ. Docker chỉ là công cụ dàn dựng ba thứ này một cách tiện lợi.

Vì sao container nhẹ hơn VM (nhắc lại Module 11)

VM ảo hoá cả phần cứng và chạy một kernel riêng đầy đủ → nặng GB, khởi động hàng chục giây. Container dùng chung kernel của host (chỉ thêm cô lập ở mức tiến trình) → nhẹ MB, khởi động trong mili-giây. Cái giá: vì chung kernel, container không cô lập mạnh bằng VM (xem mục bảo mật bên dưới) và phải chạy cùng loại kernel (đó là lý do container Linux không chạy native trên Windows mà cần một VM Linux ẩn bên dưới).

Namespaces lo "thấy gì", còn cgroups (control groups) lo "dùng bao nhiêu". cgroups cho phép kernel giới hạn, ưu tiên và đo đếm tài nguyên của một nhóm tiến trình. Đây là cơ chế đằng sau docker run --memory và --cpus.

Khi bạn đặt --memory=8g, kernel tạo một cgroup giới hạn 8GB cho container đó. Nếu tiến trình bên trong vượt ngưỡng, OOM killer ra tay trong phạm vi cgroup đó (không đụng phần còn lại của host) — thường giết PID 1 → container chết với trạng thái OOMKilled. 4. OverlayFS & lớp image — vì sao build có cache

Làm sao một image chứa cả "hệ điều hành con" mà chỉ vài chục MB, và build lại nhanh? Bí mật là union/overlay filesystem: hệ thống file của container được xếp chồng từ nhiều lớp chỉ-đọc cộng một lớp ghi mỏng ở trên cùng.

Mỗi lệnh trong Dockerfile tạo một lớp chỉ-đọc. Container thấy "tất cả gộp lại" cộng một lớp ghi riêng trên cùng.

Cơ chế overlayfs: các lớp dưới là lowerdir (chỉ-đọc), lớp trên là upperdir (ghi được). Container thấy bản hợp nhất (merged). Khi container ghi vào một file vốn ở lớp dưới, overlayfs sao chép file đó lên lớp ghi rồi mới sửa — gọi là copy-up (giống copy-on-write ở Module 14, nhưng ở tầng file). Lớp dưới không bao giờ bị đổi → nhiều container dùng chung các lớp image (tiết kiệm đĩa & RAM cache khổng lồ).

Đây là lý do thứ tự dòng Dockerfile quyết định tốc độ build (khép vòng Module 11)

Docker cache theo từng lớp và tái dùng lớp nếu lệnh + đầu vào không đổi. Quan trọng: khi một lớp thay đổi, MỌI lớp sau nó phải build lại. Vì code thay đổi liên tục còn requirements.txt ít đổi, đặt COPY requirements.txt + RUN pip install trước COPY . . giúp: sửa code → chỉ lớp cuối build lại, lớp cài thư viện (nặng nhất) được tái dùng từ cache → build trong vài giây. Đây không phải "mẹo vặt" mà là hệ quả trực tiếp của kiến trúc lớp overlayfs. Tương tự, mỗi RUN tạo một lớp → gộp các lệnh liên quan bằng && và dọn cache trong cùng lớp (rm -rf /var/lib/apt/lists/*) để image nhỏ gọn.

5. Capabilities & seccomp — bẻ nhỏ quyền root

Trong mô hình cổ điển, root (Module 03) có toàn bộ đặc quyền — quá rủi ro cho container. Linux chia quyền của root thành ~40 mảnh nhỏ gọi là capabilities (vd CAP_NET_BIND_SERVICE = bind port <1024, CAP_SYS_ADMIN = nhiều quyền quản trị). Docker mặc định chỉ cấp cho container một tập con an toàn, bỏ bớt các capability nguy hiểm.

  • Capabilities: giảm thiệt hại nếu container bị chiếm — root trong container không bằng root thật. Bỏ thêm bằng --cap-drop, thêm bằng --cap-add.
  • seccomp: bộ lọc giới hạn những system call (Module 13) container được phép gọi — chặn các syscall hiếm/nguy hiểm, thu hẹp bề mặt tấn công vào kernel.
Container KHÔNG phải ranh giới bảo mật tuyệt đối

Vì mọi container chia sẻ cùng một kernel host, một lỗ hổng kernel có thể bị khai thác để "thoát" container (container escape) — điều gần như không thể với VM (có kernel riêng). Hệ quả thực tế cho MLOps: đừng chạy code không tin cậy trong container như thể nó hoàn toàn an toàn; với workload nhạy cảm/đa người thuê, cân nhắc thêm lớp cách ly mạnh hơn (gVisor, Kata Containers, hoặc VM riêng). Và nguyên tắc vàng: tránh --privileged (mở toang mọi capability), không chạy app dưới root trong container khi không cần (dùng chỉ thị USER trong Dockerfile), giữ kernel host được vá lỗi.

6. docker run thực sự làm gì — từng bước

Giờ ghép tất cả lại. Khi bạn gõ docker run -p 8080:80 -m 2g myimage, đại khái những việc sau diễn ra:

  1. Lấy image: nếu chưa có, kéo các lớp từ registry (Module 11), giải nén thành các lowerdir.
  2. Dựng filesystem: tạo overlayfs từ các lớp image + một lớp ghi mới → đây là "/" của container.
  3. Tạo namespaces: gọi clone() với các cờ để cấp cho tiến trình mới một bộ namespace (PID, mount, net, UTS, IPC...).
  4. Lập cgroups: tạo cgroup đặt giới hạn (2GB RAM ở trên) và đưa tiến trình vào.
  5. Cấu hình mạng: tạo network namespace, dựng cặp giao diện ảo (veth) nối container với mạng bridge của Docker, thiết lập NAT/port-forward cho -p 8080:80 (iptables).
  6. Chuyển root & chạy: dùng pivot_root để "/" trỏ vào overlayfs, áp seccomp/capabilities, rồi execve chương trình (CMD) — nó khởi động như PID 1 trong namespace.

Toàn bộ chỉ là tổ hợp các tính năng kernel bạn đã học ở Module 13–17. Docker chỉ là "nhạc trưởng" điều phối chúng qua một giao diện dễ dùng.

7. PID 1 trong container & bẫy tín hiệu — khép vòng Module 15

Đây là một trong những tri thức quan trọng nhất mà chỉ người hiểu cả tiến trình lẫn container mới nắm. Chương trình của bạn chạy như PID 1 trong PID namespace của container — nhưng PID 1 có hai trách nhiệm đặc biệt mà app thường KHÔNG được thiết kế để gánh:

Bẫy 1 — Không dọn zombie

PID 1 thật (init/systemd) có nhiệm vụ wait() nhận nuôi mọi orphan (Module 15). App thường (vd python app.py) làm PID 1 nhưng không làm việc này → zombie chất đống nếu app sinh tiến trình con.

Bẫy 2 — Nuốt tín hiệu

Kernel xử lý tín hiệu cho PID 1 đặc biệt: tín hiệu không có handler bị bỏ qua. Nếu app không cài handler SIGTERM, lệnh docker stop (gửi SIGTERM) sẽ bị lờ đi → Docker chờ hết grace period rồi SIGKILL → tắt cứng, mất dữ liệu.

Giải pháp chuẩn cho MLOps

• Dùng docker run --init (hoặc thêm tini/dumb-init làm entrypoint) — một init siêu nhẹ làm PID 1 thật: nó dọn zombie và chuyển tiếp tín hiệu xuống app của bạn. Hầu hết image production nên có.
• Trong code worker xử lý dữ liệu, luôn cài signal handler cho SIGTERM để tắt sạch sẽ (flush, commit, đóng kết nối — Module 15). Đây là điều phân biệt một pipeline production-grade với một script chạy tạm.
• Dùng exec form trong Dockerfile (CMD ["python","app.py"] chứ không CMD python app.py) để app chạy trực tiếp làm PID 1 và nhận được tín hiệu, thay vì bị bọc trong một shell nuốt mất tín hiệu.

4. Builtin vs lệnh ngoài — và vì sao cd phải là builtin

Khi bash thực thi một lệnh, có hai khả năng. Liên hệ trực tiếp Module 15 (fork/exec):

Lệnh ngoài (external)

ls, grep, python... là file thật trên đĩa. Bash fork ra tiến trình con rồi exec file đó (Module 15). Lệnh chạy trong tiến trình riêng.

Builtin (lệnh tích hợp)

cd, export, echo, read... được bash thực thi trong chính tiến trình shell, không fork.

Vì sao cd bắt buộc là builtin?

Thư mục làm việc hiện tại (cwd) là thuộc tính của tiến trình (Module 15 — nhớ /proc/PID/cwd). Nếu cd là lệnh ngoài, bash sẽ fork một tiến trình con, con đổi cwd của chính nó rồi chết — cwd của shell cha không hề đổi. Vô dụng! Nên cd phải là builtin để đổi cwd của chính tiến trình shell. Cùng lý do, export phải là builtin (đổi biến môi trường của shell, để truyền xuống các lệnh sau). Kiểm tra một lệnh là loại gì: type cd (→ "cd is a shell builtin") vs type ls (→ "/usr/bin/ls").

5. Subshell & bẫy "biến mất" — lỗi gây đau đầu nhất

Một subshell là một bản sao tiến trình con của shell (qua fork). Nó kế thừa mọi biến của cha, nhưng — đây là mấu chốt — thay đổi bên trong subshell KHÔNG quay ngược lên cha (vì là tiến trình riêng, không gian bộ nhớ riêng — Module 14/15).

Bash tạo subshell trong nhiều tình huống, một số rất bất ngờ:

  • Dấu ngoặc đơn ( ... ) (cố ý tạo subshell). Ngược lại, { ...; } chạy trong shell hiện tại.
  • Mỗi vế của một pipe A | B chạy trong subshell riêng (mặc định trong bash).
  • Command substitution $(...).
  • Lệnh chạy nền cmd &.
bẫy mất biến — và cách sửa
❌ SAI: pipe tạo subshell → biến count đổi trong subshell, mất khi quay ra count=0 cat data.csv | while read line; do count=$((count + 1)) đổi count CỦA SUBSHELL done echo "$count" in ra 0 (!!) — count của shell cha không đổi ✅ ĐÚNG: dùng redirect thay pipe → while chạy trong shell hiện tại count=0 while read line; do count=$((count + 1)) done < data.csv redirect, KHÔNG pipe → không subshell echo "$count" in đúng số dòng ✓ ✅ Cách khác: process substitution while read line; do ((count++)); done < <(grep ERROR app.log)

Mẫu cmd | while read ... rồi cập nhật biến bên trong là một trong những lỗi bash phổ biến nhất và khó phát hiện nhất (không báo lỗi, chỉ ra kết quả sai âm thầm). Giờ bạn hiểu gốc rễ: vế phải pipe là subshell. Cách sửa chuẩn: dùng redirect < file hoặc process substitution < <(cmd) thay vì pipe để vòng while chạy trong shell chính. Đây cũng là lý do var=$(echo x | ...) đôi khi cho kết quả lạ — mọi thứ trong $() là subshell.

6. Biến shell vs biến môi trường — khép vòng Module 06

Có hai loại "biến", khác nhau ở phạm vi truyền — và sự khác biệt nằm ở cơ chế exec (Module 15):

export = "đánh dấu để truyền qua exec"

Biến shell (vd x=5) chỉ tồn tại trong shell hiện tại; tiến trình con không thấy. Biến môi trường (vd export x=5) được kernel sao chép qua khi exec một chương trình mới → tiến trình con thấy nó (nhớ /proc/PID/environ ở Module 15). Đó là toàn bộ ý nghĩa của export: nó "nâng cấp" một biến shell thành biến môi trường để di truyền xuống con.

Hệ quả quan trọng: môi trường chỉ truyền một chiều, xuống dưới (cha → con). Một script con KHÔNG thể đổi biến môi trường của shell cha gọi nó (vì nó là tiến trình riêng). Muốn một script ảnh hưởng tới shell hiện tại (vd kích hoạt venv — Module 06), bạn phải source nó (source script.sh hay . script.sh) — source chạy nội dung trong shell hiện tại, không fork. Đây chính là lý do source .venv/bin/activate dùng source chứ không ./activate.

$PATH và cơ chế tra cứu lệnh

Khi gõ một lệnh không phải builtin, bash tìm file thực thi bằng cách duyệt từng thư mục trong $PATH theo thứ tự, lấy cái khớp đầu tiên. Để tăng tốc, bash ghi nhớ (hash) vị trí các lệnh đã tìm — nên nếu bạn vừa cài/di chuyển một lệnh mà shell "không thấy", chạy hash -r để xoá cache. Xem lệnh nào sẽ chạy: which python hoặc type -a python (liệt kê mọi bản trong PATH). Đây là lý do thứ tự thư mục trong PATH quan trọng — vì sao venv đặt .venv/bin lên đầu PATH để "ghi đè" python hệ thống (Module 06).

8. Giải phẫu set -euo pipefail

Giờ bạn đã đủ nền để hiểu chính xác "câu thần chú" ở Module 08 làm gì ở tầng cơ chế:

CờCơ chế thật sự

Vì sao bộ ba này là bắt buộc cho script dữ liệu

Pipeline ETL xử lý dữ liệu thật: một lỗi âm thầm (tải thiếu file, biến rỗng, một khâu pipe chết) có thể nạp dữ liệu hỏng vào kho mà không báo động — hậu quả nghiêm trọng và khó truy vết. set -euo pipefail biến triết lý "thà dừng sớm với lỗi rõ ràng còn hơn chạy tiếp với dữ liệu sai" thành cơ chế tự động. Kết hợp với trap 'cleanup' EXIT để luôn dọn dẹp (xoá file tạm, đóng kết nối) dù script thoát vì lỗi — đó là dấu ấn của một script production-grade.

6. OOM killer — khi process "tự nhiên biến mất"

Job Python chạy 3 tiếng rồi biến mất không một dòng log — 90% là OOM killer: kernel hết RAM, chọn process điểm cao nhất (thường chính là job ngốn RAM của bạn) và kill -9 thẳng tay, không cho cơ hội nói lời cuối. Bằng chứng nằm ở kernel log: dmesg -T | grep -i "out of memory" hoặc journalctl -k | grep -i oom — thấy dòng "Killed process 12345 (python3)" là án đã rõ. Trong container, phiên bản của nó là OOMKilled / exit code 137 khi chạm memory limit của cgroup (module 18 Container đã dạy phần cgroup) — tra bằng docker inspect hoặc kubectl describe pod. Thuốc theo thứ tự rẻ→đắt: giảm batch size / stream thay vì gom (khoá 21), nâng memory limit, spill xuống đĩa (khoá 19 M21), đổi engine (khoá 18 M18).

Module 22 — Tự kiểm tra

Quiz tự kiểm tra — 10 câu trọng tâm

Mỗi câu là một tình huống bạn sẽ gặp thật khi vận hành pipeline. Hãy tự chọn đáp án và giải thích được vì sao trước khi mở phần đáp án. Sai câu nào, quay lại module tương ứng ôn lại.

Câu 1 — File descriptor & redirection (Module 04)

Bạn chạy python etl.py > etl.log 2>&1, đồng nghiệp chạy python etl.py 2>&1 > etl.log. Khác biệt là gì?

  1. Không khác gì, hai lệnh tương đương
  2. Lệnh thứ nhất gộp cả stdout lẫn stderr vào file; lệnh thứ hai stderr vẫn đổ ra màn hình
  3. Lệnh thứ hai gộp cả hai; lệnh thứ nhất chỉ ghi stdout
  4. Cả hai đều lỗi cú pháp vì 2>&1 phải đứng đầu lệnh
Đáp án

B. Shell xử lý redirection từ trái sang phải. Ở lệnh thứ hai, lúc 2>&1 được thực hiện thì fd 1 vẫn trỏ vào terminal, nên stderr "chụp" đích là terminal; sau đó fd 1 mới đổi sang file — stderr không đi theo.

Câu 2 — Quyền trên thư mục (Module 03)

Thư mục /data/raw có quyền drw-r--r-- và bạn là owner. Chuyện gì xảy ra khi cd /data/raw?

  1. Vào bình thường vì owner có quyền đọc
  2. Bị Permission denied vì thư mục thiếu bit x
  3. Vào được nhưng ls bên trong sẽ fail
  4. Chỉ root mới cd được vào thư mục dưới /data
Đáp án

B. Với thư mục: r = liệt kê tên file, x = quyền "đi xuyên qua" (traverse). Thiếu x thì không cd và không truy cập được bất kỳ file nào bên trong, dù bạn là owner. Sửa: chmod u+x /data/raw.

Câu 3 — Page cache & available (Module 05/14)

free -h trên server ETL: free chỉ còn 300MB, buff/cache 25GB, available 24GB. Có cần báo động hết RAM?

  1. Có — cần restart server để giải phóng RAM ngay
  2. Có — phải thêm swap gấp trước khi OOM
  3. Không — buff/cache là page cache, kernel tự thu hồi khi ứng dụng cần; con số cần nhìn là available
  4. Không kết luận được nếu chưa chạy top
Đáp án

C. Linux dùng RAM rảnh để cache dữ liệu đĩa (page cache) — đó là tính năng, không phải rò rỉ. Khi tiến trình cần RAM, kernel thu hồi cache gần như miễn phí. available ≈ lượng RAM thực sự còn cấp phát được.

Câu 4 — Tín hiệu (Module 05)

Vì sao script deploy nên dừng service bằng kill PID (SIGTERM) và chỉ dùng kill -9 làm phương án cuối?

  1. SIGKILL chạy chậm hơn SIGTERM
  2. SIGTERM cho tiến trình cơ hội dọn dẹp (flush buffer, đóng kết nối, xoá file tạm); SIGKILL không thể bị bắt nên tiến trình chết ngay, dễ để lại dữ liệu dở dang
  3. SIGKILL cần quyền root còn SIGTERM thì không
  4. SIGTERM ép kernel giải phóng page cache trước khi tắt
Đáp án

B. Ứng dụng có thể bắt (trap/handle) SIGTERM để shutdown êm: commit/rollback transaction, ghi nốt log, đóng file. SIGKILL đi thẳng tới kernel, tiến trình không kịp làm gì — rủi ro file ghi dở, lock không nhả.

Câu 5 — find + xargs (Module 02/04)

Cần xoá hàng chục nghìn file .tmp cũ hơn 7 ngày trong /data/staging; một số tên file chứa khoảng trắng. Lệnh nào an toàn nhất?

  1. rm $(find /data/staging -name '*.tmp' -mtime +7)
  2. find /data/staging -name '*.tmp' -mtime +7 | xargs rm
  3. find /data/staging -name '*.tmp' -mtime +7 -print0 | xargs -0 rm
  4. ls /data/staging/*.tmp | xargs rm
Đáp án

C. Cặp -print0 / -0 dùng ký tự NUL làm dấu phân cách nên tên file chứa khoảng trắng/xuống dòng không bị tách nhầm thành nhiều tham số. Phương án A còn có thể vượt giới hạn độ dài dòng lệnh (argument list too long); D không lọc theo tuổi file.

Câu 6 — set -euo pipefail (Module 08)

Script có set -e. Dòng psql -f load.sql | tee load.log: psql fail nhưng script vẫn chạy tiếp và báo "thành công". Thiếu gì?

  1. set -u
  2. set -x
  3. set -o pipefail — không có nó, exit code của pipeline là của lệnh CUỐI (tee = 0)
  4. trap ... EXIT
Đáp án

C. Mặc định bash lấy exit code của lệnh cuối pipeline, nên tee thành công che mất lỗi của psql và set -e không kích hoạt. pipefail khiến pipeline fail nếu bất kỳ mắt xích nào fail. Còn set -u bắt lỗi dùng biến chưa khai báo (ví dụ gõ nhầm tên biến).

Câu 7 — Cron (Module 09)

Script backup chạy tay hoàn hảo, nhưng qua cron thì fail với command not found: aws. Nguyên nhân khả dĩ nhất?

  1. User của cron không có quyền thực thi aws
  2. Cron chạy với môi trường tối giản: PATH thường chỉ có /usr/bin:/bin và không nạp ~/.bashrc — cần đường dẫn tuyệt đối hoặc khai báo PATH trong crontab
  3. Cú pháp 5 trường bị sai nên lệnh bị cắt cụt
  4. Cron không hỗ trợ script có gọi mạng ra ngoài
Đáp án

B. Đây là bẫy "chạy tay được mà cron thì không" kinh điển: cron không phải login shell, không có env của bạn. Cách chữa: dùng /usr/local/bin/aws (tìm bằng which aws), đặt PATH=... ở đầu crontab, và luôn redirect log để có bằng chứng.

Câu 8 — SSH & SIGHUP (Module 07)

Bạn SSH vào VM GPU, chạy python train.py, rớt Wi-Fi 5 phút, vào lại thấy job đã chết. Vì sao, và lần sau nên làm gì?

  1. Kernel OOM kill vì train tốn RAM; cần VM to hơn
  2. Phiên SSH đứt → shell gửi SIGHUP cho tiến trình con → job chết; lần sau chạy trong tmux (hoặc nohup ... &)
  3. VM cloud tự restart khi không có ai đăng nhập
  4. GPU driver ngắt khi mất kết nối mạng
Đáp án

B. Tiến trình chạy foreground thuộc phiên SSH; phiên chết kéo theo SIGHUP. tmux giữ phiên sống độc lập với kết nối — vào lại chỉ cần tmux attach là thấy job vẫn chạy nguyên trạng.

Câu 9 — Đĩa & inode (Module 10)

Pipeline fail với No space left on device nhưng df -h báo còn trống 45%. Bước kiểm tra tiếp theo hợp lý nhất?

  1. du -sh /* để tìm thư mục lớn nhất
  2. df -i — nghi cạn inode do hàng triệu file nhỏ (điển hình: thư mục staging sinh file liên tục)
  3. free -h — hết RAM nên không ghi được file
  4. Reboot server để hệ thống tự dọn /tmp
Đáp án

B. Mỗi file chiếm một inode; filesystem có số inode hữu hạn cấp lúc format. Cạn inode thì dù còn dung lượng byte vẫn không tạo thêm file được — lỗi trả về y hệt hết đĩa. df -i xác nhận, sau đó tìm ổ file nhỏ bằng find ... | wc -l theo từng thư mục.

Câu 10 — Namespaces & cgroups (Module 11/18)

Container Spark chết với exit code 137 dù host còn 40GB RAM trống. Cơ chế Linux nào đứng sau?

  1. Namespace PID cách ly nên container "không nhìn thấy" RAM của host
  2. cgroups giới hạn memory của container (ví dụ --memory 4g); vượt ngưỡng → OOM killer của cgroup gửi SIGKILL (137 = 128 + 9)
  3. Docker daemon hết file descriptor nên đóng container
  4. seccomp chặn syscall cấp phát bộ nhớ của JVM
Đáp án

B. Phân vai rõ: namespaces cách ly "cái nhìn" (PID, mount, network), còn cgroups giới hạn "tài nguyên" (CPU, RAM, IO). Container vượt memory limit của cgroup sẽ bị OOM kill bất kể host còn bao nhiêu RAM. Kiểm chứng bằng docker inspect (OOMKilled: true) hoặc dmesg.
