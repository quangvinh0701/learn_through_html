Module 01 — Nền tảng

WebAPI là gì & tư duy thiết kế đúng

WebAPI (Web Application Programming Interface) là một giao diện chương trình mà hai hệ thống dùng để nói chuyện với nhau qua web — thường là qua giao thức HTTP. Hiểu rộng hơn, nó không chỉ là "một URL trả về JSON": nó là khế ước giữa người cung cấp dịch vụ và người dùng, nơi mọi quyết định về bảo mật, hiệu năng, versioning, schema đều được đóng đinh từ đầu. Module này dựng nền tảng tư duy: phân biệt rõ WebAPI với "URL chạy được", hiểu vai trò của nó trong hệ thống, và định hình nguyên tắc thiết kế xuyên suốt khoá học.

1. WebAPI là gì & vì sao quan trọng

Một WebAPI chuẩn có bốn đặc điểm phân biệt với "một URL trả về dữ liệu":

① Có contract rõ ràng

Schema input/output được mô tả (OpenAPI, JSON Schema). Người dùng không phải đoán, không phải đọc source code của bạn để biết API làm gì.

② Stateless

Mỗi request độc lập, server không nhớ state giữa hai lần gọi (trừ khi qua token, cookie, hoặc shared store). Cho phép scale ngang dễ dàng.

③ Có auth & rate limit

Không phải "ai cũng gọi được". Có cơ chế xác thực (API key, JWT, OAuth2) và giới hạn tải (rate limit, quota).

④ Có thể quan sát

Có log, metric, trace. Khi hỏng ở production, bạn biết request nào, endpoint nào, tại sao chậm — không phải đoán mò.

WebAPI

Một tập các endpoint HTTP được mô tả bằng một contract cố định (URL, method, headers, body schema, status code), cho phép hai hệ thống trao đổi dữ liệu/dịch vụ qua web. WebAPI hiện đại thường trả về JSON, đôi khi XML/protobuf; bản thân format không quyết định — contract & cách vận hành mới quyết định nó có phải "WebAPI" hay chỉ là "một HTTP endpoint chạy được".

Quy tắc vàng

Đừng gọi thứ gì cũng là "API". Một script Python trả về JSON khi cầm vào URL là một function exposed; một WebAPI đúng nghĩa phải có contract + auth + observability + versioning + error semantics. Trong phỏng vấn & trong CV, phân biệt hai thứ này rất quan trọng — nó cho thấy bạn hiểu sâu, không chỉ biết dùng framework.

2. Các thành phần của một WebAPI

Một WebAPI production có ít nhất 7 lớp. Bỏ lớp nào, lớp đó sẽ bite lại khi scale hoặc khi audit:

LớpVai tròCông cụ điển hình

ApplicationBusiness logic, validation, routingFastAPI, Flask, Express, Spring Boot, Gin
AuthVerify token, scope, identityOAuth2, JWT, API Key, mTLS
Data accessORM, query, transactionSQLAlchemy, SQLModel, Tortoise, Prisma
StoragePostgres, MySQL, Redis, S3Postgres, MySQL, MongoDB, MinIO

Phân biệt rõ: Edge auth vs App auth

Edge (gateway) thường verify token trước khi request tới app — tiết kiệm CPU cho app, đẩy lùi request xấu sớm. Nhưng app vẫn phải tự verify lại ở business logic vì: (1) edge có thể bị miss-config; (2) một số endpoint có logic auth phức tạp (per-resource permission) mà edge không làm hộ được. Quy tắc: edge auth để chặn sớm, app auth để chặn đúng.

3. API contract — khế ước giữa hai bên

Contract là thứ biến một endpoint thành một API. Nó gồm: URL, method, headers, body schema (input), response schema (output), error codes, và ngữ nghĩa (idempotency, caching, side-effect).

OpenAPI / Swagger

Chuẩn de-facto để mô tả REST API. File YAML/JSON sinh được docs tương tác, client SDK, và contract test. FastAPI auto-generate OpenAPI từ Pydantic models — một trong những lý do chính người ta chọn nó.

AsyncAPI

"OpenAPI cho message-driven" — mô tả event, channel, message schema. Dùng cho Kafka, WebSocket, MQTT. Khoá học này tập trung REST nên AsyncAPI chỉ nhắc sơ.

Contract != implementation

Contract là hứa hẹn công khai. Một khi đã công bố, đổi nó = breaking change = kéo theo versioning. Nguyên tắc: mọi thay đổi schema phải qua CI test (contract test chạy consumer code dựa trên OpenAPI của bạn), và breaking change phải tăng version theo semver (MAJOR) hoặc đổi path (v1 → v2). FastAPI hỗ trợ nhiều version cùng lúc dễ dàng — đừng tiếc versioning.

Module 02 — Kiến trúc

API Architecture Styles — REST, GraphQL, gRPC, SOAP, Webhook

Trước khi viết một endpoint, phải chọn phong cách kiến trúc. Mỗi phong cách có cách tổ chức URL, schema, semantics riêng — và đẻ ra những vấn đề rất khác nhau về cache, versioning, auth. Module này so sánh 5 phong cách phổ biến nhất, chỉ ra khi nào dùng cái nào, và giải thích vì sao REST vẫn là lựa chọn mặc định cho đa số data API — trong khi các phong cách khác tỏa sáng ở những ngách cụ thể.

1. Bốn tiêu chí chọn architecture style

Chọn style không phải theo trend. Bốn câu hỏi bắt buộc trả lời trước khi chốt:

  1. Client là ai? Web frontend, mobile app, server-to-server, browser script? Mỗi loại có ràng buộc khác nhau về payload size, latency, schema flexibility.
  2. Data graph thế nào? Resource riêng lẻ (orders, users) hay graph phức tạp (user → orders → items → reviews)?
  3. Độ trễ & throughput mục tiêu? 10 RPS hay 100k RPS? Latency 100ms hay 5ms?
  4. Hệ sinh thái & công cụ? Team của bạn thạo gì? Có thư viện client, code-gen, monitoring chưa?
Architecture style

Một tập quy ước về cách tổ chức URL, method, schema, semantics, error, caching. REST, GraphQL, gRPC, SOAP là các style khác nhau — không phải "framework". Chọn style là chọn bộ quy tắc mà mọi endpoint phải tuân theo; chọn framework (FastAPI, Express) là chọn công cụ để hiện thực style đó.

2. REST — resource-oriented, chiếm 80% WebAPI

REST (Representational State Transfer) — Roy Fielding, 2000. Một resource có một URL, các method HTTP (GET/POST/PUT/PATCH/DELETE) là các hành động trên resource. REST không phải "dùng JSON" — nó là một tập ràng buộc về stateless, cache, uniform interface.

/ordersGETLiệt kê orders✓
/ordersPOSTTạo order mới✗ (trừ khi có idempotency key)
/orders/123GETLấy order 123✓
/orders/123PUTThay thế toàn bộ order 123✓
/orders/123PATCHCập nhật một phần order 123✗ (mặc định) — JSON Merge Patch (RFC 7386) thì idempotent; JSON Patch (RFC 6902) nói chung không
/orders/123DELETEXoá order 123✓

REST mạnh ở

CRUD thuần, public API, browser/client đa dạng, cache dễ (HTTP cache), debug dễ (URL + method đọc được), hệ sinh thái OpenAPI rộng.

REST yếu ở

Over-fetching (GET /orders kéo cả review không cần), under-fetching (cần 3 request để lấy user+orders+items), schema evolution khó với nhiều client cũ.

Quy ước đặt URL REST

URL = danh từ (resource), method = động từ (action). Tránh /createOrder hay /getUserById?id=123 — chúng vi phạm tinh thần REST và khó cache. Dùng POST /orders + GET /orders/123. Nested resource: /orders/123/items (acceptable, đừng lồng quá 2-3 tầng).

3. GraphQL — client định hình response

GraphQL (Facebook, 2015) cho phép client chỉ định chính xác field cần lấy trong một query duy nhất. Server có một endpoint duy nhất (POST /graphql), client gửi query mô tả shape mong muốn.

graphql-query
Một query kéo user + orders + items trong MỘT round-trip — không over/under-fetch query { user(id: 123) { name email orders(status: "paid") { id total items { name qty price } } } }

GraphQL mạnh ở

Client nhiều, mỗi client cần shape khác (mobile vs web). Frontend thay đổi liên tục mà không muốn đụng backend. Graph phức tạp, cần một request cho cả cây.

GraphQL yếu ở

Cache phức tạp hơn REST (một endpoint, cần persisted query hoặc CDN riêng). File upload khó. N+1 query là bẫy kinh điển (cần DataLoader). Không tận dụng HTTP cache thuần.

Dùng GraphQL khi nào

Bạn có nhiều client độc lập (mobile + web + partner) cần shape khác nhau từ cùng dữ liệu, và bạn chấp nhận đánh đổi cache/complexity. Với data API nội bộ (server-to-server), REST thường thắng vì đơn giản hơn. Với khoá này tập trung REST + FastAPI — GraphQL nhắc sơ để biết "có cái khác".

4. gRPC — schema binary, latency thấp

gRPC (Google, 2015) dùng Protocol Buffers (protobuf) để mô tả schema, sinh code client/server cho nhiều ngôn ngữ, giao tiếp qua HTTP/2 binary. Rất phổ biến trong microservice internal.

grpc-proto
Định nghĩa service bằng .proto — sinh code tự động cho client & server syntax = "proto3"; service OrderService { rpc GetOrder(OrderRequest) returns (OrderResponse); rpc ListOrders(ListRequest) returns (stream OrderResponse); // streaming } message OrderRequest { int64 id = 1; } message OrderResponse { int64 id = 1; string status = 2; double total = 3; }

gRPC mạnh ở

Microservice nội bộ, latency cực thấp (binary, HTTP/2 multiplexing), streaming 2 chiều, code-gen cho nhiều ngôn ngữ, contract strongly-typed.

gRPC yếu ở

Không gọi được từ browser thuần (cần grpc-web proxy). Debug khó hơn REST (nhìn binary). Hệ sinh thái tool kém rộng hơn REST. Schema evolution phải tuân thủ protobuf rules.

Khi nào nên gRPC

Khi bạn xây microservice internal cần throughput cao, latency thấp, strongly-typed contract giữa các service do một team quản. Với public API cho đối tác bên ngoài, REST vẫn thắng vì ai cũng gọi được. Với khoá này, nhắc gRPC để biết "có cái khác" và đủ để đọc .proto khi gặp.

5. SOAP & Webhook — không quên

SOAP (Simple Object Access Protocol) — XML, wsdl, "nặng nề" nhưng strongly-typed, gặp nhiều trong hệ thống doanh nghiệp cũ, ngân hàng, B2B. Có WS-Security (sign, encrypt), reliable messaging, transaction. Khi gặp SOAP, bạn dùng zeep (Python) hoặc suds; FastAPI không hỗ trợ SOAP trực tiếp — thường phải có proxy.

Webhook — server đẩy sự kiện sang client qua HTTP POST khi có thay đổi. Client đăng ký URL, server gọi URL đó khi event xảy ra. Ngược với REST polling: server chủ động. Dùng cho payment notification, CI hook, third-party event.

webhook-basics
Provider gọi URL bạn đăng ký. Bạn phải verify signature + xử lý retry POST /your/webhook X-Signature: sha256=abc... # HMAC của body, secret shared X-Event-Type: order.paid {"order_id": 123, "amount": 99.00} Verify bằng HMAC-SHA256 với secret, return 2xx trong <5s, xử lý nặng async
Webhook = pull ngược

Webhook thực ra là API do client cung cấp cho server gọi. Nghĩa là khi build webhook receiver, bạn cũng cần contract rõ (event types, payload schema, signature scheme), auth (HMAC), idempotency (event id), và timeout/retry semantics. Module 4 và Module 10 sẽ dùng chính những pattern này.

Module 03 — Giao thức

HTTP & REST chuẩn — bộ quy tắc bạn phải thuộc

HTTP không chỉ là "gửi request nhận response". Nó có phương thức (verb) với ngữ nghĩa khác nhau, status code phân loại lỗi, header kiểm soát cache/auth/content, và semantics (idempotency, safety) quyết định retry có an toàn không. Module này là "luật chơi" mà mọi REST API phải theo — để client code một lần dùng được ở nhiều API, và để tool (gateway, cache, monitoring) hoạt động chuẩn.

1. HTTP request & response anatomy

Một HTTP request có 4 phần; response cũng vậy:

Request

POST /api/orders HTTP/1.1 ← request line (method, path, version)
Host: api.example.com
Authorization: Bearer eyJ...
Content-Type: application/json
X-Request-Id: 01HXYZ... ← headers

{"items": [...]} ← body (cho POST/PUT/PATCH)

Response

HTTP/1.1 201 Created ← status line
Content-Type: application/json
Location: /api/orders/123
X-Request-Id: 01HXYZ... ← headers

{"id": 123, "status": "pending"} ← body

Đọc HTTP bằng curl

Curl là cách nhanh nhất để "xem" HTTP. Thêm -i để hiện headers, -v để xem cả TLS handshake, -X METHOD để đổi method, -H 'Key: Value' để thêm header. Dùng --trace-ascii - để dump toàn bộ request/response khi debug.

Safe method

Method không được gây ra side-effect trên server. GET, HEAD, OPTIONS là safe. Server có thể prefetch, crawler có thể gọi thoải mái. Lạm dụng GET để thay đổi state là phản mẫu: GET /delete?id=123 là thảm hoạ vì prefetch/CDN có thể xoá nhầm.

Idempotent method

Gọi 1 lần hay 100 lần với cùng input cho cùng kết quả ở trạng thái server. DELETE /orders/123 lần 1 xoá, lần 2 trả 404 — vẫn idempotent vì trạng thái cuối cùng giống nhau. Cho phép client retry an toàn khi mạng chập chờn. POST không idempotent theo nghĩa này — phải dùng idempotency key (mục 5).

POST tạo charge, tạo order, tạo user. Mạng chập chờn, client retry → 2 charge, 2 order. Khắc phục: Idempotency Key (Stripe đặt ra).

1. Authentication vs Authorization

Authentication (AuthN)

Xác minh "bạn là ai". Trả lời: token này có đúng chủ sở hữu là user X không?

Authorization (AuthZ)

Xác minh "bạn được làm gì". Trả lời: user X có quyền orders:read không?

Phân biệt rõ

AuthN trả lời WHO; AuthZ trả lời WHAT CAN THEY DO. Một API có thể AuthN đúng (đúng user) nhưng AuthZ sai (user đó không được xoá order của user khác). Hai việc cần hai lớp check riêng; đừng trộn.

2. API Key — đơn giản, cho server-to-server

Một chuỗi ngẫu nhiên dài gắn với tài khoản. Client gửi kèm mỗi request; server tra cứu → biết ai gọi. Dùng cho server-to-server, internal service, đối tác B2B.

api-key-header
Gửi key qua header. Có thể dùng Authorization: Bearer <key> cho đồng nhất với JWT GET /api/orders Authorization: Bearer sk_live_YOUR_API_KEY_HERE X-API-Key: sk_live_YOUR_API_KEY_HERE # hoặc header riêng

Mạnh

Đơn giản, dễ revoke (xoá key trong DB), dễ rotate, dễ giới hạn scope. Stripe, GitHub, AWS đều dùng.

Yếu

Lộ key = lộ quyền. Không phù hợp browser/mobile vì khó giấu (phải gửi qua HTTPS, không có refresh). Không có expiry built-in.

Best practice API key

(1) Không hard-code trong source; dùng env/secret manager. (2) Mỗi môi trường một key riêng. (3) Log key đã hash, không log key thô. (4) Có thể scope key (chỉ đọc, chỉ ghi) để giảm thiệt hại khi lộ. (5) Rate limit theo key chứ không chỉ theo IP.

3. Basic Auth

Gửi username:password base64 qua header. Rất đơn giản nhưng không an toàn nếu không có HTTPS và không nên dùng cho production. Còn dùng cho: internal tool, admin panel trong mạng nội bộ, test/dev. Khi học xong JWT/OAuth2, bạn sẽ hiếm khi cần Basic.

6. mTLS & các cơ chế nâng cao

mTLS (mutual TLS): cả client và server đều có certificate, "bắt tay" hai chiều. Dùng cho service mesh (Istio, Linkerd), API nội bộ giữa các service cực nhạy cảm. Rất an toàn, nhưng cần PKI quản lý certificate.

SAML / OIDC: SSO cho enterprise. OIDC (OpenID Connect) là lớp identity trên OAuth2 — thêm id_token chứa thông tin user.

Signed request: AWS sigv4 — ký cả request (method, path, body, timestamp) bằng secret key. Chống replay attack. Dùng cho AWS API, internal service high-security.

Bảng chọn cơ chế

API public, mobile/web app: OAuth2 + PKCE. API nội bộ server-to-server: Client Credentials hoặc mTLS. Webhook từ third-party: HMAC signature. Service mesh: mTLS. Single page app đơn giản: JWT trong httpOnly cookie + CSRF token. Không có cơ chế nào "tốt nhất" — chọn theo threat model.

6. ⭐ Dependency Injection — trụ cột của FastAPI

Dependency injection (DI) là cách FastAPI giúp bạn tách phần dùng chung (DB session, current user, config) khỏi handler. Một function def get_db() trả session, một function def get_current_user(token) trả user — handler chỉ khai báo nó cần gì.

deps
from typing import Annotated from fastapi import Depends, HTTPException, status from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials bearer = HTTPBearer() # OpenAPI: security scheme def get_db(): db = SessionLocal() try: yield db finally: db.close() def get_current_user( creds: Annotated[HTTPAuthorizationCredentials, Depends(bearer)], ) -> User: user = decode_jwt(creds.credentials) if not user: raise HTTPException(401, "Invalid token") return user @app.get("/me") def me(user: Annotated[User, Depends(get_current_user)], db: Annotated[Session, Depends(get_db)]): return db.query(Order).filter(Order.user_id == user.id).all()
Annotated[..., Depends(...)]

Dùng Annotated để khai báo dependency một lần, dùng nhiều nơi. Tránh lặp user: User = Depends(get_current_user) ở mỗi handler — tạo type alias CurrentUser = Annotated[User, Depends(get_current_user)] rồi dùng user: CurrentUser. Ngắn gọn & typed.

Quy tắc

FastAPI chạy handler def (sync) trong threadpool — blocking I/O ở đó không giết event loop, chỉ tốn một thread trong pool. Nguy hiểm thật sự là gọi blocking call bên trong async def: nó block event loop → toàn bộ server đứng. Hai cách khắc phục: (1) dùng thư viện async; (2) chạy blocking work trong run_in_threadpool. 4. Union, discriminator & polymorphism

Khi một field có thể nhận nhiều kiểu khác nhau (vd: payment method = card | bank_transfer | e_wallet), dùng Union + discriminator để Pydantic chọn schema theo một field "phân loại".

Discriminator cứu OpenAPI

Khi discriminator được khai báo, OpenAPI sinh oneOf chuẩn — client generator (openapi-generator) tạo union type đúng trong TypeScript/Go. Không có discriminator, Union trong OpenAPI chỉ là anyOf mơ hồ — generator sẽ sinh code khó dùng.

6. Validate ở edge vs validate ở business

Edge (Pydantic)

Validate shape: kiểu, format, range, required. Chạy trước khi vào handler. Không I/O. Test cực nhanh. Ví dụ: email đúng format, qty > 0, items không rỗng.

Business (function)

Validate state: order đã shipped chưa, user đã tồn tại, stock còn hàng. Cần DB / external service. Test chậm hơn. Ví dụ: kiểm tra order.status != "shipped" trước khi cho update.

Đừng để Pydantic gọi DB

Tránh viết validator kiểu @field_validator("email") def check_email(self, v): return db.query(User).filter_by(email=v).first() is None — chậm, khó test, lock DB connection. Tách: Pydantic check format; handler gọi user_service.exists_by_email().

2. ⭐ Liveness — "process còn sống?"

Liveness phải RẤT RẤT nhẹ. Nếu có thể, đừng check gì ngoài việc trả 200.

liveness
@app.get("/health/live", tags=["health"]) def liveness(): return {"status": "alive"} # 200 OK, không query, không log
Liveness phải luôn trả 200 trừ khi process thật sự chết

Đừng check DB ở liveness. DB down (5 phút) + liveness fail = restart pod không giúp gì (DB vẫn down sau restart) + mất request đang xử lý + tốn CPU cold start. Chỉ trả 200 khi process vẫn đang nhận request và trả response.

3. ⭐ Readiness — "sẵn sàng nhận traffic?"

Readiness check được phép gọi dependency. Khi fail, Kubernetes bỏ pod khỏi service endpoint (không gửi traffic mới), nhưng KHÔNG restart.

readiness
import asyncio from fastapi.responses import JSONResponse @app.get("/health/ready", tags=["health"]) async def readiness(): checks = {} overall_ok = True # Check DB với timeout ngắn try: async with db_session() as s: await asyncio.wait_for(s.execute(text("SELECT 1")), timeout=2.0) checks["db"] = "ok" except Exception as e: checks["db"] = f"fail: {e!s}" overall_ok = False # Check Redis try: await redis.ping() checks["redis"] = "ok" except Exception as e: checks["redis"] = f"fail: {e!s}" overall_ok = False return JSONResponse( status_code=200 if overall_ok else 503, content={"status": "ready" if overall_ok else "degraded", "checks": checks}, )
Quy tắc readiness

(1) Timeout ngắn (1-3s) — check không được block. (2) Song song nếu có nhiều dependency. (3) Trả 503 khi fail (không phải 200). (4) Không cache kết quả — mỗi lần check là check thật (Kubernetes sẽ check mỗi 5-10s). (5) Log khi check fail để có alert.

4. Startup — "đã init xong?"

Một số app cần thời gian init: load ML model, warm cache, chạy migration. livenessProbe.initialDelaySeconds là giải pháp tệ — phải đoán. Tốt hơn: dùng startupProbe với endpoint riêng.

6. ⭐ Đọc metric: RPS, p50/p95/p99, error rate

RPS / Throughput

Request per second. Cho biết hệ thống xử lý được bao nhiêu. Tăng user nhưng RPS không tăng = bottleneck đang giữ.

p50 / p95 / p99

p95 = 95% request có latency ≤ giá trị. p99 nhạy với "outlier". p50 là trung vị. Đừng chỉ nhìn average — user quan tâm p99.

Error rate

% 5xx. SLO thường < 0.1%. Tăng đột biến = cần check log/dependency.

Tại sao p99 quan trọng hơn avg

Average bị kéo lên bởi outlier — 1% request chậm 10s kéo average lên rất cao nhưng 99% còn lại nhanh. p99 cho bạn biết "1% tệ nhất" trải nghiệm thế nào. Đó là user than "app chậm". p99 < 500ms thường là mục tiêu khả thi cho read API.

Tình huống thực tế

Bối cảnh: Team launch data API mới, chạy Locust 1000 user. Kết quả: p50 = 80ms (tốt), p95 = 220ms (OK), p99 = 4.8s (rất tệ). Average báo 110ms — đẹp. Nhưng 1% user chờ gần 5 giây. Điều tra: một query GET /orders/{id} có full table scan khi id không có index. Caching cũng bị miss cho request đầu. Fix: thêm index, cache layer với TTL 30s, warm-up cache lúc startup. Sau fix, p99 giảm còn 380ms. Bài học: average che giấu vấn đề, p99 phơi bày nó.

8. Guideline & checklist

Trước khi chạy test:

  • Có SLO rõ (latency p95/p99, RPS, error rate).
  • Test trên staging với data shape tương đương production (≥ 30% size).
  • Baseline cũ để so sánh (commit trước vs sau).
  • Warm-up: chạy 1-2 phút tải nhẹ trước khi đo.

Khi chạy test:

  • Bắt đầu nhỏ (10-50 user), tăng dần. Đừng nhảy thẳng 10000 user.
  • Mỗi stage giữ ≥ 2-3 phút để metric ổn định.
  • Chạy 3 lần, lấy trung vị — một lần có thể có noise.

Sau khi chạy test:

  • So với SLO: pass/fail.
  • So với baseline: regression? tốt hơn?
  • Lưu report HTML vào repo CI artifact.
  • Nếu fail: phân tích bottleneck, fix, lặp lại.
Một câu mang đi

Performance test không phải một lần — là vòng lặp đo → phân tích → fix → đo lại. Locust cho bạn công cụ viết kịch bản + chạy distributed; p95/p99 cho bạn con số thật; baseline cho bạn khả năng so sánh. Đặt SLO trước, đo sau — đảo lại thứ tự là bạn đang "đo cho có rồi báo cáo đẹp".

Tình huống thực tế

Bối cảnh: 'Máy em chạy nhanh' nhưng prod sập khi 500 user đồng thời. Sửa: load test bằng Locust mô phỏng concurrency thật; nhìn p95/p99 latency + error rate + throughput (đừng nhìn trung bình); tìm điểm bão hoà. Đo trước khi hứa SLA.

3. ⭐ Tránh N+1 query — eager load

N+1 là anti-pattern phổ biến nhất của ORM: lấy 1 list (1 query), rồi với mỗi item gọi thêm 1 query → tổng N+1 query. Với 1000 order × 1 query mỗi order = 1001 query.

n-plus-one
PHẢN MẪU: 1 + N query orders = db.query(Order).limit(100).all() # 1 query for o in orders: o.items = db.query(OrderItem).filter_by(order_id=o.id).all() # 100 query → TỔNG 101 ĐÚNG: eager load với joinedload/selectinload — vẫn 1-2 query from sqlalchemy.orm import selectinload orders = db.execute( select(Order).options(selectinload(Order.items)).limit(100) ).scalars().all() # 1 query items, 1 query orders
Phát hiện N+1

Bật SQL log, chạy endpoint: thấy nhiều query giống nhau chỉ khác ID → N+1. Hoặc query_count() trong test, assert < 5 query cho endpoint. SQLAlchemy có with_loader_criteria để auto-eager load theo context.

7. Concurrency: workers, processes, gunicorn

uvicorn chạy 1 process event loop. Để tận CPU multi-core, cần nhiều worker. Hai cách:

workers
# Cách 1: uvicorn trực tiếp, nhiều process uvicorn app.main:app --workers 4 --host 0.0.0.0 --port 8000 # Cách 2: gunicorn làm process manager, uvicorn làm worker class pip install gunicorn gunicorn app.main:app -w 4 -k uvicorn.workers.UvicornWorker \ --bind 0.0.0.0:8000 --timeout 30 --graceful-timeout 30 # Quy tắc workers: 2-4 × số CPU core # 4 CPU → 8-16 worker thường là sweet spot cho I/O bound
Process vs thread

Mỗi worker là process riêng — không share memory, không share connection pool. Session ở mỗi worker phải được tạo lại. Redis cache thì share được vì là external store. Đây là lý do test phải chạy under load thật — single worker trên máy test có thể chạy ngon, multi-worker mới lộ race condition.

Một câu mang đi

Tối ưu FastAPI có 8 lớp nhưng 80% thắng lợi đến từ 3 thứ: async I/O đúng chỗ, tránh N+1, cache đúng tầng. Mỗi lần thấy p99 tăng: check (1) log cho query lặp, (2) py-spy cho function block, (3) connection pool stat. Ba chỗ đó thường đủ. Phần còn lại (orjson, gzip, brotli) là polish — làm khi đã đạt SLO bottleneck ở tầng code.

Tình huống thực tế

Bối cảnh: API chậm vì query N+1 và serialize JSON lớn mỗi request. Sửa: cache (Redis) cho dữ liệu nóng; connection pool; phân trang; gzip response; tránh N+1 (eager load/batch). Tối ưu cái đo được, đừng đoán.

2. Background task: khi nào dùng, khi nào không

FastAPI có BackgroundTasks chạy sau khi response đã gửi. Hữu ích cho: log analytics, gửi email xác nhận, invalidate cache. KHÔNG dùng cho: job dài (hơn vài giây), job cần retry, job cần visibility (monitor).

Khi nào KHÔNG dùng BackgroundTask

(1) Job > 30s — request có thể timeout. (2) Job phải thành công chắc chắn — BackgroundTask không retry, không lưu vào queue, mất nếu process crash. (3) Job cần horizontal scaling — tất cả chạy trong cùng process, không distribute được. Cho những case đó, dùng Celery, ARQ, Dramatiq, hoặc cloud queue (SQS, Pub/Sub).

Bản ghi sự kiện rời rạc. Structured log (JSON) dễ query hơn text. Dùng cho: debug, audit, security event. Giới hạn: không aggregate được, không vẽ biểu đồ latency trực tiếp.

Observability là "mắt" của production. Log cho debug, metric cho alert, trace cho bottleneck. Bỏ một trong ba, bạn sẽ "mù" ở góc đó. Đầu tư 2 giờ setup structlog + Prometheus + OTel tiết kiệm 20 giờ debug trong năm đầu. Đó là ROI rõ ràng nhất của DevOps.

2. Graceful shutdown — xử lý SIGTERM

Khi Kubernetes xoá pod, nó gửi SIGTERM. Process có 30s để xử lý in-flight request rồi exit. FastAPI + gunicorn làm đúng theo mặc định, nhưng:

# Trong lifespan: @asynccontextmanager async def lifespan(app): app.state.db = await create_db() yield # Shutdown: chờ in-flight xong, dispose pool await app.state.db.dispose() # đợi connection trả về pool # K8s: # terminationGracePeriodSeconds: 60 (lớn hơn graceful_timeout) # preStop hook: sleep 10 (đợi LB bỏ pod)

4. Container image tối ưu

dockerfile
# syntax=docker/dockerfile:1.6 FROM python:3.12-slim AS builder WORKDIR /app RUN pip install --no-cache-dir poetry && \ poetry config virtualenvs.create false && \ poetry install --no-interaction --no-ansi --no-dev FROM python:3.12-slim RUN useradd -m -u 10001 app WORKDIR /app COPY --from=builder /usr/local/lib/python3.12/site-packages /usr/local/lib/python3.12/site-packages COPY --from=builder /usr/local/bin /usr/local/bin COPY app/ ./app/ USER app EXPOSE 8000 HEALTHCHECK --interval=10s --timeout=3s CMD python -c "import httpx; httpx.get('http://localhost:8000/health/live').raise_for_status()" || exit 1 CMD ["gunicorn", "app.main:app", "-c", "gunicorn.conf.py"]
Image size

Multi-stage builder giảm image từ ~1GB (full python) xuống ~200MB. Slim base thay full Debian. Non-root user (uid 10001) là best practice security. HEALTHCHECK trong Dockerfile cho container runtime tự check.

5. Checklist go-live

Trước khi ship:

  • ✅ HTTPS bắt buộc, redirect HTTP→HTTPS.
  • ✅ Auth: JWT verify signature + exp + sub, secret trong env/secret manager.
  • ✅ Validation: Pydantic cho mọi input, extra="forbid".
  • ✅ Error: 422 / 401 / 404 / 500 với body thống nhất, KHÔNG trả stack trace.
  • ✅ Healthcheck: 3 endpoint riêng, K8s probe cấu hình.
  • ✅ Rate limit ở edge + per-user.
  • ✅ Structured log + request_id, Sentry cho unhandled exception.
  • ✅ Metrics Prometheus, dashboard + alert.
  • ✅ Trace: OTel gắn mọi request, retention > 7 ngày.
  • ✅ Locust: baseline test 1000 user 5 phút, p95/p99 đạt SLO.
  • ✅ Test: pytest ≥ 80% coverage cho handler + edge case auth.
  • ✅ Docs: OpenAPI sinh tự động, README có cách chạy local.
  • ✅ Container: multi-stage, non-root, image < 300MB.
  • ✅ Secret: từ secret manager, rotate được, .env gitignored.
  • ✅ Runbook: có hướng dẫn debug khi alert (top 5 alert phổ biến).

6. Lời cuối

WebAPI không chỉ là framework. Nó là một tập quy ước mà qua nhiều thập kỷ cộng đồng đã thử, sai, sửa. Khi bạn hiểu contract, auth, validation, healthcheck, performance — bạn không chỉ biết dùng FastAPI, bạn hiểu vì sao mọi production API trông giống nhau. Hãy bắt đầu từ Lab 10, đo baseline, và để Locust dạy bạn phần còn lại.

Một câu mang đi

Một WebAPI tốt = contract rõ + auth đúng + validation chặt + healthcheck nói thật + performance đo được. FastAPI cho bạn công cụ để đạt năm tiêu chí đó với ít code nhất trong hệ sinh thái Python. Phần còn lại là kỷ luật: viết test, đo baseline, log có request_id, secret trong vault. Đừng ship API nào mà bạn không biết "nó nói thật khi khoẻ, và nói thật khi chết".
