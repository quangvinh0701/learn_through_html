1. Tại sao AWS thống trị data cloud

AWS ra mắt S3 từ 2006 — sớm hơn Azure Blob Storage 4 năm và GCP Cloud Storage 4 năm. Lợi thế first-mover này kéo theo hiệu ứng ecosystem lock-in tích cực: tooling, third-party integrations, talent pool, documentation — tất cả đều dày nhất trên AWS.

🏆 Ecosystem maturity

S3 là chuẩn de-facto cho data lake. Mọi data tool (Databricks, Snowflake, dbt, Airflow) đều hỗ trợ S3 first-class. Bạn sẽ tích hợp nhanh hơn, debug dễ hơn.

🌍 Global infrastructure

33 regions, 105+ Availability Zones, 600+ PoP. Data của bạn có thể ở gần user, đáp ứng data residency (GDPR, PDPA) và disaster recovery.

🔧 Service breadth

Từ ingestion (Kinesis, MSK), processing (Glue, EMR), warehouse (Redshift), lake house (Lake Formation), BI (QuickSight) — AWS có đủ mọi viên gạch.

Tình huống: Startup 20 người, 5TB data/tháng, budget $3k/tháng. Họ chọn AWS thay vì GCP vì (1) team đã biết AWS từ infra, (2) QuickSight rẻ hơn Looker, (3) S3 Glacier giúp archive rẻ hơn GCS Archive 30%.

3. Khi nào KHÔNG nên dùng AWS

Cảnh báo — Vendor lock-in

AWS có hệ sinh thái rất "dính". Một khi bạn dùng Glue + Redshift + Lake Formation, việc migrate sang GCP hay Azure mất 6-12 tháng. Hãy confirm business commitment trước khi build production trên AWS.

  • Workload nhỏ (< 1TB/tháng): Heroku Postgres + Metabase có thể đủ, không cần AWS.
  • Toàn bộ stack đã trên GCP/Azure: Multi-cloud phức tạp gấp 3 lần single cloud.
  • Real-time cực thấp latency (< 5ms): AWS region xa user thì latency sẽ cao — cần CDN/edge.
  • Heavy ML training với GPU: AWS có GPU nhưng nếu workload ML là chính, cân nhắc specialized platforms (RunPod, Lambda Cloud).

🧊 Amazon S3 Tables

Công bố tại re:Invent 12/2024: một loại bucket mới (table bucket) coi bảng Apache Iceberg là tài nguyên hạng nhất của S3 — AWS tự lo phần bảo trì bảng (compaction, dọn snapshot) mà bình thường bạn phải tự chạy khi tự quản Iceberg trên bucket thường. ⚡ S3 Express One Zone

Khi nào quan tâm: workload đọc/ghi lặp lại cực nhiều trên tập dữ liệu nóng (training ML, xử lý tương tác); dữ liệu chính vẫn nên nằm ở class đa-AZ.

🧪 AWS Glue 5.0

Ra mắt cuối 2024: nâng engine lên Spark 3.5.x, runtime Python/Java mới hơn và cải thiện hiệu năng so với Glue 4.0. Khi nào quan tâm: job Glue hiện có của bạn cần tính năng Spark mới hoặc muốn hưởng cải thiện tốc độ — kiểm tra tương thích trước khi nâng version, như mọi lần nâng major.

Xu hướng lớn cần đọc ra: AWS đặt cược vào Iceberg

S3 Tables quản Iceberg native, SageMaker Lakehouse mở dữ liệu qua giao diện Iceberg-tương-thích, Glue/Athena/EMR/Redshift đều đọc-ghi Iceberg ngày càng sâu. Thông điệp cho DE: open table format (đặc biệt Iceberg) đang trở thành lớp chuẩn giữa S3 và mọi engine — kỹ năng ở Module 16 (Lakehouse & Table Format) ngày càng ít "tuỳ chọn" và ngày càng "mặc định". Lưu ý: các dịch vụ mới có mô hình tính phí riêng và giới hạn riêng theo region — luôn đối chiếu tài liệu và bảng giá hiện hành trước khi đưa vào thiết kế.

Module 02 — Bảo mật nền tảng

IAM, VPC & Security Baseline cho Data Platform

Bạn có một data lake S3 với 50TB dữ liệu khách hàng. Ngày đầu deploy, bạn cấp quyền s3:* cho mọi developer để "tiện làm việc". 3 tháng sau, một junior dev xoá nhầm production bucket. Đó là lý do IAM là module số 2, không phải số 12.

› 1. IAM cơ bản › 2. Policy strategies › 3. S3 security › 4. Network isolation › 5. Audit với CloudTrail

1. IAM — Identity and Access Management

IAM là service quản lý ai được làm gì với cái gì trong AWS. Nó hoạt động theo 3 thực thể:

👤 User / Role

Ai đang truy cập. User cho con người, Role cho service/EC2/Lambda. Luôn dùng Role, tránh Access Key dài hạn.

📜 Policy

JSON định nghĩa quyền. Dùng AWS managed policies cho thường, customer-managed cho tổ chức.

🎯 Resource

Cái mà user/role muốn truy cập: S3 bucket, Glue job, Redshift cluster...

1.1 Policy cơ bản

policy-s3-readonly.json
Cho phép đọc một S3 bucket cụ thể, không cho list all buckets { "Version": "2012-10-17", "Statement": [ { "Sid": "ListOnlyMyBucket", "Effect": "Allow", "Action": [ "s3:ListBucket", "s3:GetBucketLocation" ], "Resource": "arn:aws:s3:::my-data-lake-prod" }, { "Sid": "ReadAllObjects", "Effect": "Allow", "Action": [ "s3:GetObject", "s3:GetObjectVersion" ], "Resource": "arn:aws:s3:::my-data-lake-prod/*" } ] }

2. Policy strategies — Least Privilege

Nguyên tắc vàng: cấp đúng quyền cần thiết, không hơn, không kém. Một developer data không cần quyền glue:DeleteDatabase.

Anti-pattern phổ biến

Policy "Action": "*", "Resource": "*" rất phổ biến trong thực tế. Đây là security nightmare. Nếu access key leak, attacker có toàn quyền account.

2.1 IAM Access Analyzer — phát hiện quyền thừa

aws accessanalyzer create-analyzer --analyzer-name my-org-analyzer --type ORGANIZATION aws accessanalyzer list-findings --analyzer-name my-org-analyzer { "findings": [ { "resource": "arn:aws:s3:::my-data-lake-prod", "resourceType": "AWS::S3::Bucket", "action": ["s3:GetObject*"], "principal": {"AWS": "123456789012"}, "condition": {}, "isPublic": false } ] }

3. S3 Security — Block Public Access & Encryption

S3 là service bị misconfigure nhiều nhất. Có 4 lớp bảo vệ bắt buộc:

LớpCấu hìnhMục đích

Bucket PolicyJSON policy gắn vào bucketCross-account access, IP allowlist

# Bật Block Public Access cho tất cả 4 setting aws s3api put-public-access-block --bucket my-data-lake-prod --public-access-block-configuration \ "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true" # Bật default encryption với SSE-S3 aws s3api put-bucket-encryption --bucket my-data-lake-prod --server-side-encryption-configuration \ '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}' # Bật versioning aws s3api put-bucket-versioning --bucket my-data-lake-prod --versioning-configuration Status=Enabled

4. Network isolation với VPC

Glue, EMR, Redshift cần truy cập S3 nhưng không cần public internet. Đặt chúng trong private subnet, dùng S3 Gateway Endpoint để đi thẳng tới S3 không qua internet.

aws-cli
# Tạo S3 Gateway Endpoint (miễn phí, không tốn NAT gateway fee) aws ec2 create-vpc-endpoint --vpc-id vpc-01234567 \ --service-name com.amazonaws.us-east-1.s3 \ --route-table-ids rtb-01234567 { "VpcEndpoint": { "VpcEndpointId": "vpce-0123456789abcdef0", "ServiceName": "com.amazonaws.us-east-1.s3", "VpcEndpointType": "Gateway" } }
Best Practice

Glue connection nên dùng JDBC connection with VPC để Glue chạy trong VPC của bạn, kết nối tới RDS/Redshift private. Đừng bao giờ để database production publicly accessible.

5. Audit với CloudTrail & S3 Access Logs

CloudTrail ghi lại mọi API call tới AWS. Đây là công cụ quan trọng nhất để phát hiện security incident.

cloudtrail-query
# Query: tìm tất cả DeleteObject trong 7 ngày qua aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=DeleteObject \ --start-time 2026-06-09T00:00:00Z --end-time 2026-06-16T23:59:59Z \ --query 'Events[].{Time:EventTime,User:Username,Resource:Resources[0].ResourceName}'
Key Points M2
  • IAM là module nền tảng — sai IAM = security incident chỉ là vấn đề thời gian
  • Luôn dùng Role thay vì Access Key; Access Key chỉ dùng cho CI/CD, rotate mỗi 90 ngày
  • S3 cần 4 lớp bảo vệ: Block Public Access + Bucket Policy + Default Encryption + Versioning
  • VPC Endpoint cho S3 miễn phí và giảm đáng kể NAT gateway cost
  • CloudTrail là audit log quan trọng nhất — bật multi-region trail + log file validation

Tình huống: Glue job cần đọc S3 và ghi Redshift, dev gắn luôn AdministratorAccess cho nhanh. Sáu tháng sau audit phát hiện job có quyền xoá mọi bucket. Cách đúng: tạo IAM role riêng cho job, chỉ s3:GetObject trên đúng prefix + quyền ghi đúng bảng Redshift; thêm VPC endpoint cho S3 để traffic không ra Internet; dùng SCP chặn tạo access key dài hạn. Least privilege thu nhỏ blast radius khi role bị lộ.

Module 03 — Data Lake Foundation

Amazon S3 & Data Lake Architecture

S3 không chỉ là "cloud storage". Nó là nền tảng cho hầu hết modern data lake. Module này dạy bạn từ bucket creation, partition strategy, đến lifecycle rules — tất cả những gì cần để chạy data lake production.

› 1. S3 concepts › 2. Bucket operations › 3. Partitioning › 4. Lifecycle rules › 5. Event notifications

1. S3 Concepts

Bucket

Container cho objects. Tên globally unique (toàn bộ AWS). Không có folder thật — chỉ là key có dấu / trong tên.

Object

File + metadata. Key là đường dẫn đầy đủ. Max size: 5TB. Upload > 5GB phải dùng multipart.

Prefix

String đầu key — dùng để "giả folder". bronze/year=2026/month=06/ là một prefix.

Version

Mỗi lần overwrite tạo version mới. Bật versioning = an toàn khi xoá nhầm, nhưng tốn storage gấp đôi.

2. Bucket operations với AWS CLI

aws-cli
# Tạo bucket (region us-east-1 không cần LocationConstraint) aws s3 mb s3://my-data-lake-prod aws s3 mb s3://my-data-lake-prod --region us-west-2 --create-bucket-configuration LocationConstraint=us-west-2 # Sync dữ liệu (chỉ upload file mới/thay đổi) aws s3 sync ./local-data/ s3://my-data-lake-prod/bronze/ --exclude "*.tmp" # Copy recursive với filter aws s3 cp s3://my-data-lake-prod/bronze/ s3://my-data-lake-archive/glacier/ \ --recursive --exclude "*" --include "2025/*" # List với size aws s3 ls s3://my-data-lake-prod/bronze/ --recursive --human-readable --summarize

3. Partitioning — Hive-style vs Iceberg

Partitioning chia nhỏ dataset theo cột (thường là date). Query chỉ scan partition cần thiết — tăng tốc 10-100× và giảm cost Athena/Glue.

Hive-style (đơn giản)

s3://lake/bronze/orders/
  year=2026/
    month=06/
      day=15/
        part-0001.parquet
        part-0002.parquet

Pros: đơn giản, Athena hỗ trợ native. Cons: partition explosion nếu cardinality cao.

Apache Iceberg (hiện đại)

s3://lake/orders/
  metadata/
    v1.metadata.json
    v2.metadata.json
  data/
    part-0001.parquet
    part-0002.parquet

Pros: schema evolution, hidden partitioning, time travel. Cons: cần engine hỗ trợ.

Anti-pattern

Partition theo user_id với 10 triệu user = 10 triệu folder S3 = Athena metadata query fail. Quy tắc: chỉ partition theo cột low-cardinality (year, month, region, status).

4. Lifecycle Rules — tự động chuyển storage class

Lifecycle rules tự động chuyển objects sang storage class rẻ hơn hoặc xoá sau thời gian. Đây là cách tiết kiệm 60-80% S3 cost cho data lake.

lifecycle.json
{ "Rules": [ { "Id": "BronzeToIA", "Status": "Enabled", "Filter": {"Prefix": "bronze/"}, "Transitions": [ {"Days": 30, "StorageClass": "STANDARD_IA"}, {"Days": 90, "StorageClass": "GLACIER_IR"}, {"Days": 365, "StorageClass": "DEEP_ARCHIVE"} ] }, { "Id": "DeleteTempFiles", "Status": "Enabled", "Filter": {"Prefix": "tmp/"}, "Expiration": {"Days": 7} }, { "Id": "CleanupIncompleteUploads", "Status": "Enabled", "Filter": {}, "AbortIncompleteMultipartUpload": {"DaysAfterInitiation": 1} } ] }
Best Practice

Bronze layer (raw) thường ít query nhưng cần giữ lâu để debug → chuyển sang IA/Glacier sau 30 ngày. Gold layer (business aggregates) thường query nhiều → giữ Standard. Đừng apply rule giống nhau cho mọi prefix.

5. Event Notifications — trigger Glue khi có file mới

S3 Event Notifications cho phép trigger Lambda, SQS, SNS, hoặc Glue job khi object mới xuất hiện. Đây là pattern nền tảng cho event-driven ETL.

aws-cli
# Tạo notification: bronze/ có file mới → trigger Glue job aws s3api put-bucket-notification-configuration --bucket my-data-lake-prod \ --notification-configuration '{ "LambdaFunctionConfigurations": [ { "LambdaFunctionArn": "arn:aws:lambda:us-east-1:123456789012:function:start-glue-job", "Events": ["s3:ObjectCreated:*"], "Filter": {"Key": {"FilterRules": [{"Name": "prefix", "Value": "bronze/"}]}} } ] }'
Key Points M3
  • S3 là data lake foundation — Amazon xây dựng toàn bộ AWS xung quanh S3
  • Bucket name globally unique, không có folder thật, chỉ là key prefix
  • Partition theo low-cardinality columns (year, month) — tránh high-cardinality như user_id
  • Lifecycle rules tiết kiệm 60-80% S3 cost — Bronze → IA → Glacier tự động
  • Event Notifications kết nối S3 với Glue/Lambda — nền tảng của event-driven pipeline

Tình huống: Bảng event 50TB query Athena vừa chậm vừa đắt vì để JSON và không partition. Sửa: chuyển Parquet + partition theo dt=YYYY-MM-DD (hoặc partition projection để khỏi quản hàng triệu partition trong Glue Catalog); đặt lifecycle: S3 Standard 30 ngày → Standard-IA → Glacier sau 90 ngày. Truy vấn từ quét 50TB còn vài GB → hoá đơn Athena giảm tới ~95%.

Module 04 — Serverless ETL

AWS Glue & PySpark ETL Jobs

Glue là managed ETL service của AWS: bạn viết PySpark script, AWS lo cluster provisioning, scaling, patching. Module này dạy bạn từ Glue job đầu tiên đến production patterns với bookmark, schema evolution, và job bookmarks.

Hình: Medallion trên S3 — Bronze (thô) → Silver (Parquet) → Gold; Glue chuyển hoá từng tầng.
› 1. Glue components › 2. Glue Job đầu tiên › 3. Glue Data Catalog › 4. Bookmarks & incremental › 5. Schema evolution

1. Glue Components

📚 Data Catalog

Metadata store (Hive metastore tương thích). Schema, partition, location của mọi table.

⚙️ Crawler

Tự động scan S3, infer schema, đăng ký table trong Catalog.

🚀 Job

PySpark script chạy trên managed Spark cluster. Trả theo DPU-hour.

2. Glue Job đầu tiên

Glue job đọc JSON từ S3 bronze, transform, ghi Parquet xuống silver. Đây là pattern phổ biến nhất.

etl_orders.py
# Job bookmarks tự động track file đã xử lý → chỉ xử lý file mới import sys from awsglue.transforms import * from awsglue.context import GlueContext from pyspark.context import SparkContext from awsglue.job import Job sc = SparkContext() glueContext = GlueContext(sc) spark = glueContext.spark_session job = Job(glueContext) @args @returns def MyTransform(df): return df.filter("amount > 0").dropDuplicates(["order_id"]) # Đọc JSON từ bronze layer với bookmark bronze_df = glueContext.create_dynamic_frame.from_catalog( database="raw_db", table_name="orders_bronze", transformation_ctx="bronze_ctx" ) # Cast schema chặt chẽ silver_df = ApplyMapping.apply( frame=bronze_df, mappings=[ ("order_id", "string", "order_id", "long"), ("customer_id", "string", "customer_id", "long"), ("amount", "double", "amount", "double"), ("created_at", "string", "created_at", "timestamp") ], transformation_ctx="mapping_ctx" ) # Ghi Parquet partition theo year/month/day glueContext.write_dynamic_frame.from_options( frame=silver_df, connection_type="s3", connection_options={ "path": "s3://my-data-lake-prod/silver/orders/", "partitionKeys": ["year", "month", "day"] }, format="parquet", transformation_ctx="silver_ctx" ) job.commit()
Tránh GHI ĐÈ Partition

Mặc định write_dynamic_frame overwrite toàn bộ partition. Để update incremental, dùng enableUpdateCatalog=True và partition overwrite mode, hoặc dùng Iceberg/Delta format.

3. Glue Data Catalog

Data Catalog là single source of truth cho schema. Athena, Redshift Spectrum, EMR đều đọc từ đây.

Module 05 — Serverless SQL

Amazon Athena & SQL on S3

Bạn có dữ liệu Parquet trên S3. Bạn muốn query bằng SQL mà không cần spin up cluster. Đó chính xác là Athena — serverless query engine tính tiền theo data scanned.

Hình: Athena dùng Glue Catalog để cắt tỉa partition trên S3 — quét ít, rẻ và nhanh.

1. Athena cơ bản

Athena dùng Trino (trước là Presto) query engine, scan trực tiếp S3. Không cần load data, không có cluster, không có infra. Trả $5/TB scanned.

athena-sql
-- Query gold layer trong Athena console SELECT region, COUNT(DISTINCT customer_id) AS active_customers, SUM(amount) AS total_revenue FROM silver_db.orders WHERE year = 2026 AND month = 6 AND day BETWEEN 1 AND 15 GROUP BY region ORDER BY total_revenue DESC LIMIT 10;

2. Cost optimization — Columnar format là vua

Athena charge theo data scanned. Convert từ row-format (CSV, JSON) sang columnar (Parquet, ORC) có thể giảm 90% cost.

FormatCompressionScan cost (1TB raw)
CSV uncompressed1×$5.00
JSON.gz3-5×$1.00–$1.67
Parquet (snappy)10-15×$0.33–$0.50
ORC (zlib)15-20×$0.25–$0.33
SELECT * là anti-pattern

Athena charge theo data scanned, không theo row trả về. Query SELECT * trên Parquet scan tất cả columns. Luôn SELECT col1, col2 để dùng column-pruning.

3. File format — Parquet với Snappy

Parquet với Snappy compression là sweet spot cho hầu hết workload Athena: tỉ lệ nén tốt, query nhanh, tương thích rộng.

glue-job-snappy.py
# Khi ghi Parquet, chỉ định Snappy compression silver_df.write \ .mode("append") \ .partitionBy("year", "month", "day") \ .option("compression", "snappy") \ .parquet("s3://my-data-lake-prod/silver/orders/")

5. Federated Query — query RDS, DynamoDB, Redshift

Athena Federation cho phép query trực tiếp RDS PostgreSQL, DynamoDB, Redshift mà không cần ETL trước. Dùng cho low-frequency operational queries.

Khi nào dùng Federation

Key Points M5

  • Parquet + Snappy giảm 90% scan cost so với CSV/JSON

Tình huống: BI team chạy SELECT * trên bảng lớn nhiều lần/ngày, hoá đơn Athena tăng vọt (tính theo TB quét). Sửa: chỉ chọn cột cần + lọc theo partition; tạo bảng tổng hợp bằng CTAS (Parquet, đã partition) cho dashboard; bật workgroup data scan limit để chặn query lỡ quét cả bảng.

1. Redshift Architecture

3. Distribution Styles — quan trọng nhất cho performance

Distribution style quyết định cách rows phân bố giữa các node. Sai style = query chậm 10×, tốn network bandwidth.

EVEN

Round-robin. Mặc định. Tốt cho bảng không join với bảng khác.

KEY

Cùng giá trị key trên cùng node. Dùng cho cột thường xuyên JOIN. Tốt nhất cho fact tables.

ALL

Copy toàn bộ bảng vào mọi node. Dùng cho dim tables nhỏ (dưới vài triệu rows).

redshift-ddl.sql
-- Fact table: phân phối theo customer_id (cột JOIN nhiều nhất) CREATE TABLE orders ( order_id BIGINT NOT NULL, customer_id BIGINT NOT NULL, amount DECIMAL(10,2), created_at TIMESTAMP, region VARCHAR(20) ) DISTKEY(customer_id) -- ← KEY distribution SORTKEY(created_at); -- ← sort theo time cho time-range query -- Dimension table nhỏ: ALL distribution CREATE TABLE dim_customers ( customer_id BIGINT NOT NULL PRIMARY KEY, name VARCHAR(200), email VARCHAR(200), segment VARCHAR(50) ) DISTSTYLE ALL; -- ← copy vào mọi node

4. Sort Keys — query nhanh hơn 5-10×

Sort key sắp xếp rows theo thứ tự cố định. Query với WHERE trên sort key chỉ scan range thay vì toàn bộ table.

COMPOUND

Sort theo nhiều cột theo thứ tự. Tốt cho query với điều kiện WHERE a=X AND b=Y. Tốn storage hơn.

INTERLEAVED

Mỗi cột có weight bằng nhau. Tốt cho query không biết trước column nào filter. VACUUM REINDEX thường xuyên.

Compound vs Interleaved

AWS recommend COMPOUND cho hầu hết use case. INTERLEAVED chỉ tốt khi bạn có nhiều query pattern khác nhau và đã test kỹ.

Key Points M6
  • Redshift = MPP columnar warehouse, tối ưu cho analytical queries billion+ rows
  • RA3 với managed storage là default lựa chọn cho 95% workload
  • Distribution style: KEY cho fact tables, ALL cho dim tables nhỏ

2. Kinesis Data Streams

Data Streams là core: sharded log service, mỗi shard 1MB/s write, 2MB/s read. Provision shard count theo throughput.

aws-cli

Capacity mode

Data Streams có 2 mode: Provisioned (manual shard count) và On-demand (auto scale). On-demand đắt hơn 2-3× nhưng không cần tính capacity. Dùng On-demand cho workload mới chưa biết peak.

3. Kinesis Firehose — no-code load to S3

Firehose tự động buffer, compress, optionally transform data rồi ghi vào S3, Redshift, OpenSearch. Không cần viết consumer code.

aws-cli
aws firehose create-delivery-stream --delivery-stream-name click-to-s3 \ --delivery-stream-type DirectPut \ --s3-destination-configuration '{ "RoleARN": "arn:aws:iam::123456789012:role/firehose-role", "BucketARN": "arn:aws:s3:::my-data-lake-prod", "Prefix": "bronze/clickstream/year=!{timestamp:yyyy}/month=!{timestamp:MM}/day=!{timestamp:dd}/", "ErrorOutputPrefix": "errors/clickstream/", "BufferingHints": {"SizeInMBs": 64, "IntervalInSeconds": 60}, "CompressionFormat": "GZIP" }'
Buffer tuning

Buffer size 64MB hoặc interval 60s — tùy điều kiện nào tới trước. Volume thấp (1MB/s) → 60s buffer OK. Volume cao (50MB/s) → giảm buffer size xuống 5-10MB để giảm end-to-end latency.

4. Amazon Managed Service for Apache Flink — xử lý stream

Service này trước đây tên là Kinesis Data Analytics (KDA), được AWS đổi tên thành Amazon Managed Service for Apache Flink từ 8/2023. Nó chạy Apache Flink job dạng managed trên stream — dùng cho windowed aggregations, anomaly detection, real-time metrics. Riêng biến thể SQL (Kinesis Data Analytics for SQL) đã bị khai tử — end-of-support 1/2026.

Di sản — đã khai tử

Cú pháp CREATE STREAM / CREATE PUMP dưới đây thuộc Kinesis Data Analytics for SQL — AWS đã ngừng nhận application mới, end-of-support 1/2026. Chỉ đọc để nhận diện hệ thống cũ; project mới dùng Flink SQL / DataStream API trên Managed Service for Apache Flink.

kda-sql.sql — di sản, đã khai tử (chỉ đọc để nhận diện)
-- Tumbling window: count click per minute per page CREATE OR REPLACE STREAM clicks_per_minute ( page VARCHAR, click_count BIGINT, window_ts TIMESTAMP ) ; CREATE OR REPLACE PUMP clicks_pump AS INSERT INTO clicks_per_minute SELECT STREAM page, COUNT(*) AS click_count, ROWTIME AS window_ts FROM source_clicks GROUP BY page, FLOOR(ROWTIME TO MINUTE);

Key Points M7
  • Hệ streaming AWS: Kinesis Data Streams (custom), Firehose (no-code), Managed Service for Apache Flink (tên cũ: KDA)
  • Data Streams tính theo shard — Provisioned (manual) hoặc On-demand (auto)
  • Firehose buffer theo size hoặc time, tùy điều kiện nào tới trước
  • Managed Flink xử lý tumbling/sliding window — count/sum/avg per time window (biến thể KDA SQL với CREATE PUMP đã khai tử)

Tình huống: Traffic tăng, consumer báo ProvisionedThroughputExceeded. Nguyên nhân: thiếu shard (mỗi shard 1MB/s vào, 2MB/s ra). Sửa: tăng shard hoặc bật On-Demand mode; nếu chỉ cần đổ vào S3/Redshift thì dùng Firehose (managed, tự buffer) thay vì tự viết KCL; chọn partition key tránh hot shard. 1. EMR vs Glue — khi nào dùng cái nào

📦 Glue — managed ETL

Pros: Zero infra, tích hợp Glue Catalog, auto-scaling workers. Cons: Limited to PySpark, DPU-hour pricing đắt cho long-running jobs.

Job < 30 phút, PySpark only → Glue. Job > 1 giờ, cần custom code hoặc nhiều engine → EMR.

1. Lambda cho data engineering

Lambda thường dùng cho: trigger ETL khi có file mới, gọi API, transform data nhỏ, schedule jobs. Cold start có thể là vấn đề — cần warm-up cho latency-sensitive.

AWS Lake Formation & Data Governance

Bạn có data lake S3, có Glue Catalog, nhưng không kiểm soát được ai truy cập column nào trong row nào. Lake Formation giải quyết bài toán này với fine-grained access control.

1. Vấn đề governance truyền thống

Với IAM + S3 policy thuần, bạn chỉ control được toàn bộ object. Bạn không thể nói "user A được SELECT col1, col2 nhưng KHÔNG col3" hay "chỉ thấy rows của region US". Lake Formation giải quyết cả 2.

2. Lake Formation Architecture

3. Permissions Model

Lake Formation permission gồm 4 loại chính:

PermissionScopeUse case
DatabaseAll tables in DBGrant full access to a DB
TableAll columns of tableGrant SELECT on table
ColumnSpecific columnsHide PII columns (ssn, email)
Row filterRows matching filterRegion-based access (US team chỉ thấy US data)

4. Row-level Security

Row filter cho phép user chỉ thấy rows thoả mãn điều kiện. Ví dụ: sales team US chỉ thấy customers ở US.

aws-cli
aws lakeformation create-data-cells-filter \ --table-data '{"DatabaseName":"silver_db","Name":"orders","TableCatalogId":"123456789012"}' \ --name us-only-filter \ --row-filter '{"FilterExpression": "region = '\''US'\''"}'

5. Data Sharing — chia sẻ data giữa accounts

Lake Formation cho phép share tables giữa AWS accounts trong cùng organization. Một account sở hữu data, các account khác consumer với fine-grained permission.

Best Practice

Bắt đầu với Database-level grant cho team rộng, sau đó narrow xuống Table, Column, Row filter cho từng use case. Đừng over-engineer permissions từ đầu.

Key Points M10
  • Lake Formation = fine-grained access control trên data lake, thay thế IAM-only
  • 4 loại permission: Database, Table, Column, Row filter
  • Column-level dùng để ẩn PII (ssn, email) khỏi analyst không cần
  • Row filter dùng cho region-based hoặc tenant-based access
  • Data sharing cho phép cross-account sharing mà vẫn kiểm soát được permissions

Tình huống: Cần cho team marketing xem bảng khách hàng nhưng giấu cột email/sđt. Sửa: Lake Formation cấp quyền cấp cột (column-level) + row-level filter, thay vì copy ra bảng riêng; chia sẻ cross-account qua LF-Tags. Quản quyền một nơi, Athena/Redshift Spectrum/EMR đều tuân theo.

S3 Deep Dive — Những điều ít người biết

S3 tưởng đơn giản nhưng có hàng chục tính năng advanced. Appendix này tổng hợp những thứ data engineer production cần biết.

A.1 S3 Strong Consistency

Từ 2020, S3 cung cấp strong consistency cho tất cả GET, PUT, LIST, DELETE. Trước đó, LIST sau PUT có thể không thấy object mới trong vài giây. Strong consistency loại bỏ race condition trong ETL.

A.2 S3 Object Lambda

Object Lambda cho phép transform object on-the-fly khi GET. Ví dụ: anonymize PII trước khi trả về cho analyst, không cần copy sang bucket khác.

object-lambda.tf
resource "aws_s3objectlambda_access_point" "anonymizer" { name = "anonymizer-ap" configuration { supporting_access_point = aws_s3_access_point.original.arn transformation_configurations { actions = ["GetObject"] content_transformation { aws_lambda { function_arn = aws_lambda_function.anonymizer.arn } } } } }

A.3 S3 Eventual consistency cho DELETE

DELETE trong S3 eventual consistency: có thể mất vài giây để xoá hoàn toàn. Không nên re-create object cùng key ngay sau delete.

A.4 S3 Request Rate

Mỗi prefix hỗ trợ 3,500 PUT/COPY/POST/DELETE và 5,500 GET/HEAD requests per second. Nếu ứng dụng cần cao hơn, dùng random prefix hoặc sharding.

A.5 S3 Multipart Upload

File > 100MB nên upload bằng multipart. File > 5GB bắt buộc multipart. Multipart cải thiện throughput và cho phép resume khi network fail.

aws-cli
# Multipart upload file 1GB với 100 parts aws s3 cp bigfile.tar.gz s3://my-bucket/ \ --expected-size 1073741824 \ --multipart-upload \ --part-size 10485760
Key Points Appendix A
  • S3 strong consistency (2020) loại bỏ race condition ETL
  • Object Lambda transform on-the-fly — anonymize PII không cần copy data
  • DELETE eventual consistency — đợi vài giây trước khi re-create cùng key
  • Request rate: 3,500 PUT/s và 5,500 GET/s per prefix — shard nếu cần cao hơn

Appendix B — Reference

Glue Patterns & Anti-patterns

B.1 Top 5 anti-patterns

Anti-pattern 1: Ghi CSV xuống S3

CSV không có schema, size lớn, scan chậm. Luôn dùng Parquet. Tiết kiệm 80% storage + 90% Athena scan cost.

Anti-pattern 2: Không dùng job bookmarks

Job không có bookmark = re-process toàn bộ mỗi lần chạy. Tốn thời gian + tốn tiền. Bookmark mặc định bật cho mọi production job.

Anti-pattern 3: Glue chạy query trên OLTP DB

Dùng Glue JDBC connection cho OLTP DB = scan toàn bộ table, lock dữ liền. Dùng DMS hoặc Kinesis cho OLTP → data lake.

Anti-pattern 4: Schema không enforce

Glue schema chỉ là documentation nếu không dùng schema enforcement. ApplyMapping với explicit type conversion là bắt buộc.

Anti-pattern 5: Không retry khi upstream fail

Glue job nên có --retry-count: 3 và --timeout: 60 minutes. Production job không có retry = downtime chỉ là vấn đề thời gian.

B.2 Glue Streaming ETL

Glue hỗ trợ streaming ETL từ Kinesis/Kafka. Dùng cho micro-batch (1-5 phút) thay vì Lambda per-record.

streaming_etl.py

  • Tránh CSV — dùng Parquet luôn
  • Bật job bookmarks mặc định
  • Không query OLTP DB bằng Glue — dùng DMS/Kinesis

Appendix E — Reference

Common Pitfalls & How to Avoid

E.1 "S3 là filesystem"

S3 không phải filesystem. Không có rename, không có append. Dùng S3 như data lake pattern: write-once, read-many, partition theo date.

E.2 "Lambda cho mọi thứ"

Lambda max 15 phút, max 10GB /tmp. Cho ETL > 15 phút hoặc > 1GB data, dùng Glue/EMR. Lambda cho trigger và small transform.

E.3 "Glue job không có retry"

Default Glue job không retry khi fail. Set --retry-count: 3 và idempotent logic. Network blip không nên là downtime.

E.4 "Redshift sort key sai"

Sort key sai = full table scan cho mỗi query. Phân tích query pattern 30 ngày đầu, chọn sort key theo cột filter nhiều nhất.

E.5 "Không tag resource"

Untagged resource = untraceable cost. Sau 6 tháng bạn không biết $5k Redshift bill là từ team nào. Tag ngay từ ngày 1.

E.6 "Data transfer cost surprise"

Data transfer giữa regions tốn $0.02-0.09/GB. Glue us-east-1 đọc S3 eu-west-1 = bill cao. Giữ processing trong cùng region với data.

E.7 "Athena SELECT * trên JSON"

SELECT * trên JSON scan 100% data. Cost gấp 10-20× Parquet. Convert sang Parquet ngay khi có thể.

E.8 "Không setup backup cho Glue job"

Glue job script lưu ở S3 nhưng bookmark lưu DynamoDB — mất bookmark = mất incremental. Backup bookmark hoặc dùng Glue job versioning.

E.9 "Lake Formation permission quá rộng"

Grant Database-level cho mọi user ban đầu, sau đó narrow xuống Table/Column/Row. Audit Lake Formation logs mỗi quý.

E.10 "Bỏ qua VPC endpoint"

Glue/EMR đi qua NAT gateway để tới S3 = $0.045/GB NAT processing fee. S3 Gateway Endpoint miễn phí. Luôn setup khi Glue/EMR trong private subnet.

Key Points Appendix E
  • S3 không phải filesystem — không rename, không append
  • Lambda max 15 phút — Glue/EMR cho job dài
  • Glue job phải có retry + idempotent logic
  • Tag resource ngay từ ngày 1 — không phải sau 6 tháng
  • S3 Gateway Endpoint tiết kiệm NAT cost — luôn setup

3. Athena: trả tiền theo TB scanned

Athena tính tiền theo lượng dữ liệu quét từ S3 (~$5/TB), không theo thời gian chạy. Nghĩa là mọi tối ưu đều xoay quanh "quét ít byte hơn". Bốn đòn bẩy, theo mức tác động:

Đòn bẩyVì sao giảm tiền
Partition (theo ngày/region)chỉ quét partition cần → bỏ qua phần lớn dữ liệu
Parquet/ORC (cột hoá)chỉ đọc cột trong SELECT, không đọc cả hàng
Compression (snappy/zstd)ít byte trên đĩa = ít byte quét
Partition projectionsuy partition từ tên, bỏ hàng nghìn lần gọi Glue/S3 LIST

Quy tắc thực chiến: luôn có cột partition trong WHERE và không SELECT *. Với bảng partition theo ngày, partition projection giúp Athena khỏi quét metadata. Ví dụ tạo bảng external Parquet + partition projection:

sql — Athena: external table Parquet + partition projection
CREATE EXTERNAL TABLE events ( user_id bigint, event string, amount double ) PARTITIONED BY (dt string) STORED AS PARQUET LOCATION 's3://my-lake/silver/events/' TBLPROPERTIES ( 'parquet.compression' = 'SNAPPY', 'projection.enabled' = 'true', 'projection.dt.type' = 'date', 'projection.dt.range' = '2024-01-01,NOW', 'projection.dt.format' = 'yyyy-MM-dd', 'storage.location.template' = 's3://my-lake/silver/events/dt=${dt}' ); -- Query có partition filter ⇒ chỉ quét đúng 1 ngày, không quét cả bảng SELECT user_id, sum(amount) FROM events WHERE dt = '2026-06-01' -- BẮT BUỘC để cắt scan GROUP BY user_id;

Tình huống: Một team chạy dashboard refresh mỗi 15 phút trên bảng raw JSON 8TB không partition, mỗi query quét toàn bộ. Hoá đơn Athena ~$5.000/tháng. Cách sửa: (1) chuyển JSON → Parquet snappy qua một Glue job (giảm ~6× byte), (2) partition theo dt + bật partition projection, (3) sửa query thêm WHERE dt = ... và bỏ SELECT *, (4) bật query result reuse. Kết quả: mỗi query chỉ quét ~40GB thay vì 8TB. Hoá đơn còn ~$400/tháng — giảm ~92% mà không đổi gì ở tầng compute. Bài học: trên Athena, format + partition là tất cả.

4. Glue: DPU-hour & bookmark

Glue ETL tính theo DPU-hour (Data Processing Unit; ~$0.44/DPU-giờ, tính theo giây sau 1 phút tối thiểu). Tối ưu: (1) right-size số worker — đừng để 10 DPU chạy job vài GB; (2) bật job bookmark để chỉ xử lý dữ liệu mới (incremental) thay vì quét lại toàn bộ mỗi lần; (3) chọn worker type hợp lý (G.1X cho IO, G.2X cho memory-heavy). Với job rất nhỏ và lẻ tẻ, cân nhắc Glue Python Shell (rẻ hơn Spark). Ví dụ bật bookmark:

bash — Glue: bật job bookmark + right-size worker
aws glue update-job --job-name daily-etl --job-update '{ "Role": "GlueETLRole", "Command": { "Name": "glueetl", "ScriptLocation": "s3://scripts/etl.py" }, "GlueVersion": "5.0", "WorkerType": "G.1X", "NumberOfWorkers": 4, "DefaultArguments": { "--job-bookmark-option": "job-bookmark-enable" } }'

Glue vs EMR — khi nào dùng gì: Glue là serverless, trả theo job, không quản cluster — thắng cho ETL ngắt quãng, ít vận hành. EMR rẻ hơn trên khối lượng lớn, chạy liên tục (đặc biệt EMR trên Spot), nhưng tốn công ops. Quy tắc: job < vài giờ/ngày → Glue; cụm xử lý hàng chục TB nhiều giờ mỗi ngày → EMR.

5. EMR vs EMR Serverless & Spot

Ba cách chạy Spark/Hadoop trên AWS, chọn theo mô hình tải:

Lựa chọnMô hình giáPhù hợp

EMR on EKSchia sẻ cụm K8s sẵn cóđã chuẩn hoá trên Kubernetes

Spot instances rẻ hơn On-Demand 70-90% nhưng có thể bị thu hồi. Pattern an toàn: core nodes dùng On-Demand (giữ HDFS/ổn định), task nodes dùng Spot qua instance fleets với nhiều loại instance để giảm rủi ro thu hồi đồng loạt. EMR Serverless tự scale về 0 khi không có job — bỏ hẳn chi phí cluster idle. Quy tắc: workload không đoán trước → EMR Serverless; batch lớn biết trước → EMR on EC2 + Spot fleet.

6. Redshift: RA3, Serverless, pause/resume

Đòn bẩy chi phí Redshift:

RA3 + managed storage: tách compute khỏi storage — bạn trả compute theo node và storage theo lượng thực dùng trên S3 (RMS), thay vì phải mua node to chỉ để có dung lượng (như DC2 cũ). Spectrum: query thẳng dữ liệu Parquet trên S3 (tính ~$5/TB scanned giống Athena) — giữ dữ liệu lạnh ngoài cluster để khỏi tốn storage nóng. Concurrency scaling: tự thêm cụm tạm khi tải cao; mỗi ngày có credit miễn phí, chỉ trả khi vượt. Pause/resume: tạm dừng cụm provisioned ngoài giờ làm việc — ngừng tính compute (vẫn trả storage), tiết kiệm tới ~75% cho workload theo giờ hành chính.

RI vs Serverless: cụm provisioned chạy 24/7 ổn định → mua Reserved Instances (cam kết 1-3 năm, giảm 30-60%). Tải lên xuống thất thường, có lúc nghỉ hẳn → Redshift Serverless trả theo RPU-hour (Redshift Processing Unit), tự scale về 0 khi rảnh. Ví dụ lịch pause/resume bằng CLI:

bash — Redshift: pause/resume + kiểm tra dung lượng
# Pause cụm ngoài giờ (chạy bằng EventBridge schedule lúc 19:00) aws redshift pause-cluster --cluster-identifier analytics-prod # Resume lúc 7:30 sáng aws redshift resume-cluster --cluster-identifier analytics-prod
sql — Redshift: tìm bảng to để right-size
-- Kích thước thật của từng bảng (MB) → quyết định node/Spectrum SELECT "table", size AS mb, tbl_rows FROM svv_table_info ORDER BY size DESC LIMIT 20;

7. Kinesis: shard-hour vs on-demand

Kinesis Data Streams có hai chế độ giá. Provisioned: trả theo shard-hour (~$0.015/shard-giờ) + phí PUT payload — rẻ khi throughput ổn định và bạn biết cần bao nhiêu shard. On-demand: không quản shard, trả theo lượng data ghi/đọc (GB) — đắt hơn trên đơn vị throughput nhưng tự scale, thắng khi tải biến động mạnh hoặc khó đoán.

Quy tắc: throughput đều và biết trước → provisioned + đúng số shard (tránh over-provision shard idle); tải spiky hoặc mới chưa rõ pattern → on-demand, theo dõi vài tuần rồi chuyển sang provisioned nếu đã ổn định để tiết kiệm. Đừng để stream provisioned 20 shard chạy mãi cho throughput thực chỉ cần 3.
