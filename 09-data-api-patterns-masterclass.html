Đa số developer biết cách build Application API (CRUD, auth, validation) — nhưng Data API có những thách thức khác hẳn: dataset lên tới hàng tỷ dòng, query pattern không lường trước được, một request chậm có thể kéo sập cả hệ thống analytics. 1. Data API là gì & tại sao khác Application API

Data API phục vụ việc đọc và xuất dữ liệu cho các client tiêu thụ (BI tool, dashboard, partner, data pipeline). Khác với Application API phục vụ nghiệp vụ transactional, Data API có những đặc điểm riêng biệt:

Application API

CRUD nghiệp vụ, auth phức tạp, stateful, response nhỏ, latency thấp, tần suất vừa. Ví dụ: POST /orders, PUT /users/123.

Data API

Truy vấn phân tích, export, streaming, response lớn (hàng MB/GB), latency cao hơn được chấp nhận, read-heavy. Ví dụ: GET /reports/revenue?from=2024-01.

Data API

Một API layer phục vụ truy vấn, xuất, và streaming dữ liệu cho các consumer không trực tiếp thuộc application domain — BI tool, data warehouse, partner API, internal dashboard. Đặc điểm: read-heavy, dataset lớn, query phức tạp, latency sensitivity thấp hơn app API, và cần những pattern riêng (pagination, caching, export async).

Quy tắc phân biệt

Một endpoint là Data API khi: (1) trả về dataset lớn hoặc không giới hạn, (2) query pattern không lường trước (ad-hoc filter), (3) consumer là hệ thống khác (không phải end-user app). Ngược lại, endpoint thuộc Application API.

Module 02 — Nền tảng

Read Replica & Routing — primary/replica, write/read separation

Khi Data API phục vụ hàng trăm dashboard và BI tool cùng đọc, bạn không thể đổ hết vào primary database — nó sẽ làm chậm cả write operation của application. Read replica là pattern cốt lõi giải quyết bài toán này: tách rõ read (Data API) khỏi write (Application API), chấp nhận eventual consistency để đổi lấy throughput. Module này đi sâu vào routing logic, consistency model, và read-your-write pattern.

1. Tại sao cần read replica

Trong một hệ thống hybrid (Application + Data API cùng database), read replica giải ba bài toán cùng lúc:

Performance isolation

Analytical query scan hàng triệu rows không ảnh hưởng đến transactional write. Replica có CPU/IO riêng.

Horizontal scale read

Thêm replica = thêm read throughput tuyến tính. Primary vẫn giữ nguyên cho write.

High availability

Primary down → promote replica → downtime = 0. Application không biết failover xảy ra.

Geographic distribution

Replica ở region gần BI tool = latency thấp hơn. Cross-region replication.

Trade-off cần biết

Read replica không miễn phí: có thêm infra cost (thường 50-100% so với primary), có replication lag, và routing logic phức tạp hơn. Chỉ dùng khi read/write ratio > 80/20 hoặc analytical query gây lock trên primary.

3. Replication lag & eventual consistency

Replication lag là khoảng thời gian từ khi write commit trên primary đến khi data có sẵn trên replica. Đây là trade-off cốt lõi của read replica pattern.

Replication lag

Khoảng thời gian data trên replica chưa đồng bộ với primary. Đo bằng pg_stat_replication.reply_lag (Postgres) hoặc Seconds_Behind_Master (MySQL). Lag = 0 có nghĩa replica đã đồng bộ; lag > 0 nghĩa là eventual consistency.

pg-check-replication-lag
Kiểm tra replication lag trên PostgreSQL replica -- Trên PRIMARY: kiểm tra replicas đang kết nối SELECT client_addr, state, sent_lsn, write_lsn, flush_lsn, replay_lsn, (sent_lsn - replay_lsn) AS replication_lag FROM pg_stat_replication; -- Trên REPLICA: kiểm tra bao xa so với primary SELECT now() - pg_last_xact_replay_timestamp() AS replication_delay;
Lag không cố định

Replication lag tăng khi: (1) write burst trên primary, (2) replica đang xử lý heavy query, (3) network lag, (4) replica down rồi catch up. Monitoring lag là bắt buộc — xem Module 12 (Observability).

4. Read-your-write consistency

Read-your-write consistency (hay read-after-write) đảm bảo: sau khi user write, họ đọc lại sẽ thấy data vừa write — ngay cả khi đọc từ replica. Đây là user expectation tự nhiên nhưng khó implement với eventual consistency.

Tình huống thực tế

Bối cảnh: Một dashboard cho phép user upload CSV và xem preview ngay. Sau khi upload thành công (POST → primary), user được redirect tới trang data preview. Giải pháp: Sau POST thành công, trả về commit LSN cho client. Trang preview dùng LSN đó để verify replica đã replay trước khi query. Nếu chưa, fallback primary hoặc poll với exponential backoff.

1. Tại sao pagination quan trọng với Data API

Không pagination = return toàn bộ dataset = explosion. Một query SELECT * FROM events trên bảng 1 tỷ rows có thể:

Lỗi phổ biến

LIMIT 1000000 — không phải pagination. Server vẫn phải scan và sort toàn bộ dataset để tìm 1M rows. Data API cần pagination thực sự: mỗi page = một query nhỏ với index hỗ trợ.

2. Offset pagination

Offset pagination (LIMIT/OFFSET) là cách phổ biến nhất: SELECT * FROM orders LIMIT 50 OFFSET 100. Đơn giản, client hiểu ngay, bookmarkable.

  OFFSET PAGINATION
  ─────────────────────────────────────────────────
  Page 1:  [ row 1-50 ]         OFFSET 0
  Page 2:  [ row 51-100 ]       OFFSET 50
  Page 3:  [ row 101-150 ]      OFFSET 100
  ...
  Page 1000: [ row 49951-50000 ] OFFSET 49950

  Issue: OFFSET càng lớn, query càng chậm
  OFFSET 50000 → scan & discard 50000 rows
Offset pagination: đơn giản nhưng hiệu năng giảm khi offset lớn. Không dùng cho dataset lớn.
offset-pagination
Offset pagination: dễ nhưng không scale khi offset > 10K -- Page 10 (OFFSET 450): fast SELECT id, created_at, total FROM orders WHERE user_id = 123 ORDER BY created_at DESC LIMIT 50 OFFSET 450; -- Page 1000 (OFFSET 49500): SLOW -- DB phải scan và discard 49500 rows trước khi trả 50 rows -- Query time: ~5ms vs ~500ms

Ưu điểm

Dễ implement, client có thể jump to page bất kỳ, URL bookmarkable, total count có sẵn.

Nhược điểm

Hiệu năng giảm tuyến tính với offset. Không stable khi data thay đổi giữa page (row bị skip hoặc duplicate khi có INSERT/DELETE). COUNT(*) trên dataset lớn rất chậm.

3. Cursor pagination (keyset)

Cursor pagination (hay keyset pagination) dùng giá trị của last row thay vì offset. Query tiếp theo lấy rows sau cursor đó.

  CURSOR PAGINATION
  ─────────────────────────────────────────────────
  Initial:  [ row 1-50 ]           cursor = row_50.created_at
  Next:     WHERE created_at < cursor
            [ row 51-100 ]

  Index scan, không cần offset → O(log n) thay vì O(n)
Cursor pagination dùng index seek thay vì offset. Hiệu năng constant-time không phụ thuộc vị trí trong dataset.
Cursor (keyset)

Giá trị của cột(s) dùng làm bookmark. Thường là timestamp hoặc composite (timestamp + id) để đảm bảo uniqueness. Cursor được encode (base64/opaque) trước khi gửi cho client để tránh expose internal field.

cursor-pagination
Cursor pagination: dùng WHERE thay vì OFFSET -- Page 1 (no cursor) SELECT id, created_at, total FROM orders WHERE user_id = 123 ORDER BY created_at DESC, id DESC LIMIT 50; -- Page 2 (cursor = "2024-01-15T10:30:00Z|789") SELECT id, created_at, total FROM orders WHERE user_id = 123 AND (created_at, id) < ('2024-01-15T10:30:00Z', 789) ORDER BY created_at DESC, id DESC LIMIT 50; -- Composite cursor đảm bảo uniqueness khi nhiều rows cùng timestamp

Ưu điểm

Performance O(log n) nhờ index, không phụ thuộc vị trí. Stable khi iterate (không duplicate/skip). Không cần COUNT(*). Works great với cursor-based data streams.

Nhược điểm

Không jump to page. Cursor phải base64-encode. Không có total count. Backward traversal phức tạp hơn.

4. Seek method

1. Composite cursor: tại sao cần & cách build

Single-column cursor (VD: created_at) có vấn đề khi nhiều rows có cùng timestamp — cursor không unique, kết quả không deterministic.

Single cursor = non-deterministic

WHERE created_at < '2024-01-15 10:30:00' — nếu có 10 rows cùng timestamp 10:30:00, mỗi lần chạy có thể trả thứ tự khác nhau (phụ thuộc index). Điều này gây duplicate hoặc skip khi user next page.

Composite cursor

Cursor gồm 2+ columns: thường là (timestamp, id) hoặc (sort_field, primary_key). Đảm bảo uniqueness & deterministic ordering vì primary key luôn unique.

  COMPOSITE CURSOR STRUCTURE
  ─────────────────────────────────────────────────────
  Cursor: [timestamp, id] — 2 columns

  Page 1: ORDER BY created_at DESC, id DESC LIMIT 50
          Last row: ts=2024-01-15 10:30:00, id=789
          Cursor = [2024-01-15T10:30:00, 789]

  Page 2: WHERE (created_at, id) < (cursor_ts, cursor_id)
          ORDER BY created_at DESC, id DESC LIMIT 50
          ─────────────────────────────────────────────
          Result: deterministic ✓ (id đảm bảo uniqueness)
Composite cursor dùng (timestamp, id) để đảm bảo mỗi row có cursor duy nhất, không duplicate/skip khi sort bằng timestamp.

3. Stability qua INSERT/DELETE/UPDATE

Cursor pagination "stable" nghĩa là: khi user paginate qua dataset, không row nào bị duplicate hoặc skip — kể cả khi data thay đổi giữa các page. Đây là phần phức tạp nhất.

4. Bidirectional pagination

  [rows]                          [rows]                       [rows]

  Response metadata:
  {
    "data": [...],
    "paging": {
      "cursors": {
        "previous": "base64_cursor_PN_minus1",
        "current":  "base64_cursor_PN",

3. N+1 query problem

N+1 query là enemy #1 của GraphQL: 1 query orders + N queries customer cho mỗi order = hàng trăm queries cho 1 dashboard.

  N+1 PROBLEM
  ─────────────────────────────────────────────────────
  Query: orders → customers

  WITHOUT DataLoader:
  1. SELECT * FROM orders LIMIT 50
  2. SELECT * FROM customers WHERE id = 101   ← order 1
  3. SELECT * FROM customers WHERE id = 102   ← order 2
  4. SELECT * FROM customers WHERE id = 103   ← order 3
  ... (50+ queries)

  WITH DataLoader:
  1. SELECT * FROM orders LIMIT 50
  2. SELECT * FROM customers WHERE id IN (101, 102, 103, ...)  ← batched!
  (2 queries total)
DataLoader batches N individual requests thành 1 batch request. Từ O(N) queries → O(1) queries per field.
N+1 không obvious

N+1 xảy ra khi resolver truy cập nested field. Một dashboard "đơn giản" có thể trigger 500+ queries nếu không có DataLoader. Luôn profile queries khi implement GraphQL.

Streaming Response — chunked transfer, NDJSON, SSE, file streaming

Khi Data API trả về dataset lớn, đợi toàn bộ response trong memory là suicide. Streaming response cho phép gửi data từng chunk — client nhận từng phần ngay khi có, memory footprint thấp, perceived latency giảm. Module này cover 4 kỹ thuật: chunked HTTP, NDJSON, Server-Sent Events, và file streaming.

1. Tại sao cần streaming

Streaming giải quyết bài toán Data API đặc thù:

∞
memory saved
chunk gửi từng phần, không load toàn bộ vào RAM
~0
perceived latency
client nhận data ngay, không đợi full response
✓
timeout prevention
request không bị timeout vì bắt đầu trả sớm
Anti-pattern: buffer full response

2. RSQL/FIQL query language

RSQL (Resource State Query Language) là URI-friendly query language cho REST API, dựa trên FIQL (Feed Item Query Language). Hỗ trợ comparison, logical operators, và collection.

  RSQL SYNTAX
  ─────────────────────────────────────────────────────
  Comparison operators:
    ==   equal              status==paid
    !=   not equal          status!=cancelled
    =lt= less than          total=lt=100
    =le= less or equal      total=le=100
    =gt= greater than       total=gt=0
    =ge= greater or equal   total=ge=100
    =in= in collection      status=in=(paid,shipped)
    =out= out collection   status=out=(cancelled)

  Logical operators:
    ;   AND                 status==paid;total=ge=100
    ,   OR                  status==paid,status==shipped
    ()  grouping           (status==paid;total=ge=100),status==refunded

  String operators:
    =like=  SQL LIKE        name=like=*john*
    =in=    IN clause       category=in=(electronics,books)
RSQL dùng URI-safe characters, có thể đặt trong query param. Readable và expressive hơn raw SQL WHERE.

6. Whitelist field & SQL injection prevention

SQL Injection Warning

Dynamic filter từ user input là SQL injection attack surface. BAẮT BUỘC: whitelist field names, validate enum values, dùng parameterized queries. Không bao giờ interpolate raw user input vào SQL string.

Field whitelist

Dictionary hoặc Enum định nghĩa trước những field nào được filter. Bất kỳ field nào không trong whitelist → silently ignored hoặc 400 Bad Request. Đây là defense-in-depth chống SQL injection.

Điểm chốt

Flexible filtering là key feature của Data API. RSQL cho expressive filter language, JSON:API convention cho consistency, whitelist field để prevent injection. Query builder pattern giữ code clean và maintainable.

6. Cache stampede protection

Cache stampede (thunder herd) xảy ra khi cache expires đồng thời cho nhiều requests — tất cả hit DB cùng lúc, overload.

Tình huống thực tế

Bối cảnh: Dashboard refresh mỗi 5 phút với TTL 5 phút. Khi cache expires, 100 concurrent users cùng refresh → 100 heavy queries đồng thời vào DB. Giải pháp: probabilistic early expiration (PEAR) hoặc lock-based cache refresh.

stampede-protection
Cache stampede protection: early refresh + distributed lock import asyncio, random class CacheWithStampedeProtection: """ Probabilistic Early Expiration (PEAR): - Before TTL expires, random requests proactively refresh cache - Spread refresh load over time instead of burst at expiry """ def __init__(self, redis, base_ttl: int = 300): self.redis = redis self.base_ttl = base_ttl self.refresh_window = int(base_ttl * 0.2) # refresh trong 20% cuối async def get(self, key: str) -> dict | None: val = await self.redis.get(key) if val: # Check if within early refresh window ttl = await self.redis.ttl(key) if ttl < self.refresh_window and random.random() < 0.3: # 30% chance: trigger early refresh asyncio.create_task(self._early_refresh(key)) return json.loads(val) return None async def _early_refresh(self, key: str): """Background refresh without blocking get().""" async with self.redis.lock(f"{key}:lock", timeout=30): # Double-check still needed (lock holder may have refreshed) ttl = await self.redis.ttl(key) if ttl > self.refresh_window: return # Fetch fresh data fresh = await self._fetch_from_db(key) await self.redis.setex(key, self.base_ttl, json.dumps(fresh)) async def get_or_compute(self, key: str, compute_fn) -> dict: """Lock-based cache-aside: only 1 request computes, others wait.""" val = await self.get(key) if val is not None: return val # Try to acquire lock lock_key = f"{key}:lock" lock = self.redis.lock(lock_key, timeout=30) async with lock: # Lock acquired — double-check cache val = await self.get(key) if val is not None: return val # Compute fresh fresh = await compute_fn() await self.redis.setex(key, self.base_ttl, json.dumps(fresh)) return fresh
Điểm chốt

Caching là cách hiệu quả nhất giảm database load. Cache-aside với Redis, proper TTL, và CDN caching cho public endpoints. Nhớ protection chống cache stampede khi cache expiry đồng thời. Monitor cache hit rate và adjust TTL accordingly.

4. Schema evolution strategy

Schema sẽ thay đổi theo thời gian. Chiến lược evolution để minimize breaking changes:

Phase 1 — Additive (không breaking)
Thêm optional fields, thêm enum values, thêm endpoints mới. Consumer cũ vẫn work.

Phase 2 — Deprecated (grace period)
Đánh dấu fields sắp remove là deprecated=True trong OpenAPI. Trả warning header. Kéo dài 3-6 tháng.

Phase 3 — Breaking (version bump)
Tạo vN+1 endpoint với breaking changes. Tiếp tục maintain vN trong grace period. Redirect vN → vN+1 sau grace period.

API changelog

Maintain CHANGELOG.md hoặc OpenAPI changelog với semver. Consumer có thể subscribe để track breaking changes. Dùng git tag v1.0.0 để mark stable API versions.

Điểm chốt

Schema contract là production contract. extra="forbid" để strict, chỉ additive changes là backward compatible, path versioning là best practice. Evolution strategy (additive → deprecate → break) giữ backward compatibility trong khi vẫn phát triển API.

3. Redis sliding window counter

Sliding window rate limiting chính xác hơn fixed window (không có burst ở window boundary):

  SLIDING WINDOW LOG
  ─────────────────────────────────────────────────────
  Window: 60 seconds, quota: 100 units

  Current time: T
  Count requests in [T-60s, T)

  Key: ratelimit:{tenant_id}
  Redis ZADD: timestamp as score, unique request ID as member
  Redis ZREMRANGEBYSCORE: remove entries older than 60s
  Redis ZCARD: count remaining entries

  If count < quota: ALLOW
  Else: REJECT with Retry-After
Sliding window log dùng Redis sorted set để track từng request với timestamp. Chính xác hơn sliding window counter (approximation).
redis-sliding-window
Redis sliding window rate limiter import time, uuid import redis.asyncio as redis class SlidingWindowRateLimiter: """ Sliding window rate limiting với Redis sorted set. - ZADD: thêm request với timestamp - ZREMRANGEBYSCORE: xoá expired entries - ZCARD: đếm requests trong window """ def __init__(self, redis_url: str, window_seconds: int = 60, quota: int = 100): self.redis = redis.from_url(redis_url) self.window = window_seconds self.quota = quota async def check_rate_limit( self, tenant_id: str, cost: float = 1.0 ) -> tuple[bool, dict]: """ Returns: (allowed, metadata) """ key = f"ratelimit:{tenant_id}" now = time.time() window_start = now - self.window request_id = str(uuid.uuid4()) pipe = self.redis.pipeline() # 1. Remove expired entries pipe.zremrangebyscore(key, "-inf", window_start) # 2. Count current requests pipe.zcard(key) # 3. Add current request with score = timestamp pipe.zadd(key, {request_id: now}) # 4. Set expiry on key pipe.expire(key, self.window + 1) results = await pipe.execute() current_count = results[1] # Calculate cumulative cost (requests * avg_cost) total_cost = current_count * 1.0 # base cost = 1 if total_cost + cost > self.quota: # Over limit — remove the request we just added await self.redis.zrem(key, request_id) return False, { "quota": self.quota, "used": current_count, "remaining": max(0, self.quota - current_count), "reset_at": now + self.window, "retry_after": self.window, } return True, { "quota": self.quota, "used": current_count + cost, "remaining": self.quota - (current_count + cost), "reset_at": now + self.window, } async def get_usage(self, tenant_id: str) -> dict: """Get current usage without incrementing.""" key = f"ratelimit:{tenant_id}" now = time.time() window_start = now - self.window await self.redis.zremrangebyscore(key, "-inf", window_start) count = await self.redis.zcard(key) return { "quota": self.quota, "used": count, "remaining": max(0, self.quota - count), "reset_at": now + self.window, } limiter = SlidingWindowRateLimiter( redis_url="redis://localhost:6379", window_seconds=60, quota=100 )

3. Latency SLO: P50, P95, P99

Latency distribution mô tả user experience thực tế. P50 = median, P95 = "5% users gặp latency này hoặc cao hơn", P99 = "1% users gặp latency này hoặc cao hơn".

Mục tiêu performance cam kết với users. VD: P95 latency < 500ms, availability > 99.9%. SLO khác với SLA (Service Level Agreement) — SLA là hợp đồng pháp lý, SLO là internal target.
