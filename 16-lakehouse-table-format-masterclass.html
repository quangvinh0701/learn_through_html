Module 01 — Nền tảng

Tư duy Lakehouse

Bạn đã chạy Spark trên file Parquet trong data lake, và bạn cũng đã từng dùng warehouse (Redshift, BigQuery, Snowflake). Lakehouse không phải một sản phẩm mới — nó là một tư duy: đặt một lớp metadata giao dịch lên trên các file rẻ tiền trong object storage, để data lake có được tính năng của warehouse (ACID, schema, time travel) mà vẫn giữ giá lưu trữ rẻ và quyền mở của lake. Module này dựng khung tư duy cho toàn khoá.

📚 Lý thuyết nền tảng

Trước khi nói tới Iceberg hay Delta, hãy nắm bốn trụ cột giúp nhìn mọi quyết định lưu trữ phân tích theo cùng một cách.

Lý thuyết 1.1 — Tách tính toán khỏi lưu trữ

Warehouse cổ điển (kiểu Teradata) gắn chặt CPU và đĩa: muốn thêm tính toán phải thêm cả lưu trữ. Object storage (S3, GCS, ADLS) phá vỡ điều đó — lưu trữ rẻ, vô hạn, độc lập; nhiều engine (Spark, Trino, Flink) cùng đọc một tập dữ liệu. Nhưng object storage chỉ biết "đối tượng" (object) chứ không biết "bảng" (table). Lakehouse ra đời để lấp khoảng trống đó: cho object storage một khái niệm bảng có ngữ nghĩa giao dịch.

Lý thuyết 1.2 — Metadata là thứ tạo ra "bảng"

Một "bảng" không phải các byte dữ liệu — nó là lời hứa về một tập hợp dòng nhất quán tại một thời điểm. Lời hứa đó được giữ bởi metadata: file nào thuộc bảng, ở phiên bản nào, schema ra sao. Đổi nội dung bảng = đổi metadata trỏ tới tập file mới, một cách nguyên tử. Đây là ý tưởng trung tâm của mọi table format.

Lý thuyết 1.3 — Bất biến + con trỏ thay vì sửa tại chỗ

Object storage không cho sửa một phần file; ghi đè là thay cả object và không nguyên tử khi có nhiều file. Giải pháp: file dữ liệu là bất biến (immutable) — không bao giờ sửa, chỉ thêm file mới và "xoá" bằng cách thôi tham chiếu. "Trạng thái bảng" chỉ là một con trỏ tới danh sách file hiện hành. Đổi con trỏ = đổi bảng. Đây là vì sao time travel gần như miễn phí: các phiên bản cũ vẫn nằm đó.

Lý thuyết 1.4 — Chi phí đọc = số byte phải quét × số lần liệt kê

Trên lake, hai kẻ giết hiệu năng là (a) quét nhầm dữ liệu không cần, và (b) LIST hàng vạn file/thư mục để biết đọc gì. File format cột (Parquet) giải quyết (a); table format giải quyết (b) bằng cách lưu sẵn danh sách file + thống kê trong metadata, khỏi liệt kê thư mục.

2. Lakehouse thực chất là gì

Gói gọn một câu: Lakehouse = Object Storage + File format cột + Table format (metadata giao dịch) + Catalog. Không có gì huyền bí — chỉ là bốn lớp xếp lên nhau để lake "cư xử" như warehouse.

  ┌─────────────────────────────────────────────┐
  │  COMPUTE   Spark · Trino · Flink · Snowflake  │  ← nhiều engine cùng đọc/ghi
  ├─────────────────────────────────────────────┤
  │  CATALOG   Glue · REST · Unity · Nessie       │  ← "bảng nào ở đâu, phiên bản nào"
  ├─────────────────────────────────────────────┤
  │  TABLE FORMAT  Iceberg · Delta · Hudi         │  ← snapshot, ACID, schema, time travel
  ├─────────────────────────────────────────────┤
  │  FILE FORMAT   Parquet · ORC · Avro           │  ← byte dữ liệu thực tế (cột/hàng)
  ├─────────────────────────────────────────────┤
  │  OBJECT STORAGE   S3 · GCS · ADLS · MinIO     │  ← lưu rẻ, vô hạn, bất biến
  └─────────────────────────────────────────────┘
Năm lớp của một lakehouse. Khoá này tập trung vào hai lớp giữa: File format (M2) và Table format (M4–M14).

Module 02 — Nền tảng

File format nền tảng: Parquet, ORC, Avro

Table format ngồi trên file format, nên không hiểu file format thì không hiểu vì sao lakehouse nhanh. Câu hỏi cốt lõi: dữ liệu được xếp theo hàng hay theo cột? Lựa chọn này quyết định bạn quét bao nhiêu byte cho mỗi truy vấn.

› 1. Hàng vs Cột › 2. Parquet — giải phẫu › 3. Nén & encoding › 4. Predicate pushdown & column pruning › 5. ORC vs Avro — chọn cái nào › 6. Bệnh "small files"

1. Hàng vs Cột — cú lật nền tảng

Lưu theo hàng (CSV, JSON, Avro) gom mọi cột của một dòng cạnh nhau — tốt khi ghi và đọc cả dòng (OLTP, streaming ingest). Lưu theo cột (Parquet, ORC) gom mọi giá trị của một cột cạnh nhau — tốt khi đọc vài cột trên hàng triệu dòng (OLAP). Analytics gần như luôn chọn cột.

  Dữ liệu:  id | name  | amount
            1  | An    | 100
            2  | Bình  | 250

  ROW (Avro):   [1,An,100][2,Bình,250]      ← đọc 'amount' vẫn phải nhảy qua name
  COLUMN (Parquet): [1,2][An,Bình][100,250] ← đọc 'amount' = quét đúng 1 vùng liền
Cột cho phép chỉ quét cột cần (column pruning) + nén cực tốt vì giá trị cùng kiểu nằm cạnh nhau.

Hai lợi ích then chốt của cột: (1) column pruning — truy vấn chỉ đọc các cột nó cần, bỏ qua phần còn lại; (2) nén tốt hơn nhiều — dữ liệu cùng kiểu, thường lặp lại, nén theo cột đạt tỉ lệ cao hơn hẳn nén theo hàng.

2. Parquet — giải phẫu

Parquet là định dạng cột phổ biến nhất trong lakehouse. Cấu trúc phân tầng:

Row group

Khối ngang gồm nhiều dòng (mặc định ~128MB). Đơn vị song song hoá khi đọc.

Column chunk

Trong một row group, dữ liệu của một cột nằm liền nhau.

Page

Đơn vị nén/encoding nhỏ nhất trong column chunk (~1MB).

Footer (metadata)

Cuối file: schema + thống kê min/max/null count cho từng column chunk.

Chìa khoá hiệu năng

Footer chứa min/max mỗi row group. Truy vấn WHERE amount > 1000 sẽ bỏ qua nguyên row group nếu max của nó < 1000 — không đọc một byte dữ liệu nào. Đây là nền móng để table format ở tầng trên làm "data skipping" còn mạnh hơn.

3. Nén & encoding

Parquet encode trước, nén sau. Encoding phổ biến: dictionary (thay giá trị lặp bằng mã ngắn — tuyệt cho cột lực lượng thấp như country), RLE/bit-packing (run-length cho chuỗi giá trị lặp). Codec nén: snappy (mặc định, nhanh, cân bằng), zstd (nén tốt hơn, ngày càng được ưa), gzip (nén cao, chậm). Quy tắc thực dụng: dùng snappy hoặc zstd; tránh gzip cho dữ liệu nóng.

4. Predicate pushdown & column pruning

Hai kỹ thuật làm Parquet nhanh, được engine (Spark/Trino) tận dụng tự động:

Kỹ thuậtÝ nghĩaNhờ đâu
Column pruningChỉ đọc cột trong SELECT/WHEREBố cục theo cột
Predicate pushdownBỏ qua row group không khớp WHEREThống kê min/max ở footer

Bài học thiết kế: sắp xếp (sort) dữ liệu theo cột hay lọc làm min/max của mỗi row group hẹp lại → bỏ qua được nhiều hơn. Đây là lý do "sorting/clustering" (M11) tăng tốc truy vấn mạnh đến vậy.

5. ORC vs Avro — chọn cái nào

Parquet (cột)

Mặc định cho analytics. Hệ sinh thái rộng nhất, mọi table format đều dùng.

ORC (cột)

Tương tự Parquet, mạnh trong hệ Hive; có index nhẹ + bloom filter sẵn. Hudi/Iceberg hỗ trợ.

Avro (hàng)

Hàng + schema đính kèm. Tuyệt cho ghi & truyền tin (Kafka), schema evolution thân thiện. Iceberg dùng Avro cho file metadata.

Mẹo nhớ

Đọc nhiều, quét lớn → cột (Parquet/ORC). Ghi nhiều, đọc cả dòng, truyền message → hàng (Avro). Thú vị: Iceberg lưu dữ liệu bằng Parquet (cột) nhưng lưu metadata bằng Avro (hàng) — đúng công cụ cho đúng việc.

6. Bệnh "small files"

Streaming hay micro-batch hay đẻ ra hàng vạn file nhỏ vài KB. Hậu quả: mỗi file là một lần mở + đọc footer + lập lịch task → overhead khổng lồ, truy vấn chậm thê thảm dù dữ liệu bé. Đây là bệnh kinh điển của lake, và là lý do table format cần cơ chế compaction (M11) để gộp file nhỏ thành file ~128–512MB.

Dấu hiệu

Truy vấn đếm vài triệu dòng mà mất phút, Spark UI hiện hàng nghìn task tí hon, S3 phình số lượng object. → Gần như chắc chắn là small files. Vá bằng compaction định kỳ.

Module 03 — Động lực

Khi "thư mục = bảng" sụp đổ

Trước table format, cả ngành coi "bảng = một thư mục chứa file Parquet, partition = thư mục con key=value", với Hive Metastore giữ schema. Mô hình này chạy được nhiều năm nhưng có những vết nứt chí mạng trên object storage. Hiểu các vết nứt này là hiểu chính xác vấn đề mà Iceberg/Delta/Hudi sinh ra để vá.

› 1. Mô hình Hive table › 2. Năm vết nứt chí mạng › 3. Vì sao S3 làm mọi thứ tệ hơn › 4. Bảng yêu cầu gì để là "bảng thật"

1. Mô hình Hive table

Trong mô hình Hive: thư mục gốc là bảng; mỗi partition là thư mục con đặt tên dt=2024-01-01/; Hive Metastore (HMS) lưu schema + danh sách partition. Engine muốn đọc thì hỏi HMS lấy đường dẫn partition, rồi LIST thư mục để biết có file nào.

  s3://lake/sales/                 ← "bảng" = thư mục
    dt=2024-01-01/
      part-0000.parquet            ← phải LIST mới biết có file này
      part-0001.parquet
    dt=2024-01-02/
      part-0000.parquet
  Hive Metastore: schema + [dt=2024-01-01, dt=2024-01-02]   ← chỉ biết tới partition
"Bảng" chỉ là quy ước thư mục. Không ai ghi lại "đúng lúc này bảng gồm chính xác những file nào".

2. Năm vết nứt chí mạng

① Không nguyên tử (no atomicity)

Ghi nhiều file = nhiều thao tác. Người đọc xen vào giữa thấy bảng "nửa nạc nửa mỡ". Job lỗi giữa chừng để lại file rác không ai dám xoá.

② Liệt kê đắt đỏ

Biết đọc gì = LIST mọi thư mục partition. Bảng triệu file → liệt kê tốn phút và tiền API.

③ Không có schema evolution an toàn

Đổi cột dựa vào vị trí/tên; thêm/đổi/xoá cột dễ làm đọc sai cột vào nhau, im lặng.

④ Partition cứng nhắc

Đổi cách partition = viết lại cả bảng. Người dùng phải biết cột partition và lọc đúng nó mới nhanh.

⑤ Không time travel / rollback

Ghi đè là mất luôn dữ liệu cũ. Sai một phát không có nút undo; không audit được "hôm qua bảng ra sao".

⑥ Không UPDATE/DELETE

Muốn sửa/xoá vài dòng phải đọc–lọc–ghi lại nguyên partition bằng tay. GDPR "xoá theo user" là ác mộng.

3. Vì sao S3 làm mọi thứ tệ hơn

HDFS có thao tác rename thư mục gần như nguyên tử — nhiều job Hive lợi dụng "ghi vào thư mục tạm rồi rename" để giả lập atomicity. Nhưng object storage không có rename thật: "đổi tên" = copy từng object rồi xoá, vừa chậm vừa không nguyên tử. Thêm nữa, LIST trên S3 chỉ nhất quán cuối cùng (eventually consistent) trong quá khứ, nên có lúc engine không thấy file vừa ghi. Mô hình Hive vốn đã yếu, lên S3 thì gãy hẳn.

Gốc rễ

Mọi vết nứt quy về một nguyên nhân: "trạng thái bảng" được suy ra từ việc liệt kê hệ thống file, chứ không được ghi rõ ràng và cập nhật nguyên tử ở đâu cả. Table format vá đúng chỗ này: ghi một danh sách file tường minh, đổi nó bằng một thao tác nguyên tử.

4. Bảng yêu cầu gì để là "bảng thật"

Từ các vết nứt trên, ta rút ra "đặc tả" cho một table format tử tế — và đây chính là checklist để so sánh Iceberg/Delta/Hudi ở M13:

Commit nguyên tử

Đổi bảng = một thao tác all-or-nothing, người đọc không bao giờ thấy trạng thái dở.

Danh sách file tường minh

Metadata nói rõ bảng gồm file nào — khỏi LIST thư mục.

Snapshot isolation

Người đọc thấy một phiên bản đông cứng kể cả khi đang có ghi.

Schema/partition evolution

Đổi cấu trúc không cần viết lại dữ liệu, không đọc sai cột.

Time travel + rollback

Đọc/khôi phục phiên bản cũ theo id hoặc thời gian.

Row-level UPDATE/DELETE/MERGE

Sửa/xoá/hợp nhất dòng mà không viết lại cả partition.

Tình huống thực tế

Bối cảnh: Pháp chế yêu cầu xoá toàn bộ dữ liệu của một khách (GDPR). Bảng Hive 3 năm, partition theo ngày, khách đó rải rác khắp nơi. Cách cũ: quét mọi partition, lọc bỏ khách đó, ghi lại — hàng giờ tính toán, rủi ro hỏng bảng, không nguyên tử. Cách lakehouse: DELETE FROM sales WHERE customer_id = 42 — một câu SQL, nguyên tử, table format tự xử lý ở mức dòng (M14 sẽ giải thích delete file/deletion vector). Đây là sự khác biệt một trời một vực mà M04 bắt đầu mở ra.

Module 04 — Khái niệm lõi

Table format & lớp metadata

Đây là module bản lề. Một table format là một đặc tả về metadata đặt trên các file dữ liệu, biến một đống Parquet thành một cái bảng có ACID. Hiểu mô hình tổng quát ở đây thì đọc Iceberg/Delta/Hudi (M05–07) sẽ thấy chúng chỉ là các hiện thực khác nhau của cùng một ý tưởng.

› 1. Định nghĩa & ranh giới với file format › 2. Mô hình chung: snapshot + danh sách file › 3. Commit nguyên tử diễn ra thế nào › 4. Data skipping nhờ thống kê › 5. Ba ứng viên: nhìn nhanh

1. Định nghĩa & ranh giới

TABLE FORMAT

Một đặc tả định nghĩa tập hợp file nào tạo nên một bảng tại một phiên bản, cùng schema, partition, thống kê và lịch sử thay đổi — đủ để hỗ trợ commit nguyên tử, snapshot isolation, time travel và evolution. Nó bao bọc file format (Parquet) chứ không thay thế.

Ranh giới dễ lẫn: File format (Parquet) trả lời "các byte trong một file được sắp ra sao". Table format (Iceberg) trả lời "những file nào hợp thành bảng, ở phiên bản nào, schema gì". Một bảng Iceberg vẫn chứa file Parquet bên dưới.

2. Mô hình chung: snapshot + danh sách file

Bỏ qua khác biệt thuật ngữ, cả ba format đều theo khuôn này:

  CATALOG ──trỏ tới──► METADATA hiện hành
                          │
                          ├─ snapshot S2 (mới)  ──► [danh sách file: f1, f3, f4]
                          ├─ snapshot S1        ──► [danh sách file: f1, f2]
                          └─ snapshot S0        ──► [danh sách file: f1]
                                                       │

Mỗi snapshot = ảnh chụp "bảng gồm những file này". Ghi mới = tạo snapshot mới + đổi con trỏ. File cũ vẫn còn → time travel.

3. Commit nguyên tử diễn ra thế nào

Mấu chốt của ACID trên object storage là biến "đổi bảng" thành một thao tác nguyên tử duy nhất:

  1. Engine ghi các file dữ liệu mới (Parquet) ra storage — chưa ai thấy chúng, vì metadata chưa trỏ tới.
  2. Engine tạo metadata mới mô tả snapshot mới (gồm file cũ còn giữ + file mới).
  3. Engine thực hiện một thao tác nguyên tử để "công bố" snapshot mới: đổi con trỏ trong catalog (Iceberg), hoặc tạo file log kế tiếp 000N.json (Delta). Thao tác này hoặc thành công trọn vẹn, hoặc không có gì xảy ra.
Vì sao điều này đủ để có ACID

Trước bước 3, người đọc vẫn thấy snapshot cũ (file mới vô hình). Sau bước 3, mọi người thấy snapshot mới trọn vẹn. Không có khoảnh khắc nào lộ ra trạng thái dở. Đó là Atomicity + Isolation. Durability nhờ object storage; Consistency nhờ kiểm tra xung đột trước khi đổi con trỏ (M08).

4. Data skipping nhờ thống kê

Metadata không chỉ liệt kê file — nó còn lưu thống kê mỗi file: min/max từng cột, số dòng, số null, giá trị partition. Nhờ đó, trước khi đọc bất kỳ byte dữ liệu nào, engine đã loại được phần lớn file không khớp WHERE. Đây là tầng data skipping thứ hai, mạnh hơn cả min/max trong footer Parquet (M02) vì nó loại nguyên file, ở cấp metadata, cực rẻ.

Ba tầng lọc cộng dồn

(1) Catalog/metadata loại file theo partition + min/max → (2) Parquet footer loại row group → (3) page index loại page. Mỗi tầng quét ít hơn tầng trước. Thiết kế tốt (sort/partition hợp lý, M10–11) làm cả ba tầng hiệu quả.

Module 05 — Table Format

Apache Iceberg

Iceberg do Netflix tạo ra (2018) để vá đúng các vết nứt của Hive ở quy mô petabyte. Nó được xem là thiết kế "sạch" nhất: phân tách rõ catalog – metadata – manifest – data, hỗ trợ hidden partitioning, partition evolution và đa engine mở. Đây là format đáng học kỹ nhất vì đang dần thành chuẩn chung.

› 1. Kiến trúc bốn tầng metadata › 2. Manifest & manifest list › 3. Hidden partitioning › 4. Partition & schema evolution › 5. Format v1 vs v2 (row-level delete) › 6. SQL trên Iceberg

1. Kiến trúc bốn tầng metadata

Iceberg xếp metadata thành một cây trỏ xuống dần tới file dữ liệu:

  CATALOG  (Glue/REST/Nessie…)
     │  trỏ tới file metadata hiện hành (con trỏ nguyên tử)
     ▼
  vN.metadata.json   ── schema, partition spec, danh sách snapshot
     │
     ▼
  manifest list  (avro, 1 file / snapshot)  ── liệt kê các manifest + thống kê partition
     │
     ▼
  manifest files (avro)  ── liệt kê data file + min/max mỗi cột + partition data
     │
     ▼
  DATA FILES (Parquet/ORC/Avro)  ── dữ liệu thật, bất biến
Đọc bảng = đọc metadata.json → manifest list của snapshot → lọc manifest → lọc data file. Toàn bộ trước khi chạm dữ liệu.

Điểm tinh tế: con trỏ "file metadata hiện hành" nằm ở catalog, và commit = đổi con trỏ này một cách nguyên tử (compare-and-swap). Mọi thứ dưới nó là bất biến.

2. Manifest & manifest list

Manifest file liệt kê một nhóm data file kèm thống kê (min/max từng cột, số dòng, null count, giá trị partition). Manifest list là "mục lục của các manifest" cho một snapshot, kèm thống kê tổng hợp partition của từng manifest. Hai tầng này cho phép lọc dần: bỏ manifest không liên quan, rồi bỏ data file không khớp — tất cả ở cấp metadata, không cần LIST thư mục.

Vì sao nhanh ở quy mô lớn

Khi ghi mới, Iceberg thường chỉ tạo thêm manifest mới cho file mới, tái dùng manifest cũ. Lập kế hoạch truy vấn (query planning) chỉ đọc vài file metadata thay vì LIST hàng triệu object — đây là khác biệt sống còn so với Hive khi bảng lớn.

3. Hidden partitioning — đặc sản của Iceberg

Ở Hive, người dùng phải tự biết bảng partition theo cột nào và phải lọc đúng cột đó (vd phải WHERE dt='2024-01-01'); lọc theo event_time thường quét full bảng vì engine không nối được event_time với dt. Iceberg dùng partition transform: bạn khai báo "partition theo day(event_time)", Iceberg lưu quan hệ này trong metadata và tự suy ra partition từ event_time.

iceberg-hidden-partition
CREATE TABLE sales (id BIGINT, amount DECIMAL, event_time TIMESTAMP) USING iceberg PARTITIONED BY (day(event_time)); -- Người dùng KHÔNG cần biết cột partition. Lọc theo cột gốc là đủ: SELECT sum(amount) FROM sales WHERE event_time >= '2024-01-01'; -- Iceberg tự cắt tỉa đúng các partition ngày → không quét full bảng

Các transform có sẵn: year/month/day/hour, bucket(N, col) (băm thành N bucket — hay cho id lực lượng cao), truncate(L, col) (cắt chuỗi/số). Không còn cảnh tạo cột dt thủ công và cầu người dùng nhớ lọc nó.

4. Partition & schema evolution

Iceberg gán field ID cho mỗi cột (không dựa vào tên/vị trí). Nhờ đó add / drop / rename / reorder cột đều an toàn, không bao giờ đọc nhầm cột này thành cột kia. Quan trọng hơn: partition evolution — đổi cách partition (vd từ day sang hour) không cần viết lại dữ liệu cũ. Dữ liệu cũ giữ partition spec cũ, dữ liệu mới dùng spec mới; Iceberg đọc đúng cả hai.

Đây là thứ Hive không bao giờ làm được

Ở Hive, đổi partition = di tản toàn bộ bảng. Iceberg coi partition spec là một phần metadata có phiên bản, nên đổi spec chỉ tốn một commit. Cùng tinh thần "đổi metadata, không đụng dữ liệu" của cả lakehouse.

5. Format v1 vs v2 (row-level delete)

Iceberg có hai phiên bản đặc tả. v1: chỉ append/overwrite ở cấp file (copy-on-write). v2: thêm delete file để xoá/cập nhật ở cấp dòng mà không viết lại file lớn (merge-on-read). Hai kiểu delete: position delete (xoá theo file+vị trí dòng) và equality delete (xoá theo điều kiện giá trị, hợp với CDC). Chi tiết cơ chế ở M14.

6. SQL trên Iceberg (Spark)

iceberg-sql
-- MERGE/UPSERT ngay trên data lake MERGE INTO sales t USING staging s ON t.id = s.id WHEN MATCHED THEN UPDATE SET * WHEN NOT MATCHED THEN INSERT *; -- Time travel theo snapshot id hoặc thời gian SELECT * FROM sales VERSION AS OF 3821550127947089009; SELECT * FROM sales TIMESTAMP AS OF '2024-01-01 00:00:00'; -- Soi metadata qua bảng hệ thống SELECT * FROM sales.snapshots; SELECT * FROM sales.files;
Tình huống thực tế

Bối cảnh: Bảng event 2 năm đang partition theo day, giờ lượng dữ liệu tăng gấp 10, bạn muốn partition theo hour để truy vấn nhanh hơn — nhưng không thể downtime để viết lại 200TB. Iceberg: ALTER TABLE … REPLACE PARTITION FIELD day(event_time) WITH hour(event_time). Dữ liệu cũ giữ nguyên (vẫn đọc được), dữ liệu mới partition theo giờ. Một commit, zero rewrite. Truy vấn vẫn đúng vì Iceberg đọc đúng spec cho từng file.

Module 06 — Table Format

Delta Lake

Delta Lake do Databricks tạo (mã nguồn mở 2019). Triết lý của nó đơn giản đến mức đẹp: một transaction log dạng các file JSON đánh số tăng dần là nguồn sự thật duy nhất của bảng. Delta tích hợp cực mượt với Spark/Databricks và có MERGE, OPTIMIZE, Z-ORDER rất mạnh.

› 1. Transaction log _delta_log › 2. Một commit gồm gì › 3. Checkpoint & đọc nhanh › 4. OPTIMIZE, Z-ORDER, VACUUM › 5. MERGE & deletion vectors › 6. SQL trên Delta

1. Transaction log _delta_log

Mỗi bảng Delta có thư mục _delta_log/ chứa các file commit JSON đánh số: 00000.json, 00001.json, … Mỗi file ghi lại những thay đổi của một commit (thêm file nào, bỏ file nào, đổi schema gì). "Trạng thái bảng hiện tại" = phát lại (replay) toàn bộ log từ đầu, cộng dồn các action.

  s3://lake/sales/
    _delta_log/
      00000000000000000000.json   ← commit 0: add f1, f2 (+ metaData, protocol)
      00000000000000000001.json   ← commit 1: add f3, remove f2
      00000000000000000010.checkpoint.parquet  ← ảnh chụp gộp tới commit 10
      _last_checkpoint            ← trỏ checkpoint mới nhất
    part-0001.parquet  part-0003.parquet  …   ← data file (bất biến)
Log = nguồn sự thật. Data file chỉ "tồn tại trong bảng" nếu một commit add nó và chưa commit nào remove nó.

2. Một commit gồm gì

Các loại "action" chính trong một file commit JSON:

ActionÝ nghĩa
addThêm một data file vào bảng (kèm thống kê min/max, số dòng)
removeLoại một data file khỏi bảng (tombstone, file vẫn nằm trên đĩa tới khi VACUUM)
metaDataSchema, partition columns, cấu hình bảng
protocolPhiên bản reader/writer tối thiểu (để bật tính năng mới an toàn)
commitInfoThông tin audit: ai, lúc nào, thao tác gì

Commit nguyên tử nhờ: tạo file 000N.json chỉ thành công nếu N chưa tồn tại (put-if-absent). Hai writer cùng nhắm N → chỉ một thắng; kẻ thua thử lại với N+1 (M08).

3. Checkpoint & đọc nhanh

Phát lại hàng nghìn file JSON sẽ chậm. Nên định kỳ (mặc định mỗi 10 commit) Delta ghi một checkpoint Parquet — ảnh chụp gộp toàn bộ trạng thái tới thời điểm đó. Reader chỉ cần đọc checkpoint gần nhất rồi phát lại vài commit JSON sau nó. File _last_checkpoint trỏ tới checkpoint mới nhất.

Đối chiếu với Iceberg

Iceberg gắn con trỏ trạng thái vào catalog và dùng cây manifest. Delta gắn trạng thái vào log file trong chính thư mục bảng và dùng replay + checkpoint. Hai cách khác nhau, cùng đạt ACID. Delta gọn khi một bảng do một hệ Spark quản lý; Iceberg mạnh khi nhiều engine độc lập cùng tham gia.

4. OPTIMIZE, Z-ORDER, VACUUM

OPTIMIZE

Gộp file nhỏ thành file lớn (~1GB) — vá small files (M02/M11). bin-packing.

Z-ORDER

Sắp lại dữ liệu theo nhiều cột cùng lúc (đường cong Z) để data skipping tốt trên nhiều chiều lọc.

VACUUM

Xoá vật lý các file đã remove quá thời hạn giữ (mặc định 7 ngày). Dọn rác thật sự.

Bẫy VACUUM ↔ time travel

VACUUM xoá file cũ vĩnh viễn → time travel chỉ lùi được trong phạm vi retention. Đặt retention quá ngắn rồi VACUUM = mất khả năng quay về phiên bản cũ. Cân nhắc nhu cầu audit trước khi rút ngắn.

5. MERGE & deletion vectors

Delta nổi tiếng với MERGE INTO mạnh và biểu cảm — nền tảng cho mọi pipeline upsert/CDC. Mặc định Delta dùng copy-on-write: cập nhật/xoá vài dòng → viết lại các file chứa chúng. Tính năng mới hơn deletion vectors ghi "dòng nào bị xoá" thành một file phụ (soft delete), tránh viết lại file lớn — đây là kiểu merge-on-read của Delta, giảm write amplification rõ rệt (M14).

6. SQL trên Delta

delta-sql
MERGE INTO sales t USING updates u ON t.id = u.id WHEN MATCHED THEN UPDATE SET * WHEN NOT MATCHED THEN INSERT *; OPTIMIZE sales ZORDER BY (customer_id); DELETE FROM sales WHERE customer_id = 42; -- Time travel SELECT * FROM sales VERSION AS OF 12; SELECT * FROM sales TIMESTAMP AS OF '2024-01-01'; VACUUM sales RETAIN 168 HOURS;
Tình huống thực tế

Bối cảnh: Pipeline CDC mỗi 5 phút merge thay đổi từ Postgres vào bảng sales. Sau vài ngày, truy vấn BI chậm dần. Chẩn đoán: mỗi micro-batch sinh file nhỏ + nhiều lần MERGE copy-on-write làm phân mảnh. Xử lý: lịch OPTIMIZE … ZORDER BY (customer_id, dt) hằng đêm để gộp + sắp lại, bật deletion vectors để giảm rewrite, và VACUUM với retention hợp lý. Truy vấn nhanh lại; chi phí ghi giảm.

Module 07 — Table Format

Apache Hudi

Hudi (Hadoop Upserts Deletes and Incrementals) do Uber tạo (2017) — sớm nhất trong ba format. Nó sinh ra cho một bài toán rất cụ thể: nạp dữ liệu liên tục với cập nhật ở mức bản ghi (CDC, streaming) và đọc incremental. Nếu workload của bạn là upsert tần suất cao, Hudi có những thứ hai format kia mới bắt kịp sau này.

› 1. Copy-on-Write vs Merge-on-Read › 2. Record key, file group, timeline › 3. Index — bí quyết upsert nhanh › 4. Ba kiểu truy vấn › 5. Khi nào chọn Hudi

1. Copy-on-Write vs Merge-on-Read

Hudi cho bạn chọn kiểu bảng theo cân bằng đọc/ghi — đây là khái niệm cốt lõi (và sẽ tổng quát hoá ở M14 cho cả ba format):

Copy-on-Write (CoW)

Cập nhật → viết lại nguyên file base chứa dòng đó. Đọc nhanh (chỉ Parquet thuần), ghi đắt. Hợp khi đọc nhiều, cập nhật vừa phải.

Merge-on-Read (MoR)

Cập nhật → ghi vào log file delta (Avro). Đọc phải hợp nhất base + log. Ghi nhanh (độ trễ thấp), đọc đắt hơn tới khi compaction. Hợp streaming/CDC tần suất cao.

  CoW:  update → [base v2.parquet]            đọc: chỉ base   (nhanh)
  MoR:  update → [base.parquet] + [.log Avro]  đọc: base ⊕ log (cần merge)
                         │ compaction định kỳ
                         ▼
                    [base mới gộp log]          → đọc nhanh trở lại
MoR tách "độ trễ ghi" khỏi "chi phí đọc": ghi rẻ tức thì, trả nợ đọc dần qua compaction nền.

2. Record key, file group, timeline

Khác biệt tư duy lớn nhất của Hudi: nó biết mỗi bản ghi là ai. Mỗi dòng có record key (khoá nghiệp vụ) và thuộc một partition path; các bản ghi cùng khoá luôn rơi vào cùng một file group. Nhờ vậy "cập nhật khách 42" biết chính xác file group nào chứa khách 42 — không quét cả bảng. Timeline (trong thư mục .hoodie) ghi mọi "instant": commit, deltacommit, compaction, cleaning, rollback — đây là log giao dịch của Hudi.

3. Index — bí quyết upsert nhanh

Để upsert nhanh, Hudi phải trả lời "record key này đang nằm ở file nào?" cực nhanh. Đó là việc của index:

IndexCơ chếHợp khi
Bloom (mặc định)Bloom filter trên record key trong mỗi fileKhoá tăng dần, phổ thông
SimpleJoin thẳng với dữ liệu để tìm vị tríCập nhật rải đều, bảng vừa
BucketBăm khoá vào số bucket cố địnhThroughput cao, độ trễ ổn định
Record Level IndexIndex khoá→file trong metadata tableTra cứu điểm nhanh ở quy mô lớn
Đây là thứ Iceberg/Delta vốn không có

Iceberg/Delta tìm dòng cần sửa bằng quét + thống kê file. Hudi có index khoá → file nên upsert điểm rất nhanh — lợi thế rõ khi CDC bắn cập nhật rải rác liên tục. Đổi lại, phải duy trì index.

4. Ba kiểu truy vấn

Snapshot

Thấy dữ liệu mới nhất (với MoR = base ⊕ log). Đây là truy vấn "bình thường".

Read-Optimized

Chỉ đọc base file (bỏ log chưa compaction) → nhanh nhưng có thể thiếu cập nhật mới nhất. Chỉ MoR.

Incremental

Chỉ lấy các bản ghi thay đổi sau một instant — nền cho pipeline tăng dần, khỏi quét full.

Truy vấn incremental là đặc sản: thay vì mỗi lần chạy lại quét cả bảng, downstream chỉ kéo phần thay đổi từ lần chạy trước — tiết kiệm khổng lồ cho pipeline CDC (liên hệ M15).

5. Khi nào chọn Hudi

Hudi toả sáng khi…

…workload là upsert/CDC tần suất cao, độ trễ thấp, cần truy vấn incremental, và bạn muốn kiểm soát chi tiết cân bằng đọc/ghi (CoW vs MoR, loại index, lịch compaction). Đổi lại, Hudi nhiều "nút vặn" hơn → đường học dốc hơn và cần tinh chỉnh.

Tình huống thực tế

Bối cảnh: Bạn nhận luồng CDC từ MySQL (Debezium → Kafka) với hàng nghìn update/giây trải khắp bảng orders; SLA: dữ liệu trễ < 1 phút. Vì sao Hudi: chọn bảng MoR để ghi delta cực nhanh (độ trễ thấp), dùng bucket index cho throughput ổn định, lịch compaction nền mỗi vài phút để giữ đọc nhanh, và cấp truy vấn read-optimized cho dashboard không cần realtime tuyệt đối. Đây đúng "sân nhà" của Hudi. (Iceberg v2/Delta deletion vectors nay cũng làm được, nhưng Hudi tối ưu sẵn cho kịch bản này.)

Module 08 — Cơ chế lõi

ACID & Concurrency

Đây là "phép màu" mà table format hứa hẹn: ACID trên object storage vốn không có khoá phân tán. Bí mật là optimistic concurrency control dựa trên một thao tác nguyên tử duy nhất. Hiểu nó rồi bạn sẽ biết vì sao đôi khi commit bị "retry" và làm sao tránh xung đột.

1. ACID nghĩa là gì ở đây

2. Snapshot isolation

Khi một truy vấn bắt đầu, nó "ghim" vào snapshot/version hiện hành tại thời điểm đó và đọc trọn vẹn snapshot ấy — kể cả nếu giữa chừng có writer tạo snapshot mới. Người đọc không bao giờ thấy nửa kết quả của một ghi đang chạy. Đây là lý do dashboard không bao giờ "nhấp nháy" dữ liệu dở khi pipeline đang nạp.

Hệ quả thực dụng

Một báo cáo dài 20 phút vẫn cho kết quả nhất quán dù bảng được ghi 5 lần trong lúc đó — vì nó đọc snapshot đã ghim lúc bắt đầu. Muốn số mới, chạy lại (ghim snapshot mới).

3. Optimistic concurrency control (OCC)

Không có khoá. Thay vào đó, mỗi writer "lạc quan" giả định không ai đụng cùng lúc, làm việc, rồi tới phút chót mới kiểm tra:

  1. ĐỌC trạng thái hiện tại (snapshot N)
  2. Ghi data file mới ra storage (chưa công bố)
  3. Chuẩn bị metadata cho snapshot N+1
  4. COMMIT nguyên tử: "đổi N → N+1, CHỈ KHI hiện tại vẫn là N"
        ├─ thành công → xong
        └─ thất bại (ai đó đã commit N+1 trước) → KIỂM TRA xung đột → THỬ LẠI từ (1)
Cơ chế compare-and-swap: ai chạm vạch đích trước thì thắng; kẻ sau kiểm tra xung đột rồi thử lại.

Iceberg hiện thực bước 4 bằng compare-and-swap con trỏ ở catalog. Delta bằng "tạo file 000N.json chỉ khi N chưa tồn tại". Cùng một ý tưởng.

4. Xung đột & cách giảm

Khi hai writer cùng nhắm phiên bản kế tiếp, một sẽ phải thử lại. Liệu thử lại có an toàn không phụ thuộc loại thao tác: hai append vào vùng khác nhau thường hoà giải được; hai cái cùng sửa-xoá đụng nhau có thể phải abort.

Tách writer theo partition

Cho mỗi job ghi vùng riêng → ít đụng độ, retry rẻ.

Một writer cho mỗi bảng nóng

Gom ghi vào một tiến trình/đợt thay vì nhiều job đua nhau.

Tách compaction khỏi giờ cao điểm

Bảo trì (OPTIMIZE/compaction) dễ đụng ghi; lịch vào lúc vắng.

Bẫy thường gặp

Nhiều job Spark độc lập cùng MERGE vào một bảng mỗi phút → bão xung đột, retry liên tục, throughput sụp. Giải: hợp nhất thành một writer, hoặc phân vùng ghi, hoặc dùng format/cấu hình hợp cho ghi đồng thời (vd Hudi bucket index, hoặc tách bảng).

Module 09 — Tính năng

Time Travel & Rollback

Vì file dữ liệu bất biến và mỗi commit là một snapshot mới, các phiên bản cũ vẫn còn nguyên — nên "du hành thời gian" gần như miễn phí. Đây không chỉ là tính năng hay ho: nó là công cụ vận hành để debug, audit, tái lập và cứu hộ khi sự cố.

› 1. Cơ chế: vì sao gần như miễn phí › 2. Truy vấn theo phiên bản / thời gian › 3. Rollback & restore › 4. Use case & giới hạn (retention)

1. Cơ chế: vì sao gần như miễn phí

Time travel không cần sao lưu riêng. Mỗi snapshot đã trỏ tới một tập file cụ thể; đọc phiên bản cũ = đọc metadata của snapshot cũ và các file nó tham chiếu (vẫn còn trên đĩa cho tới khi bị dọn). Chi phí thêm gần bằng 0 — bạn chỉ "trả tiền lưu trữ" cho các file cũ chưa xoá.

2. Truy vấn theo phiên bản / thời gian

time-travel
-- Iceberg SELECT * FROM t VERSION AS OF 3821550127947089009; -- snapshot id SELECT * FROM t TIMESTAMP AS OF '2024-01-01 09:00:00'; -- Delta SELECT * FROM t VERSION AS OF 12; -- version number SELECT * FROM t TIMESTAMP AS OF '2024-01-01'; -- So sánh "trước vs sau" để truy ra cái gì đã đổi SELECT * FROM t VERSION AS OF 12 EXCEPT SELECT * FROM t VERSION AS OF 11;

3. Rollback & restore

Khi một job ghi hỏng dữ liệu, bạn không phải khôi phục từ backup — chỉ cần trỏ bảng về snapshot tốt cuối cùng:

rollback
-- Iceberg: quay bảng về một snapshot CALL sys.rollback_to_snapshot('db.t', 3821550127947089009); -- Delta: khôi phục về một version (tạo commit mới "giống" version cũ) RESTORE TABLE t TO VERSION AS OF 11;
Rollback cũng là một commit

"Quay về v11" không xoá lịch sử — nó tạo trạng thái mới phản ánh v11. Bản thân hành động khôi phục được ghi lại, nên vẫn audit được. Lịch sử là append-only.

4. Use case & giới hạn

Tái lập (reproducibility)

Train lại ML model trên đúng dữ liệu của ngày X; chạy lại báo cáo y hệt tháng trước.

Audit & debug

"Số liệu đổi lúc nào, do commit nào?" — so hai snapshot là ra.

Cứu hộ sự cố

Job lỗi ghi rác → rollback tức thì, không cần restore backup.

Giới hạn: retention

Time travel chỉ lùi được tới khi các file cũ vẫn còn. Dọn rác (Delta VACUUM, Iceberg expire_snapshots) xoá file cũ → cắt mất khả năng quay lui xa. Phải cân giữa chi phí lưu (giữ nhiều phiên bản) và nhu cầu audit/tái lập. Đặt chính sách retention có chủ đích, đừng để mặc định quyết hộ.

Module 10 — Tính năng

Schema & Partition Evolution

Dữ liệu sống thì cấu trúc phải đổi: thêm cột, đổi tên, đổi cách chia partition. Hive làm việc này rất đau (dễ đọc sai cột, đổi partition = viết lại bảng). Table format biến evolution thành thao tác metadata an toàn, gần như zero-cost. Đây là một trong những lý do mạnh nhất để chuyển sang lakehouse.

› 1. Schema evolution an toàn nhờ field ID › 2. Thao tác schema được phép › 3. Partition evolution › 4. Schema enforcement & mergeSchema

1. Schema evolution an toàn nhờ field ID

Vấn đề kinh điển của Hive/Parquet thuần: cột được nhận diện theo tên hoặc vị trí. Xoá cột giữa bảng rồi thêm cột mới → các file cũ và mới lệch vị trí, engine đọc nhầm cột này thành cột kia, im lặng không báo lỗi. Iceberg (và Delta ở mức tính năng) gán ID bất biến cho mỗi cột; đọc/ghi map theo ID, nên đổi tên hay reorder không bao giờ trộn dữ liệu cột.

Trực giác

Field ID giống số chứng minh thư của cột: đổi tên (đổi nhãn) thì người vẫn là người đó. Hive định danh cột bằng "chỗ ngồi" — đổi chỗ là nhầm người.

2. Thao tác schema được phép

3. Partition evolution

Iceberg cho đổi partition spec mà không viết lại dữ liệu (đã gặp ở M05). Dữ liệu cũ giữ spec cũ, dữ liệu mới theo spec mới; engine đọc đúng cả hai nhờ mỗi data file ghi kèm spec của nó. Delta cách tiếp cận khác: dùng liquid clustering / Z-order thay cho partition cứng, hoặc generated columns. Điểm chung: thoát khỏi cảnh "chọn sai partition là phải di tản cả bảng".

  Trước:  PARTITION BY day(ts)
                       │ ALTER … REPLACE PARTITION FIELD (1 commit, 0 rewrite)
                       ▼
  Sau:    PARTITION BY hour(ts)
     data cũ → đọc theo spec day   ┐
     data mới → đọc theo spec hour  ┘→ cùng một truy vấn, kết quả đúng
Partition spec có phiên bản, gắn theo từng file. Đổi spec là metadata, không phải di chuyển dữ liệu.

4. Schema enforcement & mergeSchema

Evolution không có nghĩa "ghi gì cũng nhận". Mặc định table format enforce schema: ghi dữ liệu lệch schema sẽ bị từ chối (bảo vệ chất lượng — liên hệ M10 Data Quality của khoá). Khi chủ đích muốn thêm cột lúc ghi, bật cờ tường minh:

evolve-schema
# Delta (PySpark): cho phép thêm cột mới khi append df.write.format("delta").mode("append") \ .option("mergeSchema", "true").save(path) -- Iceberg: tiến hoá schema bằng DDL tường minh ALTER TABLE t ADD COLUMN channel STRING; ALTER TABLE t RENAME COLUMN amt TO amount;
Tình huống thực tế

Bối cảnh: Team app thêm trường discount_code vào event. Nếu là bảng Hive/Parquet thuần, pipeline hoặc vỡ, hoặc tệ hơn — đọc lệch cột mà không ai biết. Lakehouse: ALTER TABLE events ADD COLUMN discount_code STRING (hoặc mergeSchema). Event cũ trả NULL cho cột mới, event mới có giá trị, không viết lại 1 byte dữ liệu cũ, không downtime. Schema được quản lý như một phần của bảng, có lịch sử.

Module 11 — Vận hành

Bảo trì & Compaction

Lakehouse không "tự chạy mãi mà không cần chăm". Ghi liên tục đẻ ra file nhỏ, snapshot cũ chất đống, file mồ côi tồn đọng. Không bảo trì → truy vấn chậm dần và chi phí phình. Module này là cẩm nang giữ bảng khoẻ.

› 1. Bốn việc bảo trì cốt lõi › 2. Compaction (bin-pack) › 3. Sorting / Z-order / clustering › 4. Dọn snapshot & file mồ côi › 5. Lịch bảo trì gợi ý

1. Bốn việc bảo trì cốt lõi

① Compaction

Gộp nhiều file nhỏ thành ít file lớn (~128MB–1GB). Trị bệnh small files.

② Sắp xếp dữ liệu

Sort/Z-order/cluster để min/max hẹp lại → data skipping tốt hơn.

③ Hết hạn snapshot

Bỏ snapshot cũ quá retention để cắt phình metadata + cho phép dọn data.

④ Dọn file mồ côi

Xoá file không snapshot nào tham chiếu (do job lỗi/bỏ dở để lại).

2. Compaction (bin-pack)

Compaction đọc nhiều file nhỏ và viết lại thành file kích thước mục tiêu. Đây là thao tác metadata an toàn: tạo snapshot mới trỏ tới file đã gộp, snapshot cũ vẫn còn (time travel không vỡ). Lưu ý nó tốn I/O ghi, nên lịch vào giờ vắng và tách khỏi writer chính (M08).

compaction
-- Iceberg: gộp file nhỏ CALL sys.rewrite_data_files(table => 'db.sales'); -- Delta: gộp + (tuỳ chọn) Z-order OPTIMIZE sales; OPTIMIZE sales ZORDER BY (customer_id, dt); # Hudi (MoR): gộp log vào base bằng compaction (inline hoặc async) spark.sql("CALL run_compaction(op => 'run', table => 'sales')")

3. Sorting / Z-order / clustering

Compaction trị số lượng file; sắp xếp trị chất lượng bố cục. Nếu dữ liệu trong file được sort theo cột hay lọc, min/max mỗi file hẹp → engine bỏ qua nhiều file hơn. Với một chiều lọc: dùng sort tuyến tính. Với nhiều chiều lọc đồng thời: dùng Z-order (Delta) hoặc liquid clustering — sắp theo đường cong lấp đầy không gian để mọi chiều đều "tạm tốt".

Quy tắc chọn cột

Sort/cluster theo cột hay xuất hiện trong WHERE và có lực lượng cao (vd customer_id, event_time). Cột lực lượng thấp (vd country 5 giá trị) hợp làm partition hơn là sort key.

4. Dọn snapshot & file mồ côi

cleanup
-- Iceberg: hết hạn snapshot cũ hơn 7 ngày CALL sys.expire_snapshots('db.sales', TIMESTAMP '2024-01-01 00:00:00'); -- Iceberg: xoá file mồ côi (cẩn thận thời gian!) CALL sys.remove_orphan_files(table => 'db.sales'); -- Delta: dọn file đã remove quá retention VACUUM sales RETAIN 168 HOURS;
Bẫy chí mạng

remove_orphan_files / VACUUM với ngưỡng thời gian quá ngắn có thể xoá file của writer đang chạy hoặc truy vấn dài đang đọc → hỏng dữ liệu/truy vấn. Luôn để khoảng an toàn lớn hơn job dài nhất của bạn (thường ≥ 24h). Đây là thao tác nguy hiểm nhất khi vận hành lakehouse.

Module 12 — Hệ sinh thái

Catalog & Governance

Table format định nghĩa cấu trúc một bảng; catalog trả lời "có những bảng nào, mỗi bảng đang ở metadata/version nào, ai được đụng vào". Catalog là điểm hợp nhất để nhiều engine cùng thấy một sự thật — và là nơi gắn quyền truy cập, audit, dòng dõi dữ liệu.

› 1. Catalog làm gì › 2. Các loại catalog › 3. REST catalog & catalog "git-like" › 4. Governance: quyền, audit, lineage

1. Catalog làm gì

Với Iceberg, catalog giữ con trỏ nguyên tử tới file metadata hiện hành của mỗi bảng — chính nó làm cho commit (compare-and-swap) thành nguyên tử (M08). Rộng hơn, catalog là sổ đăng ký: namespace/schema, danh sách bảng, vị trí, và thường cả quyền truy cập. Không có catalog chung, hai engine sẽ "mỗi người một sự thật".

3. REST catalog & catalog "git-like"

Hai xu hướng đáng chú ý: (1) Iceberg REST Catalog chuẩn hoá giao thức nói chuyện với catalog, nên engine nào nói được REST API là dùng được — gỡ khoá nhà cung cấp ở tầng catalog. (2) Catalog kiểu git (Project Nessie) cho phép branch và tag trên dữ liệu: tạo nhánh để thử transform, kiểm thử, rồi merge nguyên tử vào nhánh chính — đem trải nghiệm Git vào kho dữ liệu.

Vì sao catalog mở quan trọng

Format mở mà catalog đóng thì vẫn bị khoá. Sức hút của Iceberg một phần đến từ REST catalog + nhiều catalog mở, cho phép Spark ghi, Trino/Flink/Snowflake/BigQuery đọc cùng bảng. Đây là động lực chính của làn sóng hội tụ về Iceberg (M13).

4. Xu hướng hội tụ & interop

Hai diễn biến lớn (2024–2025) đáng để bạn theo dõi: (1) Iceberg đang nổi lên thành chuẩn mở chung — nhiều nhà cung cấp warehouse (Snowflake, BigQuery) hỗ trợ đọc/ghi Iceberg; (2) lớp interop như Delta UniForm (lộ bảng Delta ra dưới dạng metadata Iceberg/Hudi) và các công cụ dịch metadata, làm ranh giới "chọn format" bớt sống còn — bạn ghi một format và để công cụ khác đọc qua lớp tương thích.

Lời khuyên thực dụng

Đừng sa lầy vào "thánh chiến format". Hãy chọn theo engine team bạn dùng và workload (đọc-nặng hay upsert-nặng), thiết kế pipeline sao cho metadata/catalog tách bạch, để sau này đổi format đỡ đau. Với đa số dự án lake mới năm nay: bắt đầu bằng Iceberg + một catalog mở (REST/Glue) là lựa chọn ít hối tiếc nhất.

Diễn biến hệ sinh thái (ai mua ai, engine nào vừa hỗ trợ gì) thay đổi nhanh và có thể đã cập nhật so với thời điểm soạn tài liệu. Hãy xác minh hiện trạng engine/catalog trước các quyết định kiến trúc lớn.
Module 14 — Chuyên sâu

Cơ chế ghi sâu: CoW · MoR · deletes

Module này mổ xẻ thứ phân biệt một DE biết dùng lakehouse với một DE hiểu lakehouse: chính xác chuyện gì xảy ra khi bạn UPDATE/DELETE một dòng, vì sao có "write amplification" và "read amplification", và ba format hiện thực row-level change ra sao.

› 1. Copy-on-Write: chi phí ghi › 2. Merge-on-Read: chi phí đọc › 3. Position vs equality delete › 4. Deletion vectors › 5. Cân bằng & chọn chế độ

1. Copy-on-Write: trả nợ lúc ghi

Trong CoW, sửa/xoá một dòng buộc viết lại toàn bộ file chứa nó (file bất biến — không sửa tại chỗ được). Đổi một dòng trong file 200MB → tạo file 200MB mới (trừ một dòng). Đó là write amplification: byte ghi ra ≫ byte thực sự đổi. Bù lại, đọc cực sạch: chỉ Parquet thuần, không phải merge gì.

  CoW UPDATE 1 dòng trong base 200MB:
     base.parquet (200MB) ──rewrite──► base_v2.parquet (200MB)   ← ghi 200MB cho 1 dòng
     đọc: chỉ base_v2  (không merge)                              ← đọc nhanh, sạch
CoW: ghi đắt, đọc rẻ. Hợp bảng đọc-nặng, cập nhật thưa.

2. Merge-on-Read: trả nợ lúc đọc

MoR không đụng file base khi cập nhật — nó ghi thay đổi vào delete file/log file nhỏ bên cạnh. Ghi cực rẻ và nhanh (độ trễ thấp). Cái giá: mỗi lần đọc phải hợp nhất base + các delete/log để ra ảnh đúng hiện tại — read amplification. Nợ này được "trả" bởi compaction nền, gộp delete/log vào base mới để đọc nhanh trở lại.

  MoR UPDATE 1 dòng:
     base.parquet (giữ nguyên) + delete/log (vài KB)             ← ghi nhỏ, nhanh
     đọc: base ⊖ deletes ⊕ log  (merge khi đọc)                  ← đọc chậm hơn
     compaction: base ⊕ tất cả delta → base mới                  ← reset về đọc nhanh
MoR: ghi rẻ, đọc đắt (tạm thời). Hợp streaming/CDC ghi liên tục, độ trễ thấp.

3. Position vs equality delete (Iceberg v2)

Iceberg v2 hiện thực xoá ở mức dòng bằng delete file, hai loại:

Position delete

Ghi "trong file F, các dòng số 5, 9, 12 bị xoá". Chính xác, rẻ khi đọc (biết đúng vị trí). Cần biết vị trí lúc ghi.

Equality delete

Ghi "mọi dòng có id = 42 đều bị xoá". Không cần biết vị trí — hợp CDC streaming (chỉ biết khoá). Đọc đắt hơn (phải so giá trị).

Vì sao có hai loại

Batch update (đã đọc dữ liệu, biết vị trí) → position delete tối ưu đọc. Streaming CDC (chỉ nhận "xoá khoá K") → equality delete tiện ghi. Engine hợp nhất chúng với base khi đọc. Hudi giải cùng bài toán bằng record key + log file; Delta bằng deletion vectors.

4. Deletion vectors (Delta & Iceberg mới)

Deletion vector là một bitmap nhỏ đánh dấu "dòng nào trong file base đã bị xoá (soft delete)" mà không viết lại file base. Đọc = đọc base rồi bỏ qua các dòng được bitmap đánh dấu. Đây là cách biến UPDATE/DELETE/MERGE từ copy-on-write (đắt ghi) sang merge-on-read (rẻ ghi), giảm mạnh write amplification cho bảng cập nhật nhiều — sau đó compaction/purge dọn dần.

Một kỹ sư bật MoR "cho nhanh ghi" → truy vấn BI chậm đột biến vì read amplification + thiếu compaction. Sửa: bảng này đọc ≫ ghi → chọn CoW (hoặc deletion vectors + compaction tích cực). Module 15 — Chuyên sâu

Streaming & CDC vào Lakehouse

Lakehouse thật sự toả sáng khi nó là đích đến của dữ liệu liên tục: Kafka, CDC từ database, sự kiện realtime. Module này nối M11 (Streaming API) và M05 (Spark) của khoá với lakehouse: làm sao đổ stream vào bảng giao dịch mà vẫn đúng-một-lần (exactly-once) và không chết vì small files.

› 1. Kiến trúc CDC → Lakehouse › 2. Exactly-once & idempotent commit › 3. Small files trong streaming › 4. MERGE cho CDC upsert

1. Kiến trúc CDC → Lakehouse

  Postgres/MySQL ─(Debezium CDC)─► Kafka ─► Spark/Flink streaming ─► Bảng Iceberg/Hudi
       (nguồn OLTP)                  (log)      (xử lý + MERGE)         (lakehouse)
                                                       │
                              compaction nền ◄──────────┘  giữ bảng khoẻ
       Downstream: Trino/BI đọc snapshot   ·   ML đọc time-travel để tái lập
CDC bắt thay đổi từ OLTP → đẩy qua log → stream MERGE vào bảng giao dịch → nhiều downstream đọc nhất quán.

Liên hệ trực tiếp: Module 11 (Kafka, CDC, event-driven) của khoá lo phần vận chuyển; module này lo phần hạ cánh an toàn vào bảng có ACID. Hudi (MoR + index) và Iceberg v2 (equality delete) là hai đích phổ biến cho CDC.

2. Exactly-once & idempotent commit

Stream hay bị xử lý lại (retry, restart). Nếu mỗi lần lại append trùng, bảng phình dữ liệu sai. Giải pháp dựa vào commit nguyên tử + idempotency: engine streaming gắn mỗi micro-batch với một epoch/transaction id, và table format từ chối commit trùng id đã thấy. Spark Structured Streaming + Delta/Iceberg phối hợp checkpoint của Spark với commit của bảng để đạt exactly-once end-to-end.

spark-stream-to-delta
stream = (spark.readStream.format("kafka") .option("subscribe", "orders.cdc").load()) (parse(stream).writeStream.format("delta") .option("checkpointLocation", "s3://lake/_ckpt/orders") # đảm bảo exactly-once .trigger(processingTime="1 minute") .toTable("lake.orders")) # checkpoint của Spark + commit nguyên tử của Delta = không trùng, không mất

3. Small files trong streaming

Trigger 1 phút × nhiều partition = vô số file nhỏ mỗi giờ (M02). Ba cách trị: (1) tăng khoảng trigger (đánh đổi độ trễ lấy file lớn hơn); (2) compaction nền đều đặn; (3) format có cơ chế sẵn — Hudi MoR ghi log nhỏ rồi compaction gộp, hoặc bật auto-optimize/auto-compaction nếu engine hỗ trợ.

Nguyên tắc

Streaming ingest và truy vấn nhanh là hai mục tiêu kéo ngược nhau qua kích thước file. Đừng cố ghi file to khi đang stream (giết độ trễ); hãy ghi nhỏ + compaction nền. Tách hai mối lo bằng MoR là cách Hudi giải bài này từ gốc.

4. MERGE cho CDC upsert

CDC mang ba loại sự kiện: insert, update, delete. MERGE diễn đạt trọn cả ba trong một câu — đây là khuôn mẫu chuẩn để áp một batch CDC vào bảng đích:

cdc-merge
MERGE INTO orders t USING cdc_batch s ON t.id = s.id WHEN MATCHED AND s.op = 'd' THEN DELETE WHEN MATCHED AND s.op = 'u' THEN UPDATE SET * WHEN NOT MATCHED AND s.op != 'd' THEN INSERT *; -- một câu xử lý cả insert/update/delete của CDC, nguyên tử
Tình huống thực tế

Bối cảnh: CDC từ MySQL gửi cả "xoá khoá K" nhưng pipeline cũ chỉ append → bảng đích chứa cả bản ghi đã bị xoá ở nguồn, báo cáo sai số khách hàng active. Sửa: dùng MERGE như trên với nhánh DELETE cho op='d'; nếu là Iceberg streaming, dùng equality delete để diễn đạt "xoá theo khoá" mà không cần vị trí. Bảng đích giờ phản chiếu đúng nguồn, exactly-once nhờ checkpoint.

Một câu chốt

Data lake cho bạn lưu trữ rẻ; warehouse cho bạn sự nghiêm cẩn giao dịch. Lakehouse = một lớp metadata mỏng biến cái rẻ thành cái nghiêm cẩn. Nắm vững lớp metadata đó — snapshot, commit nguyên tử, evolution, bảo trì — là nắm vững lakehouse.
