📚 Lý thuyết nền tảng

MLOps (Machine Learning Operations) là tập hợp các thực hành kỹ thuật để đưa mô hình machine learning vào production một cách tin cậy, lặp lại được và hiệu quả — rồi vận hành chúng suốt vòng đời. Nó là giao của ba thế giới: DevOps (CI/CD, hạ tầng, vận hành), Data Engineering (pipeline, chất lượng, lineage — thứ bạn đã thạo) và Machine Learning (mô hình, thử nghiệm, đánh giá). MLOps không phải một tool; nó là cách ghép ba thế giới đó để một dự đoán có thể đi từ ý tưởng đến phục vụ hàng triệu request mà không sụp.

Định nghĩa làm việc — MLOps

Kỷ luật vận hành hoá vòng đời ML: tự động hoá việc huấn luyện, kiểm thử, triển khai và giám sát mô hình; quản lý ba tạo tác cùng lúc — code, data, model — sao cho mọi dự đoán đều tái lập được (ai chạy lại cũng ra cùng kết quả) và kiểm toán được (biết model nào, train trên data nào, sinh ra dự đoán nào).

Lý thuyết 1.1 — ML là phần mềm mà hành vi học từ dữ liệu

Trong phần mềm truyền thống, lập trình viên viết luật tường minh: if thu_nhập > 50tr and nợ < 30% then duyệt. Hành vi nằm trong code, do con người định nghĩa. Trong ML, bạn không viết luật — bạn đưa dữ liệu lịch sử (hồ sơ vay + kết quả vỡ nợ) cho thuật toán, và nó tự suy ra các trọng số. Hệ quả sâu sắc: logic của hệ thống nằm trong dữ liệu, không nằm trong code. Đổi dữ liệu → đổi hành vi, dù không sửa một dòng code nào. Đây là điểm khởi nguồn cho gần như mọi cái khó của MLOps: bạn phải version hoá, kiểm thử và giám sát một thứ (dữ liệu) mà DevOps cổ điển chưa từng phải quản như "mã nguồn".

Lý thuyết 1.2 — Ba tạo tác, không phải một

DevOps quản 1 tạo tác chính: code. MLOps quản ba, và một dự đoán chỉ tái lập được khi cố định cả ba: code (logic tiền xử lý, kiến trúc model), data (tập huấn luyện cụ thể), và model (trọng số đã học + hyperparameters). Mất dấu bất kỳ cái nào là mất khả năng trả lời câu hỏi sống còn: "dự đoán sai này đến từ model nào, train trên data nào, bằng code nào?". Toàn bộ Module 4 (experiment tracking) và 10 (CI/CD/CT) tồn tại để buộc ba tạo tác này luôn đi cùng nhau.

Lý thuyết 1.3 — Training-serving skew: kẻ giết người thầm lặng

Đây là lỗi đặc trưng và phổ biến nhất của hệ thống ML. Training-serving skew là khi dữ liệu/biến đổi lúc huấn luyện khác với lúc phục vụ. Ví dụ kinh điển: lúc train, bạn chuẩn hoá tuổi bằng mean tính trên cả tập (gồm cả tương lai — leakage), nhưng lúc serving bạn chỉ có dữ liệu hiện tại; hoặc data scientist viết tiền xử lý bằng pandas trong notebook, còn kỹ sư viết lại bằng Java ở API — hai phiên bản lệch nhau một chút. Model "chuẩn" trong offline test nhưng dự đoán rác trong production. Feature store (Module 3) ra đời chủ yếu để diệt loại bug này: một định nghĩa feature duy nhất dùng cho cả train và serve.

Lý thuyết 1.4 — Model phân rã theo thời gian (model decay)

Khác phần mềm thường — vốn không "hỏng" nếu không ai đụng vào — một model ML tự xuống cấp dù code đứng yên, vì thế giới thực thay đổi: hành vi khách hàng đổi, lạm phát, đối thủ ra sản phẩm mới, một đại dịch ập đến. Phân phối dữ liệu lúc phục vụ trôi xa dần khỏi phân phối lúc huấn luyện (data drift), hoặc mối quan hệ giữa biến đầu vào và nhãn thay đổi (concept drift). Hệ quả vận hành: triển khai model không phải điểm kết thúc mà là điểm bắt đầu của một vòng lặp giám sát → phát hiện trôi → huấn luyện lại. Đây là lý do MLOps có thêm chữ "CT" (Continuous Training) mà DevOps không có (Module 9 & 10).

Mối nối với khoá DE của bạn

Mọi thứ bạn học về idempotency, lineage, data contract, data quality (Module 10 DE) không bị bỏ đi — nó là nền móng của MLOps. Một model chỉ tốt bằng dữ liệu nuôi nó. "Garbage in, garbage out" đúng gấp đôi với ML: dữ liệu xấu không làm crash (dễ phát hiện) mà làm model sai một cách tự tin (khó phát hiện).

3. "Hidden Technical Debt" — tảng băng của hệ thống ML

Bài báo kinh điển của Google (Sculley et al., 2015, "Hidden Technical Debt in Machine Learning Systems") đưa ra hình ảnh quyết định nhất ngành: hộp code ML thực sự (thuật toán huấn luyện) chỉ là một ô nhỏ xíu giữa một biển hạ tầng bao quanh. Hầu hết người mới dồn 90% sự chú ý vào ô nhỏ đó; còn production thì sống hay chết nhờ phần còn lại.

  ┌────────────┬───────────┬──────────────┬───────────────┐
  │ Data       │ Feature   │  Data        │  Cấu hình     │
  │ Collection │ Extraction│  Verification│  (Config)     │
  ├────────────┴──┬────────┴───┬──────────┴───────────────┤
  │  Quản lý tài   │  ╔═══════╗ │  Quản lý phục vụ          │
  │  nguyên máy    │  ║  ML   ║ │  (Serving Infra)          │
  ├───────────────┤  ║ CODE  ║ ├──────────────────────────┤
  │  Phân tích     │  ╚═══════╝ │  Giám sát (Monitoring)    │
  │  & công cụ     │ (ô nhỏ xíu)│                           │
  ├───────────────┴────────────┴──────────────────────────┤
  │  Hạ tầng pipeline · Quản lý quy trình · Metadata        │
  └─────────────────────────────────────────────────────────┘
Code ML thật chỉ chiếm ~5% hệ thống. 95% còn lại là MLOps — và là nơi nợ kỹ thuật tích tụ.

Bài báo cũng đặt tên cho những loại "nợ" đặc trưng ML mà bạn sẽ gặp lại suốt khoá:

  • Entanglement (CACE): "Changing Anything Changes Everything" — đổi một feature làm trọng số mọi feature khác đổi theo. Không có module độc lập như phần mềm thường.
  • Correction cascades: chồng model lên model để vá lỗi → một chuỗi phụ thuộc dễ vỡ.
  • Undeclared consumers: ai đó âm thầm dùng output model bạn cho việc khác → bạn đổi model, họ vỡ mà không biết.
  • Data dependencies > code dependencies: phụ thuộc dữ liệu khó truy vết hơn phụ thuộc code, và không có "compiler" báo lỗi.
  • Glue code & pipeline jungles: 95% code chỉ để dán các mảnh lại với nhau → rối như rừng.

5. Ai làm gì: DS · MLE · DE · MLOps Engineer

Ranh giới vai trò trong ML mờ và khác nhau giữa các công ty, nhưng hiểu phổ này giúp bạn biết mình bù vào đâu:

Data Scientist (DS)

Đặt bài toán, EDA, chọn & train model, tối ưu metric. Giỏi thống kê/ML. Thường yếu production, testing, hạ tầng. Output: notebook + model.

ML Engineer (MLE)

Biến model của DS thành dịch vụ production: serving, tối ưu latency, đóng gói, scale. Cầu nối DS ↔ kỹ thuật. Output: API/service.

Data Engineer (DE) — bạn

Cung cấp dữ liệu sạch, đúng giờ, đúng hợp đồng cho train & serve; xây feature pipeline. Nền móng của tất cả.

MLOps / Platform Engineer

Xây nền tảng để DS/MLE tự phục vụ: pipeline templates, feature store, CI/CD/CT, monitoring, registry. Output: platform.

Vị trí của bạn

Với nền DE + business/finance, đường ngắn nhất của bạn là MLOps / ML Platform Engineer: bạn đã có data, hạ tầng, orchestration; chỉ cần thêm feature store, serving, registry, drift. Đây là vai trò khan hiếm và trả cao vì rất ít người vừa hiểu data vừa hiểu vận hành model.

📚 Vòng đời ML và bản chất lặp

Vòng đời ML là hậu duệ của CRISP-DM (Cross-Industry Standard Process for Data Mining) — khung kinh điển từ thập niên 1990 — nhưng được "vận hành hoá" cho thời production. Điểm cốt lõi cần thấm: nó không tuyến tính. Bạn không đi một mạch từ trái sang phải rồi xong. Bạn vòng lại liên tục: đánh giá tệ → quay về sửa feature; drift trong production → quay về thu thập data mới và train lại. Mỗi mũi tên quay ngược là một lần "MLOps" phải tự động hoá, nếu không bạn sẽ làm tay đến kiệt sức.

Vòng lặp ML (ML loop)

Chuỗi Problem → Data → Features → Train → Evaluate → Deploy → Monitor trong đó Monitor đổ ngược về Data để tạo một vòng kín tự cải tiến. MLOps = biến vòng lặp này từ "làm tay, vài tháng/lần" thành "tự động, lặp được, kiểm toán được".

Lý thuyết 2.1 — Phần lớn thời gian không nằm ở "model"

Khảo sát ngành (Forbes, các báo cáo của Anaconda/Kaggle) lặp lại một con số: data scientist dành 60–80% thời gian cho thu thập, làm sạch, chuẩn bị dữ liệu — và chỉ một phần nhỏ cho "chọn & train model". Với một DE, đây là tin tuyệt vời: phần chiếm-thời-gian-nhất chính là sở trường của bạn. Cái bẫy của người mới là đảo ngược tỷ lệ — vọc model cả tuần trong khi dữ liệu đầu vào còn rác.

Lý thuyết 2.2 — Mỗi vòng lặp là một thí nghiệm

Khác với sửa bug phần mềm (có/không), cải thiện model là chuỗi thí nghiệm: đổi feature này, thử thuật toán kia, chỉnh hyperparameter nọ — rồi đo. Vì thế experiment tracking (Module 4) là hạ tầng bắt buộc, không phải xa xỉ: không ghi lại thì sau 50 lần thử bạn không biết cái nào tốt, train trên data nào, vì sao. "Tôi nhớ mà" là lời nói dối kinh điển dẫn đến model không tái lập.

2. Data-centric vs model-centric AI

Andrew Ng phổ biến một dịch chuyển tư duy quan trọng. Model-centric: cố định dữ liệu, vọc model để tăng điểm. Data-centric: cố định model, cải thiện chất lượng & nhãn dữ liệu một cách hệ thống. Trong thực chiến, sau khi đã chọn một model "đủ tốt", cải thiện dữ liệu thường cho lợi suất cao hơn nhiều so với vọc thêm model — đặc biệt khi dữ liệu nhiễu, nhãn sai, hoặc lệch.

Model-centric (cũ)

"Làm sao thuật toán xử lý tốt hơn dữ liệu hiện có?" → thử model phức tạp hơn, tune hyperparameter. Lợi suất giảm dần.

Data-centric (thường thắng)

"Làm sao cải thiện dữ liệu để model hiện tại học tốt hơn?" → sửa nhãn sai, thêm mẫu hiếm, chuẩn hoá định nghĩa. Đây là sân nhà của DE.

Lợi thế DE của bạn

Data-centric AI = data engineering áp vào ML. Nhãn nhất quán, không trùng lặp, đại diện, đúng hợp đồng — toàn bộ kỹ năng Module 10 (data quality/contract) của bạn chính là đòn bẩy mạnh nhất để tăng chất lượng model mà nhiều DS không chạm tới được.

3. Từ DE pipeline đến ML pipeline

ML pipeline mở rộng data pipeline bạn đã biết, thêm các bước đặc thù ML. Cùng một Airflow/orchestrator, nhưng đồ thị task dài hơn:

  DATA PIPELINE (bạn đã biết)
   ingest → validate → transform → load to warehouse
        │
        ▼  (ML pipeline nối tiếp)
   build features → split (train/val/test) → train →
   evaluate → [GATE: đủ tốt?] → register model →
   deploy → monitor → (drift?) → trigger retrain ↺
ML pipeline = data pipeline + (feature → train → eval-gate → register → deploy → monitor → loop).

Điểm khác biệt cốt lõi so với pipeline thuần data:

  • Eval gate: một bước điều kiện — model mới chỉ được đăng ký/deploy nếu vượt baseline & ngưỡng metric. Pipeline data không có khái niệm "đủ tốt mới đi tiếp" kiểu thống kê này.
  • Model registry: pipeline data sinh ra bảng; ML pipeline sinh ra model có version cần lưu, gắn metadata, gắn data đã train.
  • Vòng retrain: tín hiệu từ monitoring (drift) kích hoạt chạy lại pipeline — một cạnh quay ngược mà DAG data thường không có.

4. Train/Validation/Test split & 7 tội đồ data leakage

Data leakage (rò rỉ dữ liệu) là khi thông tin lẽ ra không có lúc dự đoán thật lại lọt vào lúc huấn luyện, khiến model "đẹp" giả tạo offline rồi sụp trong production. Đây là nguyên nhân số một của những model "99% accuracy" mà thực tế vô dụng. Trước hết, ba tập:

Train (~60–70%)

Model học trọng số từ đây.

Validation (~15–20%)

Chọn hyperparameter, so sánh model. Không học trọng số từ đây.

Test (~15–20%)

Đánh giá cuối, chỉ chạm một lần. Chạm nhiều = leak gián tiếp.

#Tội đồ leakageBiểu hiện & cách tránh

2Train-test contaminationFit scaler/encoder trên cả tập rồi mới split. Tránh: fit chỉ trên train, transform test bằng tham số của train (Pipeline của sklearn).
3Temporal leakageRandom split dữ liệu chuỗi thời gian → dùng tương lai đoán quá khứ. Tránh: time-based split (train quá khứ, test tương lai).
4Group leakageCùng một khách hàng nằm cả ở train & test. Tránh: group split theo entity.
5Duplicate leakageBản ghi trùng rơi vào cả train & test. Tránh: dedup trước split.
6Test-set peekingTinh chỉnh model nhiều lần theo điểm test → overfit lên test. Tránh: dùng validation, đụng test 1 lần.
7Feature từ tương laiTính feature dùng dữ liệu sau thời điểm dự đoán (vd trung bình cả năm). Tránh: point-in-time correctness (Module 3).
Quy tắc vàng chống leakage

Luôn hỏi: "Tại thời điểm phải đưa ra dự đoán thật, tôi có giá trị feature này chưa?" Nếu chưa → đó là leakage. Một model 99% accuracy trên test gần như luôn là dấu hiệu của leakage, không phải thiên tài. Với dữ liệu có thời gian (đa số bài toán nghiệp vụ của bạn), luôn split theo thời gian.

📚 Feature là gì & vì sao cần một "store" riêng

Một feature (đặc trưng) là một biến đầu vào cho model — vd "tổng chi tiêu 30 ngày qua", "số lần đăng nhập tuần này", "tuổi tài khoản". Tính một feature thì dễ; vấn đề là tính nó nhất quán ở hai nơi rất khác nhau: lúc train bạn cần giá trị feature cho hàng triệu bản ghi lịch sử (truy vấn phân tích, throughput cao, độ trễ không quan trọng); lúc serve bạn cần giá trị mới nhất cho một entity trong vài mili-giây (low-latency lookup). Đây là hai khối lượng công việc đối nghịch — và đó chính là lý do feature store tồn tại với kiến trúc hai kho.

Feature Store

Một lớp dữ liệu chuyên dụng để định nghĩa, tính, lưu, và phục vụ features cho ML — đảm bảo cùng một định nghĩa feature được dùng cho cả huấn luyện (offline, batch) lẫn phục vụ (online, low-latency), đồng thời cho phép tái dùng feature giữa nhiều model/team và đảm bảo tính đúng theo thời điểm.

Lý thuyết 3.1 — Feature store là "dbt + Redis cho ML"

Cách hiểu thân thiện với DE: phần offline của feature store giống dbt — bạn định nghĩa các phép biến đổi/aggregate, version chúng, tái dùng chúng. Phần online giống một key-value store (Redis/DynamoDB) — tra cứu cực nhanh theo entity id. Feature store là thứ ghép hai cái đó lại dưới một định nghĩa feature duy nhất, cộng thêm cơ chế đồng bộ (materialization) đẩy giá trị từ offline sang online. Bạn đã có mọi mảnh ghép; feature store chỉ chuẩn hoá cách lắp chúng cho ML.

Một định nghĩa → hai kho. Offline cho train (lịch sử, batch); online cho serve (mới nhất, <10ms). Materialization đồng bộ hai bên.

Offline store

Lưu toàn bộ lịch sử giá trị feature theo thời gian. Nền: lakehouse/warehouse (Iceberg, BigQuery, Snowflake). Phục vụ tạo training set bằng point-in-time join. Throughput > latency.

Online store

Chỉ lưu giá trị mới nhất mỗi entity. Nền: key-value (Redis, DynamoDB, Bigtable). Phục vụ inference real-time: tra theo entity id trong <10ms. Latency > throughput.

3. Point-in-time correctness — tính năng sát thủ

Đây là khái niệm tinh tế nhất của feature store, và là thứ một JOIN ... ON latest ngây thơ không bao giờ làm đúng. Khi tạo training set, với mỗi nhãn tại thời điểm T, bạn phải ghép giá trị feature như nó tồn tại tại T — không phải giá trị hiện tại, cũng không phải giá trị sau T.

  Lịch sử feature "chi tiêu_30d" của KH #7:
   thời điểm:  Jan1   Feb1   Mar1   Apr1(hôm nay)
   giá trị:    100    250    400    900

  Nhãn cần train: "KH #7 có churn không?" đo tại Feb15
   ✗ SAI (latest join):    ghép 900  → leakage! dùng dữ liệu Apr
   ✗ SAI (current join):   ghép 900  → model thấy tương lai
   ✓ ĐÚNG (point-in-time): ghép 250  → giá trị có tại Feb15
                            (bản ghi gần nhất ≤ Feb15)
Point-in-time join lấy bản ghi feature mới nhất KHÔNG vượt quá thời điểm của nhãn → diệt leakage tương lai (tội đồ #7, Module 2).
Vì sao SQL thường khó làm đúng

Point-in-time join là một "as-of join" (ghép theo mốc) — với mỗi (entity, event_time) lấy row feature gần nhất mà ≤ event_time. Viết tay bằng SQL window/correlated subquery thì được nhưng dễ sai và chậm trên dữ liệu lớn. Feature store (Feast, Tecton) làm việc này tự động, đúng, và tối ưu. Đây là lý do chính người ta không "tự build" point-in-time bằng tay.

4. Feast — feature store mã nguồn mở, code thực chiến

Feast là feature store open-source phổ biến nhất, nhẹ và hợp để học. Luồng: định nghĩa entity + feature view → materialize (offline→online) → lấy training set (offline) hoặc online features (serve).

feature_repo/definitions.py — định nghĩa feature một lần
from feast import Entity, FeatureView, Field, FileSource from feast.types import Float32, Int64 from datetime import timedelta # Entity = khoá nghiệp vụ để tra feature (như primary key) customer = Entity(name="customer_id", join_keys=["customer_id"]) # Nguồn offline: bảng lịch sử trong lakehouse/warehouse source = FileSource( path="s3://data/customer_features.parquet", timestamp_field="event_timestamp", # cột thời gian → point-in-time ) # Feature View = nhóm feature + nguồn + TTL customer_stats = FeatureView( name="customer_stats", entities=[customer], ttl=timedelta(days=90), # giá trị quá 90 ngày coi là cũ schema=[ Field(name="spend_30d", dtype=Float32), Field(name="logins_7d", dtype=Int64), Field(name="account_age_days", dtype=Int64), ], source=source, online=True, # bật phục vụ online )
build_training_set.py — point-in-time join cho TRAIN (offline)

📚 Vì sao experiment tracking là hạ tầng bắt buộc

Khoa học cần sổ thí nghiệm; ML cũng vậy. Mỗi lần bạn train, bạn đang chạy một thí nghiệm với một giả thuyết ("thêm feature X sẽ tăng AUC"). Không ghi lại thì bạn không thể: so sánh (cái nào tốt hơn?), tái lập (làm sao ra lại kết quả đó?), cộng tác (đồng nghiệp thấy gì bạn đã thử?), hay audit (model production này từ run nào?). Tracking không phải để "cho đẹp" — nó là điều kiện để ML trở thành kỹ thuật thay vì thủ công mỹ nghệ.

Experiment Tracking

Việc ghi lại có hệ thống mọi run huấn luyện: tham số (params), số đo (metrics), tạo tác (artifacts: model, biểu đồ), và metadata (git commit, data version, môi trường) — sao cho mọi run đều so sánh được, tái lập được, kiểm toán được.

Experiment vs Run

Experiment = một bài toán/đợt nghiên cứu (vd "dự báo churn Q2"). Run = một lần train cụ thể bên trong experiment đó (vd "XGBoost, lr=0.1, 8 feature"). Một experiment chứa nhiều run để so sánh.

Lý thuyết 4.1 — "Tôi nhớ mà" là lời nói dối

Bộ nhớ con người không scale qua 5 run. Khi đến run thứ 30, bạn quên lr của run thứ 7, quên run nào dùng feature mới, quên vì sao bỏ thuật toán nọ. Tệ hơn: bạn vô tình so sánh hai run trên hai tập test khác nhau và kết luận sai. Tracking đẩy "trí nhớ" ra khỏi đầu bạn vào một hệ thống bền — đúng tinh thần idempotency & lineage bạn đã rèn trong DE.

1. ⭐ Bốn thứ phải ghi mỗi run

① Params (đầu vào)

Hyperparameter (lr, depth, n_estimators), danh sách feature, tỉ lệ split, seed. Mọi thứ bạn chọn trước khi train.

② Metrics (kết quả)

AUC, F1, RMSE, precision/recall, loss theo epoch. Mọi thứ đo được sau train. Theo cả slice nếu có.

③ Artifacts (tạo tác)

File model đã train, biểu đồ (confusion matrix, ROC), feature importance, requirements.txt, mẫu dữ liệu.

④ Metadata (bối cảnh)

Git commit, data version, môi trường (Docker/lib), thời gian, người chạy, phần cứng. Để TÁI LẬP.

Sai lầm phổ biến

Chỉ ghi metrics ("AUC 0.89!") mà bỏ params + metadata. Sáu tháng sau model production sai, bạn muốn điều tra — nhưng không biết nó train trên data version nào, commit nào, feature gì. Không audit được = không sửa được = phải train lại mù. Metadata quan trọng ngang metrics.

Lý thuyết 5.1 — "Pipeline là first-class, model là output"

Một dịch chuyển tư duy quan trọng khi lên MLOps cấp 1 (Module 1): cái bạn version & bảo trì không phải là model, mà là pipeline sinh ra model. Model chỉ là output. Nếu pipeline tốt (tái lập, tự động), bạn train lại lúc nào cũng được khi có data mới. Người mới bảo trì "model"; người trưởng thành bảo trì "nhà máy sản xuất model".

Module 06 — Model

Đánh giá Model & Validation Gate

"AUC 0.89" không nói cho bạn biết model có dùng được không. Một con số tổng có thể che giấu việc model thất bại thảm hại trên nhóm khách hàng quan trọng nhất, hoặc thua cả một luật if-else đơn giản. Module này dạy cách đánh giá model như một kỹ sư hoài nghi: chọn đúng metric cho đúng bài toán, đặt ngưỡng theo chi phí nghiệp vụ, soi theo slice, luôn so với baseline, và biến tất cả thành một cổng tự động chặn model tồi trước khi nó ra production.

› 0. 📚 Offline metric vs giá trị nghiệp vụ › 1. ⭐ Metric theo loại bài toán › 2. Confusion matrix & chọn ngưỡng › 3. Đánh giá theo slice & công bằng › 4. Baseline — luôn so với "kẻ ngốc" › 5. Validation gate tự động › 6. Model card & tài liệu

📚 Ba tầng đánh giá: offline → online → nghiệp vụ

Một model được đánh giá ở ba tầng, và chúng không luôn đồng thuận. Offline metric (AUC, RMSE trên test) cho bạn biết model học được pattern không — rẻ, nhanh, nhưng chỉ là đại diện. Online metric (đo khi deploy qua A/B test — Module 8): model có hoạt động trên dữ liệu thật, người thật không. Business metric (doanh thu, churn thực giảm, chi phí tiết kiệm): cái duy nhất sếp quan tâm. Cạm bẫy: tối ưu offline metric đến cực đại nhưng business metric không nhúc nhích — vì metric offline không phản ánh đúng giá trị thật.

Proxy metric vs True objective

Offline metric (vd AUC) là proxy (đại diện) cho thứ ta thật sự muốn (vd "lợi nhuận tăng"). Một MLOps engineer giỏi luôn hỏi: "metric tôi đang tối ưu có thật sự kéo theo giá trị nghiệp vụ không, hay tôi đang leo sai ngọn núi?". Đây là cầu nối quý giá giữa nền business/finance của bạn và kỹ thuật ML.

Lý thuyết 6.1 — Một con số luôn nói dối một nửa

Accuracy 99% trên bài toán mà 99% mẫu là lớp âm (vd gian lận: 99% giao dịch hợp lệ) thì vô nghĩa: một model luôn đoán "hợp lệ" cũng đạt 99% mà chẳng bắt được gian lận nào. Đây là bẫy class imbalance. Bài học: luôn nhìn nhiều metric, và metric phải hợp với phân phối & chi phí lỗi của bài toán. Không có metric "đúng" phổ quát.

Precision hay Recall? Hỏi chi phí lỗi

Không có câu trả lời chung — nó là quyết định nghiệp vụ. Bỏ lọt một ca ung thư (FN) tốn mạng → ưu tiên recall. Chặn nhầm một giao dịch hợp lệ (FP) làm mất khách → cân nhắc precision. Đây chính là chỗ tư duy finance/business của bạn định hướng kỹ thuật: dịch "chi phí mỗi loại lỗi" thành lựa chọn metric & ngưỡng.

2. Confusion matrix & chọn ngưỡng theo chi phí

Model phân loại thường xuất xác suất (0–1). Bạn phải chọn ngưỡng để biến xác suất thành quyết định. Ngưỡng 0.5 là mặc định ngây thơ — ngưỡng đúng phụ thuộc chi phí FP vs FN.

                    DỰ ĐOÁN
                  Dương      Âm
            ┌──────────────┬──────────────┐
   THỰC  Dương │ TP (đúng)  │ FN (bỏ sót)  │ ← recall = TP/(TP+FN)
   TẾ        │ ✓          │ ✗ nguy hiểm  │
            ├──────────────┼──────────────┤
        Âm  │ FP (báo nhầm)│ TN (đúng)    │
            │ ✗ phiền      │ ✓            │
            └──────────────┴──────────────┘
              ↑ precision = TP/(TP+FP)

  Tăng ngưỡng (0.5→0.8): precision↑, recall↓  (thận trọng hơn)
  Giảm ngưỡng (0.5→0.2): recall↑, precision↓  (bắt nhiều hơn, nhầm nhiều hơn)
  → Chọn ngưỡng tối thiểu hoá: cost_FP × #FP + cost_FN × #FN
Ngưỡng không phải 0.5 mặc định — chọn theo chi phí nghiệp vụ của từng loại lỗi.
Tình huống thực tế

Model phát hiện gian lận: mỗi gian lận bỏ lọt (FN) tốn trung bình 5tr; mỗi cảnh báo nhầm (FP) tốn 50k chi phí review thủ công. Tỉ lệ chi phí 100:1 → bạn nên đặt ngưỡng thấp (bắt nhiều, chấp nhận nhiều FP) vì bỏ sót đắt hơn nhiều. Tính tổng chi phí kỳ vọng theo từng ngưỡng rồi chọn điểm tối thiểu — đó là "tối ưu hoá quyết định", không phải tối ưu hoá AUC. Sếp tài chính sẽ gật đầu với cách trình bày này.

3. Đánh giá theo slice & công bằng (fairness)

Metric tổng là một trung bình, và trung bình che giấu thảm hoạ cục bộ. Model có AUC tổng 0.88 nhưng có thể chỉ đạt 0.55 trên nhóm khách hàng VIP (số ít nhưng quan trọng nhất). Slice-based evaluation: chia tập test theo các nhóm có ý nghĩa (vùng, phân khúc, kênh, nhóm nhân khẩu) và đo metric từng nhóm.

slice_eval.py — đừng tin metric tổng
for segment, group in test_df.groupby("segment"): auc = roc_auc_score(group.y, model.predict_proba(group.X)[:, 1]) n = len(group) print(f"{segment:<12} n={n:>6} AUC={auc:.3f}") # segment n= 1200 AUC=0.910 ← tốt # vip n= 80 AUC=0.560 ← THẢM HOẠ, bị che bởi metric tổng! # new_user n= 3400 AUC=0.870 # → model tệ đúng ở nhóm đáng giá nhất. Metric tổng 0.88 nói dối.
Fairness không chỉ là đạo đức

Model lệch theo nhóm nhân khẩu (giới, vùng, tuổi) vừa là rủi ro pháp lý/uy tín (đặc biệt trong tài chính, tuyển dụng, tín dụng — lĩnh vực bạn am hiểu) vừa là dấu hiệu kỹ thuật của data lệch. Đo các chỉ số như demographic parity, equalized odds giữa các nhóm. Một model "chính xác trung bình" mà phân biệt đối xử là một quả bom hẹn giờ.

4. Baseline — luôn so với "kẻ ngốc"

Một metric tuyệt đối vô nghĩa nếu không có mốc so sánh. Luôn dựng baseline trước khi ăn mừng:

  • Baseline ngây thơ: luôn đoán lớp đa số / luôn đoán trung bình. Nếu model không vượt được cái này → vứt.
  • Baseline luật: một if-else hợp lý từ chuyên gia nghiệp vụ. Nếu ML không vượt rõ rệt → dùng luật (rẻ hơn, giải thích được, không decay).
  • Baseline model hiện tại: model đang chạy production. Model mới phải vượt nó mới đáng thay (rủi ro + công deploy).
Quy tắc baseline

"So với cái gì?" là câu hỏi đầu tiên khi ai đó khoe metric. Một model AUC 0.85 nghe oai, nhưng nếu baseline luật đạt 0.83 thì +0.02 có đáng chi phí vận hành một hệ ML decay theo thời gian không? Thường là không. Baseline giữ bạn trung thực và chống over-engineering.

5. Validation gate tự động trong pipeline

Mọi thứ ở trên phải thành code chạy tự động trong pipeline (Module 5), không phải việc một người nhìn bằng mắt rồi gật đầu. Cổng eval là một bước trả về pass/fail:

eval_gate.py — cổng chặn model tồi (gọi trong DAG Module 5)
def eval_gate(model, X_test, y_test, prod_auc) -> bool: auc = roc_auc_score(y_test, model.predict_proba(X_test)[:, 1]) checks = { "vuot_baseline": auc > 0.70, # ngưỡng tối thiểu tuyệt đối "vuot_production": auc > prod_auc + 0.005, # tốt hơn model đang chạy "no_slice_collapse": min_slice_auc(model, X_test, y_test) > 0.65, "fairness_ok": demographic_parity_gap(model) < 0.10, "latency_ok": p99_latency_ms(model) < 50, # đủ nhanh để serve } for name, ok in checks.items(): if not ok: raise ValueError(f"GATE FAIL: {name}") # dừng pipeline, giữ model cũ return True
Gate = data contract cho model

Cổng eval chính là khái niệm data contract (Module 10 DE) áp lên model: một tập điều kiện phải thoả trước khi tạo tác được "phát hành". Nó tự động hoá sự hoài nghi, để con người không phải canh chừng và không phải nhớ kiểm tra mọi slice mỗi lần.

5. Latency, throughput & dynamic batching

Hai chỉ số đối nghịch của serving online (như Module 18): latency (một request mất bao lâu — quan tâm p99, không phải trung bình) và throughput (bao nhiêu request/giây). Vài đòn bẩy cốt lõi:

Dynamic batching

Gộp nhiều request đến gần nhau thành một batch để model xử lý một lần (đặc biệt trên GPU) → throughput tăng mạnh, đổi lại latency tăng chút. Triton/vLLM làm tự động.

Cache dự đoán

Input lặp lại → cache kết quả (Redis). Hữu ích khi phân phối request lệch (vài entity rất hot).

Tối ưu model

Quantization (giảm độ chính xác số), distillation (model nhỏ học model lớn), ONNX runtime → nhỏ & nhanh hơn (Module 11).

Warm start

Model nặng load chậm → giữ instance "ấm", dùng readiness probe, tránh cold start lúc autoscale.

Đo p99, đừng đo trung bình

Latency trung bình che giấu đuôi dài. Nếu p50=20ms nhưng p99=800ms, thì 1% người dùng (thường là lúc tải cao — đúng lúc quan trọng nhất) có trải nghiệm tệ. SLO serving luôn đặt trên p95/p99. Đây là bài học thẳng từ system design Module 18.

Module 08 — Serving

Chiến lược Deployment

Đẩy một model mới lên production là khoảnh khắc rủi ro nhất trong vòng đời ML: model "thắng" offline vẫn có thể thua thảm trên dữ liệu thật, người thật. Khác với deploy phần mềm (đúng/sai rõ ràng), model có thể chạy hoàn hảo về kỹ thuật mà vẫn ra quyết định tệ về nghiệp vụ — và bạn chỉ biết khi đo trên traffic thật. Module này dạy các kỹ thuật progressive delivery để giảm thiểu rủi ro đó: shadow, canary, blue-green, A/B — và cách rollback trong vài giây.

📚 Vì sao deploy model rủi ro hơn deploy code

Deploy phần mềm thường: test pass → khá chắc nó đúng. Deploy model: vượt mọi offline metric (Module 6) vẫn không đảm bảo nó tốt trên production, vì ba lý do. (1) Offline ≠ online: phân phối test có thể khác traffic thật. (2) Feedback loop: dự đoán của model thay đổi hành vi người dùng, làm dữ liệu tương lai lệch theo cách không lường được. (3) Lỗi âm thầm: model sai không crash — nó vẫn trả 200 OK với một con số tệ, nên không có exception nào báo động. Vì thế: không bao giờ thay 100% traffic ngay. Luôn phát hành từ từ và đo trên thực địa.

Progressive delivery

Triết lý phát hành dần dần và đo lường liên tục: đưa model mới đến một phần nhỏ traffic/người dùng trước, so sánh với model cũ trên metric thật, mở rộng dần nếu tốt, và rút lui tức thì nếu xấu. Mục tiêu: giới hạn "bán kính vụ nổ" (blast radius) của một model tồi.

Lý thuyết 8.1 — Tách "deploy" khỏi "release"

Một phân biệt giải phóng tư duy: deploy = đưa artifact lên hạ tầng (chưa ai dùng); release = cho traffic thật chạy qua nó. Tách hai việc này (bằng feature flag/router) nghĩa là bạn có thể deploy model mới một cách an toàn (nó nằm đó, im lặng), rồi release dần dần và độc lập — bật cho 1%, 5%, 50%, 100% mà không deploy lại. Đây là chìa khoá của mọi chiến lược dưới đây.

2. Shadow deployment — test trên thật, rủi ro bằng 0

Giới hạn của shadow

Shadow đo được kỹ thuật (latency, lỗi, phân phối output) nhưng không đo được tác động nghiệp vụ — vì output không tới user nên không có hành vi phản hồi (click, mua, churn) để so. Muốn biết model mới có tăng doanh thu không, bạn phải để nó thật sự ảnh hưởng một nhóm → cần canary/A·B. Shadow là điều kiện cần, không đủ.

3. Canary & rollout tăng dần

"Canary" (chim hoàng yến trong mỏ than) — đưa model mới cho một phần nhỏ traffic thật (vd 5%), giám sát chặt cả metric kỹ thuật lẫn nghiệp vụ, rồi tăng dần (5% → 25% → 50% → 100%) nếu mọi thứ ổn, hoặc rút nếu xấu. Giới hạn thiệt hại ở 5% trong khi vẫn đo được tác động thật.

router.py — canary định tuyến theo % + tự rút khi xấu
import random CANARY_PCT = 0.05 # bắt đầu 5%, tăng dần qua config/flag def route(request): if random.random() < CANARY_PCT: pred = model_new.predict(request) log("canary", pred, request) # gắn nhãn để so sánh sau else: pred = model_prod.predict(request) log("prod", pred, request) return pred # Automated canary analysis (ACA): job định kỳ so canary vs prod; # nếu error_rate/latency/biz_metric của canary xấu hơn ngưỡng → set CANARY_PCT=0
Canary trên hạ tầng bạn đã có

Nếu serving chạy trên K8s (Module 13), bạn có canary gần như miễn phí qua Ingress weights, Argo Rollouts, hoặc service mesh (Istio) — định tuyến % traffic theo trọng số mà không cần code router tay. KServe có canary tích hợp. Đây là GitOps (Module 17) áp cho model.

4. A/B test & champion-challenger

A/B test là canary làm đúng chuẩn thống kê để trả lời câu hỏi nghiệp vụ: "model mới (B) có thật sự tốt hơn model cũ (A) một cách có ý nghĩa, hay chỉ là nhiễu?". Chia ngẫu nhiên user thành nhóm A/B, đo metric nghiệp vụ, kiểm định ý nghĩa thống kê trước khi kết luận.

5. Rollback & kill switch

Giả định mọi model rồi sẽ có lúc cần rút (đúng tinh thần "thiết kế cho thất bại" Module 18). Khả năng rollback nhanh quan trọng hơn việc cố không bao giờ sai. Hai cơ chế:

Rollback qua registry

Vì serving load models:/churn/Production (Mod 4), rollback = trỏ stage "Production" về version cũ. Không deploy lại code. Vài giây.

Kill switch / fallback

Một cờ tắt model ngay lập tức, rơi về baseline an toàn (luật đơn giản, model cũ, hoặc giá trị mặc định). Phải test đường fallback này định kỳ.

Tình huống thực tế

3h sáng, model gợi ý mới (canary 25%) bắt đầu trả toàn sản phẩm hết hàng vì một feature upstream bị null hàng loạt. Vì đã tách deploy khỏi release và có kill switch: on-call chỉ cần set cờ canary_pct=0 — traffic về 100% model cũ trong 10 giây, không cần build/deploy/chờ. Sáng hôm sau điều tra feature null trong bình tĩnh. Rollback nhanh = ngủ ngon.

6. Feature flags cho ML

Feature flag (cờ tính năng) là công tắc bật/tắt hành vi mà không deploy lại — nền tảng kỹ thuật cho mọi chiến lược trên. Áp cho ML:

  • Bật/tắt model tức thì (kill switch) mà không động vào code.
  • Điều khiển % canary qua cờ, đổi runtime không redeploy.
  • Định tuyến theo nhóm: chỉ bật model mới cho nội bộ/beta trước.
  • Tách deploy ↔ release: deploy artifact im lặng, release bằng cờ khi sẵn sàng.
Mấu chốt Module 8

Deploy model là khoảnh khắc rủi ro nhất — model có thể đúng offline, sai online. Không bao giờ thay 100% ngay: shadow (chắc không vỡ kỹ thuật) → canary/A·B (đo nghiệp vụ, tăng dần, có ý nghĩa thống kê) → full, với rollback/kill-switch trong vài giây. Tách "deploy" khỏi "release" bằng feature flag. Giả định mọi model rồi sẽ cần rút.

Model decay (suy thoái model)

Lý thuyết 9.1 — Giám sát proxy khi chưa có "sự thật"

Vấn đề nan giải: để biết model đúng hay sai, bạn cần ground truth (nhãn thật) — nhưng nó thường đến trễ (biết KH có churn không phải đợi 90 ngày). Trong lúc chờ, bạn không thể đo accuracy trực tiếp. Giải pháp: giám sát các proxy không cần nhãn — phân phối đầu vào (data drift) và phân phối đầu ra (prediction drift). Nếu input/output trôi mạnh, gần như chắc chắn hiệu năng cũng đang trôi, dù chưa có nhãn để xác nhận. Drift là cảnh báo sớm; sụt metric là xác nhận muộn.

2. Data drift · Concept drift · Label drift

"Drift" không phải một thứ — phân biệt ba loại để chẩn đoán đúng và chọn cách xử lý đúng:

Data drift (covariate shift)

Phân phối đầu vào P(X) đổi, nhưng quan hệ X→y giữ nguyên. Vd: nhóm khách hàng mới trẻ hơn hẳn. Model vẫn "đúng luật" nhưng gặp vùng dữ liệu lạ. Xử lý: thường retrain trên data mới.

Concept drift

Quan hệ X→y đổi: cùng đầu vào giờ cho kết quả khác. Vd: hành vi "bình thường" đổi sau đại dịch; chiêu gian lận mới. Nguy hiểm nhất vì model học sai bản chất. Bắt buộc retrain (có khi rethink feature).

Label drift (prior shift)

Phân phối nhãn P(y) đổi: tỉ lệ lớp dương tăng/giảm. Vd: mùa cao điểm tỉ lệ gian lận tăng. Có thể cần chỉnh ngưỡng/recalibrate.

  TRAIN (phân phối tuổi KH)        SERVE 3 tháng sau
   ▁▃▅█▅▃▁  đỉnh ~40              ▁▃█▅▃▁▁  đỉnh ~28
   └──────────────►              └──────────────►
   = DATA DRIFT: input trôi (P(X) đổi) → cờ cảnh báo sớm, chưa cần nhãn
So sánh phân phối train (tham chiếu) vs serve (hiện tại) cho mỗi feature → đo độ trôi.

3. Phát hiện drift bằng thống kê

Drift đo được: so phân phối tham chiếu (tập train) với phân phối hiện tại (cửa sổ production gần đây) bằng các kiểm định:

Drift ≠ luôn xấu

Phát hiện drift là tín hiệu điều tra, không phải tự động kết luận model hỏng. Drift có thể do: thế giới đổi thật (cần retrain), hoặc một bug pipeline upstream (một feature đột nhiên toàn null — sửa pipeline, đừng retrain trên data hỏng!). Luôn hỏi "vì sao drift?" trước khi retrain. Đôi khi gốc rễ là data engineering, không phải model.

4. Ground truth lag & feedback loop

Thách thức vận hành lớn: nhãn thật đến trễ, và đôi khi không bao giờ đến. Phải thiết kế để thu thập nó:

Ground truth lag

Độ trễ giữa lúc dự đoán & lúc biết kết quả thật. Churn: ~90 ngày. Vay: hàng tháng. Trong lúc chờ, dựa vào drift làm proxy.

Thu thập nhãn

Phải xây pipeline ghép dự đoán cũ với kết quả thật khi nó đến → tính accuracy thật & tạo data train mới. Đây là data engineering.

Feedback loop nguy hiểm

Khi dự đoán model ảnh hưởng kết quả mà nó cố đoán, bạn có vòng phản hồi tự củng cố. Vd: model chấm "khu vực X nhiều gian lận" → tăng kiểm tra X → phát hiện nhiều hơn ở X (vì soi kỹ hơn) → "xác nhận" model → soi X nữa. Model tạo ra dữ liệu khẳng định chính nó, kể cả khi sai. Phát hiện & phá vỡ feedback loop là kỹ năng MLOps cấp cao — cần một phần traffic ngẫu nhiên không bị model can thiệp để đo khách quan.

📚 Ba chữ cái: CI, CD, CT

DevOps có hai vòng lặp tự động: CI (Continuous Integration — mỗi commit tự build & test) và CD (Continuous Delivery/Deployment — tự đưa lên môi trường). MLOps thêm CT (Continuous Training — tự huấn luyện lại khi có data mới hoặc drift). Lý do CT tồn tại đã rõ từ Module 9: model decay. Nhưng có một điểm tinh tế: trong MLOps, "thứ được CI/CD" không chỉ là code, mà là cả pipeline và model. Lên cấp 2 (Module 1) nghĩa là CI/CD áp lên chính pipeline huấn luyện.

CI · CD · CT

CI: tự động build + test mỗi thay đổi (code, và cả data/model). CD: tự động đưa pipeline/model qua các môi trường (staging→prod) một cách an toàn (Module 8). CT: tự động huấn luyện lại model khi kích hoạt (lịch/drift/data mới — Module 5), qua eval gate, rồi vào CD.

Lý thuyết 10.1 — Test thứ không tất định

CI của phần mềm thường dựa trên một giả định: cùng input → cùng output → assert được. ML phá giả định đó: train có ngẫu nhiên, "đúng" là thống kê chứ không tuyệt đối. Nên test ML không hỏi "kết quả có đúng byte-by-byte không" mà hỏi "model có đủ tốt và không tệ đi không": metric vượt ngưỡng, không sụt so với trước, không vỡ trên slice quan trọng. Đây là vì sao eval gate (Module 6) chính là "unit test" của thế giới ML.

5. Model promotion kiểu GitOps

GitOps (Module 17): trạng thái mong muốn khai báo trong git, hệ thống tự hội tụ về đó. Áp cho model: "model nào ở Production" là một khai báo được review & version, không phải ai đó copy file lúc nửa đêm.

Đây là tư duy "đơn vị kinh tế" (unit economics) áp cho ML — sân nhà của người có nền finance.

Lý thuyết 11.1 — Tam giác đánh đổi: latency × cost × quality

Không có bữa trưa miễn phí (Module 18). Ba thứ kéo nhau: muốn latency thấp + quality cao → phần cứng mạnh, đắt. Muốn cost thấp → model nhỏ hơn (giảm quality) hoặc phần cứng yếu hơn (tăng latency) hoặc batch (tăng latency). MLOps engineer giỏi không tìm "tốt nhất tuyệt đối" mà tìm điểm đủ tốt với chi phí thấp nhất cho ràng buộc nghiệp vụ — y hệt tư duy system design của bạn.

4. Autoscaling & kinh tế của batching

Autoscaling

Tăng/giảm số replica theo tải (HPA trên K8s — Module 13). Trả tiền cho cái dùng. Scale-to-zero (KServe, serverless): không request → 0 instance → 0 tiền (đổi lại cold start).

Dynamic batching

Gộp request thành batch → tận dụng GPU tốt hơn nhiều → cost/dự đoán giảm mạnh. Đổi lại latency tăng chút. Triton/vLLM tự làm.

Tình huống thực tế

Model gợi ý có tải lệch ngày/đêm 20:1. Chạy cố định 20 instance 24/7 → ban đêm 19 instance ngồi không đốt tiền. Bật autoscaling (min 2, max 24 theo QPS) → ban đêm co về 2, ban ngày nở ra → cùng SLA, hoá đơn giảm ~60%. Thêm scale-to-zero cho model nội bộ ít dùng → gần như miễn phí khi rảnh. Đây là FinOps (Module 17) áp cho serving.

5. Caching & precompute

Dự đoán rẻ nhất là dự đoán bạn không phải tính. Hai chiến lược:

  • Cache dự đoán: nếu cùng input lặp lại (phân phối request lệch — vài entity rất hot), cache kết quả trong Redis. Tra cache rẻ hơn chạy model nhiều lần.
  • Precompute (batch): nếu tập entity hữu hạn & dự đoán không cần tươi theo giây → quay lại batch (Module 7): chấm điểm trước toàn bộ, ghi bảng, serve bằng tra bảng (cực rẻ). Nhiều bài toán "tưởng cần online" thực ra precompute được.
Hỏi lại nhu cầu real-time

Online inference đắt hơn batch nhiều lần. Trước khi tối ưu một hệ online phức tạp, hỏi: "có thật cần tính lúc request không, hay precompute hằng đêm rồi tra bảng là đủ?". Với churn, LTV, phân khúc KH — precompute thường đủ. Chuyển online→batch khi được là cú cắt chi phí lớn nhất, và nó đưa bài toán về đúng sân DE của bạn.

📚 Vì sao LLM khó phục vụ hơn model thường

Ba đặc tính làm LLM serving thành một thế giới riêng. (1) Kích thước: một model 7B tham số cần ~14GB chỉ để chứa trọng số (FP16) — trước cả khi xử lý request. (2) Autoregressive: nó sinh một token, đưa lại vào đầu vào, sinh token tiếp — một câu trả lời 500 từ là ~500 lượt forward tuần tự, không song song hoá theo token được. (3) Bộ nhớ động (KV cache): mỗi token sinh ra phải lưu "key/value" của các token trước → bộ nhớ tăng theo độ dài chuỗi, khó dự đoán. Hệ quả: kỹ thuật serving model thường (Module 7) không đủ; cần server LLM chuyên dụng.

Prefill vs Decode

LLM inference có hai pha: prefill (xử lý toàn bộ prompt đầu vào một lần — song song, nặng tính toán) và decode (sinh từng token output tuần tự — nhẹ tính toán nhưng nhiều bước, bị giới hạn bởi băng thông bộ nhớ). Hiểu hai pha này giải thích vì sao "prompt dài" và "output dài" có hồ sơ chi phí khác nhau.

1. ⭐ LLM serving: KV cache & continuous batching

Hai khái niệm làm nên hiệu năng LLM serving hiện đại:

KV cache

Lưu key/value đã tính của các token trước để khỏi tính lại mỗi bước decode. Tăng tốc lớn, nhưng ngốn VRAM và là nút thắt bộ nhớ chính. PagedAttention (vLLM) quản KV cache như phân trang bộ nhớ → ít lãng phí.

Continuous batching

Thay vì chờ cả batch xong mới nhận request mới (static batching, lãng phí), continuous batching nhét request mới vào ngay khi một slot xong → throughput tăng nhiều lần. Là lý do chính dùng vLLM/TGI.

Server LLMMạnh ở

Latency LLM: TTFT vs TPOT

LLM có hai chỉ số latency riêng: TTFT (Time To First Token — chờ bao lâu để thấy chữ đầu, ảnh hưởng cảm nhận "phản hồi nhanh") và TPOT (Time Per Output Token — tốc độ chữ chảy ra sau đó). Streaming token (trả dần như gõ máy) cải thiện TTFT cảm nhận rất nhiều dù tổng thời gian không đổi. Đây là lý do mọi chatbot đều "gõ dần" chứ không chờ trả cả đoạn.

Quyết định kiến trúc lớn nhất của LLMOps platform. Không có đáp án chung — phụ thuộc ràng buộc, đúng tinh thần Module 18:

Kinh tế GPU: điểm hoà vốn của self-host

Self-host chỉ thắng khi bạn lấp đầy GPU. Một GPU (A100/H100, hay L4 rẻ hơn) tính tiền theo giờ-GPU dù bận hay rảnh — nên chìa khoá là utilization cao qua continuous batching. Volume lớn & đều → self-host trả tiền cho chính nó. Đây chính là bài toán "core-giờ" của Spark (Module 05 DE) áp cho GPU.

Tình huống thực tế

Hỏi: "Công ty fintech nên tự host LLM hay dùng API?" Trả lời chín: "Tuỳ giai đoạn & dữ liệu. Khởi đầu/PoC: dùng API — chứng minh giá trị trước, đừng đốt tiền GPU cho thứ chưa chắc dùng. Khi có dữ liệu nhạy cảm (hồ sơ tín dụng không được rời hệ thống) hoặc volume rất lớn ổn định → self-host model mở (Llama/Qwen) trên vLLM trả tiền cho chính nó về cả chi phí lẫn tuân thủ. Nhiều công ty lai: API cho tác vụ khó/ít, self-host model nhỏ cho tác vụ lượng lớn." Quyết định theo ràng buộc, không theo hype.

3. Fine-tune như một training pipeline: full · LoRA/PEFT

Từ góc platform, fine-tune không phải phép thuật — nó là một training pipeline (Module 5) đặc thù cho LLM: chuẩn bị dataset, chạy job train trên GPU, sinh ra một tạo tác (adapter/model) có version, qua eval gate rồi mới serve. Cây quyết định quan trọng nhất — và đa số người mới chọn sai (vội fine-tune khi RAG/prompt là đủ):

  Cần đưa KIẾN THỨC (facts) vào?
     └─► RAG (Masterclass 22). Cập nhật được, trích dẫn được, rẻ. KHÔNG fine-tune.

  Prompt tốt + RAG vẫn chưa đạt HÀNH VI/ĐỊNH DẠNG mong muốn?
     ├─ Thử prompt engineering kỹ + few-shot examples trước (rẻ nhất)
     └─ Vẫn chưa đạt & có ≥ vài trăm-nghìn ví dụ chất lượng?
            └─► Fine-tune cho PHONG CÁCH/ĐỊNH DẠNG/giọng điệu chuyên biệt
                 ├─ LoRA/PEFT: rẻ, nhanh, chỉ train adapter nhỏ ← mặc định
                 └─ Full fine-tune: đắt, hiếm khi cần, dễ "quên" (catastrophic forgetting)

LoRA/PEFT: fine-tune vừa túi tiền platform

LoRA (Low-Rank Adaptation) đóng băng trọng số gốc và chỉ train một tập adapter nhỏ (thường <1% tham số) → job train chạy gọn trên 1 GPU, ra một file adapter vài chục MB có thể version trong registry (Module 4) và hot-swap lúc serve. Đây là lý do LoRA là mặc định thực dụng: rẻ để train, rẻ để lưu, dễ A/B nhiều adapter trên cùng một base model. Full fine-tune đổi toàn bộ trọng số → tốn GPU gấp bội, khó rollback, dễ catastrophic forgetting.

Sai lầm đắt giá nhất của người mới LLMOps

Nhảy thẳng vào fine-tune để "dạy model dữ liệu công ty". Sai vì: fine-tune không là cách tốt để nhồi facts (model vẫn quên/bịa, không cập nhật được, không trích dẫn được) — đó là việc của RAG (Masterclass 22). Fine-tune là để đổi hành vi/phong cách, không phải kiến thức. Lẫn hai cái này đốt rất nhiều tiền & thời gian mà không giải đúng bài toán.

📚 Đọc & thiết kế một kiến trúc ML

Mọi kiến trúc ML đều có thể đọc qua cùng một "bộ xương" gồm bốn dòng chảy: (A) đường dữ liệu & feature (nguồn → feature), (B) đường huấn luyện (feature → train → registry), (C) đường phục vụ (model → dự đoán → ứng dụng), và (D) vòng giám sát (production → drift → kích hoạt train lại). Bốn dòng chảy — la bàn đọc mọi kiến trúc ML

Vì sao bắt đầu ở đây

Không model server 24/7, không online store, không lo p99 — chỉ là job định kỳ ghi bảng, đúng thứ bạn làm hằng ngày. Nếu nghiệp vụ chấp nhận dự đoán "tươi theo ngày", đây là kiến trúc đúng, không phải kiến trúc "tạm". Đừng nâng cấp khi chưa bị ép.

2. Kiến trúc Real-time Inference

Khi nghiệp vụ cần dự đoán theo từng request trong <100ms (gợi ý, duyệt vay, cá nhân hoá). Thêm online feature store + model server:

  TRAINING (B): như batch — Airflow→train→gate→MLflow registry

  FEATURE (A):  pipeline materialize → ONLINE store (Redis/Dynamo) (Mod 3)
                                            │ <10ms lookup
  SERVING (C):  client → API gateway → ┌────▼─────────────────┐
                                       │ Model server (K8s)   │
                                       │ FastAPI/KServe/BentoML│
                                       │ load models:/m/Prod  │──► dự đoán
                                       │ + canary (Mod 8)     │    + version
                                       └────┬─────────────────┘
  MONITORING (D): log mọi request+prediction → Evidently/Arize drift +
                  Prometheus p99/QPS → alert → trigger retrain ↺
Real-time thêm: online feature store + model server trên K8s + canary. Phần còn lại y như batch.

3. Kiến trúc ứng dụng RAG

  INDEXING (offline ETL — Airflow, Mod 12):
   nguồn (wiki,PDF,DB) → load → chunk → embed → pgvector/Qdrant
   (incremental/CDC khi tài liệu đổi — Mod 11 DE)

  QUERY (online):
   user → API → guardrails(injection/PII) → embed câu hỏi →
          hybrid search (vector+BM25) → rerank → top-K đoạn →
          augment prompt → LLM (API hoặc vLLM) → trả lời + trích dẫn

  OBSERVABILITY: Langfuse/LangSmith trace + token/cost + eval set (RAGAS)
                 + thu feedback → cải thiện chunk/prompt ↺
RAG: pha indexing là ETL (sân nhà bạn) + pha query là retrieve→augment→generate, bọc guardrails & observability.

5. Bẫy thường gặp khi làm capstone

  • Sa lầy ở model: dành 80% thời gian tăng AUC từ 0.88→0.89. Sai — giá trị capstone ở vòng đời, không ở điểm. Model "đủ tốt" rồi tiến lên serving/monitoring.
  • Bỏ dòng D: dừng ở "train + serve", quên monitoring + retrain. Đó chính là phần phân biệt MLOps với "train model". Đừng bỏ.
  • Over-engineer: nhồi Kafka + Kubeflow + đa GPU cho bài toán 50MB. Chọn đơn giản, làm xong, rồi mới nói "đây là chỗ tôi sẽ nâng cấp nếu scale".
  • Không viết design doc: code không kèm lý lẽ đánh đổi = mất nửa giá trị. Doc là nơi bạn thể hiện tư duy senior.
  • Train-serving skew: tính feature kiểu khác lúc serve. Dùng cùng một code/feature store — và tự bắt lỗi này là một bài học vàng.

3. Anti-patterns phải tránh (tổng hợp toàn khoá)

Về model & data

Dùng ML khi rule đủ · bỏ qua data leakage · tin một metric tổng · không baseline · sa lầy tăng AUC thay vì hoàn thiện vòng đời · train trên data đã drift/hỏng.

Về vận hành

Coi deploy là điểm kết (quên monitoring) · thay 100% traffic ngay · không rollback được · retrain phản xạ không chẩn đoán · train-serving skew · không version data/model.

Về LLM

Fine-tune để nhồi facts (phải RAG) · bỏ qua chất lượng retrieval · không có eval set · không tracing · không guardrails (prompt injection) · agent không trần bước/ngân sách.

Về kiến trúc

Over-engineer (Kafka/GPU cho bài toán nhỏ) · online khi batch đủ · MLOps cấp 2 khi chỉ 2 model · đa agent khi workflow đủ · không nghĩ tới chi phí.
