Module 01 — Nền tảng Docker

Container là gì — VM vs Container, namespace, cgroups, OCI

Container là đơn vị phân phối phần mềm nhẹ nhất hiện nay. Trước khi gõ docker run đầu tiên, bạn cần hiểu tại sao container ra đời, nó khác VM thế nào, và các công nghệ nền tảng (namespace, cgroups, OCI) giúp container an toàn và portable như thế nào. Đây là sợi chỉ đỏ xuyên suốt khoá: từ một script Python trên laptop, bạn sẽ containerize nó, rồi deploy lên Kubernetes production — mọi bước đều dựa trên nền tảng này.

1. Lịch sử — từ bare-metal tới container

Mỗi thế hệ deployment đều giải một vấn đề của thế hệ trước:

Thế hệCông nghệĐơn vịƯu điểmNhược điểm
1Bare-metal1 server / 1 appHiệu năng tối đaLãng phí, conflict thư viện, khó scale
2VM (VMware, Hyper-V)1 VM / N appIsolation, multi-OSNặng (GB), boot chậm, overhead 10-30%
3Container (Docker, Podman)1 container / N appNhẹ (MB), boot ms, portableChia sẻ kernel → cách ly yếu hơn VM
4K8s clusterPod (1-N container)Tự động scale, heal, rolling updateComplexity, learning curve cao
Container

Một tiến trình được cô lập bằng Linux namespace (cô lập tài nguyên: PID, network, mount, user, IPC, UTS) và bị giới hạn tài nguyên bằng cgroups (CPU, memory, I/O). Container image là một filesystem layer stack (readonly) + runtime config. Khi container chạy, nó tạo một writable layer trên top. Container nhẹ vì không có OS riêng — dùng chung kernel với host, chỉ cô lập namespace.

Security note

Container không thay thế VM cho workload cần security boundary mạnh (VD: shared multi-tenant environment). Trong production, container vẫn chạy trong VM hoặc gán security policy (AppArmor, seccomp, SELinux). Data engineer thường dùng container để packaging, còn infra thật sự vẫn nằm trong VM/VPC của cloud provider.

3. Linux namespace — cô lập không gian tên

Namespace là cơ chế Linux cho phép một tiến trình "thấy" một phiên bản cô lập của một tài nguyên hệ thống:

NamespaceFlagCô lập gìVí dụ
PIDCLONE_NEWPIDSố process IDContainer thấy PID 1, host thấy PID khác
NetworkCLONE_NEWNETNetwork interfaces, routing tableContainer có IP riêng, port 80 không conflict
MountCLONE_NEWNSFilesystem mount pointsContainer thấy root filesystem riêng
UserCLONE_NEWUSERUser ID / Group ID mappingUID 0 (root) trong container ≠ UID 0 host
IPCCLONE_NEWIPCShared memory, semaphoreContainer không thấy IPC của container khác
UTSCLONE_NEWUTSHostname, domain nameContainer có hostname riêng
TimeCLONE_NEWTIMESystem clockContainer thấy thời gian riêng (K8s dùng)
root trong container ≠ root ngoài

User namespace cho phép UID 0 trong container ánh xạ tới UID không phải root bên ngoài. Docker dùng userns-remap mặc định trên một số bản. Kubernetes pod security policy cũng dựa trên namespace để giới hạn quyền container.

5. cgroups v2 — unified hierarchy

Linux kernel 5.x+ dùng cgroups v2 (cgroups-v2 / unified cgroup). V2 thống nhất tất cả controller vào một tree duy nhất, thay vì mỗi controller một tree riêng như v1:

Tính năngcgroups v1cgroups v2
HierarchyMỗi controller tree riêngMột tree duy nhất cho tất cả
Memory lowCóCó + cơ chế thông báo memory/cpu/io pressure (PSI — Pressure Stall Information)
OOM kill cả nhóm (memory.oom.group)KhôngCó (kill toàn bộ process trong cgroup, không để container "chết dở")
Default trongDocker legacy, older K8sDocker 20.10+, K8s 1.25+
Docker và cgroups v2

Docker tự động phát hiện cgroups version. Kiểm tra: mount | grep cgroup. Nếu thấy cgroup2 on /sys/fs/cgroup → đang dùng v2. cgroup v2 là mặc định của các distro Linux hiện đại (Ubuntu 22.04+, RHEL 9+) — Kubernetes dùng theo host; cgroup v1 chuyển sang maintenance mode từ K8s 1.31. Nếu cluster cũ, migrate sớm.

ADD vs COPY — dùng cái nào?

Dùng COPY trong hầu hết trường hợp. ADD chỉ cần khi: (1) download file từ URL, (2) extract tar archive tự động. COPY rõ ràng hơn về intent, build cache tốt hơn, và buildkit đã hỗ trợ cache cho URL trong ADD nhưng vẫn nên dùng COPY + RUN curl cho control.

Shell vs Exec form — vấn đề signal

Shell form: CMD python app.py → chạy qua /bin/sh -c "python app.py" → PID 1 = /bin/sh, không phải Python. SIGTERM gửi tới sh, sh không forward tới Python → graceful shutdown fail → docker stop phải đợi timeout (10s). Luôn dùng exec form JSON array: CMD ["python", "app.py"].

4. Multi-stage build — slim production image

Multi-stage build cho phép dùng nhiều FROM trong một Dockerfile: stage đầu cho build (có compiler, build tools), stage cuối chỉ copy artifact cần thiết. Kết quả: image production nhỏ hơn 10x.

Dockerfile.multi-stage
# ==================== STAGE 1: BUILD ==================== FROM python:3.12-slim AS builder WORKDIR /build # Cài build dependencies (compiler, headers) — chỉ có trong stage này RUN apt-get update && apt-get install -y --no-install-recommends \ gcc \ libpq-dev \ && rm -rf /var/lib/apt/lists/* COPY requirements.txt . RUN pip install --prefix=/install -r requirements.txt # ==================== STAGE 2: PRODUCTION ==================== FROM python:3.12-slim AS production # Không có compiler, không có build tools → image nhỏ hơn nhiều RUN apt-get update && apt-get install -y --no-install-recommends \ libpq5 \ && rm -rf /var/lib/apt/lists/* WORKDIR /app # Copy chỉ artifact cần thiết từ stage build COPY --from=builder /install /usr/local COPY --from=builder /build/requirements.txt . # Không chạy as root — security best practice RUN useradd --create-home appuser && chown -R appuser:appuser /app USER appuser CMD ["python", "etl_pipeline.py"]
So sánh size image

Python 3.12 full: ~1GB. Python 3.12 slim: ~130MB. Multi-stage (slim): ~150MB (thêm libpq). Với C extension build: single-stage full ~1.2GB → multi-stage ~180MB. Data engineer nên luôn dùng multi-stage cho production.

Image & Layer — layer cache, COPY order, .dockerignore, size optimization

1. Layer — cách Docker lưu trữ filesystem delta

  DOCKERFILE                          IMAGE LAYERS (stacked read-only)
  ─────────────────────────────────    ────────────────────────────────────
  FROM ubuntu:22.04                   ┌──────────────────────────────┐
  │                                  │ Layer 0: ubuntu:22.04 rootfs  │  77MB
  RUN apt-get update                 ┌──────────────────────────────┐
  │                                  │ Layer 1: apt-get update       │  12MB
  RUN apt-get install -y python3     ┌──────────────────────────────┐
  │                                  │ Layer 2: python3 + deps       │  45MB
  COPY app /app                      ┌──────────────────────────────┐
  │                                  │ Layer 3: /app files          │   5MB
  RUN pip install pandas             ┌──────────────────────────────┐
  │                                  │ Layer 4: pandas + numpy      │  85MB
  │                                  └──────────────────────────────┘
  │                                    │
  │  Container writable layer         │
  │  (tạo khi container chạy)         ├── /app/data.csv ← được tạo
  │  (tất cả thay đổi khi chạy)      ├── /tmp/cache ← log file
                                        └── /var/log/app.log
  └── docker run → overlayfs/overlay2 mount
Image layers là read-only, stack lên nhau. Container thêm một writable layer (container layer) trên top. Nhiều container share cùng image layers → tiết kiệm disk.
Overlay filesystem

Docker dùng overlay2 storage driver (default trên Linux kernel 3.18+). overlay2 mount image layers thành một unified filesystem cho container. Khi file trong layer bị sửa, overlay copy-on-write: copy file vào writable layer trước khi sửa. Hiểu điều này giúp bạn tối ưu: tránh sửa file trong image layer bằng cách mount volume.

3. .dockerignore — giảm build context

Build context là tất cả file gửi từ host tới Docker daemon khi build. Nếu build context là 1GB, mỗi lần build gửi 1GB qua Unix socket hoặc TCP. .dockerignore ngăn file không cần thiết được gửi:

.dockerignore
# Ignore everything by default * # Allow only necessary files !src/ !requirements.txt !config/ !Dockerfile # Exclude large/secret directories __pycache__/ *.pyc .git/ .gitignore .vscode/ .idea/ *.md .env .env.* tests/ docs/ data/ models/ logs/ *.log .DS_Store venv/ .venv/ node_modules/
.env không bao giờ để trong Docker image

File .env thường chứa password, API key, database credential. Luôn exclude nó trong .dockerignore. Truyền secret runtime qua Docker secret hoặc Kubernetes Secret. TUYỆT ĐỐI không truyền secret qua build arg — giá trị build arg nằm lại trong image metadata/history, ai có image chạy docker history là đọc được. Nếu cần secret lúc build, dùng BuildKit secret mount: trong Dockerfile viết RUN --mount=type=secret,id=db_pass,target=/run/secrets/db_pass ... và build bằng docker build --secret id=db_pass,src=.env.db ... — secret chỉ tồn tại trong lúc chạy lệnh RUN, không lưu vào layer nào của image.

Liveness probe quá aggressive = cascading restart

Nếu liveness probe fail quá sớm (initialDelaySeconds quá nhỏ), container sẽ bị restart liên tục. Quy tắc: initialDelaySeconds >= startup time thực tế + buffer. Với JVM app: startup có thể 30-60s. Với Python: 5-15s.

Pod tóm tắt

Pod = 1-N container share namespace. Dùng sidecar cho cross-cutting concerns (logging, auth). Dùng init container cho setup trước khi main container chạy. Probe cần được tune đúng để tránh cascading restart. Trong thực tế, bạn hiếm khi deploy Pod trực tiếp — thường qua Deployment (M11).

Memory limit vs CPU limit — hành vi khác nhau

Memory limit: OOM kill khi vượt quá → container restart. CPU limit: throttling (chậm hơn) nhưng không kill. Đặt memory limit CHÍNH XÁC. Nếu không chắc, bắt đầu với request = limit (Guaranteed) để tránh throttling và đảm bảo resource. Đặt limit cao hơn request nhưng không quá cao để tránh resource waste.

Khi nào không dùng Kubernetes?

Dùng Nomad khi: workload đơn giản, muốn simplicity, cần chạy cả container và non-container (VD: bare-metal job). Dùng ECS/Fargate khi: team AWS-centric, không muốn quản lý control plane. Dùng Docker Swarm khi: scale nhỏ (<10 nodes), team đã quen docker-compose. Kubernetes vẫn là lựa chọn mặc định khi không có lý do cụ thể chọn cái khác.
